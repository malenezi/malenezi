    Administrator guide¶

    For Academy Admins who run the Hub. Content owners: see CONTRIBUTING.md.

    1. First-time setup (go-live checklist)¶

    Repository¶

    • Create a private repository sdaia-academy-training in the Academy's GitHub organisation (Internal visibility is also fine on GitHub Enterprise). Disable forking.
    • Install Git and Git LFS, unzip the bootstrap into a working folder, then pull the binaries from Drive (every file is verified against the SHA-256 recorded in the migration mapping): 
      python -m pip install -r requirements.txt
python scripts/migration/migrate_from_drive.py --source "G:/My Drive/SDAIA/CB/Academy/Catalog/New Catalog" --repo . --binaries-only
    • Create the first commit with scripts/migration/init_git_repo.py — not plain git add -A. Several migrated lab repositories contain their own .gitignore files that would silently drop 179 shipped assets; the script force-adds every mapped file and verifies the index: 
      python scripts/migration/init_git_repo.py
git remote add origin git@github.com:<org>/sdaia-academy-training.git
git push -u origin main          # pushes Git LFS objects too
    • Set github_repo (and later portal_url) in hub-config.yml, then python scripts/refresh_generated.py so "Report a problem" links point at the right repository.
    • Replace SDAIA-Academy in .github/CODEOWNERS with the real organisation / team slugs.

    People¶

    • Create the teams in PERMISSIONS.md and add members.
    • For each course, set content_owner and reviewer in metadata.yml (one PR per learning path is fine). The validator refuses Approved/Published status until both are set.
    • Apply the main branch ruleset from PERMISSIONS.md.
    • Enable secret scanning, push protection and Dependabot alerts.

    Portal¶

    • Choose hosting with SDAIA IT — HOSTING.md (recommended: internal hosting behind SSO).
    • Set repository variables: DEPLOY_TARGET (internal · azure-swa · github-pages · none), and for internal hosting DEPLOY_PATH.
    • Set repository secrets if needed: AZURE_STATIC_WEB_APPS_API_TOKEN (Option B only).
    • Run Actions → Publish Trainer Portal → Run workflow and verify sign-in is required.
    • Announce the portal URL to trainers; update the announcement on portal/index.md.

    2. Day-to-day¶

    Task How
    Merge content Only after required approvals and green checks; squash-merge with the PR title CODE: summary
    Publish a course version After merge: git tag SDA-AIE-311/v1.1 <sha> && git push origin SDA-AIE-311/v1.1 → Release workflow
    Add a course python scripts/new_course.py … (see CONTRIBUTING.md) — starts as Draft
    Archive a course Move to archive/…, add a README with the reason and replacement, set status: Archived
    Change the taxonomy Edit taxonomy.yml via PR; run make check — the validator catches values no longer allowed
    Feature a course on the home page featured: list in hub-config.yml
    Post an announcement Edit the Trainer announcements section of portal/index.md
    Triage feedback Issues arrive labelled feedback + type; assign the course owner, label urgent if a delivery is affected

    3. Scheduled care¶

    When What
    Weekly Check the portal's Content health page and open issues labelled urgent
    Monthly The Review reminders workflow opens an issue listing courses whose next_review is within 30 days
    Quarterly Review LFS storage/bandwidth usage; update pinned tool versions in requirements.txt; review team membership
    Yearly Review this governance model with Academy leadership

    4. When a check fails¶

    Check Typical cause Fix
    validate › metadata Missing field, value not in taxonomy.yml, bad date Correct metadata.yml; schema is schemas/course-metadata.schema.json
    validate › structure Required file or folder missing Restore it (templates in shared/templates/course-template/)
    validate › links Renamed/moved file Update the relative link
    validate › generated AUTO blocks stale Warning only — the publish workflow regenerates them
    security › secret Credential pattern found Remove it; if it was ever pushed, follow SECURITY.md
    security › personal data Phone/ID/IBAN/e-mail patterns in data Confirm synthetic and add to .security-allowlist.yml with a reason, or remove
    security › size File > 5 MB not in LFS / > 50 MB Track with LFS / move to release asset
    publish › build MkDocs error Run make portal locally; the previous portal stays online

    5. Migration follow-up (from the audit)¶

    The migration audit lists every open item. Priorities: P0 owners + hosting + 6 security items → P1 approve the complete courses → P2 recover the missing SDA-AIE-214 package, complete DSC-211/DSC-112 packages, decide L0-FDV → P3/P4 build missing materials. Each course's open items are also listed on its page under Ownership and version.

    6. Local commands¶

    make check      # validate + links + security + generated-content check
make refresh    # regenerate AUTO blocks and portal pages
make portal     # assemble and build the portal into site/
make serve      # live preview on http://127.0.0.1:8000

    7. Portal engine lifecycle (important)¶

    The portal is built with MkDocs 1.6 + Material for MkDocs 9.7, pinned in requirements.txt. The Material team has announced that MkDocs 2.0 is backward-incompatible (plugins and theme overrides stop working, no migration path) and that future MkDocs 1.x updates are unlikely. Material 9.7.5+ already restricts MkDocs to <2. Actions:

    • Never upgrade to MkDocs 2.x; review Dependabot PRs for mkdocs / mkdocs-material carefully.
    • The content is plain Markdown + YAML metadata; the only engine-specific parts are mkdocs.yml, scripts/build_portal.py (nav generation) and portal/assets/. Migrating engines is therefore a contained task.
    • Re-evaluate annually. The Material team's successor, Zensical, aims to build existing mkdocs.yml projects without changes (not fully there as of early 2026); other options include staying pinned on MkDocs 1.6 while it is secure.
