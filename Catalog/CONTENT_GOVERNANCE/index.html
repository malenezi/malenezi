    Content governance¶

    How SDAIA Academy training content is owned, changed, reviewed, versioned, published and retired. This model is deliberately lightweight: one repository, four roles, one workflow.

    1. Principles¶

    1. One source of truth. The main branch of this repository is the authoritative copy of every course. The Trainer Portal, participant bundles and any exported files are derived from it.
    2. Nothing is deleted. Superseded content moves to archive/ with its history; questionable content is flagged, never silently removed.
    3. Meaning is preserved. Reformatting and restructuring are welcome; changes to learning objectives, technical content, exercises, assessments or terminology require the content owner.
    4. No invented facts. Anything not supported by a source is written as TODO: Information not available in source material.
    5. Automation enforces, people decide. Checks block broken changes; humans approve content.

    2. Roles¶

    Role Who Can GitHub permission
    Academy Admins Hub owners in the Academy (2–3 people) Manage settings, teams, branch protection, taxonomy, releases; emergency fixes Admin
    Content Owners One named person per course (may own several) Change their courses; approve content changes; bump versions; request publication Maintain on their path, via CODEOWNERS
    Reviewers Subject-matter and instructional reviewers Review pull requests; request changes; approve Write (review)
    Trainers Everyone who delivers Read and download approved content; raise feedback issues Read (or portal-only access)

    Every course's content_owner and reviewer are recorded in its metadata.yml. Until they are set, the course cannot move beyond Under Review (enforced by scripts/validate_repo.py). Team structure and CODEOWNERS: docs/admin/PERMISSIONS.md.

    3. Naming conventions¶

    Item Convention Example
    Course code SDA-<TRACK>-<LEVEL><SEQ> (FND/AIE/DSC; 1xx Practitioner, 2xx Specialist, 3xx Expert, x90 Capstone) · Level-0: L0-<XXX> SDA-AIE-311, L0-FAE
    Course folder catalog/<learning-path>/<CODE>-<kebab-title> catalog/ai-engineer/SDA-AIE-311-agentic-ai-systems-engineering
    Standard files README.md, metadata.yml, course-overview.md, instructor-guide.md, setup.md, troubleshooting.md —
    Standard folders slides/, labs/, activities/, assessments/, datasets/, solutions/, resources/ —
    Decks <CODE>_<Short_Title>[_vN].pptx — the file in slides/ is always the current one SDA-DSC-212_Time_Series_Training_Deck.pptx
    Lab repositories kebab-case project name, kept intact under labs/ labs/tawseel-agentic-ai/
    Trainer-only files under solutions/, or containing solution, answer_key, instructor_only in the name solutions/injaz-labs-instructor/
    Branches <code>/<short-description> or hub/<topic> sda-aie-311/fix-lab4-checkpointer
    Tags <CODE>/v<major>.<minor> SDA-AIE-311/v1.1

    Avoid spaces and Arabic characters in file names (they break links and tooling); Arabic belongs in content and in course_title_ar.

    4. Content statuses¶

    Status Meaning Shown in portal as
    Draft Incomplete; core materials missing ⚪ Draft — "not ready for delivery"
    Under Review Materials exist; review not complete 🟡 Under Review — "confirm with owner before delivery"
    Approved Technical + instructional review passed 🟢 Approved
    Published Approved and released to trainers (tagged) 🟢 Published
    Archived Retired; kept for reference ⚫ Archived

    Transitions: Draft → Under Review (owner) → Approved (reviewer approval on the PR) → Published (owner tags the release) → Archived (owner + admin). A course moves back to Under Review whenever a major revision starts.

    5. Change workflow¶

    flowchart TD
    A[Change needed<br/>issue, review cycle or owner plan] --> B[Branch from main]
    B --> C[Edit content + metadata<br/>bump version, add change_history entry]
    C --> D[Open pull request<br/>template checklist]
    D --> E{Automated validation}
    E -- fail --> C
    E -- pass --> F[Technical review<br/>Reviewer: accuracy, code runs]
    F --> G[Instructional review<br/>Reviewer/owner: outcomes, timing, assessment]
    G --> H[Content-owner approval<br/>CODEOWNERS]
    H --> I[Merge to main]
    I --> J[Publish workflow<br/>validate · generate · build · link-check]
    J -- pass --> K[Trainer Portal updated]
    J -- fail --> L[Portal keeps previous version<br/>admins notified]

    Review requirements (enforced by branch protection on main):

    Change type Required approvals Notes
    Typo / formatting / broken link 1 (owner or reviewer) Patch — version unchanged or minor
    Content change within a course 2 — reviewer + content owner Minor version bump
    Curriculum revision (outcomes, modules, assessment) 2 + Academy Admin Major version bump; status → Under Review
    New course Admin + owner + reviewer Starts as Draft via scripts/new_course.py
    Taxonomy, workflows, scripts, governance docs Admin CODEOWNERS routes to @academy-admins

    6. Versioning¶

    Each course has its own version in metadata.yml: MAJOR.MINOR.

    Part Increment when Example
    MAJOR Learning outcomes, module structure, duration, assessment design or level change 1.3 → 2.0
    MINOR Content improved, lab fixed, slides updated, dataset refreshed — outcomes unchanged 2.0 → 2.1

    Typos and formatting do not require a bump. Every bump adds an entry to change_history:

    change_history:
  - version: "2.1"
    previous_version: "2.0"
    date: 2026-10-14
    summary: Lab 4 migrated from SQLite to Postgres checkpointer; slides 38-41 updated.
    approver: "Reviewer name"
    pull_request: "#123"

    python scripts/bump_version.py <CODE> minor "summary" does this for you (and sets last_updated). When a version is Published, the owner tags it (SDA-AIE-311/v2.1); the release workflow creates a GitHub Release with the change summary so trainers can see exactly what changed. The migration from Google Drive is recorded as version 1.0 for every course; source labels such as "v2" or "P6.1.04" in file names are preserved but are not Hub versions.

    7. Release process¶

    1. Owner confirms the course is Approved and sets status: Published in the same PR as the final change (or a follow-up PR).
    2. After merge, the owner (or an admin) creates tag <CODE>/v<version> on the merge commit.
    3. The release workflow builds a GitHub Release containing the change summary and, optionally, a zipped trainer bundle of the course (excluding solutions/).
    4. The portal already shows the new version (published on merge); the release is the audit record.

    8. Review cycle¶

    Content Review at least every
    Published courses 6 months (review_cycle_months in hub-config.yml)
    Courses covering fast-moving tools (Generative AI, Agentic AI, LLMOps) 3 months — set next_review accordingly
    Migrated courses (first review) within 3 months of migration (all set to 2026-12-27)

    The portal's Content health page lists reviews due in the next 30 days. A review that finds no change updates next_review only.

    9. Archive process¶

    1. Owner opens a PR moving the course (or superseded files) to archive/<original-path>/, with a README.md stating why, when and what replaces it.
    2. Set status: Archived in metadata.yml if the whole course is retired.
    3. Admin approves. Archived content is excluded from the portal navigation but stays in Git history and in archive/.

    10. Emergency corrections¶

    For errors that could harm a delivery in progress (wrong answer key, broken lab, exposed personal data):

    1. Anyone opens an issue labelled urgent.
    2. An Academy Admin (or the owner) makes the fix on a hotfix/ branch; one approval from any admin or the owner is sufficient.
    3. Automated checks still run — they are never bypassed.
    4. The change is recorded in change_history with summary starting HOTFIX: and reviewed normally within five working days.
    5. If personal or sensitive data was exposed, follow SECURITY.md — history rewrite and secret rotation are admin tasks.

    11. Preserving original meaning¶

    • Do not rewrite technically correct Academy material to change style.
    • Keep learning objectives, technical content, exercises, assessments, instructor instructions, terminology and course sequence intact unless the change is the purpose of the PR.
    • Content copied from source documents is wrapped in <!-- BEGIN SOURCE: … --> … <!-- END SOURCE --> markers so reviewers can see what is verbatim.
    • Unknown facts are written as TODO: Information not available in source material.
