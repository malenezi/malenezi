    Rafeeq — Security Model (Module 8)¶

    The threat model, layered defence, OWASP mapping, action-risk matrix and red-team operating procedure for Rafeeq as an agentic system. Companion to docs/ACTION_RISK_MATRIX.md (the standalone printable matrix) and security/README.md (the attack corpus this model is tested against).

    The governing principle, stated once and assumed everywhere below: treat all model input as untrusted and all model output as unverified. The model is a powerful, manipulable component, not a security control.

    1. Threat model¶

    1.1 Assets¶

    Asset What it is here Why it matters
    Money Refunds (issue_refund), reconciliation adjustments (mark_refunded) Reconciled nightly; a bypassed limit is a direct financial loss and an audit failure
    PII National id, IBAN, card, phone, email (Saudi-shaped, PDPL-governed) Regulatory exposure; national_id_masked is the ONLY form this system is meant to ever hold
    Enterprise system integrity The four MCP-shaped domains (orders/logistics/billing/customer) and their tools A tool call is a real side effect against a real (mock) backend, not advisory text
    Availability Step budget (MAX_STEPS), handoff budget (MAX_HANDOFFS), run cost cap (RUN_COST_CAP_USD) An adversarial loop is a denial-of-wallet attack, not just a bug

    1.2 Entry points¶

    Entry point Trust level Example
    The customer message Untrusted natural language, always Direct injection: security/injections/direct_en.json / direct_ar.json
    Tool output Could be compromised or tampered (a poisoned backend, a tampered MCP response) Indirect injection via delivery_note/delivery_note_ar — the real fixtures in data/orders/INJECTION_NOTES.md; poisoned MCP responses in security/malicious_tool_results/
    Retrieved memory / knowledge base Could be poisoned at write time or stale/forged at read time security/memory_poisoning/

    1.3 Abuse cases¶

    • Prompt injection to trigger an over-limit refund (the module's SYSTEM OVERRIDE case study).
    • Jailbreak / role-play to bypass policy or attempt a prohibited action.
    • PII exfiltration via crafted questions or a poisoned record asking the model to "reveal" data.
    • Denial-of-wallet: an adversarial loop or fan-out driving cost/step count past budget.
    • Cross-customer data access: a same-session request for another customer's records.
    • Privilege escalation: unauthorised tool chaining, refund-amount manipulation (including structuring/smurfing — see §5), fraud-flag override, identity change.

    1.4 Trust boundary¶

     UNTRUSTED                          │  TRUSTED (structural)
 ───────────────────────────────────┼───────────────────────────────────
 customer message                   │
 tool output (poisoned backend)     │  action_risk.classify()   (SPEC §5 matrix)
 retrieved memory / KB              │  security/authz.py        (server-side, per-domain)
                                     │  flows/refund_flow.py     (amount/eligibility gates)
      reasoning model  ────────────▶│  security/output_guard.py (last check before execute/send)
      (persuadable, never a         │  security/events.py       (audit trail)
       trust boundary itself)       │

    The agent is never a trust boundary by itself. Every consequential action is gated by structure on the trusted side of this line, regardless of what the model — on the untrusted side, however persuaded — decided to attempt.

    2. Layered defence¶

    Implemented in code (not just this diagram) as src/rafeeq/security/ defence_layers.py::LAYERS — run python3 -m rafeeq.security. defence_layers for the classroom table. Five layers, each documented with what it catches, what it cannot, and its OWASP category:

    customer message / tool output / memory
          │
          ▼
 1. INPUT FILTER            input_guard.screen_input
    (best-effort; NEVER blocks; flags + masks PII before memory)
          │
          ▼
      reasoning model (persuadable — assume it can be talked past layer 1)
          │  wants to call a tool
          ▼
 2. STRUCTURAL AUTHZ         security/authz.py::agent_may_access
    (per-domain, same-customer-only, PROHIBITED_TOOLS — server-side, before execution)
          │
          ▼
 3. DETERMINISTIC FLOW GATE  flows/refund_flow.py::amount_gate / eligibility_gate
    (REFUND_LIMIT_SAR / AUTO_REFUND_LIMIT_SAR as a branch, not a sentence)
          │
          ▼
 4. OUTPUT GUARD             security/output_guard.py::guard_tool_call / guard_response
    (re-checks the FULL action-risk matrix on every call; PII + cross-customer egress;
     cumulative-refund/structuring check; the single most reliable layer — it inspects
     the concrete artefact about to happen, not predicted intent)
          │
          ▼
 5. AUDIT / MONITORING       security/events.py -> reports/security_events.jsonl
    (every trip logged; feeds red_team.py's oracles and CI)
          │
          ▼
    tool executes / response reaches the customer

    Each layer alone is insufficient — this is the point, not a gap. Layer 1 is best-effort and admits novel phrasing; the module's own Lab 8 Task 3 proves layers 2-5 hold with layer 1 disabled entirely (see red_team.py::demo_layered_defence, exercised in tests/security/run_without_pytest.py::TestRedTeamSuite:: test_layered_defence_holds_with_input_guard_off). Layers 2-4 are independent, redundant structural checks against the SAME limit — not because any one of them is untrustworthy, but because a real deployment has more than one call path, and one gate on one call path is not defence in depth.

    3. OWASP Agentic Top 10 2026 — mapping¶

    Source and honesty note: OWASP's Agentic AI security work (including an "OWASP Agentic AI — Top 10" / "Agentic Security Initiative" line of publications) is the cited framing for this mapping, per SPEC §6. This repository does not reproduce OWASP's exact numbered list or verbatim item titles because the published numbering has continued to evolve and we do not want to attribute a specific item number to OWASP incorrectly. The rows below use the widely-described agentic risk categories SPEC §6 names as the safe, defensible framing — instructors should pin the exact item numbers from the current published OWASP Agentic Top 10 2026 list before presenting this table. Every row is labelled "aligned to the OWASP Agentic Top 10 2026 categories", not a claim of an exact numbered citation.

    Risk category (OWASP-aligned) How Rafeeq is exposed Control that addresses it Test that proves it
    Agent goal / instruction manipulation Prompt injection via customer message or tool output arguing the model past a stated rule (the SYSTEM OVERRIDE case study) Layers 1-4, principally 3+4 (structural gates do not read conversation text) security/injections/*, red_team.py::run_suite families instruction_override/false_authority/role_play_jailbreak/delimiter_escape/urgency_social_engineering
    Tool misuse A persuaded model calling a tool it should not, or with manipulated arguments (amount, order id) action_risk.classify + output_guard.guard_tool_call (layer 4), security/authz.py (layer 2) tests/security/test_output_guard.py, tests/security/test_action_risk.py
    Privilege compromise Cross-customer access, unauthorised tool chaining, tool calls outside an agent identity's granted domain security/authz.py::agent_may_access (per-domain, same-customer-only, PROHIBITED_TOOLS) tests/security/test_cross_customer.py, security/privilege_escalation/*
    Memory poisoning Raw hostile text persisted into long-term memory/KB and later trusted; stale or forged policy documents retrieved as if current input_guard.screen_input masks before persistence; flows/refund_flow.py/action_risk.py read core.config, never retrieved text security/memory_poisoning/*, docs/SECURITY_MODEL.md §5's forged-policy discussion
    Cascading / multi-agent failures A single successful injection or over-budget loop propagating through supervisor→specialist handoffs MAX_HANDOFFS (M6), per-layer independence (a failure in one specialist's call path does not bypass another's gate) tests/unit/test_termination.py, security/events.py audit trail
    Human-in-the-loop bypass An amount/action that should escalate to a human instead executing autonomously flows/refund_flow.py::request_human_approval, action_risk.classify's requires_human_approval tests/security/test_action_risk.py::TestRefundBanding
    Unexpected code / RCE Not directly applicable — Rafeeq's tools are narrow, typed Python functions with no code-execution or shell tool in the catalogue Least privilege / no such tool exists (tools/registry.py) tools/registry.py's fixed ALL_TOOLS catalogue; assert_matrix_covers_registry()
    Resource / denial-of-wallet An adversarial loop or fan-out request driving step count / cost past budget MAX_STEPS, RUN_COST_CAP_USD (M1/M9); the flow-level step-budget check security/privilege_escalation/denial_of_wallet.json, red_team.py's enforce_step_budget=False vulnerable-target demonstration
    Identity / impersonation A message claiming false authority ("compliance", "the security team", "developer mode") to unlock an action security/authz.py's fixed POLICY table (identity is server-assigned, never claimed in text); PROHIBITED_TOOLS for change_customer_identity security/injections/* (false_authority family), tests/security/test_action_risk.py
    Insufficient observability A guardrail trip or escalation that happens silently, so a regression returns unnoticed security/events.py::log_security_event -> reports/security_events.jsonl, consulted by every red-team Finding.detection red_team.py::_run_one's detection field, security/events.py::read_events

    4. The action-risk matrix¶

    Canonical source: src/rafeeq/security/action_risk.py::RISK + classify(). Standalone classroom artefact: docs/ACTION_RISK_MATRIX.md. Summary:

    Autonomy Meaning Example
    autonomous No gate beyond normal tracing track_shipment, get_order, issue_refund ≤ 50 SAR
    autonomous_within_policy A write, bounded by a deterministic rule the tool itself enforces reschedule_delivery
    policy_controlled Autonomous execution allowed, but MUST be logged issue_refund 50–500 SAR, add_case_note
    human_approval_required Must not execute without a recorded human approval issue_refund > 500 SAR, mark_refunded
    prohibited Must never execute, for anyone, ever change_customer_identity, override_fraud_flag, delete_order

    assert_matrix_covers_registry() fails the build if any tool in tools/registry.py::ALL_TOOLS has no classification here — verified clean as part of this module's own build (SPEC §8).

    5. A genuine finding: refund structuring / smurfing¶

    red_team.py's corpus-driven suite (entries PRV-EN-008/PRV-AR-005, family privilege_escalation) found a REAL gap during this build: three individually-under-limit issue_refund calls (300 + 300 + 300 SAR) against the SAME order each passed the per-call amount gate (each ≤ 500 SAR = policy_controlled), summing to 900 SAR with no human approval — the per-call check did not track the order's CUMULATIVE refunded total.

    Fix (structural, not a prompt): output_guard.guard_tool_call now reads the order's authoritative refund_amount_sar field before allowing any issue_refund call and blocks once already_refunded + requested > REFUND_LIMIT_SAR, regardless of how small the individual call is. See src/rafeeq/security/output_guard.py's "structuring/smurfing fix" section. Retested: retest_finding reports held for both entries (tests/security/run_without_pytest.py:: TestRedTeamSuite::test_retest_after_fix_reports_held).

    This is the module's own lesson demonstrated on this exact codebase: the fix is a code-level cumulative check reading the real order record, not a prompt telling the model "don't split refunds."

    6. Red-team operating procedure¶

    1. Corpus-driven, not ad hoc. Every attack is a fixture in security/**/*.json (schema in security/README.md) — id, family, OWASP category, locale, vector, injection point, payload, preconditions, a success_oracle key, expected block layer, severity.
    2. Run the suite. python3 -m rafeeq.security.red_team (or red_team.run_suite(StubTarget()) programmatically) drives every corpus entry through the REAL structural controls and reports a Finding per entry.
    3. Oracles check concrete effects, never model chatter. Was a refund actually allowed through the gate above the limit? Did a foreign customer_id actually appear in the response? Did the step count actually exceed MAX_STEPS? See red_team.py::ORACLES — this is what keeps the suite honest (a weak oracle is how a red-team suite lies to you, per the module's own troubleshooting note).
    4. File every finding in the seven-part shape: Attack → Vulnerability → Exploit trajectory → Business impact → Detection → Mitigation → Retest result (security/README.md's required shape; Finding's own fields in red_team.py).
    5. Triage by asset impact. Money/PII > availability > cosmetic (capstone/templates/SECURITY_REPORT_TEMPLATE.md's rubric) — fix the highest-severity finding first, and re-run to prove it now fails (retest_finding).
    6. Automate it. Run the suite on every change (CI), not as a one-off manual poke — write_report() regenerates reports/SECURITY_REPORT.md from a fresh run_suite() call every time.
    7. Zero open high-severity findings is the release bar — see the sign-off block in capstone/templates/SECURITY_REPORT_TEMPLATE.md.

    7. What this build actually proved (last run)¶

    • 78 corpus payloads across 10 families, ~46% Arabic, run end to end offline via StubTarget — 0 open breaches against the hardened target.
    • A deliberately under-defended target (enforce_step_budget=False, the "prompt-only step limit" shape of bug applied to availability) DOES trigger denial-of-wallet breaches — proof the suite is not a vacuous all-green rubber stamp.
    • demo_layered_defence() confirms the SYSTEM OVERRIDE-style payload (English AND Arabic) is blocked identically with the input guard on or off — the layered-defence demonstration made executable, not just diagrammed.
