    Rafeeq — Observability (Module 9)¶

    Tracing, cost attribution, the two cost levers, retry safety, and the monitoring dashboard for Rafeeq as a deployed agentic system. Companion to src/rafeeq/observability/{tracing,cost,optimise,retry,audit,slo}.py (the implementation this document explains) and deployment/runbook.md (operating it — health checks, the sim-incident drill, canary gating).

    The governing principle, stated once and assumed everywhere below: an agent can be wrong while running perfectly — no exception, no crash, just a bad decision, a wandering loop, or a quietly climbing bill. You cannot manage that by testing alone; you observe production.

    1. Trace-tree anatomy¶

    A trace is a run's story: a tree of spans, one per meaningful transition — the input guardrail, the supervisor's routing decision, each specialist call, each tool call, the output guardrail — each carrying name, run_type, model, tokens in/out, latency, and (for a tool span) the tool name and an args hash. Rafeeq was built as a state machine (M1) — every transition is already a discrete, traceable event; instrumentation just makes it visible.

    Run resolve:TKT-00042
└─ [chain]     resolve:TKT-00042                          58.2ms
  └─ [guardrail] input_guardrail                            0.1ms
  └─ [chain]     supervisor            model=gpt-4o-mini    56.9ms  tok_in=11 tok_out=49
    └─ [chain]     billing_specialist
      └─ [tool]      issue_refund        tool=issue_refund args#a1b2c3   0.2ms
  └─ [guardrail] output_guardrail                           0.1ms

    A good trace answers, for any run, why the agent did what it did and where the time and money went — M1's auditability promise, now with numbers.

    Two tracers, one guarantee. src/rafeeq/observability/tracing.py implements LocalTracer: a dependency-free span tree that persists every run to reports/traces/<run_id>.json, and render_tree(run), which renders exactly the waterfall above. @traceable(run_type=..., name=...) is the package's LangSmith instrumentation — when langsmith is installed it ALSO wraps the call with the real langsmith.traceable, so a live run streams to a LangSmith project too. Either way, the LocalTracer span always fires. This is load-bearing, not a fallback for its own sake: it is what makes "every lab produces a trace even offline" true (docs/OFFLINE_MODE.md) — a participant with no LangSmith key still gets a real trace tree to read.

    src/rafeeq/service/api.py::resolve_ticket is where this is wired into the actual pipeline: one tracing.start_run per ticket, with input_guardrail / supervisor / one span per tool call / one span per specialist handoff / output_guardrail nested underneath, in the exact shape the capstone's architecture diagram draws.

    2. Cost attribution¶

    "The agent costs too much" is not actionable; "the refund intent costs 0.04 USD because the supervisor and Billing specialist each re-send the full history through the frontier model" is (the module's own framing). src/rafeeq/observability/cost.py::cost_of_run(trace) walks a run's span tree and attributes USD spend along three axes at once:

    • by model — frontier vs cheap: which calls actually needed the expensive model?
    • by component — supervisor, each specialist, each tool span: where does the spend concentrate?
    • by intent — read from the run's own root.extra["intent"] (set by resolve_ticket from the classified/hinted intent): the per-intent cost model Module 2 asked for, now measured from real traces instead of estimated.

    A span prefers an EXPLICIT extra["cost_usd"] when one was computed precisely (real gateway usage); otherwise cost.py prices its tokens_in/tokens_out at core.llm.PRICE[span.model]. cost_report(runs) renders the markdown breakdown — by model, by component, by intent, each sorted with the biggest bar marked <- the fix, matching the module's "biggest bar, biggest opportunity" teaching point — plus the blended cost/contact in both USD and SAR (SAR_PER_USD = 3.75, a fixed board-friendly display peg, never a substitute for reconciling the real USD figure against the model gateway's bill — the same money-discipline rule evaluations/metrics.py already follows).

    blended_cost_per_contact(runs) is the one number finance actually tracks: total spend across a batch of runs divided by contact count.

    3. The two cost levers, and their expected magnitude¶

    src/rafeeq/observability/optimise.py implements both, per the module's own benchmark table:

    Configuration Cost/contact (USD) p95 latency Cache hit rate
    Pre-optimisation (all frontier, no cache) 0.019 3.4 s 0%
    + model routing 0.011 2.6 s 0%
    + retrieval caching 0.008 1.9 s 47%

    Caching (cached_policy): KB retrieval keyed on (question, locale, CURRENT_POLICY_VERSION). TEACHING POINT (the M4 stale-memory lesson, cashed in here): a cache keyed on the question alone serves a stale or wrong-language policy the moment the version bumps or a second locale asks the same question — the version and locale are part of what was actually asked, not an optimisation detail, so leaving either out of the key is a correctness bug, not a performance one. A version bump changes the key, which is a whole-cache invalidation by construction — no TTL clock to get wrong. CacheStats (hits, misses, hit_rate, usd_saved, seconds_saved) turns "we cache" into a measured number for BENCHMARKS.md, not an assertion.

    Model routing (route_model / route_model_name): the confident, simple majority (intent in {order_status, track} AND confidence >= 0.8) routes to the cheap model; everything else — the genuine hard tail — reserves the frontier model. A deterministic rule (M7), not a model call — routing must never itself cost a token. estimate_routing_saving reports the USD this decision saved for one call, for logging alongside the trace.

    These compound with flow engineering (M7, which removes model calls entirely for rule-shaped work): flow removes calls, cache removes repeats, routing cheapens what is left — the funnel the module's "Cost levers" diagram draws.

    4. Retry safety¶

    Transient failures (a tool timeout, a rate limit) deserve a bounded retry with backoff — only for idempotent operations. src/rafeeq/observability/retry.py::call_with_retry keys this off rafeeq.tools.registry.IDEMPOTENT (M3's read/write split — never a second, hand-maintained list):

    • a tool NOT in IDEMPOTENT (a write — issue_refund, reschedule_delivery, mark_refunded, add_case_note) is called exactly once; the retry loop does not exist in the control-flow path for that tool_name at all, so there is no flag to forget to set.
    • a tool IN IDEMPOTENT (a read — track_shipment, get_order, ...) is retried up to retries times (default 2) with exponential backoff on TransientToolError.

    RetryLedger records every attempt, so ledger.assert_never_retried("issue_refund") is a one-line proof, not a re-read of this module's source and a hope: the capstone's rubric bar ("a write tool with a retry wrapper" caps that criterion at 70%) is checkable, not just claimed. deployment/sim_env/scripts/sim_incident.py is a full worked example: it retries the idempotent track_shipment under an injected brownout and reports the ledger's retry count.

    5. LangSmith principle: production traces become evaluation datasets¶

    A production trace that went wrong should become a regression test, not a one-off bug fix. evaluations/harness.py's --baseline/--gate pair is the offline version of that idea: freeze today's metrics as a baseline report (reports/eval_stub_baseline.json), and any later run that regresses beyond tolerance fails the gate (.github/workflows/ci.yml's eval_harness_gate job) instead of merging silently. rafeeq.observability.audit.replay(ticket_id) is the complementary per-ticket version: a run that surprised someone in production reconstructs, in order, exactly what the system did — the starting point for turning that one incident into a new TawseelBench scenario or a new tickets_eval.jsonl row, the mechanism by which production reality improves the offline tests over time.

    6. Monitoring: SLOs, alerts, and the 12-dimension dashboard¶

    src/rafeeq/observability/slo.py::check_slos(metrics) compares a Metrics snapshot (see evaluations/metrics.py — the SAME 12-dimension object the eval harness and TawseelBench already produce, not a second metrics pipeline) against a SLOs set and returns every Alert that fires: metric, threshold, actual value, severity, owner. Default targets:

    SLO Default Source
    p95 latency ≤ 2.5 s Module 9's own Benchmarks table
    Cost/contact ≤ 0.012 USD the module's "+ caching" bench row (0.008) with headroom before it pages
    Escalation rate ≤ 20% classroom default — tune in the SLO-workshop exercise
    Unsafe-action rate 0% matches the capstone rubric's "0 open high-severity findings" bar

    deployment/sim_env/scripts/sim_incident.py exercises the p95-latency alert end to end: baseline green -> brownout injected -> alert fires -> brownout removed -> green again — the "watch the alert fire, respond" drill deployment/runbook.md walks an operator through.

    For the full 12-dimension dashboard this SLO layer sits on top of — task-success, policy-compliance, correct-tool-call, unsafe-action, retry/failure, tool-calls/task, tokens in/out, cost/task (USD + SAR), p50/p95 latency, memory-retrieval precision, attack-success rate, escalation rate — see evaluations/metrics.py::Metrics, whose render_table/render_comparison/render_family_table are what reports/DASHBOARD.md and BENCHMARKS.md are built from, and evaluations/dashboard.py::render_dashboard, which additionally sparkline-trends metrics run-over-run and can render an Architecture-A- vs-B comparison alongside them.
