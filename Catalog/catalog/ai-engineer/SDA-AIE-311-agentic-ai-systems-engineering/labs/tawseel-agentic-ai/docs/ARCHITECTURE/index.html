    Rafeeq — Architecture (Modules 1–7 graph/agent layer)¶

    This document is the reference map for the agent/graph layer built across Modules 1–7: the bounded core loop, the reasoning patterns, memory, the specialist/supervisor split, and flow engineering. It complements docs/MCP_TOPOLOGY.md (Module 3's tool/server boundary) rather than repeating it.

    1. Target-state diagram (capstone)¶

    The system every lab is building toward, one piece per module:

    Client (AR/EN ticket) ─▶ API /v1/resolve ─▶ input guardrail ─▶ Supervisor
                                                                   │ route (scoped handoff, logged)
                          ┌──────────────┬──────────────┬──────────┘
                     Orders spec.   Logistics spec.  Billing spec.
                          │              │               │  (deterministic refund/reschedule
                          │              │               │   flows + gates — Module 7)
                          └── MCP client ─┴──────────────┘
                                   │
        MCP servers (authz + audit): orders · logistics · billing · customer ─▶ mock Tawseel backends
                                   │
        Memory: SQLite/Postgres checkpointer (short-term) · vector store (long-term + versioned KB)
                                   │
        output guardrail ─▶ aggregate / escalate ─▶ response
        cross-cutting: tracing · cost attribution · red-team suite (CI)

    Two entry points drive the SAME compiled graph (Module 1's architectural rule): a synchronous API call (service/api.py) and an offline batch replay over data/tickets_eval.jsonl (the eval harness). If both do not exercise identical graph structure, the architecture is wrong.

    2. Layer map¶

    Layer Package What it owns Dependencies
    Domain config core/ config.py (policy constants, paths), state.py (RafeeqState), llm.py (model factory: stub/replay/live), embeddings.py, budget.py (RunBudget), errors.py stdlib + pydantic only
    Backends adapters/ Mock OMS, logistics, CRM, billing clients + the shared TawseelStore core/ only
    Tool surface tools/ Narrow, typed, governed tools per domain (orders.py, logistics.py, billing.py, customer.py) + registry.py (the catalogue authz/retry key off) + mcp_client.py adapters/, core/
    Reasoning reasoning/ ReAct (explicit + LangGraph), Plan-and-Execute, Reflection, the prompt-only anti-pattern, and compare.py core/, tools/ (impls)
    Memory memory/ Short-term (checkpointer), long-term (scoped vector recall), knowledge base (versioned policy retrieval), vector_store.py (offline-first store) core/
    Agents agents/ Specialist factory (specialist.py), context-scoping (scoping.py), the monolith baseline (baseline.py) tools/, core/
    Orchestration orchestration/ Supervisor (Architecture A), delegate/finish, agents-as-tools (Architecture B), deterministic routing + fast-path agents/, core/
    Flows flows/ Deterministic, gate-based refund and reschedule flows (Module 7) tools/, core/
    Security security/ authz.py (server-side authorisation — this build's scope), plus input_guard.py/output_guard.py/events.py/red_team.py/action_risk.py (owned elsewhere) tools/registry.py
    Observability observability/ tracing.py/optimise.py/retry.py/audit.py/cost.py (owned elsewhere — every module in this build's scope that logs an event does so through a lazy, best-effort import of observability.audit, degrading to stdlib logging when it is absent) —
    Service service/ api.py/health.py — the synchronous entry point (owned elsewhere) everything above

    The core rule this build's scope follows throughout (SPEC §1): langgraph/langchain-core are Layer-B dependencies, absent from the build/CI sandbox. Every module that touches them is import-guarded — a try/except ImportError at module load plus a _require_langgraph() (or equivalently-named) helper raising a clear pip install … message — and graph/agent CONSTRUCTION happens only inside a build_*()/get_*() function, never at import time. Pure logic (gate functions in flows/, orchestration/routing.py and fastpath.py, agents/scoping.py) has NO such dependency at all and is directly unit-testable.

    3. The state-object contract (RafeeqState, core/state.py)¶

    Every node in every graph in this repo reads and writes this ONE typed object. Fields marked "M1" are the original Module-1 skeleton; later columns show which module's code populates or consumes each extension.

    Field Type Introduced Written by Read by
    messages list[AnyMessage] (reducer: add_messages when langgraph present) M1 every reasoning/orchestration node every node, memory (checkpointer)
    customer_id str M1 entry point (handle_turn, API) agents.scoping.SCOPE, memory.long_term, security.authz
    locale "ar" \| "en" M1 entry point reply composition, memory.knowledge_base.policy_context
    order_id str \| None M1 reasoning nodes, tool results flows, specialists
    step_count int M1 core.graph.reason (+1 per step) core.graph.route, core.budget.RunBudget
    resolution "pending" \| "resolved" \| "escalated" M1 orchestration.finish.aggregate/escalate API response, eval harness
    handoff_count int M6 orchestration.delegate.make_delegate orchestration.supervisor.supervise (global budget)
    subgoal str \| None M2/M6 orchestration.supervisor.supervise, reasoning.plan_execute delegate nodes, specialists
    route str \| None M6 orchestration.supervisor.supervise orchestration.supervisor.route (conditional edge)
    last_result dict M3/M6 orchestration.delegate.make_delegate (mandatory write-back) orchestration.finish.aggregate
    ticket_id str M4/M9 entry point memory writes, audit logs, escalation records
    cost_usd float M9 model-call wrapper (owned by observability/) core.budget.RunBudget.check
    flags list[str] M8 guardrails (owned by security/) routers, escalation

    RafeeqState is defined once (core/state.py, not modified by this build's scope) and extended by ADDING fields, never by widening an existing field's meaning — the same discipline flows/refund_flow.py and flows/reschedule_flow.py apply to their own narrower TypedDicts (RefundState, RescheduleState), which are strict subsets/extensions of the same idea scoped to one flow.

    4. Reasoning patterns (Module 2) at a glance¶

    Pattern File Runs without langgraph? Bounded by
    ReAct (graph) reasoning/react.py::build_react_agent No (needs ToolNode) core.config.MAX_STEPS
    ReAct (explicit) reasoning/react.py::react_loop_explicit Yes max_steps param, defaults to MAX_STEPS
    Plan-and-Execute reasoning/plan_execute.py Yes (run_plan_execute); graph wiring needs langgraph plan length + plan_approval_gate
    Reflection reasoning/reflection.py::reflect_and_revise Yes core.config.MAX_REFLECTIONS
    Prompt-only (anti-pattern) reasoning/refund_prompt_only.py Yes (it is Lab 7's starting point, not a fix) nothing — that is the point

    reasoning/compare.py::compare_patterns runs all of the above (minus the LangGraph-only ReAct variant) on the same tickets_eval.jsonl slice and returns a cost/latency/quality table — see its module docstring for the simulated-cost methodology used under the default offline StubChatModel.

    5. Architecture A vs Architecture B: supervisor vs agents-as-tools¶

    Both are built in this scope, on the SAME three specialists (agents/specialist.py), so they are comparable on identical ground truth:

    • Architecture A — supervisor (orchestration/supervisor.py + delegate.py + finish.py). A dedicated routing hub (supervise) reads shared state, decides the next specialist (or finish/escalate) as a graph-level conditional edge, and every handoff is a distinct, logged, scoped transition (agents.scoping.scoped_input + handoff_count). Control flow is literally drawable as graph structure — a compliance reviewer can point at the exact edge a decision took.
    • Architecture B — agents-as-tools (orchestration/agents_as_tools.py). ONE agent (Rafeeq) whose tool belt includes orders_agent, logistics_agent, billing_agent — each a normal, typed, schema- validated tool call (SpecialistToolInput/SpecialistToolOutput) that happens to run a sub-agent internally. Routing IS tool selection: the same mechanism, the same per-call typing, the same place every other tool call in this repo is authorised and traced. LangGraph's own multi-agent guidance is the reason this file argues Architecture B can give GREATER CONTROL and STRONGER TYPING than a generic supervisor — see agents_as_tools.py's module docstring for the full argument, including the honest trade-off (a supervisor keeps cross-agent sequencing visible as graph structure; agents-as-tools folds it inside one agent's own step-bounded reasoning trace instead of a dedicated handoff_count).

    Both architectures reuse the SAME context-isolation control (agents.scoping.scoped_input) and the SAME specialist builders (agents.specialist.SPECIALIST_BUILDERS) — the comparison below is a routing-topology difference, not a difference in what each specialist is allowed to see or do.

    6. Flow engineering (Module 7): where the rules actually live¶

    Rule (from data/policies/en/*.md) Code location Gate function
    Refund ≤ 50 SAR: fully autonomous flows/refund_flow.py amount_gate → "auto_approve"
    Refund 50–500 SAR: autonomous, policy-controlled flows/refund_flow.py amount_gate → "approve"
    Refund > 500 SAR: human approval required flows/refund_flow.py amount_gate → "needs_human" → request_human_approval
    Never refund twice / not SLA-breached flows/refund_flow.py eligibility_gate
    Max 2 reschedules per order flows/reschedule_flow.py max_reschedules_gate
    4h–7d reschedule window flows/reschedule_flow.py window_gate
    Friday cut-off flows/reschedule_flow.py city_cutoff_gate
    Courier availability flows/reschedule_flow.py courier_availability_gate
    High-confidence single-domain routing, no model call orchestration/fastpath.py fastpath_route

    Every row in this table is a code answer a compliance reviewer can open, read, and unit-test — the opposite of reasoning/refund_prompt_only.py's ANTI-PATTERN, where the same rules are sentences a crafted input can argue past.

    7. Import-guard convention (reference)¶

    Every Layer-B module in this scope follows the same shape:

    try:
    from langgraph.graph import StateGraph, START, END
    LANGGRAPH_AVAILABLE = True
except ImportError:
    LANGGRAPH_AVAILABLE = False

def _require_langgraph() -> None:
    if not LANGGRAPH_AVAILABLE:
        raise ImportError("<module> requires langgraph/langchain-core. "
                           "Install with: pip install langgraph langchain-core")

def build_x_graph():
    _require_langgraph()
    ...   # construction happens HERE, never at import time

    Verified (SPEC §8) for every module this build touches: python3 -m py_compile clean, importable under PYTHONPATH=src with langgraph absent, and every build_*()/get_*() graph constructor raises a clean ImportError naming the exact pip install line rather than crashing on a bare ModuleNotFoundError or, worse, importing successfully but failing confusingly deep inside a third-party call.

    SDAIA Academy — internal use only. Do not distribute.
