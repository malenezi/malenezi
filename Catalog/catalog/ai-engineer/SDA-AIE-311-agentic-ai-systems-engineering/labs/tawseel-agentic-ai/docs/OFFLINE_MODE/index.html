    Rafeeq — Offline Mode¶

    How the entire repository runs with zero API keys and zero network calls, what is faithful versus simplified while it does, and exactly when a participant must switch to live mode. Companion to src/rafeeq/core/config.py (Settings, the single source of these env vars) and src/rafeeq/core/llm.py (StubChatModel, the mechanism behind RAFEEQ_MODEL_MODE=stub).

    The governing principle: the stub is not a hack bolted on for the sandbox — it is a first-class mode participants ship with, the same way a payments team ships a sandbox gateway. StubChatModel implements the same call surface a real chat model does (.invoke, .bind_tools, .with_structured_output), so code written against it works unmodified against the real thing.

    The three env vars¶

    Var Values Default Controls
    RAFEEQ_MODEL_MODE stub | replay | live stub Which "model" core.llm.get_model()/get_cheap_model()/get_frontier_model() return
    RAFEEQ_VECTOR_MODE simple | qdrant simple Which store memory.vector_store.get_store() returns
    RAFEEQ_EMBED_MODE hashing | live hashing Which embedder core.embeddings.get_embeddings() returns

    Settings.is_offline() (core/config.py) is True exactly when none of the three is set to its network-touching value — that single boolean is what service/health.py::readiness() reports as model_mode/ vector_mode/embed_mode, and what every lab's make test runs under.

    RAFEEQ_MODEL_MODE¶

    • stub (default). StubChatModel: deterministic, rule-based, bilingual (AR/EN) intent + order-id extraction over the last human message, emitting the tool call a competent agent would. Zero cost (core.llm.PRICE["stub"] == {"input": 0, "output": 0}), zero network, zero keys. This is what makes make test, the eval harness, and CI deterministic and free.
    • replay. Replays recorded traces from data/recordings/*.json — deterministic, free, no keys — with a stub fallback for any input not in the recording. Used by docker-compose.yml's full profile by default (a realistic-looking deployment with no live spend).
    • live. A real ChatOpenAI via the course gateway (OPENAI_BASE_URL/OPENAI_API_KEY), lazy-imported so Layer A never needs langchain-openai installed just to import core.llm.

    RAFEEQ_VECTOR_MODE¶

    • simple (default). SimpleVectorStore — an in-memory, cosine-similarity store over whatever RAFEEQ_EMBED_MODE produces. Mirrors QdrantVectorStore's call surface (add_documents, similarity_search, similarity_search_with_score, delete) so memory/long_term.py/memory/knowledge_base.py work unmodified against either. Filter-before-rank is enforced identically to Qdrant (the PDPL-relevant guarantee — see memory/vector_store.py's docstring), so cross-customer leakage tests are meaningful offline.
    • qdrant. A real Qdrant instance (docker-compose.yml's qdrant service in the full profile).

    RAFEEQ_EMBED_MODE¶

    • hashing (default). A deterministic, dependency-free hashing embedder (core/embeddings.py) — no model call, no network. Good enough to exercise retrieval ranking and cross-lingual filtering correctness; NOT semantically meaningful the way a real embedding model is (two paraphrases hash to different vectors even when a real embedder would place them close together).
    • live. A real embedding model call.

    What is faithful in stub mode¶

    • Every structural control. Authorisation (security/authz.py), the action-risk matrix (security/action_risk.py), the output guardrail's PII/cross-customer/over-limit blocks (security/output_guard.py), the refund amount gate (flows/refund_flow.py), retry-safety (observability/retry.py) — none of these read the model's output to decide anything; they inspect the CONCRETE tool call/args/result. A red-team finding held in stub mode is held for the same structural reason it would be held in live mode — this is why Lab 8's "disable the input guard, the over-limit refund is still blocked" demonstration works identically offline.
    • Tracing, cost attribution, budgets, and audit. observability/tracing.py's LocalTracer produces a real span tree with real (stub-priced, i.e. zero) tokens; observability/cost.py attributes it correctly; every handoff/escalation/tool-call/decision is written to reports/audit/audit_log.jsonl exactly as it would be live.
    • Data shape and referential integrity. data/generate.py's output and every adapter/tool are the real production code paths — only the "model" and "embedder" are swapped, never the backends they call.

    What is simplified in stub mode¶

    • Reasoning quality. StubChatModel is a keyword+regex classifier, not a language model — it cannot handle genuine ambiguity, novel phrasing, or multi-turn reasoning the way a real model can. TawseelBench's task_success_rate under --target stub is a floor on correctness, not a ceiling; docs/OBSERVABILITY.md's cost numbers under stub mode are all zero (PRICE["stub"] is free) — real cost attribution needs replay or live traces (see service/api.py::resolve_ticket's routed-model cost estimate, which prices stub-run tokens at the model tier optimise.route_model_name WOULD have used, precisely so the cost report has a non-zero, meaningful number to show even offline).
    • Retrieval relevance. The hashing embedder ranks by hash-vector cosine similarity, not semantic meaning — cross-lingual retrieval ("does an Arabic question retrieve the right English policy chunk, or vice versa") is exercised structurally (the filter/version logic is real) but not semantically; a live embedder is needed to judge whether retrieval quality itself is good.
    • Injection realism. security/input_guard.py's regex families catch the corpus's known attack shapes; a live model is a genuinely more persuadable target for a NOVEL phrasing a regex was never written for. Stub-mode red-team runs prove the STRUCTURAL layers hold (authz, output guard, action-risk) regardless of whether the input guard catches the attempt — they do not prove a live model resists social engineering as well as the structural layers do.

    When a participant MUST switch to live mode¶

    1. The capstone demo. The 6-minute demo (capstone/README.md) asks for "a bilingual ticket resolved end to end" and a live trace/cost walkthrough that reads as a real system, not a rules engine — run it under RAFEEQ_MODEL_MODE=live (or at minimum replay against real recorded traces) so the reasoning genuinely varies with phrasing.
    2. Red-team realism for the final security report. The stub-mode red-team run (tests/security/run_without_pytest.py, .github/workflows/ci.yml's red_team_gate job) proves the STRUCTURAL defences hold and is what CI gates on (it must stay offline-runnable — SPEC's "CI needs no keys" rule). SECURITY_REPORT.md's findings should ADDITIONALLY be retested once, live, before final submission — a novel phrasing a live model resists (or doesn't) is real evidence the stub run cannot produce.
    3. Any claim about retrieval QUALITY (not just retrieval correctness/scoping) — semantic search evaluation needs a real embedder; RAFEEQ_EMBED_MODE=hashing cannot support that claim.
    4. Once BENCHMARKS.md's cost/latency numbers need to reconcile against a real gateway bill — stub-mode cost is illustrative (routed-model pricing applied to stub token counts, see above), not a real invoice; only live/replay-against-real-recordings traces are.

    Everything else — every lab, make test, the eval harness, TawseelBench, the red-team CI gate, and this build's own verification — runs entirely under the defaults above: RAFEEQ_MODEL_MODE=stub, RAFEEQ_VECTOR_MODE=simple, RAFEEQ_EMBED_MODE=hashing. No key, no network, no cost.
