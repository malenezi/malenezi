    Rafeeq — operating the simulated Tawseel environment¶

    Module 9 / final capstone (LO8). This is the operator's guide to the deployment/ stack: bring-up, health verification, the sim-incident brownout drill, rollback, and the canary-evaluation gate. Every command below is copy-pasteable and, other than docker compose itself, uses nothing beyond this repository's own scripts.

    0. Two ways to run this¶

    Profile Command What it needs
    labs docker compose -f deployment/docker-compose.yml --profile labs up Nothing — RAFEEQ_MODEL_MODE=stub, no Qdrant/Postgres/MCP/keys. This is the profile every lab and CI runs against (docs/OFFLINE_MODE.md).
    full docker compose -f deployment/docker-compose.yml --profile full up Qdrant + Postgres + the four MCP servers + sim-backends, all brought up automatically via depends_on/healthchecks; optionally OPENAI_API_KEY/OPENAI_BASE_URL for RAFEEQ_MODEL_MODE=live (defaults to replay, which needs no key).

    Without --profile compose starts nothing — every service is tagged labs or full on purpose (SPEC's own "profiles: [labs] variant" requirement), so there is no accidental half-up state.

    1. Bring-up¶

    # labs (the default a participant with no key uses)
docker compose -f deployment/docker-compose.yml --profile labs up -d
docker compose -f deployment/docker-compose.yml --profile labs ps   # wait for "healthy"

# full
export OPENAI_API_KEY=...        # optional — omit to stay on RAFEEQ_MODEL_MODE=replay
docker compose -f deployment/docker-compose.yml --profile full up -d
docker compose -f deployment/docker-compose.yml --profile full ps   # wait for every service "healthy"

    rafeeq-api/rafeeq-api-labs's HEALTHCHECK (in Dockerfile) polls its own /healthz; compose's depends_on: condition: service_healthy on the full profile means rafeeq-api will not even start accepting the depends_on chain until Qdrant, Postgres and all four MCP server containers report healthy first — a genuinely ordered bring-up, not a hopeful sleep.

    2. Health verification¶

    curl -s http://localhost:8000/healthz | python3 -m json.tool   # liveness — process is up
curl -s http://localhost:8000/readyz  | python3 -m json.tool   # readiness — can it actually serve

    /readyz (see src/rafeeq/service/health.py) checks, and reports per-check detail for: the seed data files exist on disk, the vector store constructs, the four MCP server modules import, and which RAFEEQ_MODEL_MODE is active — a live mode with no key is flagged explicitly rather than silently reported "ok". A deploy/rollback decision below always reads /readyz, never /healthz alone — a process can be alive and still not ready to serve.

    Smoke-test the actual pipeline:

    curl -s -X POST http://localhost:8000/v1/resolve \
  -H 'Content-Type: application/json' \
  -d '{"ticket_id":"TKT-SMOKE-1","text":"أين طلبي رقم TW-2026-88120؟","locale":"ar","customer_id":"CUST-4471","order_id":"TW-2026-88120"}' \
  | python3 -m json.tool

    The response's trace_id points at reports/traces/<trace_id>.json inside the container (docker compose exec rafeeq-api cat reports/traces/<trace_id>.json) — every request is traced, matching docs/OBSERVABILITY.md's trace-coverage target.

    3. The sim-incident brownout drill¶

    Demonstrates the reliability-signal loop end to end: inject a backend brownout, watch a p95-latency alert fire, respond, confirm recovery.

    # Standalone (no compose needed — the drill is a plain Layer-A script):
PYTHONPATH=src python3 deployment/sim_env/scripts/sim_incident.py

# Against the `full` profile's running sim-backends container:
docker compose -f deployment/docker-compose.yml --profile full exec sim-backends \
  python3 deployment/sim_env/scripts/sim_incident.py --on     # inject
# ... watch reports/traces/*.json p95 climb / poll a monitoring view ...
docker compose -f deployment/docker-compose.yml --profile full exec sim-backends \
  python3 deployment/sim_env/scripts/sim_incident.py --off    # respond

    Run with no flags, the script performs the whole drill itself: measure a baseline (asserts rafeeq.observability.slo.check_slos is green), inject a brownout (extra_latency_s=1.0, error_rate=0.6), re-measure (asserts the p95-latency alert FIRES), turn the brownout back off, and re-measure once more (asserts the alert clears). It exits non-zero if any of those four assertions fails — safe to wire into a scheduled post-deploy check. Every simulated call goes through rafeeq.observability.retry.call_with_retry against the one idempotent read tool it uses (track_shipment), so the drill's retry counts are real evidence, not narration: expect a nonzero retry count on the brownout leg and — separately, proven in tests/security/observability/retry.py's own tests — an issue_refund retry count of exactly zero, always.

    See src/rafeeq/observability/slo.py for the SLO thresholds this drill checks against, and deployment/sim_env/config.py for the injection mechanism (maybe_inject) a real adapter would call at the top of a read to participate in the drill for real (not wired into src/rafeeq/adapters/ by this module — see that file's docstring for why).

    4. Rollback¶

    1. Confirm the regression: /readyz degraded, an open SLO alert (rafeeq.observability.slo.check_slos against recent traces), or a failed canary gate (§5).
    2. Roll the image back: 
      docker compose -f deployment/docker-compose.yml --profile full pull rafeeq-api  # or point at the prior tag
docker compose -f deployment/docker-compose.yml --profile full up -d rafeeq-api
      Postgres (the checkpointer) and Qdrant (long-term memory/KB) are SEPARATE services from rafeeq-api — rolling the API image back does not touch either, so in-flight threads and stored memory survive a rollback. Only roll either data service back if the regression is a confirmed data-shape issue, and only after taking the volume snapshot the rollback would otherwise discard.
    3. Re-run /readyz and the /v1/resolve smoke test (§2) against the rolled-back image before declaring the incident closed.
    4. File the incident: rafeeq.observability.audit.render_replay(ticket_id) for any ticket implicated, plus the relevant reports/traces/*.json — the audit/trace pair this whole build exists to make possible.

    5. The canary-evaluation gate¶

    Before promoting a new build, run the SAME eval-harness gate CI uses (.github/workflows/ci.yml's eval_harness_gate job) against the CANDIDATE image, comparing it to the currently-deployed baseline:

    # Freeze the currently-deployed build's numbers (do this once, commit the file):
PYTHONPATH=src python3 -m evaluations.harness --target stub \
  --out reports/eval_stub_baseline.json

# Before promoting a candidate build, from inside it (or with its code checked out):
PYTHONPATH=src python3 -m evaluations.harness --target stub \
  --baseline reports/eval_stub_baseline.json --gate

    --gate exits non-zero if any gated metric (task-success, policy-compliance, correct-tool-call, unsafe-action, attack-success — see evaluations/harness.py::_GATED_METRICS) regresses beyond --tolerance (default 2 percentage points) versus the committed baseline. A candidate that fails this gate is NOT promoted, full stop — this is the "cheaper agent that got worse is a failure, not a win" rule (Module 9's own instructor note) enforced as a deploy gate, not just a classroom aside. Once a candidate passes, promote it (§1's bring-up commands against the new image tag) and re-freeze the baseline from its own numbers for the NEXT promotion.
