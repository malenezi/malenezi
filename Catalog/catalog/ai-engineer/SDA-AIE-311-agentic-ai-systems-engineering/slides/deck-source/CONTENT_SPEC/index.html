    Deck content authoring spec — SDA-AIE-311¶

    You write JSON only. A renderer (deck/render.js, already built and tested) turns it into PowerPoint. Never write layout, colours, positions or fonts. Never produce a .pptx.

    Output file: deck/content/<NN>_<name>.json, shape:

    { "slides": [ { "type": "...", ... }, ... ] }

    Files render in filename sort order, so keep the numeric prefix you are given.

    Editorial rules (these matter more than the schema)¶

    1. The slide carries the claim; the notes carry the teaching. Every slide must have notes — 40–90 words of what the instructor says, shows, asks, and how long it takes. Write them as instructions to a competent instructor who has not memorised the package ("Draw this on the board first, then reveal", "Ask the room before you answer", "If you are behind, cut this slide").
    2. No slide is a paragraph. Bullets are one sentence, ideally under 150 characters. Use the lead field for the 2–4 word claim and text for the explanation.
    3. Titles under 48 characters. Longer titles wrap to two lines and eat the body.
    4. Every technical claim in the instructor package is authoritative. Do not soften it, do not invent numbers. Where the package gives a number (94% routing accuracy, 68% of spend, 0.019 → 0.008 USD), use exactly that number and mark it as an illustrative benchmark from the package, not a promise.
    5. Reported third-party figures must be attributed on the slide itself (e.g. "AWS reports", "Ryanair reported"). Never present them as our own measurements.
    6. Arabic: only in title_ar, statement_ar, and where a customer-facing string is the point. Correct natural MSA. Never machine-translate a whole slide.
    7. Anti-patterns are marked, not implied: use kind: "bad" / tone: "bad" and say the word "anti-pattern".
    8. Vary the slide types. A run of more than three bullets slides in a row is a defect. Aim for roughly: 35% bullets/two_col, 15% code, 12% table/metrics, 12% cards, 10% flow, 8% statement/section, 8% lab/case.
    9. British spelling (optimise, behaviour, analyse). No emoji. No exclamation marks.

    Slide types¶

    section — day and module dividers (dark)¶

    {"type":"section","kicker":"Day 2 · Hour 3","big":"M4","title":"Memory and state management",
 "title_ar":"الذاكرة وإدارة الحالة","subtitle":"One sentence on what changes after this module.",
 "items":["Two memories","Scoped recall","PDPL erasure","Stale policy"],"notes":"..."}
    big = 2–4 characters max (module code or day number). items = up to 4 short labels.

    statement — the one idea, full bleed (dark)¶

    {"type":"statement","kicker":"The rule","statement":"A prompt is not an access-control mechanism.",
 "statement_ar":"التعليمات ليست آلية تحكّم في الصلاحيات.","attribution":"Module 8","notes":"..."}
    statement under 110 characters reads best. statement_ar and attribution optional. Use roughly one of these per module — they are punctuation, not content.

    bullets — the workhorse (light)¶

    {"type":"bullets","module":"M3","kicker":"optional eyebrow","title":"...","title_ar":"optional",
 "intro":"optional one-line framing, italic",
 "bullets":[{"lead":"Errors are values.","text":"Return {\"error\": \"...\"}; the model can react and the loop does not crash.","kind":"default"}],
 "aside":{"title":"WATCH FOR","tone":"warn","body":"Short block, 2–4 sentences, appears as a side panel."},
 "notes":"..."}
    - 4–6 bullets. Never more than 7. - kind: default (teal), bad (red, anti-pattern), good (green), key (amber, the one that matters most). At most one key per slide. - aside.tone: default | warn | key. Omit aside when the slide is already full. - A bullet may also be a plain string.

    two_col — comparison, before/after, do/don't (light)¶

    {"type":"two_col","module":"M2","title":"...",
 "left":{"title":"ReAct","subtitle":"optional","items":[{"lead":"Strength","text":"..."}]},
 "right":{"title":"Plan-and-Execute","items":["..."]},
 "left_tone":"bad","right_tone":"good","notes":"..."}
    Tones optional (bad red header, good green header, omitted = teal). 3–6 items per side.

    cards — 2 to 6 concept tiles (light)¶

    {"type":"cards","module":"M1","title":"The four components",
 "cards":[{"label":"1","title":"Planning","body":"2–3 sentences.","tone":"default"}],"notes":"..."}
    label is 1–3 characters (number, letter, or "M4"). tone: default | good | bad | key. Body ≤ 240 characters at 3 cards, ≤ 180 at 6.

    table (light)¶

    {"type":"table","module":"M5","title":"...","headers":["Pattern","Cost","Latency","Best for"],
 "rows":[["ReAct","High","Medium-high","Open-ended paths"]],
 "colW":[3.2,2.0,2.0,4.9],"footnote":"optional","notes":"..."}
    - Maximum 9 rows, maximum 5 columns. colW in inches, must total 12.09 — omit for equal widths. - Prefix a cell with !bad, !good or !key to colour it.

    metrics — benchmark slide (light)¶

    {"type":"metrics","module":"M9","title":"What good looks like after M9",
 "tiles":[{"value":"-58%","label":"blended cost per contact","tone":"good"}],
 "headers":["Metric","Target","How measured"],"rows":[["Task success","≥ 90%","eval replay"]],
 "notes":"..."}
    2–5 tiles. Tiles or table or both.

    flow — diagrams, pipelines, architectures (light)¶

    {"type":"flow","module":"M6","title":"Supervisor topology",
 "rows":[{"label":"Request","steps":[{"text":"Ticket","sub":"AR or EN"},{"text":"Input guard","sub":"M8","tone":"key"}]}],
 "caption":"optional one-line reading of the diagram","notes":"..."}
    - 1–5 rows, 2–6 steps per row. label optional (left gutter, ≤ 12 chars). - text ≤ 22 chars, sub ≤ 26 chars. tone: default | key | good | bad. - This is the only diagram primitive. Layered architectures become several rows.

    code — dark code panel¶

    {"type":"code","module":"M1","title":"The bounded loop","filename":"src/rafeeq/core/graph.py",
 "code":"def route(state):\n    ...","callouts":[{"lead":"Budget branch","text":"..."}],"notes":"..."}
    - Maximum 24 lines, maximum 92 columns with callouts; 100 columns without. Trim the real file to the teaching core; add # ... elisions rather than shrinking type. - Lines containing ANTI-PATTERN or SMELL render red; TEACHING POINT renders amber. - 0–5 callouts. Prefer 3.

    lab — the lab brief¶

    {"type":"lab","module":"M3","title":"Lab 3 — Tawseel tools over MCP",
 "objective":"...","duration":"50 minutes","setup":"git checkout lab3-start; make mcp-orders",
 "tasks":[{"lead":"5 min","text":"..."}],
 "expected":"$ pytest tests/unit/test_tools.py -q\n6 passed in 0.4s","commit":"feat: ...","notes":"..."}
    4–7 tasks, each prefixed with its minute budget in lead.

    case — case study¶

    {"type":"case","module":"M1","title":"The runaway refund agent",
 "scenario":"...","challenge":"...","solution":"...",
 "questions":["...","..."],"notes":"..."}
    Three panels of 240–400 characters each, plus 2–4 discussion questions. Omit questions for a fuller three-panel layout.

    checklist¶

    {"type":"checklist","module":"M8","title":"Exit criteria for Day 4",
 "items":[{"lead":"0 open high","text":"red-team suite green in CI","state":"yes"}],"notes":"..."}
    state: yes (green tick) or no (red cross). 4–12 items.

    closing — dark wrap slide¶

    {"type":"closing","title":"Day 3 in one line","title_ar":"optional",
 "points":["...","...","..."],"notes":"..."}
    3–5 points.

    Required rhythm per module¶

    Every module gets, in this order:

    1. section divider (module code in big)
    2. bullets — why this matters commercially, Saudi/enterprise framing
    3. 6–12 slides of technical content (mix of bullets, two_col, cards, flow, table)
    4. 2–3 code slides drawn from the real repository files
    5. 1 statement — the module's one idea
    6. bullets with kind: "bad" — the common mistakes (the package lists them; use them)
    7. case — the module's case study from the package
    8. lab — the lab brief
    9. metrics — the module's benchmark table from the package
    10. closing or a checklist exit-ticket slide

    Validation (do this before you finish)¶

    cd /home/claude/build/deck
python3 -c "import json,sys; d=json.load(open('content/YOURFILE.json')); print(len(d['slides']))"
node render.js content/00_front.json content/YOURFILE.json -o out/check.pptx
    Fix every warning the renderer prints (long bullets, oversized code, unknown types, render errors). Report the slide count and that the render was warning-free.
