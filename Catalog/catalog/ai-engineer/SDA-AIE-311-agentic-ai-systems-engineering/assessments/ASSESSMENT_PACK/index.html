    Assessment Pack¶

    SDA-AIE-311 Agentic AI Systems Engineering¶

    Contains: the 20-question quiz bank with answers, a printable 10-question cohort form, PA-1 and PA-2 briefs with scoring sheets, the capstone rubric, a grade-calculation worksheet, academic-integrity checks, and badge issuance criteria. Source: assessment_package.md and final_capstone_project.md (verbatim rubric text is marked as such); scoring sheets below expand those documents into instructor-usable detail.

    Part 1 — Quiz Bank (20 questions, master set)¶

    Closed book, 15 minutes when run as a full quiz. Use 10 questions per cohort sitting (see Part 2 for a ready-to-print selection) so the exact set can rotate between cohorts.

    # Question Module Answer
    Q1 What single property distinguishes an agent from a chain? M1 The model decides control flow at runtime.
    Q2 Name the four agentic components. M1 Planning, reasoning, tool use, memory.
    Q3 The three axes an agent loop must be bounded on? M1 Steps, cost, wall-clock time.
    Q4 One-line definitions of ReAct, Plan-and-Execute, Reflection. M2 Interleave reason/act; plan then execute; critique then revise.
    Q5 Plan-and-Execute's main enterprise benefit beyond cost? M2 An inspectable, approvable plan.
    Q6 Where must tool authorisation be enforced, and why not the prompt? M3 The tool server; a prompt is not an access-control mechanism.
    Q7 Why return an error value from a tool instead of raising? M3 The model can react; the loop does not crash.
    Q8 What does MCP decouple? M3 The agent from each backend's SDK/contract.
    Q9 Short-term vs long-term memory in one line each. M4 Working state of the current task vs durable cross-session knowledge.
    Q10 Why filter memory by metadata before similarity ranking? M4 Correctness and PDPL scoping (prevents cross-customer leakage).
    Q11 Two signals a single agent has stopped scaling. M5 Tool overload, prompt overload (also context cost, ownership friction).
    Q12 What are the supervisor's two jobs? M6 Route and aggregate (not domain work).
    Q13 What is a "lost handoff" and its fix? M6 Specialist result not written back; enforce mandatory write-back.
    Q14 Why bound the whole multi-agent system, not just each agent? M6 To stop inter-agent chatter loops.
    Q15 State the flow-engineering maxim. M7 As much structure as possible, as much agency as necessary.
    Q16 Why is a rule-in-a-branch more secure than a rule-in-a-prompt? M7 Code cannot be talked around by crafted input.
    Q17 The governing agentic-security principle? M8 Treat all model input as untrusted and all output as unverified.
    Q18 Why is an input guardrail a filter, not a wall? M8 It cannot catch every injection; structural controls must hold anyway.
    Q19 The two biggest agent cost levers? M9 Caching and model routing.
    Q20 Which tools may be retried, and why the restriction? M9 Idempotent (read) tools only; retrying a write causes double actions.

    Part 3 — PA-1: Diagnose and Fix a Broken Agent¶

    Timing: 30 minutes, Day 2. Weight: part of the 20% PA-1+PA-2 course-grade line (see Part 6 for the recommended split).

    Brief (verbatim intent, assessment_package.md)¶

    Given a broken agent — a while True: loop with no step/cost/time bound, a tool that raises an exception instead of returning an error value, and a memory-retrieval call with no customer_id metadata filter — produce: (1) a bounded state machine with an explicit termination condition, (2) the tool converted to the errors-as-values contract, and (3) retrieval scoped by metadata before ranking.

    Scoring sheet (100 points, scaled to PA-1's grade weight)¶

    Criterion Points What earns full marks
    Diagnosis notes 40 All three defects correctly named (unbounded loop, raising tool, unscoped retrieval) with the concrete consequence of each stated (runaway cost/denial-of-wallet; loop crash on first bad input; cross-customer PDPL leakage) — not just "this is bad practice"
    Fixes 40 (a) 12 pts: step budget + explicit route/termination reaching END on both goal and budget branches; (b) 14 pts: tool returns {"error": ...} and the loop recovers gracefully (asks for clarification, does not crash); (c) 14 pts: retrieval filters by customer_id before similarity ranking, not after
    Verification 20 A termination test halts within MAX_STEPS on an adversarial input that never satisfies the goal, and a leakage test asserts zero cross-customer results — both actually run, not merely described

    Anti-pattern flag: a fix that adds a try/except: pass around the raising tool (silences the error without surfacing it into state) scores 0 on that sub-item regardless of how clean the rest of the diagnosis is — this is the exact M1 swallowed-error anti-pattern the exercise exists to catch.

    Part 4 — PA-2: Red-Team Report (the graded security artefact)¶

    Timing: Day 4, H4 build + H5 clinic (protect this at full length). Weight: part of the 20% PA-1+PA-2 course-grade line, the larger share (see Part 6).

    Brief (verbatim intent, assessment_package.md + capstone/templates/SECURITY_REPORT_TEMPLATE.md)¶

    Run the red-team suite against your own Rafeeq build and produce SECURITY_REPORT.md. Every finding must be filed in the seven-part shape: (1) Attack — the verbatim payload, vector, and injection point; (2) Vulnerability — which layer failed and why; (3) Exploit trajectory — the actual tool-call/state-transition reproduction, not a description; (4) Business impact — named in concrete units (SAR moved, records exposed, budget consumed); (5) Detection — which security event it tripped, or "none logged" (itself a finding); (6) Mitigation — the structural control that closes it, never a reworded prompt; (7) Retest result — the same payload re-run after the fix, with a held/breach verdict. Fix every high-severity finding and prove it now fails.

    Scoring sheet (100 points, scaled to PA-2's grade weight)¶

    Criterion Points What earns full marks What loses points
    Triage correctness 50 Every finding's severity matches the rubric exactly: High = money moved/could move without authorisation, PII exposed/could be exposed, or a prohibited action executed; Medium = availability/budget impact or an unlogged policy-controlled action; Low = cosmetic/no exploitable path. Money/PII triaged before availability, always An over-limit-refund finding marked Medium (under-triage) or a denial-of-wallet finding marked High (over-triage) are equally wrong — both cost points
    Mitigation quality 30 Every mitigation names a structural control — a specific file and function (security/output_guard.py::guard_tool_call, flows/refund_flow.py::amount_gate) — never "improve the prompt" or "add a warning". High-severity mitigations are implemented and retested held, not just proposed A mitigation that is a prompt rewording scores 0 on that finding regardless of whether the retest happens to pass — it is not a real fix
    Governance reasoning 20 The executive summary states scope, attempted/breach/held counts, and open-high-severity count accurately; the sign-off checklist is genuinely verified (each box ticked because the named command was run, not assumed) A sign-off box ticked without running its proving command is treated as a finding against the report itself

    Hard gate (independent of the 100-point score): zero open high-severity findings at submission blocks the Flagship Expert badge outright, regardless of the PA-2 percentage score (see Part 7).

    How to reproduce the report mechanically (for both participants and graders):

    export PYTHONPATH=src
make redteam                          # runs the full corpus, writes reports/SECURITY_REPORT.md
python3 -c "
from rafeeq.security.red_team import StubTarget, run_suite
f = run_suite(StubTarget())
open_high = [x for x in f if x.succeeded and x.severity == 'high']
assert not open_high, open_high
print('0 open high-severity findings')
"

    A worked exemplar report (denial-of-wallet family, correctly triaged Medium, full seven-part shape) is in capstone/grading/model_security_report.md — use it as the "what a 90–100% finding looks like" reference; INSTRUCTOR_DELIVERY_GUIDE.md extends this into distinction/pass/fail worked examples for the whole report.

    Part 5 — Capstone Rubric (100 points)¶

    Verbatim from final_capstone_project.md / capstone/rubric.md. Pass ≥ 70. Distinction ≥ 90. Extensions add up to +5 bonus (capped at 100) only if mandatory scope is ≥ 80.

    Criterion Weight 90–100% band 70–89% band < 70% band
    Agentic architecture & state 15 Bounded state machine, global budget, one graph two entry points; nothing opaque Minor gaps (a budget hoped-for, one untyped field) while-loops, unbounded, opaque state
    Reasoning patterns 10 Right pattern per workflow, justified with measured cost/quality Patterns present, justification thin One pattern everywhere; no measurement
    Multi-agent orchestration 15 Thin supervisor, scoped handoffs, write-back, aggregation, clean escalation Works; minor lost-handoff or fat-supervisor smell Peer chaos, loops, dead-end escalation
    MCP tools & authorisation 10 Governed MCP servers, server-side authz, runtime discovery Tools work; authz partial Mega-tools, authz in prompt
    Memory & PDPL 15 Checkpointing + scoped long-term + versioned KB; leakage = 0; erasure works Minor (retrieval hygiene, thin erasure) Leakage present or no erasure path
    Guardrails & security 15 Layered structural controls; red-team in CI; 0 open high-severity Guardrails present; 1 open medium Prompt-only "controls"; open high-severity
    Observability & cost 10 Full tracing, attribution, ≥ 40% cut, no quality regression, idempotent-only retries Traced; cost cut < 40% or retry gap No tracing; un-actionable cost
    Deployment, demo & decisions 10 Runs in sim env; crisp demo; DECISIONS.md shows trade-off literacy Runs; demo/rationale thin Cannot run own service cold

    Anti-pattern flags (cap a criterion at 70% regardless of everything else)¶

    • Any business rule or authorisation living only in a prompt — caps Multi-agent orchestration, MCP tools & authorisation, and Guardrails & security.
    • A cross-customer leakage test absent or red — caps Memory & PDPL at 70% outright.
    • A cost "cut" that regressed eval success — caps Observability & cost at 70%.
    • A write tool with a retry wrapper — caps Observability & cost at 70%.
    • An open high-severity red-team finding at submission — caps Guardrails & security at 70% and blocks the badge outright.
    • An unbounded core loop (no step/cost/wall-clock budget reachable from every code path) — caps Agentic architecture & state at 70%.

    Verified live by the instructor (per participant)¶

    • A fresh injection payload (not from the corpus) still gets structurally blocked.
    • forget_customer run live on a real seeded customer; count_customer_memories(...) == 0 confirmed on the spot.

    Part 6 — Grade Calculation Worksheet¶

    Per-participant worksheet. Weights are verbatim from assessment_package.md's Evaluation Criteria Summary.

    Component Weight Raw score (/100) Weighted score
    Lab completion (9 labs) 30% ______ ______
    PA-1 + PA-2 combined 20% ______ ______
    Quiz (10-question sitting) 10% ______ ______
    Capstone (Part 5 rubric) 40% ______ ______
    Total 100% ______ / 100

    Recommended PA-1/PA-2 internal split (the course package states the 20% combined figure only; the split below is a recommendation, not a fixed rule — apply evenly (10%/10%) instead if your Academy prefers a simpler worksheet):

    • PA-1 (diagnostic exercise, 30 minutes): 30% of the 20% line → 6 percentage points of the total course grade.
    • PA-2 (the graded security artefact, multi-hour): 70% of the 20% line → 14 percentage points of the total course grade, reflecting its stated weight as "the graded security artefact" and its dedicated Day-4 H5 clinic.

    Lab completion scoring. Each of the 9 labs is pass/fail against its own verify.py checklist (see SETUP_GUIDE.md and each lab's README "Expected outputs"). Raw score = (labs passed / 9) × 100.

    This participant passes (≥ 70), does not reach distinction (capstone < 90), and — subject to the badge gates in Part 7 — qualifies for the Flagship Expert badge if their capstone's security report shows zero open high-severity findings and their leakage test passes.

    Part 7 — Badge Issuance Criteria¶

    Verbatim, assessment_package.md. The Flagship Expert badge requires all four, not an average:

    1. Overall course grade ≥ 70 (Part 6's total).
    2. Capstone score ≥ 70 (Part 5's total, independent of the overall figure).
    3. Zero open high-severity security findings at submission (Part 4's hard gate).
    4. A passing cross-customer leakage test (labs/lab04/solution/verify.py and labs/sim/sim_memory_leak.py's "FAILURE DEMONSTRATED ... AND FIX PROVEN" result against the participant's own recall()).

    Issue badge recommendations within 5 working days of the Day-5 demo (per instructor_guide.md's wrap-up note), alongside collected repository URLs, LangSmith project links (where live mode was used), SECURITY_REPORT.md, and BENCHMARKS.md.

    Part 8 — Academic-Integrity Checks¶

    Verbatim intent, assessment_package.md: "identical red-team payloads or benchmark numbers across repositories are flagged." Applying this needs care, because stub-mode determinism (RAFEEQ_MODEL_MODE=stub, RAFEEQ_SEED=20260311) means many numbers are legitimately identical across every participant's repository by design — the shared attack corpus (security/**), the shared eval sets (tickets_eval.jsonl, routing_eval.jsonl), and a correctly-implemented StubTarget() red-team run will produce the same pass/fail pattern for everyone who did not modify the underlying src/rafeeq/** logic. Flag on the following instead:

    Signal Why it is a real integrity concern Where to check
    Identical prose in PA-1 diagnosis notes, PA-2 executive summaries, or DECISIONS.md paragraphs across two participants These are individually authored explanations, not generated output — verbatim matches (beyond shared boilerplate headings) indicate copying Diff the free-text sections between submissions
    Identical custom red-team payloads that are not from the shared security/** corpus A participant who crafts a genuinely new attack (fast-finisher / bonus work) producing text identical to another participant's genuinely new attack is implausible Diff any payload not matching an id in security/**/*.json
    Identical live-mode BENCHMARKS.md numbers (cost/contact, p95 latency) between two participants Live-model runs have real variance (timing, token counts, occasional retries) — two participants' live-mode numbers matching to the same decimal place is implausible; two participants' stub-mode numbers matching is expected and not a flag Compare only RAFEEQ_MODEL_MODE=live sections of BENCHMARKS.md; ignore stub-mode sections entirely
    A capstone SECURITY_REPORT.md's seven-part finding text (attack/vulnerability/impact prose, not the mechanical trajectory output) matching another submission's wording The trajectory block ([tool_name(args) -> ALLOWED/BLOCKED, ...]) is machine-generated and legitimately identical for identical inputs; the surrounding analysis prose is not Diff prose fields only, never the trajectory code blocks

    When a flag is raised: request each participant explain their finding/benchmark in their own words live, before escalating — a shared stub-mode number or a shared corpus payload explained correctly by both participants is not misconduct.
