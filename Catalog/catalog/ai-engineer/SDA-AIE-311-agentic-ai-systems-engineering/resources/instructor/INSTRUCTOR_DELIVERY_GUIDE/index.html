    Instructor Delivery Guide¶

    SDA-AIE-311 Agentic AI Systems Engineering¶

    How to Run the Week¶

    The golden thread. Every module and lab evolves the same system — Rafeeq, the Tawseel operations agent. Never introduce a throwaway example; always extend Rafeeq. This is what makes the Day-5 capstone an assembly, not a from-scratch scramble.

    Non-determinism is the theme. Establish on Day 1 that "it worked once in the demo" never counts — every lab has an evaluation harness, and tickets_eval.jsonl is reused Day 1 to Day 5 specifically so participants build the habit of measuring, not eyeballing.

    Pacing. Labs 2, 6, and 8 overrun most cohorts. Publish checkpoint commits (lab1-start … lab9-start, -solution variants) so a straggler can git checkout lab6-start and rejoin without falling permanently behind — every lab's verify.py runs standalone against src/rafeeq/**, so nothing downstream is blocked by one unfinished lab. Protect Lab 8 and its H5 security-report clinic at full length — cut theory, never triage time — and start Day-5 capstone assembly (H3) on time, no exceptions; cut discussion, not build time.

    What to cut for a weak cohort. Reduce Module 5's monolith baseline to a guided demo instead of a build. Never skip the cross-customer leakage test (M4) or the structural-authz demo (M8) — they are the course's conscience. What to add for a strong cohort. Pull the deterministic fast-path router (M6/M9) and human-in-the-loop approval into capstone main scope on Day 5.

    Model access. Default every lab to RAFEEQ_MODEL_MODE=stub — zero cost, zero keys, fully deterministic. Reserve a live gateway key exclusively for the capstone demo and the PA-2 live retest; publish a token budget and live spend on the shared board regardless, so cost literacy (LO7) is visibly modelled, not just taught.

    Per-Hour Facilitation Script¶

    Say/show/ask, condensed for the front of the room. "Checkpoint" is the minute mark by which that hour's core deliverable should exist — if the room is behind, cut discussion time, not build time, to hit it.

    Day 1¶

    H Say (open with) Show / demo Transition question Checkpoint
    1 "You've all shipped a chatbot. This week you ship something that acts." Introduce Rafeeq/Tawseel: five cities, bilingual customers, real money movement. A failure story: an agent that "worked in the demo" and refunded twice in production (preview M1's case study without naming it yet). "What's the one thing an agent can do that a chatbot cannot?" 40 min: everyone can name the four agentic components
    2 "An agent is a state machine — today you build the smallest possible one." Draw the loop: observe → reason → act → update → repeat, with a guaranteed exit. Live: sketch RafeeqState on the projector; show broken_agent.py's three # SMELL comments. "What happens if route never returns END?" 40 min: RafeeqState fields agreed as a class
    3 "Run broken_agent.py on the confused-customer input. Let it burn tokens — watch the counter." Live runaway loop on the projector, then Ctrl-C; convert to the bounded state machine live in under 8 minutes. — (lab time) 45 min: every pair's termination test is green
    4 "Same task, three different ways to think. Watch the cost spread." Trace walkthrough: the same refund ticket through ReAct, Plan-and-Execute, and Reflection, side by side. "Which pattern would you trust with your own money?" 40 min: comparison table on the whiteboard has real numbers from a live run
    5 "Build all three. The money shot is your own cost table, not mine." — (guided lab) "Post your three numbers to the shared board." 45 min: every pair has BENCHMARKS.md with a three-pattern comparison committed

    Day 2¶

    H Say Show / demo Transition question Checkpoint
    1 "A tool schema is the prompt for the tool — an easily confused consumer reads it." Stand up an MCP server live, bind its tool to Rafeeq, under 8 minutes; then show a prompt-only "never refund > 500" bypassed by a crafted input. "If the prompt said never — what actually stopped it?" (nothing, yet) 35 min: one MCP server running standalone in every pair's terminal
    2 "Wrap the real Tawseel APIs. Errors are values, not exceptions — remember Module 1." — (guided lab) — 45 min: pytest tests/unit/test_tools.py green for every pair
    3 "Your agent forgets every customer between messages. Today it stops." Show same-thread continuity live, then trigger the no-filter cross-customer leak and fix it with one line — a metadata filter. "Why is that filter a security control, not a performance one?" 35 min: everyone can state the short-term vs long-term distinction in one sentence each
    4 "Filter before you rank. Every read, every write." — (guided lab) — 45 min: every pair's leakage test is green
    5 "Wire it all together. Then measure it, don't eyeball it." PA-1 runs this hour. — (integration lab + PA-1) "Collect repository state before you leave — Day 4 needs it." 45 min: PA-1 submitted

    Day 3¶

    H Say Show / demo Transition question Checkpoint
    1 "One agent, 18 tools, one contradiction-riddled prompt. Watch it misroute." Run a cross-domain ticket through the Lab-5 monolith live — watch issue_refund fire on a tracking intent. "Which of the four scaling symptoms just bit?" 35 min: everyone names tool overload correctly
    2 "Split it. Three specialists, tidy toolbelts, isolated context." — (guided lab) — 45 min: context-isolation test green (Billing carries no address field)
    — M5.3 — When NOT to Use Multi-Agent Systems (25 min). See the dedicated plan below; run this here, between Lab 5 and the M6 lecture.
    3 "Three capable specialists, no one in charge yet." Route a cross-domain ticket live through a hand-drawn supervisor first (whiteboard), then show sim-lost-handoff's customer-gets-nothing failure. "What's the supervisor's job — and what is it NOT allowed to do?" 35 min: everyone can state "route and aggregate, never domain work"
    4 "Build the hub. Bound the whole system, not just each agent." — (guided lab); trigger the chatter-loop probe live, watch it escalate at handoff 4 instead of looping 30 times — 45 min: routing accuracy measured against the Lab-5 baseline
    5 "Compare against your own monolith. The +15–20pt jump is today's payoff." — (integration + benchmark) "Post your routing-accuracy delta to the shared board." 45 min: every pair's comparison table committed

    Day 4¶

    H Say Show / demo Transition question Checkpoint
    1 "This prompt has a 500 SAR limit. Watch a sentence lose to a customer's wording." Run the "ignore the limit" adversarial ticket on refund_prompt_only.py live — it issues 4,000 SAR. "The model followed the rule as written. So what actually failed?" 35 min: everyone can state "a prompt rule is decided fresh every time"
    2 "Every rule becomes a branch today. Then we test it in milliseconds." — (guided lab); re-run the same 4,000 SAR ticket against the finished flow, live — 45 min: 7 branch unit tests green, zero model calls
    3 "Today you attack your own system. The rule: input is untrusted, output is unverified." Run SYSTEM OVERRIDE against a prompt-only build (money leaves) then the hardened build (blocked) — with the input guardrail switched off, to prove structure holds when the filter misses. "Which layer actually stopped it that time?" 35 min: everyone can name all six layers of defence
    4 "Build the guards, then build the attacker." — (guided lab: guardrails, then the red-team agent) — 45 min: red-team run produces at least one real, reproducible finding
    5 "This is the graded artefact. Triage money and PII before anything else, always." PA-2 clinic — full length, protect this. Walk one finding through the seven-part shape live on the projector. "Collect repo URL + LangSmith link before you leave." 45 min: zero open high-severity findings in every pair's report

    Day 5¶

    H Say Show / demo Transition question Checkpoint
    1 "You knew it was 'expensive.' Today you learn why, in one afternoon." Open a live trace, attribute cost by model/component/intent, and predict the fix before applying it. "What's your single biggest cost bar?" 35 min: every pair has opened one real trace
    2 "Cache the repeats, route the confident majority. Watch cost fall — and eval success stay flat." — (guided lab) "Report your cost cut alongside your eval-success number — both, always." 45 min: ≥40% cost cut with unchanged eval success, per pair
    3 "Assembly starts now, on time — full stop." Point at the capstone checklist; walk the M-A through M-D milestone gates once, then step back. — Hard checkpoint: M-A gate green (eval replay passes locally)
    4 "Trade reports with the pair next to you. Attack each other." Circulate; spot-check one injection payload and one forget_customer call per pair live. — Zero open high-severity findings, PDPL erasure proven, per pair
    5 "Six minutes each. Evidence first, demo second." Run demos; score against the rubric live, from BENCHMARKS.md/SECURITY_REPORT.md before the live show. "Where does this system go next — SDA-AIE-313, or -390?" All demos delivered; badge recommendations drafted

    The Nine Case Studies — Facilitation Notes and Model Answers¶

    Discussion questions are verbatim from each module package; do not invent new ones. Facilitate, do not lecture — let the room propose the fix before confirming it.

    M1 — The Runaway Refund Agent at SahlPay. Facilitation: let someone propose "a better prompt" first, then ask them to defend it against a crafted "ignore the limit" message — it always loses. (1) An explicit refund_issued state flag entering the refund branch at most once; a prompt cannot enforce this because it is re-evaluated fresh every request. (2) Timestamp, model/graph version, input state, decision and tool call with arguments, result, and policy version in force. (3) Add budgets and gates, not remove them — sell it as fewer incidents and fewer wasted tokens, which is cheaper as well as safer. (4) Replay from the logged discrete state transitions — this is possible only because the agent is a state machine, not a black box.

    M2 — Cost Blowout at a Saudi Telecom. Facilitation: ask for a guess at the overrun multiple before revealing 18×; the gap between guess and reality is the point. (1) Tag every contact by intent, replay historically through an instrumented agent, sum tokens×price grouped by intent. (2) Arabic's higher token count multiplies ReAct's super-linear cost further — strengthens the case for moving routine Arabic intents to Plan-and-Execute. (3) Only on billing-adjustment outputs, with concrete criteria (amount within eligibility, correct language, policy cited). (4) Replay one day's contacts through the eval harness pre/post; canary before full rollout.

    M3 — Unifying Three Systems Behind MCP. (1) One server per system isolates trust boundaries and lets each backend team own their own release cadence. (2) At the MCP server (or a thin gateway every agent traverses) — never the agent or its prompt. (3) From per-integration review (every new agent × backend pairing) to per-capability review (once per published tool, reused safely by every future agent). (4) A direct caller breaks; the adapter absorbs the field-name change so the tool's contract to the agent never moves.

    M4 — The Cross-Customer Memory Leak. Facilitation: this is the module's conscience — do not let the room treat it as a corner case. (1) Without it, retrieval can structurally return another customer's PII; the filter is what makes cross-customer access impossible, not merely unlikely. (2) forget_customer must purge vector-store entries by customer_id and remove or redact the corresponding checkpointer rows — both stores, one call. (3) A resolution summary and stable preferences belong; raw national IDs, full card numbers, and raw hostile message text never do. (4) A standing leakage test in CI plus periodic production sampling of retrieval calls for cross-customer hits.

    M5 — The 28-Tool Monolith at SoukNow. (1) Tool overload, measured directly via tool-selection accuracy on a labelled eval set. (2) Ownership maps to accountability and data scope — exactly what a PDPL/audit review wants to see. (3) Use the eval set: route trivial single-domain tickets to one specialist directly, mixed/complex tickets through the supervisor. (4) Lost handoffs and chatter loops — guarded by mandatory write-back and a global budget (Module 6's subject).

    M6 — The Apology Loop at a Telecom Support Desk. (1) All coordination flows through one bounded hub; a peer network has no central budget to stop A→B→A forever. (2) Scoped context plus an explicit sub-goal plus a correlation id; never the full raw history or another domain's PII. (3) From the eval data's typical resolution hop count, with margin, reviewed by risk/compliance and documented. (4) Every routing, handoff, and escalation decision: who/what decided, inputs, outputs, timestamps.

    M7 — The Talk-Around Refund at Anaqah. (1) A prompt is advisory text a model can be argued out of; a branch is code executed regardless of wording. (2) If it is a checkable condition on typed state, it is a rule; if it requires interpreting genuine ambiguity or composing empathy, it is judgement. (3) A reproducible, deterministic proof (a passing unit test) versus a human's best-effort reading of prose. (4) Forcing genuinely novel complaint handling into a rigid tree fails on the first unseen case — keep reply composition and open judgement with the model.

    M8 — The SYSTEM OVERRIDE Refund Attack. (1) The server-side/flow-gate refund limit; the input guardrail alone is a filter that can miss a novel phrasing. (2) High severity — money moved; mitigation is server-side authz plus a flow gate plus an output guard blocking over-limit calls before execution. (3) Because a manual test does not survive the next code change — CI makes the block permanent and provable on every commit. (4) Route over-limit refunds to human-in-the-loop approval rather than outright refusal, preserving legitimate large refunds.

    M9 — The 68% Bill Hiding in Plain Sight. (1) One number cannot be targeted; attribution turns "it's expensive" into a specific, fixable lever. (2) Apply whichever the attribution shows is the biggest bar — typically flow (removes calls entirely), then caching (removes repeats), then routing (cheapens what remains), since they compound in that order. (3) Re-run the eval harness after the change and confirm task_success_rate is unchanged. (4) Cost/contact and p95-latency SLOs with alert thresholds, a review cadence, and a named owner for the response.

    Enterprise Teaching Cards¶

    Reported, third-party figures — always attributed, never presented as this course's own measurement. Full source citations are in RESOURCES.md.

    DTDC DIVA (Day 3, fits Module 5). DTDC's DIVA 2.0 AI-powered logistics support agent, built on Amazon Bedrock, reported strong response accuracy and a substantial reduction in support-query burden (AWS Machine Learning Blog). Question to the room: "DTDC is a logistics company, just like Tawseel. What would you need to see in DIVA's architecture before trusting its reported accuracy figure?" Steer toward: an eval harness with labelled ground truth, not a headline number — exactly the TawseelBench habit this course teaches.

    DoorDash Dasher support (Day 3, fits Module 5/6). DoorDash's LLM/RAG-based automated support system for its courier population, documented in DoorDash's own engineering blog, including explicit work on reducing hallucination. Question: "Why would a courier support agent need less creative latitude than a customer-facing one?" Steer toward: operational actions (a courier's pay, a delivery reassignment) are higher-stakes and more checkable than open conversation — flow engineering (M7) applies even harder here.

    OPLOG (Day 3, fits Module 6). A regional e-commerce fulfilment operator's use of AI agents in warehouse and operations orchestration, documented via AWS Solutions case studies and OPLOG's own coverage. Question: "OPLOG orchestrates warehouse operations, not customer chat. What changes about specialist boundaries when the 'customer' is internal operations staff?" Steer toward: the same scoped-tool, isolated-context discipline applies; the data-governance stakes shift from PDPL/customer PII toward operational integrity and safety.

    Ryanair — twelve agents to one (Day 3, anchors Module 5.3). Ryanair's reported consolidation of domain-specific customer-service agents into one, alongside its five-year AI/data partnership with Google Cloud (Computer Weekly, PRNewswire, August 2026). Question: "Everyone in this room just built three specialist agents. Why would a real airline go the other way?" Steer toward: the ten-criteria worksheet — domain count, autonomy, context separation, and the rest — not a reflex answer either way. See the dedicated M5.3 plan below.

    DHL Supply Chain (Day 5, fits Module 9). DHL Supply Chain's generative and, more recently, agentic AI programme for data management, customer support, proposal accuracy, and operational communications (DHL Group press releases, 2024–2025). Question: "DHL frames this as 'operational communications,' not 'customer support.' What's different about the cost/latency stakes?" Steer toward: internal operational messages tolerate different latency SLOs than a customer waiting on chat — cost/contact still matters, but the p95 target likely does not.

    Air India AI.g (Day 5, fits Module 9). Air India's Azure-OpenAI-based virtual agent, reported to answer around 40,000 customer queries a day across 1,300+ query types (Microsoft Customer Stories). Question: "Your eval set has 120 tickets. Air India's volume is two orders of magnitude past that, daily. What breaks first at that scale that didn't break in your lab?" Steer toward: observability and cost attribution (M9) stop being a nice-to-have at that volume — a 0.01 SAR/contact miss becomes a real annual number.

    Module 5.3 — "When NOT to Use Multi-Agent Systems" (full 25-minute plan)¶

    Placement: Day 3, between Lab 5 (specialist agents) and the Module 6 lecture — run it while the room still feels the cost of having just built three agents.

    0–3 min — Hook. Present the Ryanair card above. Ask: "You just spent 50 minutes building three specialists. A major airline reportedly just went the other way. Were you wrong?" Let the tension sit; do not answer yet.

    3–8 min — The ten-criteria matrix. Present the decision matrix (below); walk through applying it to the Ryanair case illustratively — the room does not have Ryanair's internal data, so treat every row as a plausible inference, explicitly labelled as such, not a confirmed fact.

    Criterion Favours single agent Favours multi-agent
    Number of domains Few, overlapping Many, genuinely distinct
    Degree of autonomy Low-to-medium per domain High, domain-specific autonomy needed
    Context separation Domains share most context Domains need hard context isolation
    Permission boundaries One permission set suffices Different teams need different scopes
    Independent state Domains share state naturally Each domain owns genuinely separate state
    Parallelism Requests are mostly sequential Genuine benefit from parallel specialist work
    Failure isolation A shared failure mode is acceptable One domain's failure must not touch another
    Cost Routing overhead dominates at this volume Specialisation saves more than routing costs
    Latency Extra hops meaningfully hurt the SLO Hops are within budget
    Auditability One log is enough for review Regulator/audit wants per-domain accountability

    8–18 min — Decision worksheet (individual, then pair-share). Give the room a live Tawseel scenario: "Product wants to add an Accounts domain — billing disputes that also touch loyalty points and corporate invoicing. Score it against all ten criteria and commit to single-agent or multi-agent before you compare with your partner." Circulate; do not give the answer yet.

    18–23 min — Synthesis. Take two or three pairs' answers, including at least one disagreement if one exists. Model answer: Accounts likely favours multi-agent — it touches billing (existing Billing specialist scope conflict), a genuinely separate loyalty data domain, and corporate invoicing with different permission boundaries than consumer refunds — but the deciding factor is permission boundaries and independent state, not "another domain sounds complex." Make the point explicitly: a workflow scoring single-agent on eight of ten criteria should not become a fourth specialist just because the team likes agents.

    23–25 min — Transition. "Now that you know when not to multiply agents, Module 6 teaches you how to run the ones you decided to keep, well." Move directly into the supervisor topology lecture.

    Instructor note. This session works because it produces genuine disagreement in the room — if every pair reaches the same answer instantly, the scenario was too easy; have a harder second scenario ready (a single "VIP customer concierge" workflow that clearly favours staying single-agent) for a cohort that converges too fast.

    Troubleshooting Reference¶

    Combines instructor_guide.md's classroom table with every check scripts/doctor.py performs — run python3 scripts/doctor.py first for any "my machine won't..." report.

    Issue Frequency Resolution
    Runaway token spend from a routing bug High Cheap-model default + per-participant caps; teach recursion_limit as a backstop in M1
    GraphRecursionError from missing termination High The M1 lesson; check both goal and budget branches reach END
    MCP server not discovered by the client Medium Verify the server runs standalone first; check command/path in the client config
    Vector store connection / empty retrieval Medium Confirm the container is up (full profile) and the collection is seeded; check the embedding mode
    Cross-customer leakage test red Medium Missing metadata filter; treat as a simulated PDPL incident and fix before proceeding
    Arabic query returns nothing Medium English-only embeddings; switch to a multilingual model and test both languages
    Cheap model too weak for the capstone demo Medium Route only the confident majority to cheap; reserve frontier for the demo path
    Red-team suite flaky / always "succeeds" Medium Strengthen the outcome oracle to check concrete effects (was a refund actually issued?)
    Windows/WSL2 Docker not enabled Medium Pre-session email + first-hour floater support; cloud fallback (SETUP_GUIDE.md Track C)
    doctor.py reports a missing Layer-B package Expected for Labs 5/6/3-live without pip install Not a fault — it names the exact pip install line; only matters for that lab
    doctor.py's data-file check fails make data never run, or interrupted mid-write make clean && make data; re-run scripts/selfcheck.py directly for detail
    doctor.py's gateway-reachability check fails Only runs when RAFEEQ_MODEL_MODE=live; a genuine network/proxy/key issue Confirm the gateway host is on the classroom allowlist; verify the key in .env
    doctor.py reports Docker not on PATH No Docker installed/started Irrelevant for any offline lab or CI check; only needed for the full compose profile

    Classroom Logistics¶

    Prayer and break scheduling. Each "hour" is 50 minutes of instruction plus a 10-minute buffer; schedule the long break around Dhuhr. Day-4 and Day-5 afternoons are deliberately lab-heavy and lighter on theory, giving natural flexibility around Asr.

    Pairing strategy. Rotate pairs daily. Pair a strong-prompting participant with a strong-software-engineering participant — the agentic mindset lives exactly at that seam, and the course's own material (M1's state-machine discipline meeting M2's reasoning-pattern intuition) rewards it directly.

    The shared cost board. Maintain, visibly, for the whole week: live token spend per participant/pair, routing accuracy (from Day 3 onward), and a cost/contact leaderboard once Module 9 begins. This is not decoration — cost literacy is a graded outcome (LO7), and seeing the board update after every lab is how the lesson lands before the lecture does.

    A2 posters to print (see VISUAL_ASSET_BRIEF.md for full specs): the agent loop (M1-D1), the MCP client/server topology (M3-D2), the two-memory architecture (M4-D1), the supervisor topology (M6-D1), the layered-defence diagram (M8-D2), and the trace-tree anatomy (M9-D1). Six posters, one per major architectural milestone of the week, left up for the full five days so the room can literally point at "where does agency live" or "where does authorisation live" during any later discussion.

    What Good Looks Like — Three Worked Examples (PA-2 Red-Team Report)¶

    All three address the same finding family (a refund-limit bypass attempt) to make the grading difference legible at a glance. Use capstone/grading/model_security_report.md as the full reference exemplar — it is the real, repository-produced source for the distinction-band example below.

    Distinction (90–100%). Triage is exact: a genuine over-limit-refund attempt is filed High, a denial-of-wallet attempt is filed Medium — never the reverse. Every finding is in the full seven-part shape, with the exploit trajectory as an actual tool-call/state transition log, not a description. Mitigation names the precise file and function (security/output_guard.py::guard_tool_call, flows/refund_flow.py::amount_gate) and is retested held after the fix, evidenced by a pasted command output, not asserted. The executive summary states exact attempted/breach/held counts and zero open high-severity findings, matched by a live run_suite() output attached at the end.

    Pass (70–89%). Triage direction is correct (High stays High, Medium stays Medium) but severities are occasionally borderline without justification — a finding sits at the edge of High/Medium with no stated reasoning for the call made. Mitigations are structural and correctly located, but described more thinly ("fixed in the output guard" without naming the function). The sign-off checklist is fully ticked, but one box (e.g. "no monetary limit lives only in a prompt") is asserted rather than evidenced by the named test's actual output.

    Fail (< 70%). At least one High-severity finding (an over-limit refund actually issued) is mis-triaged as Medium or Low, or a mitigation is a reworded prompt sentence rather than a named structural control — either alone caps the whole Guardrails & security capstone criterion at 70% per the rubric's anti-pattern rule. A report with any open high-severity finding at submission additionally blocks the Flagship Expert badge outright, regardless of every other section's quality.
