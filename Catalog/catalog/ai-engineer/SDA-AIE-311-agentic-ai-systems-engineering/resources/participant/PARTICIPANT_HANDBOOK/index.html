    Participant Handbook¶

    SDA-AIE-311 — Agentic AI Systems Engineering (هندسة أنظمة الذكاء الاصطناعي الوكيلي)¶

    5 days × 5 hours · Expert level · SDAIA Academy

    Welcome¶

    You are about to spend a week building one system, not nine toy examples. By Friday afternoon you will have designed, built, hardened, and deployed Rafeeq (رفيق) — an enterprise agentic operations assistant for Tawseel (توصيل), a fictional Saudi last-mile logistics and e-commerce fulfilment company. Tawseel delivers across five Saudi cities — Riyadh, Jeddah, Dammam, Makkah, Madinah — and its customers write to Rafeeq in Arabic and English, in equal measure, about the same three things every logistics operator's support desk lives or dies on: where is my order, can you move my delivery, and I want my money back.

    On Monday morning Rafeeq is three lines of scaffolding around a chat call — indistinguishable, architecturally, from the runaway while True: loop this handbook will show you failing live. By Friday afternoon Rafeeq is a bounded, multi-agent, guarded, traced, cost-optimised service running in a simulated Tawseel operations environment, and you will demo it live: a bilingual ticket resolved end to end, one live attack blocked in front of the room, one trace-and-cost walkthrough, and one proof that a customer's data can actually be erased.

    Every lab this week adds one real component to the same system — never a throwaway "weather agent" example. That is deliberate: the discipline this course teaches is that an agent is not a clever prompt, it is an engineered system, and engineered systems are built incrementally, tested at every step, and prove their own quality rather than asking you to take their word for it.

    What you will have built by Friday¶

    • A bounded core loop with typed state and an explicit termination condition — no agent in this course can loop forever, because you will build the budget that stops it yourself.
    • Three explicit reasoning patterns (ReAct, Plan-and-Execute, Reflection), applied to the workflow each actually fits, with your own measured cost and latency numbers proving which is which.
    • Sixteen governed enterprise tools exposed over four Model Context Protocol (MCP) servers — orders, logistics, billing, customer — the same pattern a real enterprise uses to let many agents share governed capabilities safely.
    • Short-term (thread-scoped) and long-term (customer-scoped, versioned, bilingual) memory, with a PDPL erasure path you will run live against a real seeded customer.
    • Three specialist agents — Orders, Logistics, Billing — under a thin supervisor that routes, aggregates, and escalates cleanly, with a global budget that stops inter-agent chatter loops before they start.
    • A refund workflow refactored from a 40-line prompt that a crafted message could talk into a 4,000 SAR mistake, into a deterministic, unit-tested flow that the same message cannot move at all.
    • Layered guardrails and your own red-team agent, attacking your own Rafeeq, producing a triaged SECURITY_REPORT.md with zero open high-severity findings.
    • Full tracing, cost attribution by model/component/intent, caching, model routing, and bounded retries — with a measured cost cut, proved on the same evaluation set that measured your baseline.
    • A running, containerised, health-checked service in the simulated Tawseel environment, demoed live in six minutes.

    Prerequisites¶

    SDA-AIE-214 (foundational AI/LLM engineering) or equivalent working experience. This course assumes you are comfortable with Python, git, and REST APIs, and that you have seen an LLM API call before. It does not assume prior LangGraph, MCP, or vector-database experience — Modules 1, 3, and 4 teach those from first principles, on this system.

    Pre-Course Setup (complete two days before Day 1)¶

    The full instructions, with verification commands after every step and a troubleshooting appendix, are in the companion SETUP_GUIDE.md. The short version, so you know what is coming:

    1. Clone the repository and run the offline track. Python 3.11+, git — nothing else. export PYTHONPATH=src, then python3 scripts/doctor.py, make data, make test-offline, and python3 labs/lab01/solution/verify.py (ends 10/10 checks passed). This is the whole of Track A in SETUP_GUIDE.md, and it is sufficient for the entire course.
    2. Optional: the full local stack. If you want to run the real LangGraph/Qdrant/Postgres stack rather than the offline stub (recommended before the capstone demo, not required before Day 1), install Docker and follow Track B.
    3. Do not wait until Monday morning. The two-day window exists so a Windows/WSL2 Docker issue, a corporate-proxy block, or a missing Python version is someone else's Tuesday problem, not your first-hour-of-the-course problem. If python3 scripts/doctor.py reports anything other than a clean pass on the offline checks, raise it with your instructor before Day 1.

    The offline-mode promise¶

    Every lab, make test, CI, and the evaluation harness in this course run with zero API keys and zero network calls by default (RAFEEQ_MODEL_MODE=stub). This is not a sandboxed toy version of the real thing — StubChatModel implements the same .invoke()/.bind_tools()/.with_structured_output() surface a real model client does, so every line of agent code you write this week works unmodified the moment you point it at a real model gateway. You will only need a live key for two things: the capstone's 6-minute demo and the final live retest of your red-team findings. Everything else — including every graded lab checkpoint — you can complete with nothing beyond Python installed.

    The Nine Modules¶

    Each spread below is written to revise from directly — read it the night before that day's session, or the morning of, as a refresher. Skip the module content files unless you want the full depth; this is the version built for recall.

    Module 1 — Agentic System Architectures and Components¶

    What it is. The difference between an LLM call, a chain, and an agent is control flow. An LLM call is one shot. A chain is a fixed sequence the developer decided at authoring time. An agent is a loop where the model decides the next step at runtime from the current state — observe, decide, act, update, repeat — until a goal is met or a limit is hit. That loop is built as a typed state machine: explicit State, Nodes that read and write it, Edges where the conditional edge is where agency lives, and a guaranteed path to END.

    Why it matters. An agent that can do things can also do the wrong things, at scale, with real money and real personal data. A while True: loop around a chat call is not a smaller version of a proper agent — it is a liability with no way to explain, afterwards, why it did what it did. Structure is what makes an agent auditable, and auditability is the precondition for every guardrail, budget, and cost control the rest of the course adds.

    What you build. RafeeqState (a typed dataclass carrying messages, customer id, locale, order id, step count, resolution), a reason node, and a route conditional edge that terminates on both goal-reached and budget-exhausted. You run it on an Arabic order query and an English refund request, and you write one test proving it halts within MAX_STEPS on an input engineered never to satisfy the goal.

    The one idea to remember. An agent is a state machine, so build it as one — and bound its loop on three axes, always: step budget, cost budget, wall-clock timeout. "The model will decide when it's done" is not a termination condition; it is the absence of one.

    The mistake to avoid. Swallowing a tool error with a bare except: pass so the loop continues on a stale or empty observation. The agent does not crash — it confidently gives a wrong answer, and nothing in the trace tells you why, because the error never entered state.

    Module 2 — Planning and Reasoning Patterns¶

    What it is. Three canonical ways to make an agent think. ReAct interleaves reasoning and acting step by step — flexible, but cost grows super-linearly with steps because every step re-sends the growing history. Plan-and-Execute separates an upfront planner from a cheap executor — the plan is an inspectable, loggable, human-approvable artefact, but brittle without a replan step. Reflection adds a critic pass after a candidate answer — it catches confident-but-wrong outputs at the cost of at least one extra round-trip, so it belongs only on high-stakes, hard-to-reverse outputs.

    Why it matters. Pattern choice is the single biggest lever on an agent's cost and reliability — bigger than model choice. A support agent defaulting to ReAct for every routine "where is my order" contact can cost 20× a Plan-and-Execute flow doing the exact same job, invisibly, until the first billing cycle.

    What you build. All three patterns, on the same task, with real measured numbers: a ReAct agent on order-status tickets, a Plan-and-Execute flow (with a logged plan) on refund tickets, and a Reflection gate on the refund output — then a comparison table (cost per ticket, latency, eval-set success) and a one-paragraph recommendation.

    The one idea to remember. These compose. Rafeeq's target shape is Plan-and-Execute for the overall workflow, ReAct inside a step whose path is genuinely uncertain, and Reflection only where money or compliance is on the line — as much structure as possible, as much reasoning as necessary.

    The mistake to avoid. Defaulting to ReAct everywhere because it is the tutorial pattern — the single most common cause of a runaway agent bill in production.

    Module 3 — Tool Use, Function Calling, and MCP Integration¶

    What it is. Function calling is a structured contract: you describe a tool as name + description + JSON-schema parameters, the model requests a call, the runtime decides whether and how to honour it, and the model never runs code directly — that separation is your first security boundary. The Model Context Protocol (MCP) is the open standard that turns each backend system into a governed, discoverable tool server — one server per trust boundary (orders, logistics, billing, customer), never one mega-server — so many agents can consume the same governed capability without each hard-wiring its own integration.

    Why it matters. Real enterprise APIs are rarely LLM-ready, and a mega-tool with a mode/action argument causes an LLM to misroute constantly — narrow, well-described tools are how you buy reliable tool selection. And authorisation belongs in the tool server, never in the agent's prompt: nothing stops a jailbroken prompt from calling a prompt-only "rule" a lie.

    What you build. track_shipment and get_order_details as typed tools with error values, wrapped in logistics_server.py and orders_server.py MCP servers with server-side authorisation stubs, consumed via MultiServerMCPClient and bound to your ReAct agent from Lab 2 — plus a non-idempotent open_case write tool that must never be blindly retried.

    The one idea to remember. The tool schema is the prompt for the tool — design it for an easily confused, non-human consumer: one tool one job, descriptions stating when to use it and when not to, and errors returned as values so the model can react instead of the loop crashing.

    The mistake to avoid. Returning raw backend payloads instead of a trimmed, typed output — it bloats context, inflates cost, and risks exposing PII the model never needed to see.

    Module 4 — Memory and State Management with Vector Databases¶

    What it is. Two memories, two jobs. Short-term is the working state of the current task, made resumable and inspectable by a checkpointer keyed on thread_id. Long-term is durable knowledge across sessions — customer history, past resolutions, a versioned policy knowledge base — retrieved by semantic similarity from a vector store, filtered by metadata before ranking. Confusing them (stuffing everything into the prompt forever, or writing transient noise into durable storage) is the classic failure.

    Why it matters. Long-term memory is personal-data storage under PDPL. An agent's memory design is simultaneously a UX feature, a correctness control, and a data-governance surface — and memory's unique danger is that it can be confidently wrong: a superseded policy or another customer's note retrieved with no error, no exception, just a silently corrupted answer.

    What you build. A SQLite checkpointer proving same-thread continuity across two turns; long-term memory populated with one resolved-case summary per returning customer, scoped strictly by customer_id; a versioned knowledge-base lookup tested for cross-lingual recall (an Arabic question retrieving the correct policy chunk); a working forget_customer PDPL-erasure function; and a leakage test that must show zero of another customer's notes ever returned.

    The one idea to remember. Filter by metadata before similarity ranking — this is a security control, not an optimisation. Short-term is the working set for now; long-term is what deserves to outlive the task.

    The mistake to avoid. Retrieving with no metadata filter at all — "just embed everything and retrieve top-5" — which surfaces a different customer's order number and address the moment two customers' phrasing happens to be similar. No crash, no exception: a PDPL incident discovered only when someone complains.

    Module 5 — Single-Agent versus Multi-Agent Architectures¶

    What it is. A single capable agent scales until one of four symptoms bites: tool overload (past roughly a dozen overlapping tools, selection accuracy falls), prompt overload (the system prompt accretes contradictory rules from every domain), context cost (every request pays for the whole tool schema even when it needs a fraction of it), or ownership friction (no single team can safely own a prompt encoding five teams' policies). When one of these bites, you split into specialist agents — scoped tools, a focused single-domain prompt, isolated context — usually under a thin supervisor (the workhorse "hub-and-spoke" topology; a peer network is rarely the right enterprise default).

    Why it matters. Specialisation is not free capability, it is a trade: a supervisor over specialists usually costs more on a trivial single-domain task (the extra routing hop) and less on a complex, mixed one, because scoped tools prevent the runaway misrouting a monolith suffers there. You prove which regime you are in with the eval set, not intuition — which is exactly why you never delete the single-agent baseline.

    What you build. Three scoped specialists (Orders, Logistics, Billing) built from one make_specialist factory, each asserted to have no tool outside its domain (the Billing list contains no tracking/geo tool); a scoped_input projection so the Billing agent's input structurally never carries a shipment address; and a two-sided benchmark against the Lab-5 monolith baseline — where the monolith wins and where it loses, both reported honestly.

    The one idea to remember. Split when a real symptom bites, not because more agents sounds more sophisticated — and keep the single-agent baseline in the eval harness forever, so you can always answer "is the multi-agent version actually better here?"

    The mistake to avoid. "Fixing" a struggling monolith by adding a 24th tool and three more prompt paragraphs. The real fix is decomposition, and the accretion path only delays the same selection-accuracy collapse Module 3 already measured for you.

    Module 5.3 — When NOT to Use Multi-Agent Systems¶

    What it is. A dedicated 25-minute session anchored on a real, reported industry case — Ryanair's move from twelve domain-specific customer-service agents to one consolidated agent — that turns Module 5's four scaling symptoms into a formal ten-criteria decision worksheet: number of domains, degree of autonomy, context separation, permission boundaries, independent state, parallelism, failure isolation, cost, latency, auditability.

    Why it matters. The industry's default instinct in 2025–2026 has been "more agents, more capability." The Ryanair case is the course's live counter-example: consolidation, not proliferation, was the reported fix, for reasons the ten criteria make explicit rather than vibes-based. Multi-agent orchestration cost (Module 6) is real and compounding — every extra agent is another routing hop, another failure surface, another thing that can lose a handoff.

    What you build. Nothing new in code — this session produces a completed decision worksheet against a real Tawseel workflow (typically the "Accounts" domain-expansion scenario), scored on all ten criteria, with a committed single-vs-multi decision defended in pairs before the instructor reveals the recommended answer.

    The one idea to remember. Every criterion that favours "single" is a criterion your supervisor topology is paying tax on for no return. Consolidation is not a retreat from agentic maturity — sometimes it is the mature call.

    The mistake to avoid. Treating the ten criteria as a formality to rubber-stamp a decision you had already made. The worksheet only has value if you let it change your answer at least once this week.

    Module 6 — Hierarchical Delegation and Agent Orchestration¶

    What it is. The supervisor is itself an agent whose "tools" are the specialists: it reads shared state, routes to a named specialist (or finishes, or escalates), hands off scoped context with an explicit sub-goal and a correlation id, and — critically — writes the specialist's result back into shared state before deciding again. Specialists never talk to each other directly; every coordination flows through the hub, which is also the single auditable point for every routing decision.

    Why it matters. The classic multi-agent bug is the lost handoff: a specialist runs, produces a result, and the supervisor never merges it back — the customer is told nothing happened. The second classic bug is the chatter loop: A hands to B, B hands back to A, forever, because nothing bounds the system, only each agent individually. Both are Module 1's termination lesson, recurring one level up.

    What you build. A supervisor with routing and a global MAX_HANDOFFS budget; a make_delegate node with mandatory write-back; a forced chatter-loop ticket that must escalate at handoff 4 rather than loop 30 times; and an escalate path that hands a human the full trace and state, never a dead end — tested against routing_eval.jsonl for first-hop accuracy compared with your Lab-5 monolith.

    The one idea to remember. The supervisor's two jobs are route and aggregate — never domain work. Bound the whole system, not just each agent, or handoffs become an inter-agent while True:.

    The mistake to avoid. A "fat" supervisor that calls tools itself "to save a hop." It defeats specialisation, destroys auditability, and is exactly the anti-pattern Module 6's code-review exercise exists to catch.

    Module 7 — Flow Engineering over Prompt Engineering¶

    What it is. The course's founding maxim gets its own module: as much structure as possible, as much agency as necessary. Every business rule you can state as an if/then belongs in a conditional edge, not a prompt sentence. A prompt rule is decided fresh by the model on every request — non-deterministic, unbillable-for-free, and defeatable by a crafted input. A flow-logic branch is a pure function of typed state — deterministic, unit-testable in milliseconds with no model call, and impossible to talk around because it is code, not text the model interprets.

    Why it matters. "Show me where the refund-approval rule lives" must have a code answer for a regulated enterprise, not a prompt answer. A mega-prompt is the least testable, least auditable, most expensive artefact in an agentic system — and it silently drifts every time someone edits a sentence with no test to catch the behaviour change.

    What you build. You start by running refund_prompt_only.py on a crafted "ignore the limit" message and watching it issue a 4,000 SAR refund. Then you inventory every imperative in the prompt, classify each as rule or judgement, and build refund_flow.py: typed RefundState, an eligibility_gate, an amount_gate (the 500 SAR limit as an uncrossable branch), and a shrunk prompt used only to compose the reply — table-tested with seven branch unit tests that run in milliseconds with zero model calls.

    The one idea to remember. Anything that can be decided by a rule should be a branch, not a sentence. What stays in the prompt is the genuinely irreducible judgement — composing an empathetic, bilingual reply, interpreting real ambiguity.

    The mistake to avoid. "Fixing" a bug by appending one more sentence to the prompt, until the prompt contradicts itself and nobody remembers which sentence is load-bearing.

    Module 8 — Guardrails, Security, and Adversarial Testing¶

    What it is. The governing principle, stated once and assumed everywhere after: treat all model input as untrusted and all model output as unverified. The model is a manipulable component, never a security control. Defence is layered — structural authorisation (strongest: the server checks, no prompt can grant what it denies), deterministic gates (Module 7's uncrossable branches), input guardrails (a filter, not a wall — it will miss things), output guardrails (the most reliable layer, because it inspects the concrete action about to happen), least privilege (scope tools/data to the task), and human-in-the-loop for the highest stakes.

    Why it matters. An agent connected to enterprise systems is an attack surface that talks back. A prompt-injection payload targets the exact flexibility that makes agents useful, and the stakes are financial, regulatory, and reputational all at once. Red-teaming is how you find the holes before an attacker does — and only automated red-teaming, run in CI, catches a security regression that silently returns.

    What you build. screen_input ahead of your supervisor, flagging injection/PII patterns bilingually; guard_tool_call/guard_response blocking over-limit refunds, cross-customer access, and PII egress as structural stops; a demonstration that the over-limit refund is blocked even with the input guardrail disabled (layered defence made undeniable); a red-team agent attacking your own Rafeeq across four attack goals; and SECURITY_REPORT.md, triaged, with your highest-severity finding fixed and re-run to prove it now fails. This is PA-2, the graded security artefact.

    The one idea to remember. A prompt instruction is never a security control. Every real control is structure the model cannot argue with — and one layer alone is never enough, because one layer alone is exactly what the attacker is targeting.

    The mistake to avoid. Trusting the input guardrail as a wall instead of a filter. It will miss a novel phrasing eventually; the structural controls behind it must hold anyway, which is precisely what your Task 3 demonstration exists to prove.

    Module 9 — Observability, Cost Optimisation, and Monitoring¶

    What it is. An agent can be wrong while running perfectly — no exception, no crash, just a bad decision or a quietly climbing bill. Tracing turns every run into a tree of spans with inputs, outputs, timing, and token counts on every node — because Rafeeq was already built as a state machine, every transition is already a discrete, traceable event. Cost attribution answers "which intent, which agent, which model is spending the money?" along three axes (by model, by component, by intent) so the biggest bar tells you the fix. The two biggest cost levers are caching (never recompute an identical input; scope the key, set a TTL) and model routing (send the confident, simple majority to a cheap model, reserve the frontier model for genuine difficulty).

    Why it matters. You cannot manage a non-deterministic system by testing alone — you must observe production. At 18,000 contacts a day, a 0.1 SAR/contact difference is a real annual number, and observability is how you find and defend it, with evidence rather than a feeling that "the agent seems expensive."

    What you build. Tracing across 30 mixed tickets, identifying the single biggest cost span; a cost report by model and component; KB-retrieval caching with a scoped, versioned key and confident-intent model routing, re-measured on the same 30 tickets; a bounded retry on a flaky read tool with proof that issue_refund is retried zero times, ever; and a BENCHMARKS.md recording cost/contact and p95 latency before and after, with eval-set success confirmed unchanged.

    The one idea to remember. The two biggest cost levers are caching and model routing, and they compound with Module 7's flow engineering (which removes model calls for rules entirely). A cheaper agent that got worse is a failure, not a win — always report the success number alongside the cost cut.

    The mistake to avoid. Retrying a write tool "for reliability." A retried issue_refund on a timeout is the double-refund incident from Module 1, reborn at the tool layer — retry only idempotent, read-safe operations, ever.

    Cheat Sheet — The Ten Rules¶

    Print this page. Every rule below has a lab, a case study, and a sim-* branch behind it.

    1. Bounded loops, always. Step budget, cost budget, wall-clock timeout — every agent loop, no exceptions. "The model will stop when it's done" is not a termination condition.
    2. Errors are values, not exceptions. A tool returns {"error": ...} so the model can react. A raised exception kills the loop on the first bad input.
    3. Authorisation lives at the server, never in the prompt. A prompt rule is a sentence the model decides to honour. A server-side check is structure it cannot argue with.
    4. Filter memory before you rank it. Scope every long-term read/write by customer_id. This is a security control, not an optimisation.
    5. Structure over prompt. Anything decidable by a rule is a branch, not a sentence. Reserve the model for genuinely irreducible judgement.
    6. A supervisor routes and aggregates — it never does domain work. And bound the whole multi-agent system, not just each agent, or handoffs become an inter-agent loop.
    7. Every handoff is a typed, logged transition with mandatory write-back. A specialist result that never reaches shared state is a lost handoff, not a saved one.
    8. Treat all model input as untrusted, all output as unverified. Defend in layers; assume any single layer can be fooled, and make sure the ones behind it still hold.
    9. Never retry a write tool. Retry only idempotent, read-safe operations. Retrying a write is the double-refund incident, every time.
    10. Measure before you claim. A cost cut that regressed eval success is a failure, not a win. The system must testify to its own quality — traces, tests, and benchmarks, not a demo that happened to go well once.

    Glossary — English / العربية¶

    Standard Modern Standard Arabic technical terminology, matching the terms used in this course's own repository documentation (docs/SECURITY_MODEL.md, docs/ACTION_RISK_MATRIX.md).

    Term (EN) المصطلح (AR) Definition
    Agent وكيل A system in which the model decides the next action at runtime, from the current state.
    Agentic AI الذكاء الاصطناعي الوكيلي AI systems that plan, reason, use tools, and act autonomously toward a goal.
    Chain سلسلة ثابتة A fixed, developer-authored sequence of steps with no runtime branching by the model.
    Tool use استخدام الأدوات An agent's ability to call external functions or APIs to observe or affect the world.
    Function calling استدعاء الدوال The structured protocol by which a model requests a tool call with typed arguments.
    Reasoning الاستدلال Deciding the single next step, given what is known now.
    Planning التخطيط Deciding the overall approach to a multi-step task before or during execution.
    Memory الذاكرة What an agent carries within a task (short-term) or across sessions (long-term).
    State الحالة The typed, explicit object every node in an agent graph reads and updates.
    State machine آلة الحالات A system modelled as discrete states and transitions between them.
    Orchestration التنسيق (التنظيم) Coordinating multiple specialist agents toward one outcome.
    Supervisor المُشرِف The thin agent that routes tickets to specialists and aggregates their results.
    Delegation التفويض Handing a sub-task, with scoped context, from a supervisor to a specialist agent.
    Handoff التسليم The typed, logged transition of a task from one agent to another.
    Specialist agent الوكيل المتخصص An agent scoped to a narrow toolset and a single domain's prompt.
    Multi-agent system نظام متعدد الوكلاء A system composed of more than one cooperating agent.
    ReAct الاستدلال والفعل التفاعلي (ReAct) The reasoning pattern that interleaves thought, action, and observation.
    Plan-and-Execute التخطيط ثم التنفيذ The reasoning pattern separating an upfront plan from its execution.
    Reflection التأمل الذاتي A self-critique pass that evaluates and revises a candidate output.
    Termination condition شرط الإنهاء The explicit, testable rule by which an agent's loop stops.
    Bounded loop حلقة محدودة A control loop with explicit limits on steps, cost, and time.
    Step budget ميزانية الخطوات The maximum number of loop iterations an agent may take.
    Model Context Protocol (MCP) بروتوكول سياق النموذج An open client-server standard for exposing tools and resources to LLM applications.
    MCP server خادم بروتوكول سياق النموذج A service that publishes governed tool capabilities to MCP clients.
    Guardrails ضوابط الحماية Structural controls applied before or after model reasoning to prevent unsafe behaviour.
    Prompt injection حقن الأوامر An attack in which untrusted text is interpreted by the model as instructions.
    Jailbreak تجاوز القيود An attempt to make a model ignore its intended behavioural constraints.
    Authorisation التفويض بالصلاحية The server-side check confirming an actor may perform a specific action.
    Red-teaming اختبار الفريق الأحمر Adversarial testing designed to make a system misbehave, to find its weaknesses.
    Observability قابلية الملاحظة The ability to inspect why a system did what it did, from its traces and logs.
    Tracing التتبع Recording a run as a tree of timed, attributed steps (spans).
    Cost attribution إسناد التكلفة Assigning spend to the model, component, or intent that caused it.
    Model routing توجيه النموذج Sending confident, simple work to a cheap model and hard work to a frontier model.
    Caching التخزين المؤقت Reusing a previous result for an identical input instead of recomputing it.
    Latency زمن الاستجابة The time an agent takes to respond — the customer's felt experience.
    Idempotency اللاتغيّرية بالتكرار A property allowing an operation to be safely retried without a different effect.
    Retry إعادة المحاولة Automatically re-attempting a failed operation, safe only for idempotent operations.
    Checkpointing نقاط الحفظ Persisting agent state so a run can pause, resume, and be inspected.
    Vector store مخزن متجهي A database that retrieves content by the semantic similarity of embeddings.
    Embedding تمثيل متجهي A numeric vector representation of text, used for similarity search.
    Retrieval الاسترجاع Fetching the most relevant stored items for a given situation.
    Escalation التصعيد Handing an unresolved case to a human, with full context, as a first-class outcome.
    PDPL نظام حماية البيانات الشخصية Saudi Arabia's Personal Data Protection Law, governing the handling of personal data.
    Flow engineering هندسة التدفق Moving business logic out of prompts and into explicit, testable graph structure.
    Deterministic gate بوابة حتمية A conditional branch that always produces the same route for the same input.
    Least privilege مبدأ الحد الأدنى من الصلاحيات Granting an agent only the tools and data scope its task genuinely needs.
    Trust boundary حد الثقة The line separating untrusted input from structurally authorised, trusted action.
    Denial-of-wallet استنزاف الميزانية (استنزاف التكلفة) An attack or bug that drives an agent's cost or step count far beyond its intended budget.
