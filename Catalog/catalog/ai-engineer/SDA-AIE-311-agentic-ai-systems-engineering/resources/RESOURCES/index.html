    Resources — Annotated Bibliography¶

    SDA-AIE-311 Agentic AI Systems Engineering¶

    This bibliography covers every source named in the course's external-research brief (SPEC.md §6), organised by the module or lab that uses it. For each item: what it is, why it is in this course, which module/lab uses it, and how to use it. Items marked Third-party — access at source are not reproduced or mirrored in the course repository; follow the named link. Items marked Reference code only are example repositories the course points to for pattern illustration — they are not authoritative training material and are not graded against.

    Module 1 — Agentic System Architectures¶

    No external research citation; the module's content (the agent loop, the state-machine model) is original course material built directly on top of the LangGraph programming model referenced throughout the bibliography below.

    Module 2 — Planning and Reasoning Patterns¶

    ReAct: Synergizing Reasoning and Acting in Language Models¶

    Yao, S., Zhao, J., Yu, D., Du, N., Shafran, I., Narasimhan, K., Cao, Y. (2022). Third-party — access at source: arXiv:2210.03629.

    What it is. The paper that named and formalised the "thought → action → observation" interleaved reasoning loop that the whole agentic-AI field now calls ReAct.

    Why it is in this course. The course deliberately implements ReAct explicitly, by hand, in src/rafeeq/reasoning/react.py, before ever using a framework's create_react_agent convenience wrapper — the point is that participants can name every part of a "prebuilt" agent because they built it first. Measuring unnecessary tool calls (thrashing) against this paper's original framing is the module's diagnostic habit.

    Which module/lab. Module 2, Lab 2 (ReAct implementation and cost/step measurement).

    How to use it. Required reading before Lab 2. Read the loop description and the failure modes the authors report (hallucinated reasoning steps, error propagation); Lab 2's ReAct thrash exercise (sim-react-thrash) reproduces one of them directly.

    LangChain Academy — "Introduction to LangGraph"¶

    LangChain, Inc. Third-party — access at source: academy.langchain.com/courses/intro-to-langgraph (course); github.com/langchain-ai/langchain-academy (companion notebooks).

    What it is. LangChain's own free foundational course on building agents with LangGraph's graph-based workflow model — state, nodes, conditional edges, memory, human-in-the-loop.

    Why it is in this course. This is the designated technical companion to Modules 1–6: where the course's own Technical Content sections give the engineering reasoning behind a design choice, this course gives the hands-on mechanics of the underlying LangGraph APIs participants are expected to already be comfortable navigating (StateGraph, add_conditional_edges, checkpointers, create_react_agent). It is not required reading to pass SDA-AIE-311, but participants who have not touched LangGraph before Day 1 should complete at least its first two notebooks beforehand.

    Which module/lab. Modules 1, 2, 4, 5, 6 (anywhere a build_*() graph is constructed).

    How to use it. Pre-course self-study for anyone without prior LangGraph exposure; ongoing API reference during labs.

    Module 3 — Tool Use, Function Calling, and MCP Integration¶

    LaDe — a comprehensive last-mile delivery dataset¶

    Cainiao Network / Alibaba research. Third-party — access at source: search "LaDe last-mile delivery dataset" for the current hosting location (Cainiao's open-data programme); cite via the dataset's own paper when referencing it in written work.

    What it is. A large-scale, real-world last-mile delivery dataset (~10.7 million packages, ~21,000 couriers, five Chinese cities) covering package, courier, and delivery-event records.

    Why it is in this course — and the honesty note that matters. Tawseel's data schema (order, delivery event, courier, exception-code vocabulary) is inspired by LaDe's shape, not derived from its content. This course does not ship, redistribute, or train on any LaDe data. data/generate.py produces fully synthetic, deterministically-seeded Saudi data (five Saudi cities, TW-YYYY-NNNNN order ids, Arabic delivery notes) that merely follows a schema shape LaDe made a useful reference point for last-mile logistics fields (get_delivery_status, get_driver_status, estimate_eta, get_delivery_events, find_delivery_exception). Anyone wanting the real dataset must obtain it from its own source under its own terms; the course repository's README.md states this explicitly.

    Which module/lab. Module 1 (orders_seed.json, delivery_events.jsonl shape), Module 3 (the logistics tool surface mirrors this event vocabulary).

    How to use it. Background reading for instructors explaining why the delivery-event schema looks the way it does; not required participant reading.

    τ-bench and τ²-bench — Sierra AI¶

    Yao, S. et al. / Sierra AI. Third-party — access at source: arXiv:2406.12045 (τ-bench paper); github.com/sierra-research/tau2-bench (τ²-bench, the current maintained benchmark and code); sierra.ai/resources/research/tau-bench.

    What it is. A benchmark methodology for evaluating tool-using conversational agents in realistic enterprise domains (retail, airline), structured around a user, a domain policy, and a set of tools, scored on whether the agent reaches the correct end state.

    Why it is in this course. TawseelBench's own scenario schema is built directly on this structure: customer request → applicable policy → environment state → available tools → expected state transition → pass/fail criteria (see evaluations/tawseelbench/schema.json and docs/TAWSEELBENCH.md). This is the course's model for what "the system testifies to its own quality" means in practice — an eval harness that checks concrete state, not subjective response quality.

    Which module/lab. Every module's "Benchmarks and Evaluation" section; the capstone's eval-harness gate (LO8).

    How to use it. Required reading before Lab 1; re-read before the capstone milestone M-A gate ("eval replay green locally").

    Module 4 — Memory and State Management¶

    No new third-party citation beyond LangGraph's own checkpointer and vector-store integration patterns (covered by the LangChain Academy companion above). The PDPL framing (erasure, scoping, retention) is course-original, grounded in Saudi data-protection practice rather than a single external source.

    Module 5 — Single-Agent versus Multi-Agent Architectures¶

    Hugging Face — "Multi-Agent Systems" (AI Agents Course)¶

    Hugging Face. Third-party — access at source: huggingface.co/learn/agents-course/unit2/smolagents/multi_agent_systems.

    What it is. A unit of Hugging Face's free AI Agents Course covering when and how to decompose a single agent into a multi-agent system, using the smolagents framework.

    Why it is in this course. A second, framework-independent perspective on the single-vs-multi decision that reinforces Module 5's own four scaling symptoms (tool overload, prompt overload, context cost, ownership friction) from outside the LangGraph-specific lens the rest of the course uses.

    Which module/lab. Module 5, as supplementary/optional reading around Lab 5.

    How to use it. Optional discussion-case reading; not required, useful for the Split-or-keep clinic activity.

    Module 6 — Hierarchical Delegation and Agent Orchestration¶

    LangGraph — Supervisor vs Agents-as-Tools guidance¶

    LangChain, Inc. Third-party — access at source: reference.langchain.com/python/langgraph-supervisor (the langgraph-supervisor package reference); github.com/langchain-ai/langgraph-supervisor-py.

    What it is. LangChain's own documentation and reference implementation of the supervisor multi-agent topology, contrasted against the agents-as-tools pattern (where a top-level agent calls specialists as ordinary tool calls rather than through an explicit routing/handoff contract).

    Why it is in this course. The capstone explicitly asks for both architectures — Architecture A (LangGraph supervisor, src/rafeeq/orchestration/supervisor.py) and Architecture B (agents-as-tools, src/rafeeq/orchestration/agents_as_tools.py) — compared on task success, tool calls, tokens, latency, handoff failures, and unauthorised-action risk (scripts/compare_arch.py). This is the primary technical reference for that comparison.

    Which module/lab. Module 6, Lab 6; the capstone's Architecture A/B comparison.

    How to use it. Required reading before the Lab 6 fast-finisher extension and before running scripts/compare_arch.py.

    Module 8 — Guardrails, Security, and Adversarial Testing¶

    OWASP Top 10 for Agentic Applications (2026)¶

    OWASP. Third-party — access at source: the current OWASP GenAI Security Project publication for agentic applications — locate the live edition via owasp.org (OWASP GenAI Security Project) rather than a mirrored copy, since the list is actively revised; several independent explainer write-ups (Giskard, Cycode, Practical DevSecOps, VamiSec) summarise the current categories if a quick reference is needed, but the OWASP publication itself is the authoritative source to cite in SECURITY_REPORT.md.

    What it is. The OWASP community's structured taxonomy of the top security risks specific to agentic (tool-using, autonomous-action) AI applications — the agentic counterpart to the long-standing OWASP Top 10 for web applications.

    Why it is in this course. Mandatory Day-4 pre-reading. Every guardrail Module 8 builds and every red-team finding the course's attack corpus produces is mapped to an owasp_id field (security/**/*.json, docs/SECURITY_MODEL.md), so a participant's SECURITY_REPORT.md speaks the same taxonomy a real enterprise security review would expect.

    Which module/lab. Module 8, Lab 8; PA-2; the capstone's SECURITY_REPORT.md.

    How to use it. Required reading before Lab 8. Cross-reference every finding's owasp_id against the current published category names — the mapping in docs/SECURITY_MODEL.md should be treated as a teaching aid, not a substitute for reading the source list itself, since OWASP revises category names between editions.

    AgentDojo (ETH Zurich)¶

    Debenedetti, E., Zhang, J., Balunović, M., Beurer-Kellner, L., Fischer, M., Tramèr, F. (2024). Third-party — access at source: arXiv:2406.13352 (paper); github.com/ethz-spylab/agentdojo-core (code); agentdojo.spylab.ai (project site).

    What it is. A dynamic evaluation environment from ETH Zurich's SPY Lab for measuring both the utility and the security of tool-using LLM agents under prompt-injection attack, jointly — an agent that refuses everything scores well on security and badly on utility, and AgentDojo's methodology penalises that.

    Why it is in this course. The direct structural model for the course's own attack corpus (security/**/*.json). Every family in the corpus — direct/indirect injection, tool-result injection, memory poisoning, privilege escalation, denial-of-wallet — mirrors an AgentDojo attack category, and the corpus's success_oracle field (a concrete, checkable outcome, never "did the model say something bad") is a direct application of AgentDojo's insistence on measuring real effects, not surface refusals.

    Which module/lab. Module 8, Lab 8; src/rafeeq/security/red_team.py's run_suite().

    How to use it. Required reading before Lab 8. Read the paper's framing of the utility/security trade-off specifically — it is the source of the course's own rule that a red-team suite with a weak oracle "always succeeds" and is therefore worthless (Module 8's troubleshooting table).

    OpenAI Agents SDK — guardrail and human-in-the-loop patterns¶

    OpenAI. Third-party — access at source: openai.github.io/openai-agents-python (SDK docs); developers.openai.com/api/docs/guides/agents/guardrails-approvals ("Guardrails and human review").

    What it is. OpenAI's own SDK documentation for input/output guardrail functions and human-approval interrupt points around tool calls.

    Why it is in this course. Referenced conceptually, not as an implementation dependency — Rafeeq's guardrails (src/rafeeq/security/input_guard.py, output_guard.py) are framework-independent, dependency-free Python so they run in stub mode with zero installed packages. The OpenAI SDK material is useful for participants who will also work with that SDK, to see the same layered-defence principle (structural checks, not prompt sentences) expressed in a different framework's vocabulary.

    Which module/lab. Module 8, as a cross-framework comparison point.

    How to use it. Optional discussion reading; useful for the "which parts of Rafeeq's behaviour must never be a prompt sentence" discussion (Module 7/8 crossover).

    Module 9 — Observability, Cost Optimisation, and Monitoring¶

    LangSmith¶

    LangChain, Inc. Third-party — access at source: smith.langchain.com (product); LangChain's documentation site for API reference.

    What it is. LangChain's agent-tracing and evaluation platform — captures a run as a tree of spans with inputs, outputs, timing, and token counts, and lets failed runs become regression test cases.

    Why it is in this course. The course's target tracing tool for a live/deployed Rafeeq (src/rafeeq/observability/tracing.py's @traceable decorator wires to it when RAFEEQ_LANGSMITH=1). Offline/stub-mode labs use the repository's own LocalTracer (reports/traces/*.json) instead, which produces the same span-tree shape so the skill transfers directly once a participant has a LangSmith key.

    Which module/lab. Module 9, Lab 9; the capstone's tracing/cost-attribution demo requirement.

    How to use it. Provision a LangSmith key per participant for the capstone demo (per instructor_guide.md's preparation checklist); not required for any offline lab or CI check.

    LangGraph 101 and OpenAI Agents SDK example repositories¶

    LangChain, Inc. / OpenAI. Reference code only — access at source: github.com/langchain-ai/langchain-academy; github.com/openai/openai-agents-python's linked examples.

    What it is. Framework-maintained example code demonstrating agent, tool, and orchestration patterns in each SDK.

    Why it is in this course, and the caveat that matters. Flagged explicitly as reference code only, not authoritative training material. These repositories show a working pattern, not necessarily the enterprise-governed, security-hardened pattern this course teaches — a participant who copies an example repo's tool-authorisation approach verbatim (frequently prompt-based or absent entirely in a minimal example) would fail Module 8's rubric. Use them to see idiomatic framework syntax; use src/rafeeq/** as the authoritative pattern for how a governed enterprise tool, a scoped handoff, or a structural guardrail should actually be built.

    Which module/lab. Cross-cutting, Modules 3–9.

    How to use it. Syntax reference only, cited nowhere as a source of engineering practice in any graded artefact.
