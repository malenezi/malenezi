    0. Instructor pre-flight (T-minus 1 day)¶

    Check Command Must show
    Kafka image pre-pulled docker compose pull kafka redis no network fetch during the lab
    Spark Kafka jars warm python -m masar.spark --warm jars resolved from ~/.ivy2 cache

    2. Reference solutions¶

    Task 1 — gps_producer.py¶

    The participant file is complete as printed in the lab. The only deliberate defect is in lab5-start, where emit() reads:

    producer.send(TOPIC, value=ping)          # STARTER (wrong) — no key
producer.send(TOPIC, key=ping["trip_id"], value=ping)   # SOLUTION

    Diagnostic to show the room why it matters:

    docker compose exec kafka kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic masar.gps.pings \
  --partition 0 --from-beginning --max-messages 20 \
  --property print.key=true --property key.separator=' | ' | cut -d'|' -f1 | sort -u | wc -l

    Unkeyed: ~20 distinct trip_ids in partition 0 (round-robin, per-trip order destroyed across partitions). Keyed: pings for one trip are contiguous within a single partition.

    Task 2 — ingest_gps_stream.py¶

    As printed in the participant guide. Three points to draw out at the whiteboard:

    1. foreachBatch is a choice, not a requirement. A plain writeStream ... .start(path) to a Delta sink is already exactly-once. foreachBatch is used here to obtain the batch_id for the bronze _batch_id lineage column and to demonstrate txnAppId/txnVersion. Say this out loud — participants otherwise conclude that exactly-once requires foreachBatch.
    2. _source_file for a stream is kafka://topic/partition, not a path. The bronze contract says the column must exist and identify provenance; it does not say the provenance must be a file.
    3. mergeSchema=false on bronze is deliberate. If the producer adds a field, you want the job to fail loudly, not to silently widen the raw table. Schema drift must be a decision.

    Task 3 — Reference numbers¶

    Stage Pings produced Rows in bronze.gps_events Distinct event_id Pipeline-introduced dupes
    Clean run 50,000 50,000 49,801 0
    After kill 110,000 90,000 89,642 0
    After restart, drained 110,000 110,000 109,562 0

    sim-nocheckpoint branch for the counter-demo: 127,300 rows for 110,000 pings → 17,300 phantom positions.

    Rows minus distinct event_id is always ~0.4% — that is the seeded source defect from CONVENTIONS, not a pipeline fault. Participants confuse these constantly. Write both columns on the board and label them "data problem — fixed at silver" and "engineering problem — prevented by the checkpoint."

    Task 4 — Answers to the three questions¶

    Question Answer
    Which defect can a watermark fix? Late arrival. The watermark decides how long a window stays open for stragglers. It does not fix duplicates and does not fix out-of-order — out-of-order needs no fixing at all under event-time semantics
    Which can dropDuplicates fix, and at what cost? Duplicate event_id. Unbounded dropDuplicates retains every key ever seen → unbounded state → OOM. dropDuplicatesWithinWatermark bounds it to the lateness window, at the cost of missing a duplicate that arrives more than 5 minutes after its twin
    Which is invisible to both? The m/s semantic drift. It is not late, not duplicated, not out of order, and structurally valid. Only a per-producer_version distribution comparison sees it — which is LAB-06

    Task 5 — build_vehicle_positions.py, corrected write chain¶

        (deduped.writeStream
        .format("delta")
        .queryName("vehicle_positions_silver")
        .outputMode("append")
        .option("checkpointLocation", CHECKPOINT)
        .trigger(processingTime="30 seconds")
        .start(SILVER_PATH)
        .awaitTermination())

    On partitioning silver.vehicle_positions: the defensible answer at lab scale is do not partition. 1.2M rows/day with a 30-second trigger already produces ~2,900 files/day; adding a partition column multiplies directory count without improving any query in this course. At production scale, partition by event_date only, and ZORDER by vehicle_id. Accept either answer if the participant measured; reject "partition by vehicle_id" (14,000 directories/day) in every case.

    Reference verification numbers:

    bronze_rows  silver_rows  silver_dupes  late_rows  max_speed_250  max_speed_240
110,999      108,914      0             487        118.8          121.4

    Before the unit fix, max_speed_250 = 33.0. Show both. The 33.0 is what makes the incident dangerous — it is a plausible speed.

    The 2,085-row gap (110,999 → 108,914) decomposes as: ~762 duplicate event_id removed, ~13 late pings beyond the watermark, ~1,310 rows filtered by accuracy_m > 50 and the KSA bounding box. Have participants account for the gap; a participant who cannot explain their own row loss has not understood the transform.

    3. Answer key — self-check questions¶

    Q One-line grading criterion
    Q1 Must name both mechanisms (checkpointed offsets + atomic Delta commit) and identify the checkpoint path. Naming only Kafka, or only Delta, is a partial answer
    Q2 Must say event-time windows make arrival order irrelevant. Bonus: notes that sorting an unbounded stream is undefined, not merely expensive
    Q3 Must identify unbounded state growth as the cost, and name the trade-off (a duplicate arriving after the watermark passes through)
    Q4 Must distinguish structural validation from semantic correctness, and place the fix at the bronze→silver transform, not in bronze
    Q5 Must say neither is wrong and tie the clock to the question being asked. A participant who says "always use event time" has memorised the slide, not the reasoning
    Q6 Must quantify file growth (~30×) and name at least one of: per-file read cost, _delta_log growth, object-storage request charges

    4. Common participant errors and the intervention¶

    # Error Frequency Intervention
    1 Deletes the checkpoint to "reset" after a failure Very high Stop the room. This is the exact action that manufactures the duplicates the lab is proving you avoid. Make the offender demonstrate the duplication, then restore
    2 Two queries pointing at one checkpoint directory High Show the state-store corruption. Establish the rule: checkpoint path = query name, always
    3 Confuses source duplicates (0.4% seeded) with pipeline duplicates Very high Two-column board diagram. Ask "who introduced this row?"
    4 startingOffsets=latest with a producer that already finished High Explains the "Batch 0: 0 pings forever" symptom. Ties to troubleshooting row 6
    5 Filters accuracy_m in bronze Medium Bronze is append-only and as-received. Filtering there destroys the evidence needed to prove what the device sent
    6 Fixes the m/s drift by clamping speed_kmh to a range Medium The clamped values are wrong, not missing. Normalise on producer_version
    7 Sorts the stream to handle out-of-order Medium Ask what "sorted" means for an unbounded input. Usually resolves itself
    8 1-second trigger "for lower latency" Low–medium Let them run it for two minutes, then DESCRIBE DETAIL. The file count teaches faster than the explanation

    5. Facilitation script for Task 3 (the module's thesis)¶

    Run this as a synchronised room activity, not as independent work.

    1. "Everyone stop. Hands off keyboards." (30 s)
    2. "Run the count. Write the number on your sheet." Collect three numbers verbally from around the room. (1 min)
    3. "Start the producer. Start the stream. When you see a batch line, count to three and hit Ctrl-C." (2 min)
    4. "Run the count again. Write it down." (1 min)
    5. "Restart. Change nothing. No flags. No deleted directories." (2 min)
    6. "Final count." Then ask one pair: "How many pings did you produce? How many rows are in bronze? Are those the same number?" (2 min)
    7. Counter-demo on the projector: sim-nocheckpoint, same drill, 17,300 extra rows. (1.5 min)

    Close with the question that carries to the capstone: "Which two mechanisms did that, and where do they live in your repo?" Do not accept a conceptual answer — make them name lakehouse/_checkpoints/gps_events_bronze and the Delta commit.

    7. Grading guidance (contributes to capstone rubric criterion Streaming, 15 pts)¶

    Band Evidence
    90–100 Kill/restart proof executed and counted by the participant, dedicated checkpoints, watermark choice justified with measured lateness data, m/s normalisation applied with producer_version preserved in bronze, can explain both exactly-once mechanisms unprompted
    70–89 Stream works and restarts cleanly, but the watermark is a default rather than a decision, or dedup is unbounded, or the participant recites the mechanisms without locating them in their own repo
    < 70 Duplicates on restart · shared or deleted checkpoint · processing-time aggregation · m/s drift unhandled and undetected

    Automatic cap at 70% (capstone anti-pattern flag): streaming without a dedicated checkpoint.
