    LAB 07 — INSTRUCTOR SOLUTION GUIDE¶

    Assemble And Orchestrate The Mini-Lakehouse¶

    Field Value
    Lab ID LAB-07 · Solution
    Module / Day M7 · Day 5 Hours 1–2
    Duration 90 min
    Git tag lab7-solution
    Audience Instructor only
    Pedagogical crux Task 5 — inject a failure, recover with a full re-run, prove the end state is identical. This is the capstone rehearsal

    Scale note. Figures quoted in this document assume the full-scale generator run (--scale 1.0); the shipped sample is --scale 0.15 — 7,230 trips/day over 5 days (36,150 trips), 873,763 GPS pings, 3,450 drivers, 3,864 vehicles, 48 zones. Grains, ratios and file-count reductions hold at either scale; absolute row counts do not.

    0. Instructor pre-flight¶

    Check Command Must show
    All prior labs present python -m masar.tools.preflight --lab 7 8/8
    Airflow installs pip install 'apache-airflow==2.9.3' --constraint … no dependency conflict with pyspark 3.5
    Fallback runner works python -m masar.orchestration.runner --dag masar_medallion --list 8 tasks
    Failure switch works MASAR_INJECT_FAILURE=build_silver make pipeline fails at build_silver
    jq available jq --version used by the snapshot diff
    Solution green the acceptance checks in section 6 (make lab7-verify is not shipped) 11/11

    Airflow installation is the highest-risk pre-flight item of the whole course. The constraint file is mandatory; without it pip resolves a flask/werkzeug combination that breaks the CLI. Test on a clean venv the week before. If more than a third of the room fails to install, switch the whole cohort to the shipped lightweight runner — it is API-compatible for everything this lab needs, and the teaching is identical. Do not spend lab time on Airflow packaging.

    1. Timing plan¶

    Task Budget Median Note
    1 Wire the DAG 15 min 18 min PYTHONPATH for the DAG parser costs most cohorts 5 min
    2 BI marts + idempotency 20 min 22 min The double-run proof is fast; writing the grain assertion is not
    3 PIT features 15 min 16 min The spot-check SQL is long — allow copy-paste
    4 Full run 10 min 8 min Mostly waiting; use it for the layer-contract discussion
    5 Failure + recovery 15 min 15 min Protect absolutely. Every pair must see the empty diff
    6 Maintenance + docs 10 min 14 min MINI_LAKEHOUSE.md overruns; it is a capstone deliverable, so let it
    7 Commit 5 min 3 min

    If behind at Task 4: cut Task 6's maintenance implementation (demo it, ship lab7-solution's file) but keep MINI_LAKEHOUSE.md — it is graded. Never cut Task 5.

    2. Reference solutions¶

    Task 1 — the DAG¶

    Complete as printed. Three teaching points:

    1. t_land >> t_gate >> t_silver >> t_obs >> [t_demand, t_driver, t_feats] >> t_maint is the only line that matters. Everything else is configuration. Ask the room which line they would defend hardest in review before revealing the answer.
    2. max_active_runs=1 is not obvious and is usually omitted. Without it, two runs can MERGE into silver.trips concurrently; Delta's optimistic concurrency keeps the table consistent but fails one run with ConcurrentAppendException at 02:00 with nobody watching. Surface this.
    3. The default trigger rule (all_success) is a safety property. If a participant "fixes" a skipped maintenance task with trigger_rule="all_done", they have just arranged to compact and vacuum a table whose build failed. Catch this.

    Reference tree output is in the participant guide.

    Task 2 — reference numbers¶

    Table Grain Rows (run 1) Rows (run 2) Write strategy
    gold.zone_hourly_demand (city, pickup_zone_id, date, hour) 8,640 8,640 replaceWhere 3-day partition overwrite
    gold.driver_daily (driver_id, date) 42,612 42,612 MERGE on grain key
    gold.trip_features (trip_id) 42,038 42,038 full overwrite

    The append counter-demo (.mode("append") run twice) produces:

    RuntimeError: GRAIN VIOLATION in ./lakehouse/gold/zone_hourly_demand:
  17,280 rows but only 8,640 distinct ['city', 'pickup_zone_id', 'date', 'hour'].
  The write strategy is not idempotent.

    Run this on the projector. It converts module mistake #3 from a bullet point into a stack trace.

    Why zone_hourly_demand uses replaceWhere and driver_daily uses MERGE. Both are idempotent; the choice is about grain-to-partition alignment. zone_hourly_demand is partitioned by date and its grain is fully contained within a date partition, so a partition overwrite is exact and cheap. driver_daily's grain is also date-scoped, but the lookback window rebuild would need to know which driver/date pairs existed previously to avoid orphaning rows for drivers who had no trips in the new window — MERGE handles that naturally. Accept either strategy for either table if the participant can defend it and the double-run proof passes. The wrong answer is append, and the sophisticated-looking wrong answer is overwrite without replaceWhere (which silently deletes history outside the lookback).

    On partitioning. partitionBy("date") only. Reject partitionBy("city", "date", "driver_id") — 14,000 directories per day, module mistake #5. If a participant proposes it, have them run DESCRIBE DETAIL and count files.

    Task 3 — point-in-time correctness¶

    Reference spot-check:

    trip_id      feature_ts           feature_value  recount_strictly_prior  recount_if_leaking
TRP-770118   2026-06-28 07:14:33  17             17                      44

    The -1 in rangeBetween(-3600, -1) is the exam question. rangeBetween bounds are inclusive and operate on the ordering column's value range, not on row offsets. With an upper bound of 0, the frame includes every row whose pickup_epoch equals the current row's — every trip starting in the same second, in the same zone. At Riyadh rush-hour density that is several trips, and they are the future.

    Make participants say why the inflation is especially dangerous: it is small (a few percent), it correlates with congestion (exactly the thing being predicted), and it therefore looks like signal rather than like a bug. Large leakage gets caught; small leakage gets shipped.

    _assert_point_in_time is a weak lint by design — it only detects the degenerate case where a wider window adds nothing. Say so. The real defence is the code review of the window bound, plus LAB-08's leakage drill. A lint that participants believe is complete is worse than no lint.

    Task 4 — reference full-run output¶

    As printed in the participant guide. Total ~3m 40s on a 16 GB laptop with spark.sql.shuffle.partitions=8. If a cohort is seeing 20+ minutes, check for per-task SparkSession creation (JVM startup ×8) and the default 200 shuffle partitions.

    Task 5 — the recovery proof¶

    Reference snapshots:

    before.json = during.json    (dependency held: gold untouched)
before.json = after.json     (full re-run reproduced the exact state, checksums included)

    The question participants must answer: why is re-running land_bronze safe?

    Reference answer, in three parts:

    1. Bronze may grow on a re-run, and that is within contract. Bronze is append-only and immutable, and carries _batch_id and _source_file precisely so a duplicate landing is identifiable. Bronze's contract is "everything we ever received," not "one row per real-world event."
    2. The duplication stops at the first keyed write. The gate promotes into silver.trips with a MERGE on trip_id; re-applying a matched row updates it to the same values — a no-op. Every gold table derives from silver.
    3. The streaming bronze table (bronze.gps_events) is additionally idempotent per batch via txnAppId/txnVersion from LAB-05.

    Reject the answer "we should skip land_bronze on a re-run." A task you are afraid to re-run is a task you cannot recover, and the whole thesis of the lab collapses. If a participant's land_bronze genuinely is not re-runnable, that is a real defect and Task 5 is the correct moment to find it.

    Task 6 — maintenance and contracts¶

    Reference numFiles:

    [maintain] bronze/gps_events:        248 -> 6
[maintain] silver/trips:              37 -> 3
[maintain] silver/vehicle_positions: 214 -> 9
[maintain] gold/zone_hourly_demand:   12 -> 3
[maintain] gold/driver_daily:         18 -> 3
[maintain] gold/trip_features:         9 -> 2

    MINI_LAKEHOUSE.md gold rows — answer key:

    Table Grain Source Write strategy Contract enforced by
    gold.zone_hourly_demand one row per (city, pickup_zone_id, date, hour) silver.trips (completed only) replaceWhere partition overwrite, 3-day lookback _assert_grain in build_gold.py; partition alignment
    gold.driver_daily one row per (driver_id, date) silver.trips + silver.drivers MERGE on (driver_id, date) _assert_grain; MERGE key
    gold.trip_features one row per trip_id silver.trips + silver.vehicle_positions full overwrite _assert_grain + _assert_point_in_time

    Also required per layer: who may read it (bronze = platform engineers only; silver = data scientists; gold = analysts and the model service), what breaks if the contract is broken, and the file and line where enforcement lives. Participants routinely write the first two and omit the third; the third is the one that makes the document useful six months later.

    3. Answer key — self-check questions¶

    Q Grading criterion
    Q1 Must say no, and name all_success as the default trigger rule. Bonus: identifies that all_done would vacuum a failed build
    Q2 Must describe the stampede (N concurrent runs mutating shared tables). Bonus: notes that backfills should be commands, not scheduling side effects
    Q3 Must identify the silent gap in the mart while silver is correct. Must propose at least one of: measured lookback, reconciliation check, targeted backfill. Bonus: connects to LAB-05's watermark as the same trade-off at a different time scale
    Q4 Must distinguish bronze's contract from silver's, and locate idempotency at the MERGE key. A participant who says "skip the task" fails this question
    Q5 Must name the dependency line and articulate at least two of its three guarantees. Bonus: identifies t_gate >> t_silver specifically, or max_active_runs=1
    Q6 Must explain that rangeBetween bounds are inclusive value ranges, and that 0 admits same-second rows. Bonus: explains why small leakage is more dangerous than large

    4. Common participant errors¶

    # Error Frequency Intervention
    1 No module named 'masar' in the DAG parser Very high export PYTHONPATH=$PWD/src or pip install -e .. Forbid sys.path.append inside a DAG file — DAG files are re-parsed constantly and must stay side-effect-free
    2 Gold task reads from bronze High Bypasses the gate. Every control from LAB-06 becomes decorative. Make them trace one quarantined row
    3 append on a gold aggregate High (it is the starter) The GRAIN VIOLATION stack trace
    4 Grain documented but not asserted Very high "A contract that is not tested is a comment." Require _assert_grain
    5 replaceWhere predicate ≠ source filter Medium–high Delta raises Data written out does not match replaceWhere. It is protecting them from a partial overwrite
    6 Re-runs only the failed task in Task 5 High The whole point is the full re-run. If only the failed task is safe to re-run, they have not proven idempotency
    7 Over-partitioning gold Medium DESCRIBE DETAIL and count files
    8 trigger_rule="all_done" on maintenance Medium Vacuuming a failed build
    9 Deletes gold tables to "get a clean run" Medium That is not recovery, it is amnesia. Recovery means the pipeline restores state without manual deletion
    10 20-minute pipeline on a laptop Medium spark.sql.shuffle.partitions=8, one shared session. M2 lesson applied to their own code
    11 ConcurrentAppendException from a still-running LAB-05 stream Medium Streams write bronze.* and silver.vehicle_positions; the DAG MERGEs silver.trips. Keep the write surfaces disjoint

    5. Facilitation script for Task 5¶

    Run synchronised, whole room, 15 minutes:

    1. "Snapshot. Read me your gold.driver_daily count." Collect three. (2 min)
    2. "Set the failure variable. Run the pipeline. Do not touch anything when it fails." (4 min)
    3. "Diff before and during. Read me the output." Expect silence — the diff is empty. Ask: "Why is gold unchanged? Nobody told it not to build." Answer: the dependency edge. (3 min)
    4. "Unset the variable. Run the WHOLE pipeline. Not the failed task. The whole thing." (4 min)
    5. "Diff before and after." Empty again. (2 min)

    Close with: "You just recovered a production data platform from a mid-pipeline failure without knowing what failed, without running anything by hand, and without inspecting a single table. That is what orchestration buys. Everything else is a scheduler."

    This is the capstone rehearsal — the rubric's Orchestration & recovery criterion is decided entirely by whether diff before.json after.json comes back empty.

    7. Grading guidance (capstone criterion Orchestration & recovery, 15 pts)¶

    Band Evidence
    90–100 One-command idempotent DAG, clean recovery with an empty snapshot diff, grains documented and asserted, max_active_runs=1 with a reason, maintenance as a task, contracts written with enforcement locations
    70–89 DAG runs and ordering is correct, but idempotency is asserted rather than proven, or recovery required manual intervention, or grain is documented but not tested
    < 70 Hand-run steps · non-idempotent gold · no recovery path · gold built from bronze

    Automatic cap at 70% (capstone anti-pattern flag): non-idempotent gold.
