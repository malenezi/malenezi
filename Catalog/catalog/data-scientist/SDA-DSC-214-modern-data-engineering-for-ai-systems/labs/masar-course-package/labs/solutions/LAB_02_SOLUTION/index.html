    1. Reference solution¶

    1.1 src/masar/econ/cost_model.py — complete, with reference prices¶

    Reference prices used for the numbers in §5 (state to the room that these are illustrative list prices and that participants must cite their own):

    Input Reference value Note
    storage_gb_month 0.023 standard object storage, $/GB-month
    core_hour 0.06 decoupled general-purpose compute, on-demand
    spot_multiplier 0.35 ≈ 65% discount
    warehouse_core_hour 0.18 coupled MPP node, always on
    warehouse_storage_gb_month 0.21 storage inside the warehouse 
    """Transparent storage-vs-compute cost model for the Masar platform."""
from __future__ import annotations

from dataclasses import dataclass, replace


@dataclass(frozen=True)
class Prices:
    storage_gb_month: float = 0.023
    core_hour: float = 0.06
    spot_multiplier: float = 0.35
    warehouse_core_hour: float = 0.18
    warehouse_storage_gb_month: float = 0.21


@dataclass(frozen=True)
class Job:
    name: str
    cores: int
    runtime_hours: float
    runs_per_month: int
    spot: bool = False

    def monthly_core_hours(self) -> float:
        return self.cores * self.runtime_hours * self.runs_per_month

    def monthly_compute(self, p: Prices) -> float:
        rate = p.core_hour * (p.spot_multiplier if self.spot else 1.0)
        return self.monthly_core_hours() * rate


def lakehouse_monthly_cost(total_gb, jobs, p: Prices = Prices()):
    storage = total_gb * p.storage_gb_month
    compute = sum(j.monthly_compute(p) for j in jobs)
    total = storage + compute
    return {"storage": round(storage, 2), "compute": round(compute, 2),
            "total": round(total, 2), "compute_share": round(compute / total, 3)}


def warehouse_monthly_cost(total_gb, nodes, cores_per_node, p: Prices = Prices()):
    hours = 730.0
    compute = nodes * cores_per_node * hours * p.warehouse_core_hour
    storage = total_gb * p.warehouse_storage_gb_month
    total = storage + compute
    return {"storage": round(storage, 2), "compute": round(compute, 2),
            "total": round(total, 2), "compute_share": round(compute / total, 3),
            "idle_share": round(1 - (0.9 * 30) / hours, 3)}


def break_even_utilisation(total_gb, nodes, cores_per_node, p: Prices = Prices()):
    wh = warehouse_monthly_cost(total_gb, nodes, cores_per_node, p)
    budget_for_compute = wh["total"] - total_gb * p.storage_gb_month
    return round(budget_for_compute / p.core_hour, 1)

    1.2 src/masar/econ/scan_cost.py¶

    The participant version is the reference. Two instructor notes:

    • The Py4J metric walk (df._jdf.queryExecution().executedPlan()) works on stock Spark 3.5.1 but is build-sensitive. Always have the Spark UI fallback ready (localhost:4040 → SQL/DataFrame → the query → number of files read / size of files read). Announce the fallback at the start of Task 3 so nobody loses five minutes to it.
    • explain("formatted") alone is not evidence — it shows intent, not bytes. Insist on numbers.

    1.3 src/masar/econ/prepare_benchmark_input.py (fallback if the sample is missing)¶

    """Build a benchmark-shaped silver.trips from the participant's own bronze."""
from pyspark.sql import functions as F
from masar.spark import get_spark


def main() -> None:
    spark = get_spark("prepare-benchmark-input")
    b = spark.table("bronze.trips")
    df = (b.dropDuplicates(["trip_id"])
           .withColumn("fare_sar", F.col("fare_sar").cast("double"))
           .withColumn("distance_km", F.col("distance_km").cast("double"))
           .withColumn("pickup_ts", F.coalesce(
               F.to_timestamp("pickup_ts", "yyyy-MM-dd HH:mm:ss"),
               F.to_timestamp("pickup_ts", "dd/MM/yyyy HH:mm")))
           .filter("status = 'completed'"))
    (df.repartition(12, "city")
       .write.format("delta").mode("overwrite").option("overwriteSchema", "true")
       .partitionBy("city").save("./lakehouse/silver/trips"))
    print("benchmark input rows:", df.count())


if __name__ == "__main__":
    main()

    2. Teaching moments — what to say and exactly when¶

    When Trigger The moment Say this
    Min 2, before Task 1 — Force the prediction "Before you touch the model: write down, now, whether storage or compute will be the bigger line for Masar. Fold the paper. We open it at minute 25."
    Min 8, Task 1 A pair uses the default prices An uncited price is an unusable model "In a review, the first question is 'where did $0.023 come from?' If the answer is 'the lab file', the model dies in that sentence."
    Min 25, Task 2 — the headline moment compute_share prints Open the folded papers Poll the room. Most predicted storage. "Compute is 30% of a $394 bill on the decoupled side — and 87% of a $19,000 bill on the coupled side. Decoupling did not make compute cheaper per hour. It made you stop paying for the hours you do not use: 96% of the warehouse's compute hours are idle."
    Min 30, Task 3 First ReadSchema with 3 columns This is why decoupling works at all "Compute is on the far side of a network. The only reason that is affordable is that Parquet lets it read 3 columns of 27 and skip row groups that cannot match. Format choice is an economic decision."
    Min 35, Task 3 Partition-filter row shows a 4× file drop Layout is a cost control "Same question, same answer, 6% of the bytes. Nobody bought a bigger cluster."
    Min 40, Task 4 Break-even number appears Reframe break-even as headroom "Masar runs at 0.7% of break-even utilisation. That is not a warning — it is the budget to retrain weekly instead of monthly. Elasticity is what buys the AI team its cadence."
    Min 45, Task 5 — The unifying question "What happens to Masar's AI system if the economics fail? Nothing dramatic. History gets truncated to save money, retrains get cut to monthly, and the model drifts. Cost failures starve AI; they do not crash it."

    Rehearse: the folded-prediction reveal. It is the entire emotional arc of this lab.

    3. Common wrong answers and how to redirect¶

    What you will see Why it happens Redirect
    compute_share ≈ 1.0 Storage GB estimated from the sample (172 GB) with no extrapolation, or retention months forgotten "How many months are you keeping, and is that the whole platform or just raw?" Make them state the extrapolation factor out loud
    Storage estimate off by 1000× Mixed GB/TB, or per-TB prices used per-GB Force normalisation into Prices before any arithmetic
    "Lakehouse saves 98%, done" Comparing list-price always-on warehouse against elastic Lakehouse with no caveats "Your CFO has a 40% committed-use discount. Re-run with the warehouse at 0.6×. Is the story still true?" (It is — ~96% — but they must show they anticipated the challenge)
    Naive and pruned plans identical Filter applied after collect()/toPandas() Have them print the plan for both; the ReadSchema line settles it
    Using wall-clock seconds as the benchmark Familiar from application performance work "Run it three times." The variance makes the argument. Bytes and files are stable; seconds are not
    PushedFilters: [] on the partition-filtered query and a claim of failure city moved to PartitionFilters, which is better than pushdown Teach the distinction: partition filters skip directories before any file is opened; pushed filters skip row groups inside files
    Modelling the warehouse as also elastic Not internalising coupling "If the warehouse can scale compute to zero overnight, what happens to the data stored on those nodes?"
    Guardrail rationale written as "best practice" No cost reasoning Require a number: "10 minutes of idle × how many days × the cluster rate = what?"
    Concluding "storage is free, keep everything forever" Over-correcting from the compute reveal Point at PDPL: retention is also a legal constraint, not only a cost one. Bridges to M4/M6

    Interpretation to give the room: columns dropped from 27 to 3 (89% fewer) but bytes only dropped 72%. Why? Because trip_id and city are wide, low-entropy strings and the remaining columns compress well — column count is a proxy, bytes are the truth. This is exactly why the lab insists on measuring.

    6. Grading notes¶

    Criterion Weight Full marks Partial Zero
    Prices real and cited 15% Every price has a URL + read-date Cited but stale/regional mismatch Lab defaults left in place
    Storage estimate derived, not assumed 15% Daily volume × retention × stated extrapolation factor, all shown Number given, derivation missing Copied from the slide
    Model output correct and interpreted 20% Storage/compute/total/compute_share for both architectures, dominant driver stated with a reason Numbers without interpretation Model does not run
    Measured scan evidence 25% Three rows with files and bytes read; plans show PartitionFilters, PushedFilters, reduced ReadSchema; identical counts across variants Plans only, no measured bytes No evidence, or counts differ between variants (a correctness bug)
    Break-even + comparison table 15% Break-even stated with assumptions and compared to actual utilisation Break-even without assumptions Missing
    Guardrails justified 10% Each of autotermination / max_workers / spot-with-on-demand-driver / tags justified in cost terms Restates the YAML Missing

    Red flags - Identical LAB2_NOTES.md numbers across pairs when prices were supposed to be independently sourced → flag for the Day-5 integrity check. - A saving claim > 95% presented with no caveat → not wrong, but coach it: an un-caveated model loses reviews. Require the discount sensitivity. - Bytes-read column left empty with "the plan shows pushdown" → this is the single most common shortfall; it fails the capstone's BENCHMARKS.md requirement, so mark it down now while it is cheap.

    Carry into Module 3. Put the class's median compute_share and the median relative-bytes-scanned figure on the board. Open M3 with: "ELT is only affordable because of these two numbers. Now let us spend that compute correctly."
