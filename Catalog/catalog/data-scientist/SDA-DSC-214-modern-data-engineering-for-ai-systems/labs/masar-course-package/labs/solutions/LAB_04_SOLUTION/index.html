    LAB 04 — INSTRUCTOR SOLUTION GUIDE¶

    Delta Lake: ACID, MERGE, Time Travel, Maintenance¶

    Field Value
    Lab LAB-04 (4a + 4b) · Module 4 · Day 3 Hours 2 and 4, wrapped in Hour 5 · 90 minutes total · pairs
    Tags lab4-start (4a) → lab4a-solution; lab4b-start (4b) → lab4-solution
    Room setup Projector with a text editor open on lakehouse/silver/trips/_delta_log/00000000000000000000.json (pretty-printed, large font) and a second terminal aliased to DESCRIBE HISTORY. Print the A4 "Delta transaction log" and "Optimistic concurrency" posters
    Pre-flight On a clean clone: run Lab 3 to completion, then verify SHOW TBLPROPERTIES is empty of constraints (participants must add them), the corrections fixture has exactly 5 unique trip_ids that exist in silver, and pdpl_erasure_2026-06-10.json names a rider_id with > 0 rows
    Overrun risk Highest of the course alongside Lab 5. Protect Task 1 (log reading) and Task 3 (second MERGE). Everything else is compressible

    Scale note. Figures quoted in this document assume the full-scale generator run (--scale 1.0); the shipped sample is --scale 0.15 — 7,230 trips/day over 5 days (36,150 trips), 873,763 GPS pings, 3,450 drivers, 3,864 vehicles, 48 zones. Grains, ratios and file-count reductions hold at either scale; absolute row counts do not.

    1. Reference solution¶

    1.1 src/masar/delta/create_silver.py¶

    Participant version is the reference. Instructor notes:

    • The bad = ... WHERE NOT (expr) pre-check exists so the ALTER TABLE never fails opaquely. If a pair's Lab 3 filters were weaker than the reference, positive_fare may report skipped rows — that is a good outcome to surface: constraints and upstream filters are the same contract expressed twice, and a mismatch is a real finding.
    • known_city is a third, optional constraint. Add it if the room is fast; it produces the most instructive failure (whitespace / casing from a sloppy staging model).

    1.2 src/masar/delta/merge_ops.py¶

    Participant version is the reference. Two design choices to defend if asked:

    Choice Why
    .schema(target_schema) when reading the corrections CSV Enforces the contract on the source, so a malformed correction file fails at read time with a clear error rather than inside the MERGE
    Explicit duplicate check before whenMatchedUpdateAll() whenMatchedUpdateAll is only safe with exactly one source row per key. Delta would raise Cannot perform Merge as multiple source rows matched...; raising our own error first makes the cause obvious

    1.3 src/masar/delta/time_travel.py and maintain.sql¶

    Participant versions are the reference. The diff_versions helper is what turns "time travel exists" into "time travel answers a question" — make sure every pair runs it, not just --history.

    1.4 Reference command sequence (the instructor demo, 8 minutes)¶

    # 1. the log (2 min)
python -m json.tool < lakehouse/silver/trips/_delta_log/00000000000000000000.json | head -60

# 2. enforcement (1 min) — three rejections, row count unchanged
python -m masar.delta.create_silver
python - < scripts/demo_negative_writes.py

# 3. idempotent MERGE (2 min) — the reveal
python -m masar.delta.merge_ops --corrections data/fixtures/corrections/trips_corrections_2026-06-03.csv
python -m masar.delta.merge_ops --corrections data/fixtures/corrections/trips_corrections_2026-06-03.csv

# 4. audit (1.5 min)
python -m masar.delta.time_travel --history
python -m masar.delta.time_travel --diff 2 3

# 5. erasure + maintenance (1.5 min)
python -m masar.delta.merge_ops --erase-request data/fixtures/erasure_request/pdpl_erasure_2026-06-10.json
python - < scripts/demo_maintenance.py

    Rehearse this end to end the evening before. The log-opening and the updated=0 reveal are the two beats that carry Module 4.

    2. Teaching moments — what to say and exactly when¶

    Lab 4a (25 min)¶

    When Trigger The moment Say this
    Min 8 — the headline moment of 4a First commit JSON on the projector Read the log aloud Point at each action: "protocol — what a reader must understand. metaData — the schema is a log entry, and so is your CHECK constraint. add — one Parquet file, with its min/max stats: those are the statistics that made your Lab 2 query skip 8 of 12 files. remove — a tombstone; the bytes are still on disk. commitInfo — the audit record." Then: "The current state of this table is not what is in the directory. It is what you get by replaying this log. Everything else in Module 4 follows from that one sentence."
    Min 12 Someone asks about half-written files Atomicity, concretely "If Spark dies mid-write, the Parquet files exist but no commit references them. A reader replaying the log never sees them. There is no such thing as a half-applied Delta write."
    Min 18 Negative-fare write rejected Schema enforcement is the anti-swamp "This is the property a raw lake lacks. Module 1's swamp is exactly a directory of Parquet with nobody checking. One line of metadata is the difference."
    Min 22 New-column write rejected Enforce by default, evolve on purpose "mergeSchema exists. It is opt-in and it writes a metadata commit — so a schema change is a reviewed event with an audit trail, not a surprise you find in a dashboard."

    Lab 4b (65 min)¶

    When Trigger The moment Say this
    Min 18 — the headline moment of 4b Second MERGE prints updated=0 Idempotency at the storage layer "dbt gave you this in Lab 3. Now you have seen what it actually is: a keyed, atomic, retryable operation. This is why your orchestrator may retry a failed task, why a six-month backfill is safe to run twice, and why recovery is a re-run rather than a project."
    Min 20 Someone notices a commit was still written State, not commits "Idempotency is about the table's state, not the commit count. Two runs, one result. If you also need commit-level idempotency — say, to avoid triggering a change feed — guard on a batch marker."
    Min 28 --diff 2 3 output on screen Audit made real "Five fares changed. You can show a regulator the before, the after, and the commit that did it, without having taken a backup."
    Min 32 RESTORE creates a new version History is append-only "You cannot un-happen a bad MERGE. You can only record the correction. That is what makes the trail trustworthy."
    Min 40 — the governance moment Rider absent from current, present in v(n−1) An erasure that touches one table is not an erasure "Legally, is this rider erased? No. They are in the time-travel history, in tombstoned files, in bronze, in your gold features, and in Redis. Erasure is a platform operation. Write the runbook."
    Min 52 numFiles 214 → 9 Maintenance is scheduled, not heroic "Nobody bought a bigger cluster. Read time fell 4.6× because you stopped opening 214 files. OPTIMIZE belongs in the DAG next to backups."
    Min 58 RETAIN 0 HOURS blocked Retention is governance, not a space hack "Two failures at once: your audit trail dies, and any query holding an older snapshot gets a FileNotFoundException mid-flight. Leave the check on."
    Min 62 Retention justification written The unifying question "What happens to Masar's AI system if this table layer fails? A training run reads a half-written table, or a disputed number can never be reproduced, or an erasure request cannot be honoured. None of those show up as a red pipeline."

    3. Common wrong answers and how to redirect¶

    What you will see Why it happens Redirect
    "The table is already Delta, so 4a is done" Lab 3 wrote Delta "Delta the format is not Delta the contract. Show me what happens when a negative fare arrives." Then run the negative test
    ALTER TABLE ... ADD CONSTRAINT fails and they drop the constraint Existing rows violate it The constraint is right and the data is wrong. Find the rows, decide (quarantine vs fix upstream), then add it. This is the same lesson as "never delete a failing test"
    Disabling retentionDurationCheck to make VACUUM 0 work Wants to see storage reclaimed now "You just deleted your audit trail to save 4 MB on a laptop." If they want the demo, do it on a throwaway copy — never on silver.trips
    Expecting updated=0 to mean "no commit" Conflating state with log See the min-20 moment
    Expecting VACUUM to reclaim space immediately Default 7-day retention Use DRY RUN to show what would be removed and when. Expected behaviour, not a bug
    Claiming the erasure is complete after DELETE Only looked at the current version Have them query versionAsOf n-1. Then ask about bronze, gold and Redis
    whenMatchedUpdateAll() with a partial-column corrections file Copied the pattern Missing columns become null and silently wipe good data. Either supply the full target schema (reference solution) or use an explicit whenMatchedUpdate(set={...})
    ZORDER on trip_id "because it is the key" Index intuition again ZORDER helps range and equality predicates that queries actually use. Nobody filters silver by a single trip_id in analytics. ZORDER what the dashboards filter on
    Partitioning by (city, trip_date) on a one-day sample and reporting no gain Over-partitioning at small scale Correct observation — reward it. Then ask what changes at 36 months and 5 cities
    Reading numFiles from ls instead of DESCRIBE DETAIL Habit ls counts tombstoned files too; only the log knows the live set. Good bridge back to the min-8 moment
    Hand-copying a Parquet file into the table directory to "add data" Curiosity Excellent teachable accident: Delta ignores it entirely. "The directory is not the table. The log is the table."

    4. Timing checkpoints¶

    Lab 4a — 25 minutes¶

    Clock Participants should be… If behind If ahead
    Min 5 lab4-start checked out; DESCRIBE DETAIL confirms 42,038 rows, format delta, partitioned by city Fast-forward from lab3-solution Add the optional known_city constraint
    Min 12 Constraints added; first commit JSON opened and its actions named Do the log reading as a whole-room activity on the projector — nobody misses it Diff commit 0 against a later commit and identify the remove actions
    Min 20 All three negative writes rejected; error text captured; row count unchanged Give them the negative-test script Try a mergeSchema=true write and inspect the resulting metadata commit
    Min 25 4a notes written — —

    Lab 4b — 65 minutes¶

    Clock Participants should be… If behind If ahead
    Min 15 Corrections loaded; first MERGE run (updated=5) Give them merge_ops.py; the drill matters more than the typing —
    Min 20 Second MERGE run; updated=0 seen and understood Do not skip. Pause the room Explain it to the neighbouring pair
    Min 30 DESCRIBE HISTORY read; version diff produced Give them the diff_versions helper Run RESTORE both ways and describe what the history shows
    Min 40 Erasure run; present-in-old / absent-in-current proven Give them the drill script Start the multi-table erasure runbook
    Min 52 OPTIMIZE + ZORDER run; before/after numFiles and read time recorded Skip the timing, keep numFiles Separate compaction from ZORDER (self-check Q6)
    Min 58 VACUUM DRY RUN + 168h run; RETAIN 0 blocked Show the block on the projector instead Set logRetentionDuration / deletedFileRetentionDuration as properties
    Min 62 Retention justification written in LAB4_NOTES.md Assign as homework — but it is a capstone deliverable, so it must be done Concurrency drill (stretch goal 1)
    Min 65 Benchmark table filled; committed — —

    Overrun policy. Compressible: Task 4's RESTORE round trip, the known_city constraint, the benchmark timings. Not compressible: Task 1 (log reading) and Task 3 (the second MERGE). If Hour 4 overruns, Hour 5 ("table maintenance and small files") is the designed catch-up window — run Task 6 there as a guided whole-room exercise.

That is not a failure — have them create the small files honestly (run the corrections MERGE five times with different fixtures) rather than reporting a number they did not produce.

    6. Grading notes¶

    Lab 4 is a direct capstone component (requirement 4) and is also the subject of PA-1, the 30-minute Day-3 practical assessment. Grade strictly; a weak Lab 4 predicts a failed PA-1.

    Criterion Weight Full marks Partial Zero
    Constraints present and enforced 20% positive_fare + valid_duration in SHOW TBLPROPERTIES; negative write rejected with the error captured Constraints added, negative test not run Constraints dropped to make writes pass
    Schema enforcement understood 10% Wrong-type and new-column writes rejected; row count unchanged afterwards One of two mergeSchema left enabled on the table
    Log literacy 10% Can name protocol / metaData / add (with stats) / remove / commitInfo and say what replaying the log means Opened the file, cannot explain it Not attempted
    MERGE idempotency 20% Run 1 = 5 updated, run 2 = 0, both operationMetrics captured; explains state-vs-commit Both runs done, no metrics captured Only one run, or non-keyed upsert
    Time-travel audit 15% DESCRIBE HISTORY plus a version diff showing the 5 changed fares; RESTORE understood as append-only History shown, no diff Not attempted
    PDPL erasure 15% Current/previous version contrast proven and the multi-table runbook written (bronze, gold, Redis, history) Delete demonstrated, runbook missing Claims erasure is complete after DELETE
    Maintenance + retention 10% Before/after numFiles recorded; VACUUM DRY RUN then 168h; RETAIN 0 blocked and left blocked; three-input retention justification Numbers recorded, justification thin retentionDurationCheck disabled

    Red flags — act immediately - spark.databricks.delta.retentionDurationCheck.enabled = false anywhere in a participant's code → this is a production-safety failure and a capstone red flag. Have them revert it and write two sentences on why. - A "demonstrated erasure" with no mention of bronze, gold or the online store → PDPL red flag. Badge issuance requires no PDPL red flags; catch it here, on Day 3, where it is cheap to fix. - Identical benchmark tables across repositories → version numbers and timestamps are per-run; identical DESCRIBE HISTORY blocks mean copied output. Flag for the Day-5 integrity check. - A pair whose silver.trips holds 96,400 rows → Lab 3 dedup never worked. Fix before Day 4; every gold aggregate will be double.

    Fast-forward path. git checkout lab4-solution then re-run the four drills against their own table. A pair that fast-forwards Lab 4 must still personally run the second MERGE and the erasure drill — those two are assessed in PA-1 and demoed in the capstone.

    Carry into Module 5. Ask the room for their numFiles before/after. Open M5 with: "A streaming sink writes a file every trigger. At a 30-second trigger that is 2,880 files a day. You now know exactly what that costs and exactly which scheduled job fixes it."
