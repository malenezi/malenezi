    LAB 08 — INSTRUCTOR SOLUTION GUIDE¶

    Serve Gold To AI And BI¶

    Field Value
    Lab ID LAB-08 · Solution
    Module / Day M8 · Day 5 Hour 3
    Duration 60 min
    Git tag lab8-solution
    Audience Instructor only — do not release before every pair has submitted LAB8_LEAKAGE.md
    Pedagogical crux Task 3, the leakage drill. The module's emotional peak and the course's most durable lesson

    Scale note. Figures quoted in this document assume the full-scale generator run (--scale 1.0); the shipped sample is --scale 0.15 — 7,230 trips/day over 5 days (36,150 trips), 873,763 GPS pings, 3,450 drivers, 3,864 vehicles, 48 zones. Grains, ratios and file-count reductions hold at either scale; absolute row counts do not.

    2. THE LEAKAGE DRILL — COMPLETE ANSWER KEY¶

    Do not distribute this section until every pair has submitted their classification.

    2.1 Per-column answer key¶

    # Column Classification Rationale — what is knowable at feature_ts, and what the starter code actually used Fix
    1 trip_id VALID The entity key, assigned at request time. It is an identifier, not a model input, and must be excluded from the feature vector — but it is knowable at feature_ts and reproducible online, so it is VALID rather than LEAKAGE. Accept a participant who argues it should be excluded from the drill entirely, provided they say why None. Exclude from the feature vector; keep for joins and traceability
    2 pickup_zone_id VALID The rider's current location, resolved to a zone at request time. Available online as a direct request parameter None
    3 dropoff_zone_id VALID Masar's booking flow requires a stated destination before request, so this is an input, not an outcome. Contrast with distance_km (#10), which describes the same journey but is written at dropoff_ts. Product-dependent: if destination-less requests existed, this would be UNAVAILABLE ONLINE for that segment None. Document the product assumption it rests on
    4 hour_of_day VALID Derived purely from feature_ts, which at inference is the request timestamp. Deterministic, zero-latency, no source dependency None
    5 day_of_week VALID Same as #4. Note the KSA working week (Fri–Sat weekend) when interpreting it, consistent with gold.dim_date.is_weekend None
    6 rolling_zone_demand_15m LEAKAGE rangeBetween(-450, 450) is a centred ±7.5-minute window. Diagnostic D1 shows 17 of 31 counted trips started after feature_ts. Those trips had not happened. Worse, the leaked half correlates with exactly the congestion the model is predicting, so it reads as strong genuine signal rangeBetween(-900, -1) — the prior 15 minutes, strictly before. Recompute; expect the feature's mean to roughly halve
    7 rolling_avg_speed_10m LEAKAGE The starter averages speed_kmh over the trip's own GPS pings, grouped by trip_id. Diagnostic D2 shows the last such ping was recorded 21.5 minutes after pickup — i.e. after the trip ended. This is not a feature, it is a compressed encoding of the label: a slow trip is a long trip. Pearson r with the label is −0.72 Average the speed of other vehicles in the pickup zone over the 10 minutes strictly before feature_ts, from silver.vehicle_positions, excluding this trip_id. Zone-grained, so it is also materialisable to Redis
    8 driver_recent_trip_count STALE rangeBetween(-86400, 0) is point-in-time correct offline except for the inclusive upper bound (a minor same-second leak). The dominant problem is online: the value is refreshed by a nightly batch, so at 19:00 on a Thursday it is 19 hours old. A driver who has completed 11 trips today reads as 0, and the model treats an exhausted driver as a fresh one. Accept LEAKAGE as a defensible second answer if the participant identifies the 0 bound — but require them to also name the staleness, because that is the failure that will actually bite Two-part: change the bound to -1; and refresh the driver slice into the online store on a cadence matched to the feature's volatility (hourly, not nightly), with feature_ts age monitoring
    9 weather_condition UNAVAILABLE ONLINE data/raw/weather_hourly.csv lands after the hour it describes. Joining a 07:14 trip to the 07:00 row is legitimate offline — that observation existed when the feature table was built — but at 07:14 live, the 07:00 row has not arrived. Point-in-time correct and unobtainable. The distinction from LEAKAGE is operational: a leaking feature must be changed, an unavailable one must be re-sourced Join to the last observed hour: hour_ts <= date_trunc('hour', feature_ts) - INTERVAL 1 HOUR. Apply the identical shift in training and in materialisation, and serve from the Redis zone key. One hour of staleness, but the same hour on both sides
    10 distance_km LEAKAGE In silver.trips this is the metered distance the vehicle actually travelled, written at dropoff_ts. Pearson r with the label is 0.947 and it carries 0.612 of the model's gain — the model is essentially reading the answer. At inference the value does not exist, so the serving code must substitute something, and the model was trained to trust it heavily. This is the single largest contributor to the inflated metric Recompute as the planned route distance at booking: the routing engine's estimate, or offline the route/great-circle distance between gold.dim_zone centroids. Keep the column name (the contract is fixed); change only the source. Participants may internally alias it planned_distance_km for clarity
    11 historical_route_duration VALID rangeBetween(-2592000, -1) — the mean duration_min of completed trips on the same (pickup_zone_id, dropoff_zone_id) pair over the prior 30 days, strictly before feature_ts. Correctly excludes the current trip. Zone-pair grained, so it is materialisable to Redis. After the fix it becomes the model's top feature at 0.381 gain — which is the right outcome: historical route behaviour should be the strongest honest signal None. Verify the -1 bound explicitly. Define and document the null contract for zone pairs with no prior trips (impute city median with an is_imputed flag, or omit)
    12 feature_ts VALID The as-of timestamp itself — the anchor every other column's correctness is defined against. Metadata, not a model input. It is knowable by definition (it is the request time) None. Exclude from the feature vector; retain for point-in-time joins, materialisation and freshness monitoring
    13 label_actual_duration_min LEAKAGE The target. Trivially leaking if it ever enters the feature vector, and a PDPL/operational hazard if it is materialised to Redis — the online store would then be serving the answer. Participants sometimes want to mark this "N/A"; do not accept that. Classifying the label as LEAKAGE is the discipline that catches the non-obvious label proxies, which is what #7 and #10 are Strip from the serving payload and from ONLINE_COLUMNS. Keep in the offline table (that is what a training set is)

    2.3 The four deliberate defects in build_eta_features.py¶

    Each is marked with # <-- inspect this in the starter:

    Marker Line Defect Fixed form
    (A) w_demand .rangeBetween(-450, 450) — centred window .rangeBetween(-900, -1)
    (B) w_driver .rangeBetween(-86400, 0) — inclusive upper bound .rangeBetween(-86400, -1) + hourly online refresh
    (D) speed pos.groupBy("trip_id").agg(avg(speed_kmh)) — the trip's own pings Zone-grained, prior 10 min, excluding this trip
    join weather join date_trunc('hour', pickup_ts) == hour_ts — current hour hour_ts == date_trunc('hour', feature_ts) - INTERVAL 1 HOUR
    select distance_km metered distance passed straight through planned route distance from dim_zone centroids / routing estimate

    2.4 Reference metrics¶

    Pre-fix (leaking) Post-fix (honest) Δ
    R² 0.943 0.712 −0.231
    MAE (min) 1.81 4.58 +2.77 (×2.53)
    Top feature distance_km (0.612) historical_route_duration (0.381) —

    Pearson r with the label, pre-fix: distance_km 0.947 · rolling_avg_speed_10m −0.722 · historical_route_duration 0.514 · rolling_zone_demand_15m 0.288 · driver_recent_trip_count 0.041 · hour_of_day 0.111.

    The rule of thumb to give the room: any feature correlating above ~0.85 with the label deserves a written defence before it ships. It is occasionally legitimate; it is usually a confession.

    2.5 Facilitation script for Task 3¶

    1. Pens down, terminals closed. Five minutes, pairs, no code. Classify all 13 columns from the column names and the CONVENTIONS schema alone. (5 min)
    2. Collect votes on three columns only — distance_km, rolling_avg_speed_10m, weather_condition — by show of hands per class. Record the split on the board. Most rooms mark distance_km VALID. (2 min)
    3. Run D1, D2, D3 together. Read the numbers aloud: "seventeen of thirty-one had not started"; "the last ping was twenty-one and a half minutes after pickup"; "nought point nine four seven." (4 min)
    4. Re-vote the same three columns. The shift is the lesson. (1 min)
    5. Fix and retrain. (5 min)
    6. The close. Put 0.943 and 0.712 side by side and ask: "Which of these two models would you rather deploy, and which would you rather present?" Then: "The honest one tells you it will miss by four and a half minutes. The other tells you one point eight, and then misses by five. The second is more expensive precisely because you believed it." (3 min)

    Do not tell them the answer before step 3. The re-vote is what makes it stick.

    3. Reference solutions — the rest¶

    Task 1 — the BI star¶

    All five models are complete as printed. Grading notes:

    • Exactly one dim_date and one dim_driver. If a participant adds a fiscal-calendar variant, they have rebuilt the M1 two-tier divergence inside their own gold layer. This is a named common mistake (#4) and should be caught.
    • dim_date.is_weekend must use the KSA working week (Fri–Sat). Getting this wrong shifts every weekend-demand analysis by two days and is invisible in testing.
    • fact_trip must not select rider_id. sha2(rider_id, 256) as rider_pseudonym is the correct treatment. Check the select list, not the docstring.
    • Reconciliation must be exact (rel_diff = 0). Both descend from one silver.trips through one gate. A non-zero diff is almost always a status = 'completed' filter mismatch or a lookback-window range mismatch — never "adjust" one side.

    Reference reconciliation output is in the participant guide.

    Task 4 — online materialisation and consistency¶

    Reference: 412 zone keys, 4 columns each, 0 mismatches.

    materialize_online.py must contain zero feature logic. This is the acceptance criterion that matters most and the easiest to fudge. Read the file. Any F.avg, F.count, Window, or arithmetic on a feature value is a fail — the only permitted operations are select-latest-per-key, serialise, and write.

    The injected-divergence test is mandatory. A consistency check that has never failed is a check that has not been tested. Reference:

    [consistency] mismatches    : 1
[consistency]   MISMATCH zone=ZN-RUH-014 col=rolling_zone_demand_15m offline=14 online=99
exit=1

    The MISSING_ONLINE discussion (troubleshooting row 6) is worth two minutes if time allows: zones with no recent trips have no latest row and therefore no key. Three options — documented default with an is_default flag, service-side fallback with logging, or omission — and the worst option is the one that happens by accident: silently serving last week's key. Ask which of the three a participant's inference service would actually do.

    Task 5 — PDPL boundary¶

    Reference output is in the participant guide. The dim_zone centroid question (troubleshooting row 12) is the substantive one: coordinates at zone grain are aggregate reference data; coordinates at trip or ping grain are personal data. That distinction is data minimisation, and it should appear in GOVERNANCE.md.

    Required in LAB8_NOTES.md: three PDPL principles implemented (minimisation, purpose limitation, and either retention limits or access control), and one thing an analyst genuinely cannot do. Reference answer for the second: an analyst cannot compute per-rider lifetime value or repeat-rider cohorts by identity — only by pseudonym, which breaks if the pseudonym salt rotates, and cannot be joined to any external customer system. That is a real cost. A participant who claims the governance costs nothing has not thought about it.

    4. Answer key — self-check questions¶

    Q Grading criterion
    Q1 Must explain that 0.943 was measured wrong, not better, and that reverting does not restore it in production. Bonus: the "tells you 1.8 and misses by 5" framing, or notes that serving must invent substitutes for missing columns
    Q2 Must locate the difference in when the value is written (feature_ts vs dropoff_ts), not in what it describes. Bonus: the destination-less-request counterfactual
    Q3 Must distinguish UNAVAILABLE ONLINE from LEAKAGE and propose the last-observed-hour shift applied on both sides. A participant who fixes only the serving path has created textbook skew and should be told so
    Q4 Must argue that duplicated logic diverges through ordinary maintenance, not negligence. Bonus: names the bounded cost (staleness, managed by refresh cadence + monitoring) against the unbounded one (skew, unmonitorable)
    Q5 Must name the shared silver.trips and the single gate. Bonus: names both residual risks — filter divergence and build-timing divergence — and the guards for each
    Q6 Must identify the type-1 dimension problem: today's rating attached to a three-week-old trip. Bonus: proposes SCD2 as-of join, or derivation from gold.driver_daily restricted to prior dates. Best answers note the column name is the tell

    5. Common participant errors¶

    # Error Frequency Intervention
    1 Marks distance_km VALID Very high — most rooms The D3 correlation (0.947). Then ask: "when is that number written?"
    2 Marks rolling_avg_speed_10m VALID because "speed is an input" High D2: the last ping is 21.5 min after pickup. The trip was over
    3 Marks label_actual_duration_min "N/A" High Refuse. Classifying the label is the discipline that catches label proxies — which is what #1 and #2 are
    4 Marks weather_condition LEAKAGE Medium Reasonable confusion. Draw the distinction: leaking = must change; unavailable = must re-source. The category exists precisely to force different remediation
    5 Disappointed by the metric drop; asks whether they broke it Very high This is the emotional peak. Say plainly: this is the correct outcome and it is what the lab is for
    6 Fixes leakage, R² rises Medium A fix reintroduced leakage elsewhere — usually historical_route_duration rebuilt with a 0 upper bound. Re-run D3
    7 Recomputes features in materialize_online.py High Skew by construction. Read their file; delete the computation
    8 Random train/test split High Itself a form of leakage — the model sees future trips from the same zone-hour. Always split by time
    9 Two dim_date variants Medium The M1 two-tier divergence, rebuilt in their own gold layer
    10 rider_id in fact_trip Medium PDPL boundary violation and a rubric anti-pattern flag
    11 Adds columns to gold.eta_features Medium The 13-column contract is fixed by CONVENTIONS. Fixes change the computation, never the column set
    12 Redis connection refused from Spark, works in redis-cli Medium Container vs host. Published port + host="localhost"

    7. Grading guidance (capstone criterion Serving (AI + BI) & demo, 10 pts)¶

    Band Evidence
    90–100 All 13 columns classified correctly with written rationale, all four defects found and fixed at the computation (not the contract), both metrics recorded with an explanation of why the drop is correct, offline == online proven across all keys and shown to fail on injection, conformed star reconciling at 0, PDPL boundary asserted
    70–89 Works, but the classification misses one or two columns (typically weather_condition or driver_recent_trip_count), or reconciliation is asserted rather than shown, or consistency is spot-checked on one key rather than all
    < 70 Leakage remains · online ≠ offline · raw PII served · star does not reconcile

    Automatic caps at 70% (capstone anti-pattern flags): feature leakage, raw rider IDs in BI outputs.

    Live verification the assessment notes authorise: ask the participant to run the leakage drill and explain the inflated metric. A distinction-band answer names the specific column, the specific window bound, the specific diagnostic that revealed it, and both numbers — without opening a file.
