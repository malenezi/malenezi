    ACT-03 — Cost-Model Auction / Cloud-Bill Autopsy¶

    Field Value
    Activity ID ACT-03
    Module M2 — Compute–Storage Separation and Cloud Economics
    Day / Hour Day 1 · Hour 6 (after LAB-02's cost model, before or after CS-02)
    Duration 20 minutes
    Format Two-phase: a silent sealed-bid auction on cost drivers, then a bill autopsy against the truth
    Group size 3–4 per team; 3–6 teams
    Deliverable A bid sheet per team, then a ranked remediation list scored by SAR saved per engineering day

    1. Objective¶

    Two skills, in this order:

    1. Estimate before you measure. Participants commit a number to each cost driver before seeing the bill. Committing publicly to a wrong number is the fastest way to dislodge appliance-era intuitions — chiefly the belief that storage is expensive.
    2. Rank by return, not by size. The most valuable fix in a cloud bill is almost always the least interesting one. Forcing a ranking by SAR saved per engineering day produces a different order than every team's instinct.

    2. Materials (printable)¶

    • Bid sheet (§6), one per team.
    • The bill (§7), one per team, kept face-down until phase 2.
    • Remediation menu (§8), one per team, distributed with the bill.
    • Calculators or a laptop per team. A visible scoreboard on a flipchart.

    3. Setup (2 minutes)¶

    Place a bid sheet face-up and the bill face-down on each table. Draw the scoreboard:

              | idle | scan | spot | storage | API | TOTAL | rank error
  Team A  |      |      |      |         |     |       |
  Team B  |      |      |      |         |     |       |

    4. Run of show¶

    Min What happens Facilitator
    0–2 Frame. "A Lakehouse platform costs SAR 462,000 a month. Before you see a single line of the bill, you will bid: how much of it is each of these five things? Sealed bids. No talking between teams." Give the context in §6's header only. No hints.
    2–8 Phase 1 — the auction. Teams fill the bid sheet: a SAR figure for each of five drivers, summing to ≤ 462,000. Circulate to confirm every cell has a number. "Wrong is fine; blank is not."
    8–10 Post the bids. Write every team's five numbers on the scoreboard. Do not reveal the truth yet. Note publicly where the spread is widest. It is always storage (teams over-bid it 5–10×) and idle (teams under-bid it).
    10–11 Reveal. Turn the bills over. Score: 1 point per driver within ±20% of truth; 3 bonus points for the correct rank order of the five. The reveal is loud. Let it be.
    11–18 Phase 2 — the autopsy. Using the remediation menu, teams rank fixes by SAR saved per engineering day and commit to what they would do with only 3 engineering days. Push: "You have 3 days, not 12. Which three fixes?"
    18–20 Debrief. §5. Land the ratio table and the storage revelation.

    5. Debrief questions¶

    1. Who over-bid storage, and by how much? (Most teams bid SAR 80,000–150,000. The truth is 27,000 — 5.8% of the bill. This is the appliance-era intuition dying in public, which is why the auction is worth the six minutes.)
    2. Who under-bid idle compute? (Idle is SAR 121,000 — the single largest recoverable line — and it is invisible on a bill, because a cloud invoice charges you for a running cluster identically whether or not anything ran on it.)
    3. Did your rank order match? (Rank matters more than magnitude. A team with the right order and wrong magnitudes will make correct decisions; the reverse will not.)
    4. What did you buy with your 3 days? (Correct: idle termination + right-sizing (0.5 d), spot for the nightly build (0.5 d), and start on compaction (2 d). That is SAR ~180,000/month for 3 days.)
    5. Why does every team's instinct rank compaction first? (Because it is the interesting problem. Name the bias out loud: engineers optimise for intellectual return, and FinOps pays for financial return. The gap between those two is where cloud bills go to die.)
    6. What would you have bid if the platform were on-premises? (Storage would genuinely have been a large share. The intuition is not stupid — it is stale. Decoupling inverted the ratio.)

    9. Answer key¶

    Bid truth and typical error¶

    Driver Truth (SAR/mo) Share Typical team bid Typical error
    1. Idle compute 121,000 26.2% 40,000–70,000 Under by 2–3×
    2. Full-scan tax ~104,000 22.5% 90,000–160,000 Roughly right
    3. On-demand premium 42,000 9.1% 20,000–50,000 Roughly right
    4. Storage at rest 27,000 5.8% 80,000–150,000 Over by 3–6×
    5. Storage API requests 31,000 6.7% 5,000–15,000 Under by 2–5×

    The two systematic errors are the lesson: storage at rest is over-estimated and the cost of reading is under-estimated. In a decoupled architecture, data is nearly free to keep and expensive to read badly. Rows 4 and 5 together say it precisely: keeping 340 TB costs less than the API calls to open its files.

    Remediation ranking (the deliverable)¶

    Rank Fix SAR/mo saved Days SAR per eng-day
    1 A — idle termination + right-size + Saudi-week schedule 121,000 0.5 242,000
    2 B — spot for the nightly build 42,000 0.5 84,000
    3 C — OPTIMIZE + ZORDER + partition 76,000 (+28,000 API) 3 34,700
    4 D — column pruning on the top 10 queries 18,000 1.5 12,000
    5 F — tags + unit-cost report 0 direct (enabling) 2 —
    6 E — hot mart / result cache 28,000 5 5,600
    7 G — cut retention ~8,000 1 8,000 — but rejected: destroys audit and PDPL evidence to save 1.7%
    — H — — Excluded: the business fixed the refresh cadence
    — I — — Excluded: re-spends the migration, reinstates a fixed peak-sized commitment against 8%/month growth

    With 3 days: A + B + C-partial ≈ SAR 180,000–200,000/month. With all 12 days: A+B+C+D+F ≈ SAR 267,000/month, taking the run-rate to ~SAR 195,000 — below the original business-case target of 231,000. The case was beatable all along, and it was lost to configuration rather than to architecture.

    Scoring¶

    • 1 point per driver bid within ±20% of truth (max 5).
    • 3 bonus points for the exactly correct rank order of the five.
    • 5 points for a remediation ranking whose top 3 match A, B, C in that order.
    • −3 points for including G, H or I in the top 5. Announce this penalty only at scoring.

    10. Cohort variants¶

    Small cohort (< 8 participants). Run as individual sealed bids rather than team bids, then a single group autopsy. With 6 people you get 6 independent estimates, which makes the spread — and therefore the shared misconception — far more visible than 2 team bids would. Add a closing question with the extra time: "Your bill grows 8% a month. Which of these fixes survives that, and which is a one-off?" (Answer: A and F survive because they are policies; C survives only if optimizeWrite/autoCompact make it continuous; D and E are one-offs consumed within a year.)

    Large cohort (> 20 participants). Run the auction as a live open outcry rather than sealed bids, one driver at a time, with teams calling numbers and the facilitator recording the range on the scoreboard. It is faster (4 minutes for all five) and the anchoring effect becomes visible and discussable — early loud bids drag later ones, which is exactly how cost estimates converge on wrong numbers in real organisations. Then split phase 2: half the teams rank the menu, half write the one-page CFO memo from CS-02 §8.4, and pair them for a 3-minute exchange. Duration 25 minutes.
