    ACT-05 — The Human Delta Transaction Log¶

    Field Value
    Activity ID ACT-05
    Module M4 — Delta Lake, ACID and the Transaction Log
    Day / Hour Day 3 · Hour 3 (between LAB-04a and LAB-04b, before CS-04)
    Duration 20 minutes
    Format Embodied simulation — participants physically enact commits, concurrent writers, time travel and VACUUM
    Group size Whole room, with assigned roles; 8–24 works ideally
    Deliverable A correct reconstruction of the table at three different versions, and a written statement of what VACUUM destroyed

    1. Objective¶

    Participants stop thinking of Delta as "Parquet with features" and start thinking of it as an ordered log of add/remove actions over an immutable file set, from which any version of the table is derived rather than stored.

    By the end they can: replay a log by hand to produce the current file set; explain why two concurrent writers do not corrupt each other; explain exactly what time travel reads; and state precisely what VACUUM makes impossible.

    2. Materials (printable)¶

    • File cards (§7): ~20 blue A5 cards, each representing one Parquet data file, with a filename and its row contents.
    • Commit cards (§7): ~12 white A5 cards, each a _delta_log entry with a version number and its add / remove actions.
    • Role badges (§7): READER, WRITER-A, WRITER-B, VACUUM, LOG-KEEPER.
    • Two long tables or floor areas: one marked _delta_log (ordered, left to right), one marked object storage (unordered heap).

    3. Setup (5 minutes)¶

    Lay out the two areas. Place file cards part-0000 through part-0004 in object storage and commit cards for versions 0–2 in the log area, in order. Distribute role badges: one LOG-KEEPER, one READER, two WRITERS, one VACUUM. Everyone else is an auditor and scores the READER's reconstructions.

    Write the rule on the board and enforce it all session:

    Object storage is a heap. It has no order and no idea what a table is. The log is the only thing that knows which files are the table.

    4. Run of show¶

    Min Phase What happens Facilitator
    0–2 Frame. "This table is not a folder. It is a list of instructions for which files are currently in the table. You are going to be the reader that follows them." Point at the heap. "How many rows are in the table right now?" Nobody can answer without the log. That is the point.
    2–5 Replay 1. READER walks the log from version 0 to version 2, physically picking up files that are added and putting down files that are removed. Announces the resulting file set and row count. Auditors check. Expected: part-0000, part-0002, part-0003 (see §6).
    5–9 Concurrent writers. WRITER-A and WRITER-B each prepare a commit at the same time, both having read version 2. Both write their new data files into the heap. Both then try to hand LOG-KEEPER a card numbered version 3. LOG-KEEPER accepts only the first. The second must retry: re-read the log (now at v3), check whether the conflict is real, renumber to v4, and re-submit. Do not explain this — let LOG-KEEPER discover the collision.
    9–11 Discuss the collision. What just happened, and why is the loser's data file still fine in the heap? Land: the data write is not the transaction. The commit is the transaction, and the log is the serialisation point.
    11–14 Time travel. READER reconstructs the table VERSION AS OF 2 while the current version is 4. Then VERSION AS OF 0. Auditors check both. Note aloud that the reader is holding a past table while writers continue — no locks, no blocking.
    14–17 VACUUM. VACUUM takes a retention parameter called out by the facilitator (RETAIN 0 HOURS) and physically removes from the heap every file not referenced by the current version. Then READER is asked to reconstruct VERSION AS OF 2 again. It fails. Files are gone. Let the READER physically search the heap and not find them. This is the most memorable ten seconds of M4.
    17–20 Debrief. §5. Land the three-line summary.

    5. Debrief questions¶

    1. Before the replay, could anyone say how many rows were in the table? (No. The heap is meaningless without the log. The log is the table; the files are just bytes.)
    2. Why did the losing writer not corrupt anything? (Its data file was written to a new path in the heap, unreferenced by any commit. An unreferenced file is invisible — it is not "bad data in the table", it is not in the table at all. This is why writes can be optimistic: the expensive part is safe to do in parallel and only the cheap part is serialised.)
    3. What did the losing writer have to do? (Re-read the log, determine whether its change actually conflicts — two writers touching different partitions usually do not — and retry at the next version. Optimistic concurrency: assume no conflict, verify at commit, retry if wrong.)
    4. While READER held version 2, did any writer have to wait? (No. Readers never block writers and writers never block readers, because a reader is holding a fixed list of files that nothing will delete — until VACUUM.)
    5. What exactly did VACUUM destroy? (Not data in the current table — that is untouched. It destroyed every past version, i.e. the audit trail, the ability to reproduce a filing (CS-04), and the ability to roll back a corrupted feature (CS-11 R1).)
    6. What would RETAIN 0 HOURS have done to the READER mid-query? (Deleted files the READER was actively reading. This is the sim-vacuum0 failure and it breaks concurrent readers, not just history.)
    7. So what is the right retention? (A governance number set by the longest window over which someone may credibly ask "what did it say then" — the regulatory dispute window, not a storage convenience. And for fixed points like a filing, pin the version rather than relying on a sliding window.)

    6. Answer key¶

    Replay 1 — the file set at each version¶

    Version Commit actions File set after Rows
    0 add part-0000 (200), add part-0001 (200) 0000, 0001 400
    1 add part-0002 (150) 0000, 0001, 0002 550
    2 remove part-0001, add part-0003 (180) 0000, 0002, 0003 530
    3 (WRITER-A wins) add part-0004 (120) 0000, 0002, 0003, 0004 650
    4 (WRITER-B retries) remove part-0000, add part-0005 (210) 0002, 0003, 0004, 0005 660

    Key observations to draw out: - part-0001 still physically exists in the heap after version 2. It was removed from the table, not deleted from storage. That distinction is what makes time travel possible and what VACUUM later erases. - Version 2's file set (0000, 0002, 0003) is fully reconstructible as long as 0000 and 0001's successors survive in the heap. - After VACUUM RETAIN 0 HOURS, only files referenced by version 4 survive: 0002, 0003, 0004, 0005. part-0000 and part-0001 are gone, so versions 0, 1, 2 and 3 are all unreadable — a single command destroyed four versions of history.

    The concurrent-write resolution¶

    WRITER-A WRITER-B
    Read version 2 2
    Data files written to heap part-0004 part-0005
    Commit attempted v3 v3
    Outcome Accepted Rejected — v3 exists
    Retry — Re-read log (now v4 is next). Check conflict: B removes part-0000, A did not touch it → no real conflict. Commit as v4.
    Final Both changes present Both changes present

    If B's change had conflicted — say both removed part-0000 — the retry must fail rather than silently proceed, and the writer's application logic decides what to do. Make this explicit: optimistic concurrency does not mean "everyone wins"; it means "conflicts are detected at commit rather than prevented by a lock."

    The three-line summary (write on the board at the end)¶

    1. The log is the table.        Files are bytes; the log says which bytes count.
2. The commit is the transaction.  Data can be written in parallel; only the
                                   log entry is serialised. That is ACID on a heap.
3. VACUUM is a governance decision. It does not free space from your table;
                                    it deletes your past.

    8. Cohort variants¶

    Small cohort (< 8 participants). Everyone holds a role and the facilitator is LOG-KEEPER (which lets you control the collision timing precisely). Drop the auditor role and instead have each participant, after every phase, write the current file set on a shared sheet — the discipline of writing it down is what the auditors would otherwise provide. Add an extension with the spare time: introduce OPTIMIZE as a sixth role, who removes four small files and adds one large one in a single commit, then ask the READER whether the table's contents changed (they did not — only its layout, which is the exact point of compaction).

    Large cohort (> 20 participants). Run two identical tables in parallel (two logs, two heaps, two full role sets) and give them different VACUUM retentions: table 1 RETAIN 0 HOURS, table 2 RETAIN 168 HOURS. Everyone else audits. At minute 14, ask both READERs to reconstruct version 2 simultaneously — one succeeds, one cannot. The side-by-side failure is far more persuasive than a single demonstration and it makes the retention debate concrete without a single slide. Then run a 4-minute plenary on "what retention would you set for gold.fact_trip, and what for bronze.gps_events, and why are they different?" Duration 26 minutes.
