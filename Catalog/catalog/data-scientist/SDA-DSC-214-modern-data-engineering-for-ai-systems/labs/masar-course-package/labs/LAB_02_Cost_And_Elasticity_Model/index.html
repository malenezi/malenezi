    Field Value

    Day / Hour Day 1, Hour 5

    LO mapping LO2 (primary — compute–storage separation, cost, elasticity, scale), LO1 (reinforced — why the Lakehouse is economically viable), LO7 (contributes — BENCHMARKS.md seed)
    Prerequisites LAB-01 complete (bronze.trips, bronze.gps_events landed); M2 lecture (object storage, Parquet, elasticity spectrum, cost model)
    Checkpoint git tag lab2-start (solution: lab2-solution)

    Scale note. Figures quoted in this document assume the full-scale generator run (--scale 1.0); the shipped sample is --scale 0.15 — 7,230 trips/day over 5 days (36,150 trips), 873,763 GPS pings, 3,450 drivers, 3,864 vehicles, 48 zones. Grains, ratios and file-count reductions hold at either scale; absolute row counts do not.

    Why this lab matters¶

    Masar's ETA model is only retrained if someone approves the compute budget, and the operations dashboard only refreshes every 15 minutes if that refresh is affordable. When the economics of the platform fail, the AI system fails quietly through starvation: history gets truncated to save storage (so the model loses seasonality), retrains are cut from weekly to monthly (so the model drifts), and features are sampled instead of computed (so training and serving diverge). The counter-failure is just as real — an unbounded autoscaling cluster with no idle termination produces a bill that gets the whole platform cancelled in month two. This lab teaches you to defend a Lakehouse in an architecture review with numbers you measured yourself, and to name the layout decisions that turn decoupling from a possibility of savings into realised savings.

    Task 1 — Fill in real prices and cite them (10 min)¶

    Open src/masar/econ/cost_model.py.     # src/masar/econ/cost_model.py
"""Transparent storage-vs-compute cost model for the Masar platform.

All prices are INPUTS; the point is to SEE which axis dominates, and to be
able to defend every number in an architecture review.

Sources (fill in and keep current):
  storage_gb_month : <provider> standard object storage, <region>, list price, read <date>
  core_hour        : <provider> general-purpose 4-core node, <region>, on-demand, read <date>
  spot_discount    : <provider> published spot/preemptible discount range, read <date>
"""
from __future__ import annotations

from dataclasses import dataclass, replace


@dataclass(frozen=True)
class Prices:
    storage_gb_month: float = 0.023      # object storage $/GB-month
    core_hour: float = 0.06              # decoupled compute $/core-hour (on-demand)
    spot_multiplier: float = 0.35        # spot ≈ 65% cheaper than on-demand
    warehouse_core_hour: float = 0.18    # coupled MPP warehouse: node runs 24/7
    warehouse_storage_gb_month: float = 0.21   # storage inside the warehouse node


@dataclass(frozen=True)
class Job:
    """One scheduled workload on the decoupled platform."""
    name: str
    cores: int
    runtime_hours: float
    runs_per_month: int
    spot: bool = False

    def monthly_core_hours(self) -> float:
        return self.cores * self.runtime_hours * self.runs_per_month

    def monthly_compute(self, p: Prices) -> float:
        rate = p.core_hour * (p.spot_multiplier if self.spot else 1.0)
        return self.monthly_core_hours() * rate


def lakehouse_monthly_cost(total_gb: float, jobs: list[Job],
                           p: Prices = Prices()) -> dict[str, float]:
    """Decoupled: pay per byte KEPT and per second of compute that RUNS."""
    storage = total_gb * p.storage_gb_month
    compute = sum(j.monthly_compute(p) for j in jobs)
    total = storage + compute
    return {"storage": round(storage, 2),
            "compute": round(compute, 2),
            "total": round(total, 2),
            "compute_share": round(compute / total, 3)}


def warehouse_monthly_cost(total_gb: float, nodes: int, cores_per_node: int,
                           p: Prices = Prices()) -> dict[str, float]:
    """Coupled: the cluster must be sized for the DATA and runs 24/7.

    Storage and compute cannot be scaled independently, so idle hours are
    billed and retaining history forces you to add compute you do not need.
    """
    hours = 730.0
    compute = nodes * cores_per_node * hours * p.warehouse_core_hour
    storage = total_gb * p.warehouse_storage_gb_month
    total = storage + compute
    return {"storage": round(storage, 2),
            "compute": round(compute, 2),
            "total": round(total, 2),
            "compute_share": round(compute / total, 3),
            "idle_share": round(1 - (0.9 * 30) / hours, 3)}   # ~0.9h of real work/day


def break_even_utilisation(total_gb: float, nodes: int, cores_per_node: int,
                           p: Prices = Prices()) -> float:
    """Monthly decoupled core-hours at which the Lakehouse stops being cheaper.

    Above this many core-hours per month, an always-on coupled cluster of the
    same shape would cost less than paying per second — i.e. the workload is
    steady 24/7 and elasticity buys you nothing.
    """
    wh = warehouse_monthly_cost(total_gb, nodes, cores_per_node, p)
    lakehouse_storage = total_gb * p.storage_gb_month
    budget_for_compute = wh["total"] - lakehouse_storage
    return round(budget_for_compute / p.core_hour, 1)


if __name__ == "__main__":
    prices = Prices()

    # Masar's three scheduled workloads (sizes from the M2 lecture)
    jobs = [
        Job("nightly_elt",           cores=16, runtime_hours=0.33, runs_per_month=30),
        Job("hourly_stream_compact", cores=4,  runtime_hours=0.10, runs_per_month=720),
        Job("weekly_feature_build",  cores=32, runtime_hours=0.50, runs_per_month=4,
            spot=True),
    ]

    TOTAL_GB = 12_000        # 36 months of raw GPS + trips + curated layers

    lh = lakehouse_monthly_cost(TOTAL_GB, jobs, prices)
    wh = warehouse_monthly_cost(TOTAL_GB, nodes=8, cores_per_node=16, p=prices)

    print("lakehouse :", lh)
    print("warehouse :", wh)
    print("saving    : %.1f%%" % (100 * (1 - lh["total"] / wh["total"])))
    print("break-even core-hours/month:",
          break_even_utilisation(TOTAL_GB, 8, 16, prices))
    print("actual core-hours/month    :",
          round(sum(j.monthly_core_hours() for j in jobs), 1))

    # Sensitivity: what if GPS volume doubles (new city)?
    doubled = replace(prices)                       # same prices, more data
    print("2x data   :", lakehouse_monthly_cost(TOTAL_GB * 2, jobs, doubled))

    What to look for: the model has no hidden constants. Every number is either a cited price, a stated data volume, or a job shape you can defend. That property is what lets it survive a review.

    Task 3 — Measure data skipping, do not assume it (10 min)¶

    Complete src/masar/econ/scan_cost.py. The point is to measure bytes and files read, not to trust the physical plan's appearance.

    # src/masar/econ/scan_cost.py
"""Demonstrate that columnar + partitioned reads scan far less data.

The cost of decoupled compute is dominated by BYTES SCANNED, so we
measure it directly rather than trusting intuition.
"""
from __future__ import annotations

import argparse

from pyspark.sql import DataFrame, functions as F

from masar.spark import get_spark

SILVER = "./lakehouse/silver/trips"


def scan_metrics(df: DataFrame) -> dict[str, int]:
    """Execute the plan and read the scan metrics Spark recorded.

    'number of files read' and 'size of files read' come from the file-scan
    node; they are the honest measure of what decoupled compute paid for.
    """
    df.count()                                   # force execution
    plan = df._jdf.queryExecution().executedPlan()
    out: dict[str, int] = {}

    def walk(node) -> None:
        it = node.metrics().iterator()
        while it.hasNext():
            entry = it.next()
            name, metric = entry._1(), entry._2()
            if name in ("numFiles", "filesSize", "numOutputRows"):
                out[name] = out.get(name, 0) + metric.value()
            if "files read" in metric.name().get() or "file" in metric.name().get():
                out[metric.name().get()] = out.get(metric.name().get(), 0) + metric.value()
        kids = node.children().iterator()
        while kids.hasNext():
            walk(kids.next())

    walk(plan)
    return out


def compare_scans(silver_path: str = SILVER) -> None:
    spark = get_spark("scan-cost")
    df_all = spark.read.format("delta").load(silver_path)
    total_cols = len(df_all.columns)

    # A. Naive: every column, filter applied after the scan is planned wide.
    naive = df_all.filter(F.col("city") == "Riyadh")

    # B. Column-pruned: only the 3 columns the question needs.
    pruned = (df_all
              .select("trip_id", "city", "fare_sar")
              .filter(F.col("city") == "Riyadh"))

    # C. Pruned + partition filter + a stats-friendly range predicate.
    #    `city` is the partition column => whole directories are skipped.
    pruned_part = (df_all
                   .select("trip_id", "city", "pickup_ts", "fare_sar")
                   .filter((F.col("city") == "Riyadh")
                           & (F.col("pickup_ts") >= F.lit("2026-06-01"))
                           & (F.col("pickup_ts") <  F.lit("2026-06-02"))))

    for label, q, cols in (("naive full read", naive, total_cols),
                           ("column-pruned", pruned, 3),
                           ("pruned + partition filter", pruned_part, 4)):
        m = scan_metrics(q)
        files = m.get("number of files read", m.get("numFiles", 0))
        size = m.get("size of files read", m.get("filesSize", 0))
        print(f"{label:28s} rows={m.get('numOutputRows', 0):>9,} "
              f"cols={cols:>2}/{total_cols} files={files:>4} "
              f"bytes={size:>12,}")

    print("\n--- physical plan of the pruned query ---")
    pruned.explain("formatted")
    print("\n--- physical plan of the pruned + partition-filtered query ---")
    pruned_part.explain("formatted")


def main() -> None:
    p = argparse.ArgumentParser()
    p.add_argument("path", nargs="?", default=SILVER)
    args = p.parse_args()
    compare_scans(args.path)


if __name__ == "__main__":
    main()

    What to look for in the plan (this is what you paste into your notes as evidence):

    • PartitionFilters: [isnotnull(city#123), (city#123 = Riyadh)] — whole directories skipped, the cheapest possible saving.
    • PushedFilters: [IsNotNull(pickup_ts), GreaterThanOrEqual(pickup_ts,...)] — the predicate reached the Parquet reader, so row groups whose min/max cannot match are never decompressed.
    • ReadSchema: struct<trip_id:string,city:string,fare_sar:double> — three columns, not twenty-six. This is column pruning and it is where most of the byte saving comes from.
    • All three queries return the same Riyadh trip count. Same answer, a fraction of the bytes: that is the entire economic argument for Parquet under a decoupled engine.

Record those numbers instead; the lesson is identical.

    Task 5 — Write the elasticity guardrails and justify them (5 min)¶

    Inspect infra/cluster/masar-elt-cluster.yaml and justify each guardrail in LAB2_NOTES.md:

    # infra/cluster/masar-elt-cluster.yaml
# Ephemeral job cluster: exists only for the ELT run, then dies.
cluster:
  name: masar-elt
  spark_version: "3.5"
  autoscale:
    min_workers: 2
    max_workers: 8          # bounded elasticity: no runaway bill
  autotermination_minutes: 10   # MANDATORY: kill idle compute
  node_type: general-4core
  spot:
    enabled: true           # restartable ELT tolerates preemption
    on_demand_driver: true  # keep the driver stable
  tags:
    cost_center: masar-data-platform
    workload: elt-nightly

    Your rationale must answer, in one line each:

    • Why autotermination_minutes: 10 and not 60 or 0? (What does each extreme cost?)
    • Why max_workers: 8 and not unbounded? (Elasticity without a bound is an unbounded bill; also, past a point the ELT is shuffle-bound, not core-bound.)
    • Why spot for the weekly feature build but on_demand_driver: true? (Losing an executor costs a retried task; losing the driver costs the whole job.)
    • What do the tags buy you? (Unattributed compute is unmanageable; per-workload attribution is how you find the one dashboard costing 40% of the bill.)

    Self-check questions¶

    Q1. You predicted storage would dominate the bill and the model says compute is 30% of a small total while the warehouse's compute is 87% of a large one. Reconcile the two.

    Answer They measure different things. In the decoupled model you pay for compute *only while jobs run* — Masar's three jobs total ~2,100 core-hours/month, so compute is a modest line and storage is the steady floor. In the coupled model the cluster is sized for the **data** and billed 24/7 whether or not work happens, so ~96% of its compute hours are idle and compute swamps everything. The lesson is not "compute is big" or "storage is big" — it is that decoupling converts a fixed cost into a variable one, which is why *elasticity* is the lever.

    Q2. Decoupling moved data to cheap object storage, yet a team's bill went up after migration. Give the two most likely causes and the fix for each.

    Answer (1) Every query full-scans an unpartitioned, uncompacted table, so compute pays to read data a filter could have skipped — fix with partitioning on a low-cardinality column, ZORDER on the common filter columns, and scheduled OPTIMIZE. (2) Autoscaling clusters never idle-terminate, so "elastic" compute is running 24/7 anyway — fix with `autotermination_minutes` and bounded `max_workers`, plus spot for restartable jobs. Decoupling *enables* savings; layout and elasticity discipline *realise* them.

    Q3. Why does partitioning by city help the scan benchmark, and why would partitioning by trip_id hurt it catastrophically?

    Answer `city` has ~5 distinct values, so each partition is a directory containing large files; a `city = 'Riyadh'` filter eliminates whole directories before any file is opened (`PartitionFilters`). `trip_id` is a unique key: partitioning by it produces one tiny file per trip — millions of objects. Listing dominates the job, per-file overhead dwarfs the data, and no filter can skip anything useful. That is the small-files problem, and it makes object storage both slow *and* expensive (Module 4 fixes it with OPTIMIZE).

    Q4. Masar adds a new city and daily GPS volume doubles. Which line item grows, by how much, and does the compute/storage balance shift?

    Answer Storage roughly doubles (it is linear in bytes kept): in the model, $276 → $552/month. Compute does **not** double automatically — it grows only with the additional runtime needed to process the extra rows, which is sublinear if the cluster is already parallel and the layout supports skipping. So `compute_share` falls (0.30 → 0.18 in the shipped example), and the platform gets relatively *more* storage-weighted as it scales. This is the argument for retaining raw history: the marginal cost of keeping more is small compared with the option value of reprocessing.

    Q5. When is a coupled warehouse still the right architectural call for Masar?

    Answer When the workload is small, structured, steady and latency-critical with high concurrency — e.g. a sub-second, hundreds-of-concurrent-users operational dashboard over a few GB. There, the always-on cost is small in absolute terms, the elasticity has nothing to exploit (utilisation is near break-even), and the warehouse's coupled storage gives lower latency than fetching objects over the network. The honest position in a review is: decoupling wins for the AI/analytics estate; a small serving-tier warehouse or cache in front of gold can still be justified — provided it is a *cache*, not a second source of truth (that would recreate the M1 two-tier problem).

    Q6. Your break-even calculation says the Lakehouse loses above ~318,000 core-hours/month. A colleague says "then we should just make our jobs bigger to get closer to break-even." What is wrong with that reasoning?

    Answer Break-even is a *comparison point*, not a target. Consuming more core-hours does not create value; it just raises the bill until the alternative architecture would have been equally bad. The correct reading is a risk statement: Masar operates at under 1% of break-even utilisation, so there is enormous headroom to add workloads (more retrains, more backfills, more ad-hoc analysis) before the economics would favour a coupled system. That headroom is precisely what lets the AI team retrain weekly instead of monthly.
