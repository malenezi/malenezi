    LAB 04 — Delta Lake: ACID, MERGE, Time Travel, Maintenance¶

    Field Value

    Module M4 — Delta Lake and ACID Transactions
    Day / Hour Day 3, Hour 2 (Lab 4a) and Day 3, Hour 4 (Lab 4b), wrapped in Hour 5
    Duration 90 minutes total — 4a: 25 min, 4b: 65 min (10–15% theory / 85–90% lab), pairs
    Difficulty Intermediate–Advanced
    LO mapping LO4 (primary — Delta tables, ACID, schema enforcement), LO6 (secondary — audit trail, PDPL erasure, retention governance), LO2 (reinforced — small-files cost), LO7 (contributes — the hardened silver node)
    Prerequisites LAB-03 complete (silver.trips built by dbt, 42,038 rows, all tests passing); M4 lecture (transaction log, OCC, MERGE, time travel, OPTIMIZE/ZORDER/VACUUM)
    Checkpoint git tags lab4-start (4a), lab4b-start (4b) · solutions: lab4a-solution, lab4-solution
    Deliverable silver.trips as a constrained Delta table with positive_fare and valid_duration CHECK constraints; an idempotent MERGE proven twice; a time-travel audit diff; a demonstrated PDPL erasure; OPTIMIZE/ZORDER/VACUUM run with before/after numFiles; LAB4_NOTES.md with the retention justification and the filled benchmark table

    Scale note. Figures quoted in this document assume the full-scale generator run (--scale 1.0); the shipped sample is --scale 0.15 — 7,230 trips/day over 5 days (36,150 trips), 873,763 GPS pings, 3,450 drivers, 3,864 vehicles, 48 zones. Grains, ratios and file-count reductions hold at either scale; absolute row counts do not.

    Why this lab matters¶

    silver.trips is written by a nightly dbt job, corrected by ad-hoc upserts, read by the ETA model's training run and by the operations dashboard — sometimes at the same moment. Without a transaction layer, a reader that arrives mid-write sees a half-written table, and the AI system trains on a state that never existed. Delta's log makes that impossible, and it buys three more things Masar cannot operate without: schema enforcement, so a source that starts sending fare_sar as a string fails loudly instead of poisoning the feature table; time travel, so a disputed report can be recomputed from the exact table state it was filed from; and MERGE, so a PDPL erasure request is an atomic, auditable commit rather than a rewrite-and-pray. This lab also confronts the tension you will actually have to defend in a governance review: aggressive VACUUM saves storage but destroys the audit trail, while conservative VACUUM preserves history and can retain data an erasure was supposed to remove. There is no universal right answer — only a documented, defensible one, and you will write yours.

    Part 4a — Enforcement and the transaction log (25 min)¶

    Task 1 — Add constraints and read the log aloud (15 min)¶

    Complete src/masar/delta/create_silver.py:

    # src/masar/delta/create_silver.py
"""Harden silver.trips into a self-validating Delta table.

Partitioning is chosen to AVOID the small-files trap: `city` has 5 values,
not 42,038. Constraints are checked on EVERY future write, so the table
defends its own contract without a downstream job having to remember to.
"""
from __future__ import annotations

from masar.spark import get_spark

SILVER = "./lakehouse/silver/trips"

CONSTRAINTS = {
    "positive_fare":  "fare_sar > 0",
    "valid_duration": "dropoff_ts > pickup_ts",
    "known_city":     "city IN ('Riyadh','Jeddah','Dammam','Mecca','Medina')",
}


def create_silver_trips(staged_df) -> None:
    """Only needed if silver.trips does not already exist (dbt normally builds it)."""
    (staged_df.write
        .format("delta")
        .partitionBy("city")            # low-cardinality: 5 cities, not trip_id
        .mode("overwrite")
        .option("overwriteSchema", "true")
        .save(SILVER))


def add_constraints() -> None:
    """Constraints apply to FUTURE writes; existing rows must already comply."""
    spark = get_spark("delta-constraints")
    for name, expr in CONSTRAINTS.items():
        # violating rows must be cleaned first, or the ALTER is rejected
        bad = spark.sql(
            f"SELECT count(*) AS n FROM delta.`{SILVER}` WHERE NOT ({expr})"
        ).first()["n"]
        if bad:
            print(f"[skip] {name}: {bad:,} existing rows violate `{expr}` — clean first")
            continue
        spark.sql(
            f"ALTER TABLE delta.`{SILVER}` ADD CONSTRAINT {name} CHECK ({expr})"
        )
        print(f"[ok]   {name}: CHECK ({expr})")


def show_properties() -> None:
    spark = get_spark("delta-constraints")
    spark.sql(f"SHOW TBLPROPERTIES delta.`{SILVER}`").show(truncate=False)


if __name__ == "__main__":
    add_constraints()
    show_properties()

    ls -1 lakehouse/silver/trips/_delta_log/
python -m json.tool < lakehouse/silver/trips/_delta_log/00000000000000000000.json | head -60

    Read aloud to your pair, naming each action:

    • {"protocol": {...}} — the reader/writer versions required to understand this table.
    • {"metaData": {..., "schemaString": "...", "partitionColumns": ["city"], "configuration": {"delta.constraints.positive_fare": "fare_sar > 0"}}} — the schema is metadata in the log; so are your constraints.
    • {"add": {"path": "city=Riyadh/part-00000-....snappy.parquet", "size": 984213, "stats": "{\"numRecords\":18418,\"minValues\":{...},\"maxValues\":{...}}"}} — a file added by this commit, with its min/max statistics. Those statistics are exactly what powered the data skipping you measured in Lab 2.
    • {"remove": {...}} in a later commit — a file logically deleted (tombstoned). The bytes are still on disk until VACUUM.
    • {"commitInfo": {"operation": "MERGE", "operationMetrics": {...}}} — the audit record.

    The insight to state out loud: the current table state is not a directory listing — it is the replay of the log. That is why a half-written set of Parquet files is invisible (atomicity), why a reader is pinned to one version (snapshot isolation), and why hand-copying a Parquet file into the directory corrupts nothing except your own understanding — Delta will simply ignore it, because it is not in the log.

    Task 2 — Prove enforcement rejects bad writes (10 min)¶

    Two negative tests. Both must fail; capture the exact error text in LAB4_NOTES.md.

    # run as: python - <<'PY' ... PY
from pyspark.sql import functions as F
from masar.spark import get_spark

spark = get_spark("negative-tests")
SILVER = "./lakehouse/silver/trips"
good = spark.read.format("delta").load(SILVER).limit(1)

# --- Test A: CHECK constraint violation (negative fare) ---
bad_fare = good.withColumn("trip_id", F.lit("trp_BADFARE")) \
               .withColumn("fare_sar", F.lit(-5.0))
try:
    bad_fare.write.format("delta").mode("append").save(SILVER)
    print("FAIL: the constraint did not fire")
except Exception as e:
    print("PASS (constraint):", str(e).splitlines()[0])

# --- Test B: schema enforcement (wrong type) ---
bad_type = good.withColumn("trip_id", F.lit("trp_BADTYPE")) \
               .withColumn("fare_sar", F.lit("forty-two"))     # string, not double
try:
    bad_type.write.format("delta").mode("append").save(SILVER)
    print("FAIL: schema enforcement did not fire")
except Exception as e:
    print("PASS (schema):", str(e).splitlines()[0])

# --- Test C: what mergeSchema would have done (DO NOT leave this enabled) ---
extra = good.withColumn("trip_id", F.lit("trp_NEWCOL")) \
            .withColumn("driver_mood", F.lit("cheerful"))
try:
    extra.write.format("delta").mode("append").save(SILVER)
    print("FAIL: a new column was accepted without mergeSchema")
except Exception as e:
    print("PASS (new column rejected):", str(e).splitlines()[0])
print("row count unchanged:", spark.read.format("delta").load(SILVER).count())

    What to look for: all three rejected, and the row count is unchanged — the rejected writes left no partial data behind. That is atomicity: there is no such thing as a half-applied Delta write.

    Discuss with your pair: enforcement is the default and evolution is opt-in. mergeSchema / on_schema_change='append_new_columns' exists for changes you decide; the log records them as metadata commits so an auditor can see when the contract changed and who changed it. A schema surprise is a bug; a schema change is a reviewed event.

    Task 3 — Idempotent MERGE upserts (20 min)¶

    Complete src/masar/delta/merge_ops.py:

    # src/masar/delta/merge_ops.py
"""Upsert corrected trips and apply a PDPL right-to-erasure delete.

Both are atomic Delta commits: auditable, retryable, isolated from readers.
"""
from __future__ import annotations

import argparse
import json

from delta.tables import DeltaTable
from pyspark.sql import DataFrame, functions as F

from masar.spark import get_spark

SILVER = "./lakehouse/silver/trips"


def load_corrections(path: str) -> DataFrame:
    """Corrections arrive with the silver grain: one row per corrected trip_id."""
    spark = get_spark("merge-ops")
    target_schema = spark.read.format("delta").load(SILVER).schema
    return (spark.read
            .option("header", True)
            .schema(target_schema)          # enforce the contract on the SOURCE too
            .csv(path))


def upsert_corrections(corrections_df: DataFrame) -> None:
    """MERGE keyed on trip_id => re-running is a no-op (idempotent).

    whenMatchedUpdateAll is safe here ONLY because the source has exactly the
    target schema and exactly one row per key. Both are checked above.
    """
    spark = get_spark("merge-ops")
    dupes = (corrections_df.groupBy("trip_id").count()
             .filter("count > 1").count())
    if dupes:
        raise ValueError(f"{dupes} duplicate trip_id in corrections: MERGE would be ambiguous")

    target = DeltaTable.forPath(spark, SILVER)
    (target.alias("t")
        .merge(corrections_df.alias("s"), "t.trip_id = s.trip_id")
        .whenMatchedUpdateAll()
        .whenNotMatchedInsertAll()
        .execute())

    metrics = (spark.sql(f"DESCRIBE HISTORY delta.`{SILVER}` LIMIT 1")
               .select("version", "operation", "operationMetrics").first())
    m = metrics["operationMetrics"]
    print(f"v{metrics['version']} {metrics['operation']}  "
          f"matched={m.get('numTargetRowsMatchedUpdated', m.get('numTargetRowsUpdated'))} "
          f"inserted={m.get('numTargetRowsInserted')} "
          f"updated={m.get('numTargetRowsUpdated')}")


def erase_rider(rider_id: str) -> None:
    """PDPL right to erasure: remove a data subject's rows. Atomic, logged commit.

    Physical removal from history completes at the next VACUUM past retention.
    """
    spark = get_spark("merge-ops")
    target = DeltaTable.forPath(spark, SILVER)
    before = spark.read.format("delta").load(SILVER) \
                  .filter(F.col("rider_id") == rider_id).count()
    target.delete(F.col("rider_id") == rider_id)
    after = spark.read.format("delta").load(SILVER) \
                 .filter(F.col("rider_id") == rider_id).count()
    print(f"erasure committed for {rider_id}: {before} rows removed, {after} remain "
          f"in the CURRENT version; run VACUUM past retention to purge history")


def main() -> None:
    p = argparse.ArgumentParser()
    p.add_argument("--corrections", help="path to a corrections CSV")
    p.add_argument("--erase-request", help="path to a PDPL erasure request JSON")
    args = p.parse_args()

    if args.corrections:
        upsert_corrections(load_corrections(args.corrections))
    if args.erase_request:
        with open(args.erase_request) as fh:
            req = json.load(fh)
        erase_rider(req["rider_id"])


if __name__ == "__main__":
    main()

    Task 4 — Time travel: audit and recovery (10 min)¶

    # src/masar/delta/time_travel.py
"""Read a past table state for audit or to reproduce a model's training set."""
from __future__ import annotations

import argparse

from pyspark.sql import DataFrame, functions as F

from masar.spark import get_spark

SILVER = "./lakehouse/silver/trips"


def history(limit: int = 20) -> None:
    spark = get_spark("time-travel")
    (spark.sql(f"DESCRIBE HISTORY delta.`{SILVER}` LIMIT {limit}")
          .select("version", "timestamp", "operation", "operationMetrics")
          .show(truncate=False))


def as_of_version(v: int) -> DataFrame:
    spark = get_spark("time-travel")
    return (spark.read.format("delta").option("versionAsOf", v).load(SILVER))


def as_of_date(ts: str) -> DataFrame:
    spark = get_spark("time-travel")
    return (spark.read.format("delta").option("timestampAsOf", ts).load(SILVER))


def diff_versions(v_old: int, v_new: int, key: str = "trip_id",
                  col: str = "fare_sar") -> None:
    """Which rows changed between two versions, and by how much?"""
    old = as_of_version(v_old).select(key, F.col(col).alias(f"{col}_old"))
    new = as_of_version(v_new).select(key, F.col(col).alias(f"{col}_new"))
    (old.join(new, key)
        .filter(F.col(f"{col}_old") != F.col(f"{col}_new"))
        .withColumn("delta", F.round(F.col(f"{col}_new") - F.col(f"{col}_old"), 2))
        .show(truncate=False))


def restore(v: int) -> None:
    spark = get_spark("time-travel")
    spark.sql(f"RESTORE TABLE delta.`{SILVER}` TO VERSION AS OF {v}")
    print(f"restored to v{v}; note this creates a NEW version, it does not erase history")


def main() -> None:
    p = argparse.ArgumentParser()
    p.add_argument("--history", action="store_true")
    p.add_argument("--version", type=int)
    p.add_argument("--timestamp")
    p.add_argument("--diff", nargs=2, type=int, metavar=("OLD", "NEW"))
    p.add_argument("--restore", type=int)
    a = p.parse_args()

    if a.history:
        history()
    if a.version is not None:
        print("rows at v%d: %d" % (a.version, as_of_version(a.version).count()))
    if a.timestamp:
        print("rows at %s: %d" % (a.timestamp, as_of_date(a.timestamp).count()))
    if a.diff:
        diff_versions(*a.diff)
    if a.restore is not None:
        restore(a.restore)


if __name__ == "__main__":
    main()

    Or in SQL, which is the form an auditor will ask for:

    SELECT count(*) FROM delta.`./lakehouse/silver/trips` VERSION AS OF 2;
SELECT count(*) FROM delta.`./lakehouse/silver/trips` TIMESTAMP AS OF '2026-06-15 00:00:00';

    What to look for: RESTORE does not rewind history — it appends a new commit whose state equals the old one. The audit trail is append-only, which is precisely what makes it trustworthy: you cannot quietly un-happen a bad MERGE, you can only record the correction.

    Task 6 — OPTIMIZE, ZORDER, VACUUM (15 min)¶

    -- src/masar/delta/maintain.sql  (run on a schedule, e.g. nightly)

-- 0) Baseline: record numFiles and sizeInBytes BEFORE anything.
DESCRIBE DETAIL delta.`./lakehouse/silver/trips`;

-- 1) Compact small files and cluster by the columns queries filter on.
--    ZORDER co-locates related rows so min/max stats prune more aggressively.
OPTIMIZE delta.`./lakehouse/silver/trips`
  ZORDER BY (city, pickup_ts);

-- 2) Verify: file count should drop sharply, average file size should rise.
DESCRIBE DETAIL delta.`./lakehouse/silver/trips`;

-- 3) Reclaim storage older than the retention window.
--    RETENTION IS A GOVERNANCE DECISION: 168h keeps 7 days of time travel.
--    Do NOT set 0 hours: it destroys audit history and can break concurrent readers.
VACUUM delta.`./lakehouse/silver/trips` RETAIN 168 HOURS;

-- 4) What WOULD be deleted, without deleting it (always run this first in prod):
VACUUM delta.`./lakehouse/silver/trips` RETAIN 168 HOURS DRY RUN;

import time
from masar.spark import get_spark
spark = get_spark("maintenance")
P = "./lakehouse/silver/trips"

def detail(tag):
    d = spark.sql(f"DESCRIBE DETAIL delta.`{P}`").first()
    print(f"{tag:8s} numFiles={d['numFiles']:>4}  sizeMB={d['sizeInBytes']/1048576:7.1f}"
          f"  avgFileKB={d['sizeInBytes']/max(d['numFiles'],1)/1024:8.1f}")

def timed_query(tag):
    t = time.time()
    n = spark.sql(f"""SELECT count(*) FROM delta.`{P}`

    Self-check questions¶

    Q1. A concurrent reader starts a query at version 5 while a MERGE commits version 6. What does the reader see, and what mechanism guarantees it?

    Answer The reader sees the complete, consistent state of version 5 for the whole query — snapshot isolation. Delta resolves the file list once, from the log up to version 5, and reads exactly those Parquet files. Version 6's commit adds new files and tombstones old ones in the log, but does not delete bytes, so the reader's files remain readable. The danger is VACUUM: if it physically removes those tombstoned files while the query is still running, the reader fails with a `FileNotFoundException`. That is the concurrency half of why `RETAIN 0 HOURS` is blocked.

    Q2. Your second MERGE run reported updated = 0 but still created a new version in the history. Is idempotency broken?

    Answer No. Idempotency is a property of the resulting **table state**, not of the commit count. The second MERGE evaluated the same source against the same target, found every row already equal, and wrote a commit that changed no data. A consumer reading version *n* and version *n+1* gets identical results. If you need commit-level idempotency too (for example to avoid triggering a downstream change-data-feed), guard the operation with a source-batch marker so a repeated batch is skipped entirely.

    Q3. Why is partitioning by city right here, and partitioning by trip_id catastrophic?

    Answer `city` has five values, so each partition holds thousands of rows in a handful of large files, and a `city = 'Riyadh'` predicate eliminates whole directories before any file is opened. `trip_id` is unique, so partitioning by it creates one directory and one tiny file per trip — 42,038 objects here, hundreds of millions in production. Listing dominates every job, per-file metadata dwarfs the data, no filter can skip usefully, and OPTIMIZE cannot merge across partition boundaries. It converts a cheap decoupled read into an expensive one — the exact failure Module 2 warned about, self-inflicted at the table layer.

    Q4. A regulator asks what silver.trips contained on 1 June. Under what conditions can Delta answer, and what would make the answer impossible?

    Answer Delta answers with `TIMESTAMP AS OF '2026-06-01'` provided (a) the commits from that date are still in `_delta_log` (log retention, default 30 days, `delta.logRetentionDuration`) and (b) the Parquet files those commits reference have not been physically removed by VACUUM (`delta.deletedFileRetentionDuration`, default 7 days). A short VACUUM retention, or a log cleanup shorter than the audit window, makes the answer impossible — the query fails rather than returning wrong data, which is the correct failure mode but no help to the regulator. The operational habit that prevents the problem is pinning and recording the table version used for every filing.

    Q5. You erased a rider from silver.trips. Name at least three places their data still exists and what your runbook must do about each.

    Answer (1) Delta time-travel history and tombstoned files under `lakehouse/silver/trips` — removed by VACUUM once past retention; the erasure is only complete after that runs. (2) `bronze.trips`, which is immutable and append-only — the runbook must either apply a documented exception (bronze is the ledger, protected by access control and its own retention policy) or run a scoped delete against bronze as a deliberate, logged exception to immutability. (3) Downstream gold and feature tables (`gold.trip_features`, `gold.eta_features`) and the Redis online store, which must be rebuilt or key-deleted. Plus any exported reports and dbt test artefacts. An erasure that touches one table is not an erasure — this is why the classification and retention job in Module 6 is a platform-level control, not a per-table script.

    Q6. OPTIMIZE cut numFiles from 214 to 9 and the filtered read from 1.9 s to 0.4 s. Which part of that improvement is compaction and which is ZORDER, and how would you separate them?

    Answer Compaction removes per-file overhead: 214 file opens, 214 footer reads and 214 task launches collapse into 9. ZORDER changes *which* files a predicate can skip, by co-locating rows with similar `city` and `pickup_ts` so each file's min/max range is narrow. Separate them by running `OPTIMIZE` with no `ZORDER BY` on a copy of the table, measuring, then running `OPTIMIZE ... ZORDER BY (city, pickup_ts)` and measuring again. On a small single-day sample most of the win is compaction; at production scale, with months of data and selective predicates, ZORDER is usually the larger term because it multiplies the effect of the file statistics you saw in the log's `add` actions.

    Troubleshooting¶

    Symptom Cause Fix
    ConcurrentModificationException / ConcurrentAppendException Two writers hit optimistic-concurrency conflict on the same files Retry the commit; narrow each writer to disjoint partitions (city) so their file sets do not overlap; discuss OCC — no corruption occurred
    VACUUM removes nothing All tombstoned files are still inside the retention window Expected. Explain the default 7-day safety; use DRY RUN to see what would go, and re-run after the window passes
    VACUUM RETAIN 0 HOURS blocked Delta's retentionDurationCheck safety Keep the check enabled. If a demo needs it, disable it on a throwaway copy only, never on silver.trips and never in production
    Constraint not enforced / ALTER TABLE fails Rows violating the predicate already exist Constraints validate future writes and are rejected if current data violates them — clean or quarantine the offending rows first (create_silver.py reports the count)
    Millions of tiny files Partitioned by a high-cardinality column, or a streaming sink with no maintenance Repartition by city; schedule OPTIMIZE as a nightly task, not as an incident response
    MERGE fails: Cannot perform Merge as multiple source rows matched ... the same target row The corrections source has duplicate trip_ids Deduplicate the source first (merge_ops.py raises on this deliberately); decide which version wins by an explicit ordering, never arbitrarily
    Time travel fails: Cannot time travel Delta table to version 2 The log was cleaned (delta.logRetentionDuration) or the files were vacuumed Nothing recovers it. Set delta.logRetentionDuration ≥ your audit window and delta.deletedFileRetentionDuration to match, before you need them
    RESTORE appears to do nothing You restored to the version you are already on, or read the table by a stale cached snapshot Check DESCRIBE HISTORY — RESTORE writes a new version; call spark.catalog.refreshTable("silver.trips") if you cached it
    Erasure "succeeded" but the rider still appears in a dashboard Gold/feature tables and the online store were not rebuilt Erasure is a platform operation: re-run the gold models and purge the Redis keys; this is exactly why the runbook in GOVERNANCE.md is a capstone deliverable
    numFiles did not drop after OPTIMIZE Files were already at target size, or the table is tiny Check the metrics map returned by OPTIMIZE (numFilesAdded / numFilesRemoved); on a sample table run several MERGE cycles first to create the small files
    Filtered read got slower after ZORDER ZORDER on columns nobody filters on, or the sample is too small for clustering to matter ZORDER only the columns that appear in real predicates (city, pickup_ts); measure with the Lab 2 scan-metrics helper, not by intuition
    DESCRIBE DETAIL shows format: parquet, not delta Someone wrote raw Parquet into the table directory, or the path is wrong Never write non-Delta files under a Delta path — the log will not see them and the table's view of reality diverges. Rebuild from Lab 3
    Every write is rejected after adding known_city The data contains a city outside the constraint list (e.g. trailing whitespace, riyadh lowercase) This is the constraint doing its job — fix the staging normalisation (initcap(trim(city))) rather than dropping the constraint
