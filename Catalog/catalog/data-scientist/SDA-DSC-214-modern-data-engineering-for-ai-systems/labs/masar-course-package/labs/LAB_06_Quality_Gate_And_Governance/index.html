    LAB 06 — Quality Gate And Governance¶

    Field Value

    Scale note. Figures quoted in this document assume the full-scale generator run (--scale 1.0); the shipped sample is --scale 0.15 — 7,230 trips/day over 5 days (36,150 trips), 873,763 GPS pings, 3,450 drivers, 3,864 vehicles, 48 zones.     1. Why this lab matters¶

    The course question: "What happens to Masar's AI system if THIS part of the data platform fails?"

    Lab 5 proved the pipeline moves data without losing or duplicating it. That guarantees delivery, not truth. A pipeline can be flawlessly exactly-once and still deliver 48,200 rows of nonsense on time, every time.

    The ETA model is trained on silver.trips and silver.vehicle_positions. It has no way to know whether a duration_min of -14 is a bug or a fact; it will fit a curve through it. It has no way to know that on 12 June the fare_sar column silently changed units. It will learn whatever you promote.

    If this fails… The AI system experiences…
    No gate at promotion 40 rows with null trip_id reach silver.trips. The MERGE key is null, so the incremental model's WHEN MATCHED never matches and every subsequent run re-inserts them. By Friday the fact table has 280 phantom trips and the driver-daily mart under-reports utilisation.
    Alert-only gate ("we emailed someone") 120 negative fares reach gold.eta_features via silver.trips. historical_route_duration is computed from trips including the corrupt ones. Nobody reads the email. The model degrades by 6% and the investigation starts three weeks later.
    Fail-fast applied too broadly The whole 48,200-row batch is blocked because 120 fares are negative. silver.trips goes stale. The morning BI dashboard shows yesterday. The ETA model retrains on a gap. You have converted a 0.25% data problem into a 100% availability outage.
    No distribution monitoring The producer_version = "2.5.0" m/s incident from Lab 5 passes every schema check and every range check, because m/s values are valid doubles inside a plausible range. rolling_avg_speed_10m drops silently. Only a drift check on the mean sees it.
    No PDPL retention Precise lat/lon for identifiable riders accumulates in bronze indefinitely. There is no lawful basis for keeping it past its purpose, no mechanism to honour an erasure request, and the platform is one audit away from a finding.

    The line to hold in this lab: a quality gate is a decision, not an alarm. An alarm that fires while bad data still flows past it is worse than no alarm, because it manufactures the belief that someone is watching.

    3. Tasks¶

    Task 1 — The suite: silver.trips as executable contract (10 min)¶

    Every expectation below maps to one level of the quality pyramid and carries a response class — FAIL_FAST or QUARANTINE. Writing the response class into the suite metadata is what makes the gate in Task 2 a decision rather than a print statement.

    # quality/suites/silver_trips_suite.py
"""The silver.trips data contract, expressed as executable expectations.

Column set is EXACTLY data/raw/trips_YYYY-MM-DD.csv conformed to silver:
  trip_id, rider_id, driver_id, vehicle_id, city, pickup_zone_id,
  dropoff_zone_id, pickup_ts, dropoff_ts, distance_km, duration_min,
  fare_sar, surge_multiplier, payment_type, status, dropoff_geohash

Every expectation carries meta.response_class, consumed by masar.quality.gate:
  FAIL_FAST  -> integrity. Promoting anything is worse than promoting nothing.
  QUARANTINE -> partial. Isolate the bad rows, promote the good ones, alert.
"""
from __future__ import annotations
import great_expectations as gx

SUITE_NAME = "silver_trips.contract"
KSA_CITIES = ["Riyadh", "Jeddah", "Dammam", "Mecca", "Medina"]
TRIP_STATUS = ["completed", "cancelled_rider", "cancelled_driver", "no_show"]
PAYMENT_TYPES = ["mada", "credit_card", "apple_pay", "cash", "wallet"]

FAIL_FAST = {"response_class": "FAIL_FAST"}
QUARANTINE = {"response_class": "QUARANTINE"}


def build_suite(context) -> None:
    suite = context.add_or_update_expectation_suite(SUITE_NAME)
    validator = context.get_validator(
        batch_request=(context.get_datasource("masar_lakehouse")
                       .get_asset("silver_trips")
                       .build_batch_request()),
        expectation_suite=suite,
    )

    # ---- Level 1: schema -------------------------------------------- FAIL_FAST
    validator.expect_table_columns_to_match_set(
        column_set=["trip_id", "rider_id", "driver_id", "vehicle_id", "city",
                    "pickup_zone_id", "dropoff_zone_id", "pickup_ts", "dropoff_ts",
                    "distance_km", "duration_min", "fare_sar", "surge_multiplier",
                    "payment_type", "status", "dropoff_geohash"],
        exact_match=False, meta=FAIL_FAST)
    validator.expect_column_values_to_be_of_type("fare_sar", "DoubleType", meta=FAIL_FAST)
    validator.expect_column_values_to_be_of_type("pickup_ts", "TimestampType", meta=FAIL_FAST)

    # ---- Level 2: key integrity ------------------------------------- FAIL_FAST
    validator.expect_column_values_to_not_be_null("trip_id", meta=FAIL_FAST)
    validator.expect_column_values_to_be_unique("trip_id", meta=FAIL_FAST)
    validator.expect_column_values_to_not_be_null("pickup_ts", meta=FAIL_FAST)

    # ---- Level 3: value constraints --------------------------------- QUARANTINE
    validator.expect_column_values_to_be_between(
        "fare_sar", min_value=0, strict_min=True, max_value=5000, meta=QUARANTINE)
    validator.expect_column_values_to_be_between(
        "duration_min", min_value=0, strict_min=True, max_value=600, meta=QUARANTINE)
    validator.expect_column_values_to_be_between(
        "distance_km", min_value=0, strict_min=True, max_value=400, meta=QUARANTINE)
    validator.expect_column_values_to_be_between(
        "surge_multiplier", min_value=1.0, max_value=5.0, meta=QUARANTINE)
    validator.expect_column_values_to_be_in_set("city", KSA_CITIES, meta=QUARANTINE)
    validator.expect_column_values_to_be_in_set("status", TRIP_STATUS, meta=QUARANTINE)
    validator.expect_column_values_to_be_in_set("payment_type", PAYMENT_TYPES, meta=QUARANTINE)
    validator.expect_column_pair_values_A_to_be_greater_than_B(
        "dropoff_ts", "pickup_ts", or_equal=False, meta=QUARANTINE)

    # Known 3.1% null rate: tolerated, monitored, NOT silently accepted.
    validator.expect_column_values_to_not_be_null(
        "dropoff_geohash", mostly=0.95, meta=QUARANTINE)

    # ---- Level 4: distribution -------------------------- QUARANTINE (scheduled)
    # Baseline FROZEN from a known-good period (2026-05-01..2026-05-31).
    # Never recompute a baseline from the batch you are validating.
    validator.expect_column_mean_to_be_between(
        "fare_sar", min_value=28.0, max_value=52.0, meta=QUARANTINE)
    validator.expect_column_median_to_be_between(
        "duration_min", min_value=9.0, max_value=26.0, meta=QUARANTINE)

    validator.save_expectation_suite(discard_failed_expectations=False)
    print(f"[gx] saved suite {SUITE_NAME} with "
          f"{len(suite.expectations)} expectations")


if __name__ == "__main__":
    build_suite(gx.get_context(context_root_dir="./quality/gx"))

    Now write the companion suite for the streaming table from Lab 5. It is shorter but carries the check that a schema validator can never make:

    # quality/suites/gps_events_suite.py
"""Contract for bronze.gps_events / silver.vehicle_positions.

The point of interest is the LAST expectation. producer_version 2.5.0 emits
speed_kmh in m/s: same key, same type, wrong unit. No schema or range rule can
see it. Only a per-version distribution comparison can.
"""
import great_expectations as gx

SUITE_NAME = "gps_events.contract"
FAIL_FAST = {"response_class": "FAIL_FAST"}
QUARANTINE = {"response_class": "QUARANTINE"}


def build_suite(context) -> None:
    suite = context.add_or_update_expectation_suite(SUITE_NAME)
    v = context.get_validator(
        batch_request=(context.get_datasource("masar_lakehouse")
                       .get_asset("silver_vehicle_positions").build_batch_request()),
        expectation_suite=suite)

    v.expect_column_values_to_not_be_null("event_id", meta=FAIL_FAST)
    v.expect_column_values_to_be_unique("event_id", meta=FAIL_FAST)
    v.expect_column_values_to_not_be_null("event_ts", meta=FAIL_FAST)
    v.expect_column_values_to_be_between("lat", 16.0, 33.0, meta=QUARANTINE)   # KSA bounds
    v.expect_column_values_to_be_between("lon", 34.0, 56.0, meta=QUARANTINE)
    v.expect_column_values_to_be_between("accuracy_m", 0, 50, meta=QUARANTINE)
    v.expect_column_values_to_be_between("heading_deg", 0, 360, meta=QUARANTINE)
    v.expect_column_values_to_be_in_set("producer_version", ["2.4.0", "2.5.0"], meta=QUARANTINE)

    # A hard range rule passes on m/s values (8.7 is a valid "km/h").
    # This mean check is the ONLY rule that catches the semantic drift.
    v.expect_column_mean_to_be_between("speed_kmh", 24.0, 46.0, meta=QUARANTINE)

    v.save_expectation_suite(discard_failed_expectations=False)


if __name__ == "__main__":
    build_suite(gx.get_context(context_root_dir="./quality/gx"))

    Task 2 — The gate that acts: fail-fast and quarantine (14 min)¶

    The starter src/masar/quality/gate.py ships with deliberate mistake #1 — it alerts and promotes anyway. Replace it.

    # src/masar/quality/gate.py
"""Quality gate at the bronze -> silver promotion boundary.

Three outcomes, decided by the response_class in each expectation's meta:

  FAIL_FAST  failed  -> raise. Nothing is promoted. The batch is blocked.
  QUARANTINE failed  -> split. Bad rows -> silver.trips_quarantine (with the
                        reason), good rows -> silver.trips. Alert either way.
  all passed         -> promote everything. Alert nothing.

The gate never promotes a row it could not justify, and never blocks a batch
for a fault it could isolate.
"""
from __future__ import annotations
from dataclasses import dataclass
from pyspark.sql import DataFrame, functions as F
from masar.spark import get_spark

SILVER = "./lakehouse/silver/trips"
QUARANTINE = "./lakehouse/silver/trips_quarantine"

KSA_CITIES = ["Riyadh", "Jeddah", "Dammam", "Mecca", "Medina"]
TRIP_STATUS = ["completed", "cancelled_rider", "cancelled_driver", "no_show"]


class GateBlocked(RuntimeError):
    """Raised on FAIL_FAST. The DAG task fails; nothing is promoted."""


@dataclass
class GateResult:
    promoted: int
    quarantined: int
    blocked: bool
    reasons: dict


def _failed_by_class(gx_result, response_class: str) -> list[str]:
    """Return expectation ids that FAILED and carry this response_class."""
    return [
        r["expectation_config"]["kwargs"].get("column", "<table>")
        + ":" + r["expectation_config"]["expectation_type"]
        for r in gx_result["results"]
        if not r["success"]
        and r["expectation_config"]["meta"].get("response_class") == response_class
    ]


# One predicate per QUARANTINE expectation. Keeping these beside the suite is a
# duplication you accept knowingly: GX tells you WHICH rule failed; Spark tells
# you WHICH ROWS failed it. Both are needed to quarantine with a reason.
QUARANTINE_RULES = {
    "fare_non_positive":     F.col("fare_sar") <= 0,
    "fare_implausible":      F.col("fare_sar") > 5000,
    "duration_non_positive": F.col("duration_min") <= 0,
    "duration_implausible":  F.col("duration_min") > 600,
    "distance_non_positive": F.col("distance_km") <= 0,
    "city_not_in_ksa_set":   ~F.col("city").isin(*KSA_CITIES),
    "status_unknown":        ~F.col("status").isin(*TRIP_STATUS),
    "dropoff_before_pickup": F.col("dropoff_ts") <= F.col("pickup_ts"),
    "surge_out_of_range":    ~F.col("surge_multiplier").between(1.0, 5.0),
}


def gate_and_promote(candidate: DataFrame, gx_result, batch_id: str) -> GateResult:
    spark = get_spark()

    # ---- 1. FAIL FAST on integrity ------------------------------------------
    integrity_failures = _failed_by_class(gx_result, "FAIL_FAST")
    if integrity_failures:
        alert(f"FAIL-FAST: batch {batch_id} blocked. "
              f"Integrity expectations failed: {integrity_failures}")
        raise GateBlocked(
            f"FAIL-FAST: integrity expectations failed {integrity_failures}; "
            f"batch {batch_id} blocked, nothing promoted")

    # ---- 2. QUARANTINE partial value failures -------------------------------
    reason = F.array_remove(F.array(*[
        F.when(pred, F.lit(name)).otherwise(F.lit(None))
        for name, pred in QUARANTINE_RULES.items()
    ]), None)

    tagged = candidate.withColumn("_quarantine_reasons", reason)
    bad = tagged.filter(F.size("_quarantine_reasons") > 0)
    good = tagged.filter(F.size("_quarantine_reasons") == 0).drop("_quarantine_reasons")

    bad.cache(); good.cache()
    n_bad, n_good = bad.count(), good.count()

    if n_bad:
        (bad.withColumn("_quarantined_at", F.current_timestamp())
            .withColumn("_batch_id", F.lit(batch_id))
            .write.format("delta").mode("append")
            .option("mergeSchema", "true")
            .save(QUARANTINE))
        by_reason = (bad.select(F.explode("_quarantine_reasons").alias("r"))
                       .groupBy("r").count().collect())
        detail = {row["r"]: row["count"] for row in by_reason}
        alert(f"QUARANTINED {n_bad} rows to silver.trips_quarantine -> {detail}")
    else:
        detail = {}

    # ---- 3. Promote the good rows (idempotent MERGE on trip_id, from LAB-04b)
    from delta.tables import DeltaTable
    tgt = DeltaTable.forPath(spark, SILVER)
    (tgt.alias("t").merge(good.alias("s"), "t.trip_id = s.trip_id")
        .whenMatchedUpdateAll().whenNotMatchedInsertAll().execute())

    print(f"[gate] batch {batch_id}: promoted {n_good:,}, quarantined {n_bad:,}")
    return GateResult(promoted=n_good, quarantined=n_bad, blocked=False, reasons=detail)


def alert(msg: str) -> None:
    print(f"[DATA-ALERT] {msg}", flush=True)   # wire to Slack/PagerDuty in production

    Task 3 — Observability: freshness, volume, drift (10 min)¶

    Row-level rules validate content. These three validate the pipeline's health, and they catch what no row rule can.

    # src/masar/quality/observe.py
"""The four data-SRE signals. Freshness, volume, schema drift, distribution drift.

Every one of these can fire while EVERY ROW passes EVERY expectation.
"""
from __future__ import annotations
from datetime import datetime, timedelta
from pyspark.sql import functions as F
from masar.spark import get_spark
from masar.quality.gate import alert

BASELINE_WINDOW = ("2026-05-01", "2026-05-31")   # FROZEN known-good period


def check_freshness(path: str, table: str, sla_hours: int = 6) -> None:
    spark = get_spark()
    last = (spark.read.format("delta").load(path)
            .agg(F.max("_ingested_at").alias("m")).collect()[0]["m"])
    age_h = None if last is None else (datetime.now() - last).total_seconds() / 3600
    if last is None or age_h > sla_hours:
        raise RuntimeError(
            f"FRESHNESS breach: {table} last updated {last} "
            f"({age_h:.1f}h ago, SLA {sla_hours}h)")
    print(f"[obs] freshness {table}: {age_h:.2f}h old, SLA {sla_hours}h  OK")


def check_volume(path: str, table: str, expected: int, tol: float = 0.30) -> None:
    spark = get_spark()
    n = spark.read.format("delta").load(path).count()
    dev = abs(n - expected) / expected
    if dev > tol:
        raise RuntimeError(
            f"VOLUME anomaly: {table} has {n:,} rows vs expected ~{expected:,} "
            f"({dev:+.1%}, tolerance {tol:.0%})")
    print(f"[obs] volume {table}: {n:,} rows ({dev:+.1%} of baseline)  OK")


def check_schema_drift(path: str, table: str, expected_columns: set[str]) -> None:
    spark = get_spark()
    actual = set(spark.read.format("delta").load(path).columns)
    added, removed = actual - expected_columns, expected_columns - actual
    if added or removed:
        alert(f"SCHEMA drift in {table}: added={sorted(added)} removed={sorted(removed)}")
    else:
        print(f"[obs] schema {table}: {len(actual)} columns, no drift  OK")


def check_distribution_drift(path: str, table: str, column: str,
                             baseline_mean: float, tol: float = 0.20,
                             group_by: str | None = None) -> None:
    """The signal that catches semantic drift. Baseline is FROZEN, never recomputed
    from the batch under test — that is the 'baseline-the-bug' failure mode."""
    spark = get_spark()
    df = spark.read.format("delta").load(path)
    if group_by:
        rows = df.groupBy(group_by).agg(F.mean(column).alias("m")).collect()
        for r in rows:
            dev = abs(r["m"] - baseline_mean) / baseline_mean
            flag = "DRIFT" if dev > tol else "ok   "
            print(f"[{flag}] {table}.{column} [{group_by}={r[group_by]}]: "
                  f"{r['m']:.2f} vs baseline {baseline_mean:.2f} ({dev:+.1%})")
            if dev > tol:
                alert(f"DISTRIBUTION drift: {table}.{column} for "
                      f"{group_by}={r[group_by]} is {dev:+.1%} off frozen baseline")
    else:
        m = df.agg(F.mean(column).alias("m")).collect()[0]["m"]
        dev = abs(m - baseline_mean) / baseline_mean
        if dev > tol:
            alert(f"DISTRIBUTION drift: {table}.{column} mean {m:.2f} "
                  f"vs baseline {baseline_mean:.2f} ({dev:+.1%})")
        else:
            print(f"[obs] drift {table}.{column}: {m:.2f} vs {baseline_mean:.2f}  OK")

def enforce_gps_retention(dry_run: bool = True) -> int:
    """Blanket retention on precise location. Minimisation, not deletion for its own sake."""
    spark = get_spark()
    path = "./lakehouse/silver/vehicle_positions"
    t = DeltaTable.forPath(spark, path)
    predicate = f"event_ts < current_date() - INTERVAL {GPS_RETENTION_DAYS} DAYS"
    n = spark.read.format("delta").load(path).where(predicate).count()
    print(f"[pdpl] retention: {n:,} rows older than {GPS_RETENTION_DAYS}d")
    if not dry_run and n:
        t.delete(predicate)
        spark.sql(f"VACUUM delta.`{path}` RETAIN 168 HOURS")   # 7 days, justified below
        print(f"[pdpl] deleted {n:,} rows + VACUUM RETAIN 168 HOURS")
    return n


def erase_rider(rider_id: str, ticket_ref: str, dry_run: bool = True) -> dict:
    """Data-subject erasure request. Touches EVERY table holding the identifier."""
    spark = get_spark()
    targets = {
        "silver.trips":     "./lakehouse/silver/trips",
        "silver.trips_quarantine": "./lakehouse/silver/trips_quarantine",
        "bronze.trips":     "./lakehouse/bronze/trips",
    }
    counts = {}
    for name, path in targets.items():
        df = spark.read.format("delta").load(path)
        if "rider_id" not in df.columns:
            continue
        n = df.where(F.col("rider_id") == rider_id).count()
        counts[name] = n
        if not dry_run and n:
            DeltaTable.forPath(spark, path).delete(F.col("rider_id") == rider_id)
            spark.sql(f"VACUUM delta.`{path}` RETAIN 168 HOURS")

    record = {"ticket_ref": ticket_ref, "rider_id_hash": _h(rider_id),
              "executed_at": datetime.utcnow().isoformat() + "Z",
              "rows_deleted": counts, "dry_run": dry_run,
              "vacuum_retain_hours": 168}
    if not dry_run:
        (spark.createDataFrame([json.dumps(record)], "string")
             .toDF("record").write.format("delta").mode("append").save(AUDIT_LOG))
    print(f"[pdpl] erasure {ticket_ref}: {counts} (dry_run={dry_run})")
    return record

    import hashlib
    return hashlib.sha256(v.encode()).hexdigest()[:16]

    5. Self-check questions¶

    Q1. A batch arrives with 40 null trip_id values and 120 negative fares. Your gate blocks it entirely. What did you get wrong, and what should have happened?

    Answer Nothing — this specific batch is correctly blocked. The **null key** is a FAIL_FAST fault, and fail-fast dominates: once integrity fails you cannot safely promote *anything*, because a null key breaks the MERGE that every downstream idempotency guarantee depends on. Splitting the batch would mean promoting rows whose key semantics you no longer trust. The mistake would be blocking a batch that had *only* the 120 negative fares. That is a 0.25% partial fault, isolable by predicate, and blocking it converts a small data problem into a total availability outage — the upstream ETA model retrains on a gap, and the BI dashboard shows yesterday. The rule: **fail-fast dominates when both classes fail; quarantine is the answer when only value constraints fail.**

    Q2. Every row in the currency-shift fixture passes expect_column_values_to_be_between("fare_sar", 0, 5000). Explain why, and name the two other checks that would have caught it.

    Answer Because `3847.55` is a perfectly valid number strictly between 0 and 5000. Range rules test *plausibility per row*; they cannot test *plausibility per population*. A 100× shift produces values that are individually unremarkable. Two checks catch it: (1) **distribution drift** against a frozen baseline — the Jeddah mean moves from 38.40 to 3847.55, a +9918% deviation no tolerance band survives; and (2) **reconciliation** — the sum of `fare_sar` in `silver.trips` for Jeddah against the same day's total in `data/raw/payments_YYYY-MM-DD.csv` (`amount_sar`). Reconciliation is the strongest check in the pyramid and the most expensive, which is why it runs daily rather than per batch. Note that raising `max_value` to 5000 was itself a judgement. Had it been 200, the range rule would have caught this incident by accident — and would have quarantined every legitimate long-haul intercity fare as a side effect. Tight bounds are not free.

    Q3. Your team proposes computing the drift baseline as "the mean of the last 30 days, refreshed nightly." What is wrong with that?

    Answer The baseline absorbs the bug. If the currency shift began on 12 June, then by 13 June it is 1/30th of the rolling baseline, by 20 June it is a quarter of it, and by 12 July it *is* the baseline. The deviation shrinks every night until the check reports OK on permanently corrupt data. This is the `sim-baseline-the-bug` simulation, and it is the most common way a working drift check silently stops working. The correct pattern: freeze the baseline over an explicitly chosen **known-good period** (here, 2026-05-01..2026-05-31), store it as a versioned literal or a Delta table with its own history, and change it only through review — the same discipline you apply to loosening an expectation. Re-baselining is a decision with an owner, not an automatic process. A rolling window is acceptable only for genuinely seasonal quantities, and even then you compare against the same period last year, not against last week.

    Q4. What does VACUUM have to do with PDPL, and what does RETAIN 0 HOURS cost you?

    Answer A Delta `DELETE` is logical: it writes a new version whose snapshot excludes the rows, but the underlying Parquet files still contain them and remain readable via time travel (`VERSION AS OF`). For a **retention limit** or a **data-subject erasure request**, the data has not actually been erased — it is one `SELECT ... VERSION AS OF 12` away. `VACUUM` physically removes files no longer referenced by any retained version, which is what converts a logical delete into an erasure you can defend to an auditor. `RETAIN 0 HOURS` is flagged as an anti-pattern in the capstone rubric for two reasons. Operationally it can delete files that a **concurrently running reader or streaming query** still holds a reference to, producing `FileNotFoundException` on a job that was working a second ago — Delta requires an explicit `spark.databricks.delta.retentionDurationCheck.enabled=false` override precisely because this is dangerous. Governance-wise it destroys your entire audit trail: you can no longer prove what the table looked like before a correction, which is a different compliance obligation pulling in the opposite direction. `RETAIN 168 HOURS` (7 days) is the defensible middle: longer than any running job, short enough that the erasure obligation is met within a reasonable window, and documented as a deliberate choice.

    Q5. Your model's accuracy dropped 8% last month. Every expectation in every suite passed, every day. Where do you look first?

    Answer **Distribution drift**, on the feature columns rather than the raw columns. Passing expectations tell you the data is *well-formed*; they say nothing about whether its statistical shape still matches what the model was trained on. The two Masar incidents in this lab are exactly this shape: the m/s speed drift and the currency shift both produce 100% valid rows. The diagnostic order: (1) compare the current distribution of each `gold.eta_features` column against the training snapshot — Delta time travel lets you read the exact version the model trained on, which is why `_feature_version` and time travel matter; (2) check **volume** per segment, because a feed outage in one city shifts the population mix without changing any distribution within a city; (3) check **freshness** per feature, because a feature that silently stopped refreshing looks statistically fine but is answering last week's question. Only then look at the model.

    Q6. A stakeholder asks for rider_id in a shared operations dashboard "so we can call the customer back." How do you answer in PDPL terms while still solving their problem?

    Answer The refusal is grounded in **purpose limitation** and **data minimisation**: the lawful basis for holding `rider_id` is service delivery and dispute resolution, not analytics, and a shared dashboard exposes the identifier to a population far wider than that purpose supports. Publishing it also makes every dashboard viewer a processor of personal data, expanding the compliance surface across the whole organisation. The need behind the ask is legitimate, and it is not "see the rider ID" — it is "reach this specific rider from this specific trip." Three ways to meet it without breaching: (1) expose `trip_id` only, and have the support tool perform the lookup inside the system that already has a lawful basis, with the access logged; (2) publish a **pseudonym** (`sha2(rider_id, 256)`) so cohort analysis and repeat-customer counting still work without exposing the identifier; (3) for the dashboard itself, serve aggregates — which is exactly what `gold.fact_trip` and the BI-safe view in LAB-08 do. Governance is rarely a refusal; it is a redesign that meets the need at a lower data cost.
