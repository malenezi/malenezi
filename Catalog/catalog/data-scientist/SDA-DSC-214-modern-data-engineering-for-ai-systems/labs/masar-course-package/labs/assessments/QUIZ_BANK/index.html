    SDA-DSC-214 — Quiz Bank¶

    Course: Modern Data Engineering for AI Systems (SDA-DSC-214), SDAIA Academy Golden thread: Masar (مسار) — every item is set in the Masar Lakehouse the cohort built. Weight: 10% of the course grade. Closed book, 15 minutes, 10 questions per cohort.

    Scale note. Figures quoted in this document assume the full-scale generator run (--scale 1.0); the shipped sample is --scale 0.15 — 7,230 trips/day over 5 days (36,150 trips), 873,763 GPS pings, 3,450 drivers, 3,864 vehicles, 48 zones. Grains, ratios and file-count reductions hold at either scale; absolute row counts do not.

    How to use this bank¶

    Field Value
    Items 60, tagged M1–M8
    Bloom levels recall (state it) · apply (use it on a Masar case) · analyse (diagnose evidence and justify)
    Difficulty easy (≥ 85% expected correct) · medium (60–85%) · hard (< 60%; discriminates the distinction band)
    Formats MCQ (four options; every non-key option is a misconception observed in delivery) · T/F+J (true/false plus a one-sentence justification — the justification carries the mark) · SHORT (one to three sentences) · DEBUG (read code or output and state what is wrong)
    Marking MCQ 1 mark. T/F+J 2 marks (0.5 verdict + 1.5 justification). SHORT 2 marks. DEBUG 3 marks (1 identify, 1 consequence, 1 fix).
    Ready sets Three balanced 10-question papers (A/B/C) at the end, each with a separate printable answer key

    Rules of thumb for the marker. A correct verdict with a wrong reason scores the verdict only. On DEBUG items, "it will break" scores nothing; the participant must name the mechanism. Numbers quoted from the reference runs are accepted within ±10% unless the item says otherwise.

    Item distribution: M1 7 · M2 7 · M3 8 · M4 9 · M5 9 · M6 8 · M7 6 · M8 6.

    Module 1 — Evolution of Data Architecture (Day 1)¶

    Q1 · MCQ · recall · easy¶

    Which architecture combines lake storage economics with warehouse transactional reliability?

    A. A two-tier lake-plus-warehouse estate B. Lakehouse C. An MPP data warehouse with external tables D. An operational data store fed by CDC

    Answer: B. Rationale: Only the Lakehouse puts a transaction layer directly over open files; A is the two-tier problem, not its solution.

    Q2 · MCQ · recall · easy¶

    What single property turns a directory of Parquet files into a Delta table?

    A. A Hive metastore entry pointing at the directory B. A _SUCCESS marker written by the last job C. The _delta_log transaction log D. Consistent partition directories

    Answer: C. Rationale: ACID, time travel and schema enforcement all derive from replaying _delta_log; the Parquet files alone are just files.

    Q3 · T/F+J · apply · medium¶

    "When a single bad row is found in bronze.trips, the correct action is to edit that row in place."

    Answer: False. Rationale: Bronze is append-only and immutable; corrections belong in silver as reproducible logic, because an in-place edit destroys the raw record the late-arrival backfill and the time-travel audit both depend on.

    Q4 · SHORT · analyse · medium¶

    A data-science notebook reports 91% on-time deliveries; the executive dashboard reports 87%. Name the architectural cause and the architectural fix.

    Answer: Two copies of the same data with two different late-arrival rules — the two-tier problem. Fix: consolidate onto one governed silver table with a single late-arrival rule, read by both BI and DS. Rationale: The defect is not a bad ETL job but the existence of a second pipeline; only consolidation removes the class of bug.

    Q5 · MCQ · apply · medium¶

    Which bronze layout choice is the fastest route to a data swamp?

    A. partitionBy("ingest_date") B. partitionBy("trip_id") C. Writing one Delta table per source feed D. Carrying _source_file on every row

    Answer: B. Rationale: A high-cardinality partition key produces millions of one-row files — the small-files problem, self-inflicted at landing time.

    Q6 · SHORT · recall · easy¶

    Name the three lineage columns every Masar bronze table carries, and say what each answers.

    Answer: _ingested_at (when we received it), _source_file (which file or Kafka partition it came from), _batch_id (which run wrote it). Rationale: Together they let any bronze row be traced to a run and a source without consulting an external log.

    Q7 · DEBUG · analyse · hard¶

    (df.write.format("delta")
   .mode("overwrite")                 # land_bronze.py
   .partitionBy("ingest_date")
   .save("./lakehouse/bronze/trips"))
    The landing job is re-run for the same day. State what is wrong, the consequence, and the fix.

    Answer: mode("overwrite") violates the bronze append-only contract. Consequence: the previous landing of that partition is destroyed, so a re-ingest of a corrected file silently erases the original record and the late-arrival backfill and time-travel audit lose their source of truth. Fix: mode("append"), and rely on the keyed MERGE at silver to make re-runs harmless. Rationale: Bronze's contract is "everything we ever received", not "one row per real-world event" — de-duplication is silver's job.

    Module 2 — Compute–Storage Separation and Cloud Economics (Day 1)¶

    Q8 · MCQ · recall · easy¶

    In a decoupled platform, which cost axis is normally the controllable lever?

    A. Storage, because object storage is billed per GB-month B. Compute, because it is elastic and mostly idle if unmanaged C. Network egress within one region D. Metastore operations

    Answer: B. Rationale: In the Lab-2 reference model compute is 87% of the coupled bill with 96.3% of it idle; storage is the small, steady line.

    Q9 · SHORT · recall · easy¶

    Name the two Parquet features that make remote reads cheap.

    Answer: Column pruning (read only the columns the query projects) and row-group min/max statistics that let the reader skip row groups (data skipping). Rationale: Both reduce bytes scanned, which is the unit the decoupled bill is actually driven by.

    Q10 · T/F+J · apply · medium¶

    "Migrating from a coupled warehouse to a Lakehouse guarantees a lower monthly bill."

    Answer: False. Rationale: Decoupling enables savings; layout and elasticity discipline realise them — the reference retailer's first month rose because every dashboard full-scanned an unpartitioned gold table, and only partitioning, ZORDER, caching and 10-minute idle-termination brought month two 45% below the old warehouse.

    Q11 · MCQ · analyse · medium¶

    Your scan benchmark reads 3 of 27 columns — 89% fewer columns — but bytes scanned fall only 72%. The most likely explanation is:

    A. The query plan did not actually prune columns B. Delta read the transaction log for every file C. The three retained columns are wide, low-entropy strings that compress differently from the dropped ones D. The table needs OPTIMIZE before pruning works

    Answer: C. Rationale: Column count is a proxy; bytes are the truth — which is why the lab insists on measuring bytes rather than reasoning about column counts.

    Q12 · SHORT · apply · medium¶

    Name the two elasticity guardrails that must appear in the Masar ELT cluster definition, with the reference values.

    Answer: Idle auto-termination (autotermination_minutes: 10) and a bounded autoscale ceiling (max_workers: 8). Rationale: Infinite scale means an infinite bill; the guardrails are what make an ephemeral job cluster safe to hand to a scheduler.

    Q13 · DEBUG · analyse · hard¶

    == Physical Plan ==
FileScan parquet [trip_id,rider_id,driver_id,vehicle_id,city,... 27 columns]
   PartitionFilters: []
   PushedFilters: []
   ReadSchema: struct<trip_id:string,rider_id:string, ... >
    The query was SELECT city, fare_sar FROM silver.trips WHERE city = 'Riyadh'. State what is wrong and the fix.

    Answer: Neither pruning nor pushdown happened — 27 columns are in ReadSchema and both filter lists are empty, so the job is paying to read the whole table. Cause is usually a preceding wide action (a collect, a UDF, or a cached full DataFrame) or a non-partitioned, non-statistics-bearing layout. Fix: project before acting, partition by city, and confirm the plan shows PartitionFilters: [city#12 = Riyadh] and a 2-column ReadSchema. Rationale: The reference run moves relative bytes scanned from 1.00 to 0.06 purely through pruning plus a partition filter.

    Q14 · MCQ · apply · medium¶

    The Lab-2 model reports "break-even utilisation 318,717 core-hours/month; actual 2,118". This means:

    A. The Lakehouse becomes cheaper once you exceed 318,717 core-hours B. The coupled warehouse would only match the Lakehouse's cost at ~150× Masar's actual compute demand C. The cluster is under-provisioned by a factor of 150 D. Storage cost dominates below the break-even point

    Answer: B. Rationale: Break-even states the utilisation at which always-on capacity stops being wasteful; Masar runs at 0.7% of it, which is the whole argument for elastic compute.

    Module 3 — ETL versus ELT in Modern Stacks (Day 2)¶

    Q15 · MCQ · recall · easy¶

    Why did ELT displace ETL on cloud platforms?

    A. SQL is faster than Python for transformations B. Cheap storage lets you keep raw, and elastic compute transforms in-platform — so transformations are reprocessable and auditable C. ELT removes the need for data tests D. ETL cannot handle semi-structured data

    Answer: B. Rationale: The decisive property is retained raw: when the cleaning logic is wrong you re-derive rather than re-ingest.

    Q16 · SHORT · apply · medium¶

    What bug does a lookback window fix in an incremental model, and what does it cost?

    Answer: Late-arriving rows that a WHERE date = current_date() filter silently drops. It costs re-processing the lookback window on every run (Masar: 3 days), which is cheap because the MERGE makes re-application a no-op. Rationale: The reference undercount was ~2% and invisible — it skewed driver incentives and model labels for months.

    Q17 · T/F+J · apply · medium¶

    "SELECT DISTINCT * FROM stg_trips is an acceptable way to enforce one row per trip_id in silver."

    Answer: False. Rationale: DISTINCT keeps every distinct version of a corrected trip, so a corrected row and its stale predecessor both survive; the correct pattern is latest-row-per-key (window on _ingested_at) followed by a MERGE on trip_id.

    Q18 · DEBUG · analyse · hard¶

    {{ config(materialized='incremental', unique_key='trip_id') }}
SELECT * FROM {{ ref('stg_trips') }}
{% if is_incremental() %}
WHERE pickup_ts::date = current_date()
{% endif %}
    A trip that ended yesterday but landed in bronze today is missing from silver.trips. Explain and fix.

    Answer: The incremental predicate filters on the trip's own pickup_ts, so a trip that occurred yesterday is excluded even though it arrived today. Consequence: dbt run reports success, inserted -> 0, and the trip is lost — a silent undercount. Fix: widen to a lookback on the event date, WHERE pickup_ts >= current_date() - INTERVAL 3 DAYS, keeping unique_key='trip_id' so the re-scanned rows merge as no-ops. Rationale: In the reference run the corrected model reports inserted -> 1 on the backfill and inserted -> 0 on the repeat; the naive filter reports 0 / 0 and loses the trip.

    Q19 · MCQ · recall · medium¶

    Why is MERGE-on-key idempotent where INSERT is not?

    A. MERGE runs inside a transaction and INSERT does not B. Re-applying an already-matched row updates it to the same values — a no-op — whereas INSERT appends a second copy C. MERGE deduplicates the source automatically D. INSERT cannot be run twice on a Delta table

    Answer: B. Rationale: Idempotency is a property of the table state after the run, not of whether a commit was written.

    Q20 · SHORT · analyse · hard¶

    bronze.trips has a dbt source freshness SLA of 6h warn / 24h error. State one upstream failure it catches and one it misses.

    Answer: Catches: a stopped or crashed landing job — the newest _ingested_at ages past the threshold. Misses: a landing job that runs exactly on time and lands empty or wrong data, because freshness only inspects recency, not volume or content. Rationale: This is precisely the gap that the M6 volume and distribution checks close.

    Q21 · MCQ · apply · medium¶

    Where do source quirks — a mixed hire_date format, a renamed column — belong in the dbt layering?

    A. In the mart, so the fix is close to the consumer B. In the staging model, so the quirk is isolated once C. In a post-hook on the silver table D. In the source declaration itself

    Answer: B. Rationale: Casting and renaming in marts leaks source quirks everywhere; one rename then breaks ten models.

    Q22 · SHORT · apply · medium¶

    Reconstruct the Masar silver row derivation: 96,400 bronze rows become 42,038 silver rows. Name each step.

    Answer: 96,400 bronze rows (two landings of the same day) → 48,200 after latest-per-key dedup → 42,096 after status = 'completed' → 42,038 after the validity predicates (dropoff_ts > pickup_ts, fare_sar > 0, distance_km > 0); the 58 rejected rows go to silver.trips_quarantine. Rationale: A participant who cannot account for their own row loss has not understood the transform.

    Module 4 — Delta Lake and ACID Transactions (Day 3)¶

    Q23 · MCQ · recall · easy¶

    A reader opens a query at version 5 while a MERGE commits version 6. The reader sees version 5 throughout. Which ACID property is this, and what provides it?

    A. Atomicity, via the single commit file B. Consistency, via CHECK constraints C. Isolation, via snapshot isolation over the transaction log D. Durability, via object storage

    Answer: C. Rationale: The reader pinned a snapshot at query start; the new commit is simply a later log entry it does not read.

    Q24 · SHORT · recall · easy¶

    What does VACUUM trade away in exchange for reclaimed storage?

    Answer: Time-travel history beyond the retention window — versions older than the retention can no longer be read, because their data files are physically deleted. Rationale: Retention is therefore a governance decision, not a housekeeping one.

    Q25 · T/F+J · apply · medium¶

    "A DELETE on a Delta table immediately frees the storage and removes the rows from history."

    Answer: False. Rationale: DELETE writes a commit that tombstones the affected files; the rows remain readable via time travel and present on disk until a VACUUM past the retention window removes them — which is why a PDPL erasure is a two-step operation.

    Q26 · DEBUG · analyse · hard¶

    spark.conf.set("spark.databricks.delta.retentionDurationCheck.enabled", "false")
spark.sql("VACUUM delta.`./lakehouse/silver/trips` RETAIN 0 HOURS")
    State what is wrong, the two distinct consequences, and the correct operation.

    Answer: The safety check was disabled specifically to bypass a guardrail that exists for two reasons. Consequence 1: every prior version's data files are deleted, so VERSION AS OF and the audit diff fail with FileNotFoundException — the regulator question "what did this table contain three weeks ago" becomes unanswerable. Consequence 2: files that a concurrently running reader or streaming query is about to open are deleted underneath it, failing a healthy job. Correct operation: leave retentionDurationCheck enabled and run VACUUM ... RETAIN 168 HOURS, preceded by a DRY RUN. Rationale: 168h is longer than any Masar job's runtime and short enough that an honoured erasure completes within a defensible window.

    Q27 · MCQ · apply · medium¶

    Your corrections MERGE reports updated=5 on run 1 and updated=0 on run 2 — but DESCRIBE HISTORY shows a new version for run 2. Is the operation idempotent?

    A. No — a second commit means the table changed B. Yes — idempotency is a property of the resulting table state, and a MERGE that changes nothing is still a transaction C. Only if whenNotMatchedInsertAll is omitted D. Only if the source is empty on the second run

    Answer: B. Rationale: The reference run produces v3 updated -> 5 and v4 updated -> 0; both commits exist and the table state is identical.

    Q28 · SHORT · apply · medium¶

    Why is partitionBy("trip_id") on silver.trips a mistake, and what is the correct Masar partitioning?

    Answer: trip_id is unique per row, so it produces one directory and one tiny file per trip — millions of small files, catastrophic listing and read cost. Correct: partition by a coarse, query-aligned key (city and/or date) and use ZORDER BY (city, pickup_ts) for skipping within partitions. Rationale: The reference OPTIMIZE takes numFiles from 214 to 9 (23.8×) and the filtered read from 1.91s to 0.41s.

    Q29 · MCQ · analyse · medium¶

    A write with fare_sar = -5.0 is rejected, and a separate write sending fare_sar as a string is also rejected. Which mechanisms fired?

    A. Both were CHECK constraints B. Both were schema enforcement C. The negative value was the positive_fare CHECK constraint; the string was schema enforcement (type merge failure) D. The negative value was schema enforcement; the string was a CHECK constraint

    Answer: C. Rationale: Constraints police values, schema enforcement polices shape and type; a table needs both, and neither catches semantic drift (the m/s incident).

    Q30 · SHORT · analyse · hard¶

    A PDPL erasure request for rid_0000042 is executed as a MERGE DELETE on silver.trips. Where does that rider's data still exist, and what completes the erasure?

    Answer: In Delta time-travel history and in tombstoned Parquet files on disk; in bronze.trips (append-only, still holds the raw rows); in silver.trips_quarantine if any of the rider's rows were quarantined; and in any gold table or Redis key derived before the deletion. Completion requires the DELETE on every such table, a VACUUM past retention on each, a rebuild of the derived gold and feature tables, and a purge of the online store — recorded in GOVERNANCE.md as a runbook. Rationale: Most participants delete from silver and bronze and forget the quarantine table, which is by construction full of personal data.

    Q31 · DEBUG · analyse · hard¶

    (target.alias("t")
   .merge(source.alias("s"),
          "t.trip_id = s.trip_id AND t._ingested_at = s._ingested_at")
   .whenMatchedUpdateAll()
   .whenNotMatchedInsertAll()
   .execute())
    The corrections job is run twice. State what is wrong, the consequence, and the fix.

    Answer: _ingested_at is set to the current run time, so the match condition can never be satisfied across runs. Consequence: whenMatchedUpdateAll never fires and every run takes the whenNotMatchedInsertAll branch — the table gains a duplicate copy of every corrected trip per run, silently breaking the one-row-per-trip_id grain that every gold table and both consumers depend on. Fix: match on the business key alone (t.trip_id = s.trip_id), and check the source for duplicate keys before merging so whenMatchedUpdateAll is unambiguous. Rationale: This is the classic non-idempotent MERGE and the starting state of PA-1.

    Module 5 — Streaming and Event-Driven Architectures (Day 4)¶

    Q32 · MCQ · recall · easy¶

    Which two mechanisms together give Structured Streaming + Delta exactly-once?

    A. Kafka transactions and consumer-group offsets B. Checkpointed Kafka offsets and Delta's atomic per-micro-batch commit C. dropDuplicates and a watermark D. Idempotent producers and acks=all

    Answer: B. Rationale: Kafka alone gives at-least-once with replay; Delta alone gives an idempotent sink; exactly-once is the composition.

    Q33 · SHORT · recall · easy¶

    What does a streaming watermark bound?

    Answer: How long the query waits for late events before finalising a window — and therefore how much state it must retain. Rationale: No watermark on an event-time aggregation means unbounded state and eventual OOM.

    Q34 · T/F+J · apply · medium¶

    "Kafka provides exactly-once delivery, so a Spark consumer inherits it."

    Answer: False. Rationale: Kafka provides durable, replayable at-least-once delivery; the consumer must supply a durable record of which offsets were included in each committed sink transaction — in Masar that is ./lakehouse/_checkpoints/gps_events_bronze plus the Delta commit, with txnAppId/txnVersion making a replayed batch_id a no-op.

    Q35 · DEBUG · analyse · hard¶

    (parse(raw).writeStream
   .foreachBatch(write_batch)
   .outputMode("append")
   .trigger(processingTime="30 seconds")
   .start()
   .awaitTermination())
    110,000 pings are produced; the job is killed mid-batch and restarted; bronze.gps_events then reports 127,300 rows. Explain and fix.

    Answer: There is no checkpointLocation, so on restart the query has no record of committed Kafka offsets and re-reads from the configured starting position — 17,300 pings are appended a second time. Consequence: the 15-minute demand feature inflates, the ETA model predicts a rush hour that never happened and surge fires in an empty district. Fix: add .option("checkpointLocation", "./lakehouse/_checkpoints/gps_events_bronze") — one dedicated directory per query — and keep the txnAppId/txnVersion idempotent-write guard in write_batch. Rationale: The reference clean run is 110,000 pings → 110,000 rows with 0 pipeline duplicates; the sim-nocheckpoint counter-demo is 127,300.

    Q36 · MCQ · apply · medium¶

    A windowed demand aggregation must use event time rather than processing time because:

    A. Event time is always monotonically increasing B. Processing time is not available in Structured Streaming C. A ping delayed 30 minutes would otherwise be counted in the window in which it arrived, not the window in which it happened D. Event time removes the need for a watermark

    Answer: C. Rationale: The reference run shows a maximum event-time lag of 1,798 seconds — a processing-time aggregation would file all of it under one wrong window.

    Q37 · SHORT · analyse · hard¶

    The GPS feed carries three defects: late pings, duplicate event_id, and out-of-order ts. Say which a watermark fixes, which dropDuplicates fixes, and which of the four known GPS problems neither can see.

    Answer: The watermark handles late arrival (how long a window stays open). dropDuplicatesWithinWatermark(["event_id"]) handles duplicates, at the cost of state bounded to the lateness window. Out-of-order needs no fixing at all under event-time semantics. The fourth problem — producer_version 2.5.0 emitting speed_kmh in m/s — is invisible to both: it is structurally valid, on time, unique and correctly ordered, and only a per-producer_version distribution comparison detects it. Rationale: This distinction is the hand-off from M5 to M6.

    Q38 · MCQ · apply · medium¶

    Two streaming queries are pointed at the same checkpointLocation. The most likely outcome is:

    A. Spark refuses to start the second query B. The two queries safely share offsets C. One query reads the other's offset log and state — silent data loss or state corruption, often without an error D. Throughput halves but correctness is preserved

    Answer: C. Rationale: Spark does not always fail loudly on this, which is why "one checkpoint per query" is a rule rather than a preference.

    Q39 · SHORT · apply · medium¶

    The GPS stream's trigger is changed from 30 seconds to 1 second. Name three consequences.

    Answer: (1) ~30× the files — roughly 7,400 files per 15 minutes and ~1.7M files/year for this feed alone, so every downstream read pays per-file open cost. (2) One _delta_log commit per second, so listing and checkpointing the log becomes the bottleneck. (3) Object-storage request charges scale with file count — a direct cost regression. Rationale: Latency is bought with file count; OPTIMIZE is maintenance, not a licence to over-trigger.

    Q40 · DEBUG · analyse · hard¶

    (events
   .groupBy(F.window(F.current_timestamp(), "15 minutes"), "pickup_zone_id")
   .count())
    State what is wrong, what the demand mart will show, and the fix.

    Answer: The window is built on current_timestamp() — processing time — not on the event's own ts. Consequence: every ping processed in one micro-batch lands in the same window regardless of when it happened, so a 30-minute-late batch of pings inflates the current window and empties the correct one; the zone demand feature is wrong in both directions and the error correlates with pipeline lag. Fix: withWatermark("event_ts", "5 minutes") then groupBy(F.window("event_ts", "15 minutes"), "pickup_zone_id"). Rationale: Event time is a correctness property; processing time is an operational metric and should be kept alongside, never substituted.

    Module 6 — Data Quality, Observability, and Governance (Day 4)¶

    Q41 · MCQ · recall · easy¶

    Where in the medallion should the quality gate run?

    A. On landing, before bronze B. At promotion, bronze → silver C. On the gold marts, before the dashboard reads them D. In the BI tool, as a report-level filter

    Answer: B. Rationale: Bronze must accept everything received; silver is the first layer that carries a contract, so it is the first place a gate can legitimately refuse data.

    Q42 · SHORT · apply · medium¶

    Give one Masar failure that warrants fail-fast and one that warrants quarantine, with the reason for each.

    Answer: Fail-fast: 40 rows with a null trip_id — the MERGE key is null, so WHEN MATCHED never matches and those rows re-insert on every run; the promotion mechanism is unsound for that batch, so blocking is the only containment. Quarantine: 120 rows with fare_sar <= 0 out of 42,096 — 0.25%, isolable by a predicate, and blocking would convert a data problem into a total availability outage. Rationale: Proportionality is the whole of the fail-fast/quarantine decision.

    Q43 · T/F+J · analyse · hard¶

    "The currency-shift batch (Jeddah fares ×100) should be routed to silver.trips_quarantine."

    Answer: False. Rationale: No individual row violates any predicate — the failure is a distribution failure (the mean expectation), and a distribution failure is not isolable by a row-level rule, so quarantine is impossible by definition; the correct response is a third class, ALERT_AND_HOLD — promote nothing and page a human — or escalating the mean expectation to FAIL_FAST.

    Q44 · SHORT · recall · easy¶

    Name two observability signals that row-level expectations cannot provide.

    Answer: Freshness (how old the newest row is) and volume (how many rows arrived versus expectation); distribution drift is a third. Rationale: Every row can pass every rule while the feed is stale, halved, or silently rescaled.

    Q45 · DEBUG · analyse · hard¶

    $ python -m masar.quality.observe --check drift --column fare_sar --baseline auto
[obs] drift silver.trips.fare_sar: 421.30 vs 421.30 (0.0%)  OK
    The Jeddah currency shift is present in the table. Explain why the check passes and give the fix.

    Answer: --baseline auto computes the expected value from the same data it is testing, so the comparison is a tautology and the check can never fail. Consequence: a working quality system silently stops working — the most dangerous failure mode, because the dashboard is green. Fix: pin the baseline to a stored historical reference (a prior Delta version, or a committed expectation value under review), and segment the comparison by city and by producer_version so a per-segment shift is visible. Rationale: This is the sim-baseline-the-bug simulation; a check that computes its own expectation is not a check.

    Q46 · MCQ · apply · medium¶

    Why can a null trip_id not simply be quarantined?

    A. Great Expectations cannot express a not-null predicate B. The quarantine table has a NOT NULL constraint C. The MERGE key is null, so those rows never match and re-insert on every run — quarantining relocates the rows without containing the fault D. Null keys are legal and should be promoted

    Answer: C. Rationale: Integrity failures compromise the operation, not just the data.

    Q47 · SHORT · analyse · hard¶

    rider_id and driver_id are both personal data. Why do they have different retention periods in GOVERNANCE.md?

    Answer: Because they rest on different lawful bases. Rider data is purpose-limited to service delivery, support and disputes — 24 months. Driver data is employment/contractual and legitimately retained longer — 7 years. A single blanket retention policy applied to both is a governance smell, because it is either over-retaining rider data or under-retaining employment records. Rationale: Retention follows purpose, not data type.

    Q48 · MCQ · apply · medium¶

    Which PDPL principle most directly argues against retaining precise GPS coordinates indefinitely?

    A. Transparency B. Data minimisation and retention limitation C. Accuracy D. Right of access

    Answer: B. Rationale: Masar's answer is a 180-day raw retention on lat/lon with geohash-6 at the boundary — the safest personal data is the data you no longer hold.

    Module 7 — Building a Mini-Lakehouse (Day 5)¶

    Q49 · MCQ · recall · easy¶

    Which ordering does masar_medallion declare?

    A. land >> silver >> gate >> [gold...] >> maintain B. land >> gate >> silver >> observability >> [gold...] >> maintain C. land >> [gold...] >> gate >> silver >> maintain D. gate >> land >> silver >> [gold...] >> maintain

    Answer: B. Rationale: The gate sits at the promotion boundary; the three gold tasks are siblings running in parallel; optimize_vacuum waits for all three.

    Q50 · T/F+J · apply · medium¶

    "Because land_bronze appends, a full DAG re-run would duplicate data, so the recovery procedure should skip it."

    Answer: False. Rationale: Bronze may legitimately grow on a re-run — its contract is "everything we ever received", and _batch_id/_source_file make a duplicate landing identifiable — while the duplication stops at the first keyed write, the MERGE on trip_id into silver; a task you are afraid to re-run is a task you cannot recover.

    Q51 · SHORT · apply · medium¶

    Why does gold.zone_hourly_demand use replaceWhere while gold.driver_daily uses MERGE? Both are idempotent.

    Answer: Grain-to-partition alignment. zone_hourly_demand is partitioned by date and its grain (city, pickup_zone_id, date, hour) is fully contained in a date partition, so a partition overwrite is exact and cheap. driver_daily's rebuild would need to know which (driver_id, date) pairs existed previously to avoid orphaning drivers with no trips in the new window — MERGE handles that naturally. Rationale: Either strategy is acceptable for either table if defended and proven by a double run; append is wrong, and overwrite without replaceWhere silently deletes history outside the lookback.

    Q52 · DEBUG · analyse · hard¶

    RuntimeError: GRAIN VIOLATION in ./lakehouse/gold/zone_hourly_demand:
  17,280 rows but only 8,640 distinct ['city', 'pickup_zone_id', 'date', 'hour'].
    Name the cause, the consumer-visible symptom, and the fix.

    Answer: The gold write used .mode("append") and the DAG was run twice, so every grain key exists twice. Symptom: the demand mart double-counts — every zone's hourly demand reads exactly 2×, so surge logic and the ETA demand feature both see a phantom rush hour, and the BI dashboard stops reconciling with the star schema. Fix: replaceWhere over the lookback partition (or MERGE on the grain key), plus the _assert_grain check as a task-level gate so a non-idempotent write fails the DAG instead of shipping. Rationale: Non-idempotent gold is one of the capstone anti-pattern flags that caps a criterion at 70%.

    Q53 · SHORT · analyse · hard¶

    In gold.trip_features, why must the window be rangeBetween(-3600, -1) rather than rangeBetween(-3600, 0)?

    Answer: rangeBetween bounds are inclusive and operate on the ordering column's value range, so an upper bound of 0 admits every row whose pickup_epoch equals the current row's — every trip starting in the same second, in the same zone. At Riyadh rush-hour density that is several trips, and they are the future. -1 makes the frame strictly prior. Rationale: The inflation is dangerous precisely because it is small, and it correlates with the congestion being predicted — so it reads as signal rather than as a bug.

    Q54 · MCQ · apply · medium¶

    A failure is injected into build_silver mid-DAG. What must the gold tables show?

    A. Partially rebuilt rows from the failed run B. Unchanged — yesterday's correct data, because the dependency prevented the gold tasks from running C. Empty, because the DAG rolls back D. Rebuilt from bronze via the fallback path

    Answer: B. Rationale: The recovery proof is before.json == during.json (dependency held) and before.json == after.json (a full re-run reproduced the exact state, checksums included).

    Module 8 — Serving Data to AI and BI Workloads (Day 5)¶

    Q55 · MCQ · recall · easy¶

    What makes numbers reconcile across two dashboards?

    A. Running both queries on the same cluster B. Conformed dimensions — one shared dim_date, one shared dim_driver C. Caching the gold marts D. Rebuilding both marts in the same DAG task

    Answer: B. Rationale: A second, non-conformed dim_date reintroduces two-tier divergence inside a single platform.

    Q56 · SHORT · apply · medium¶

    How do you keep online and offline features consistent?

    Answer: Materialise — copy the value from the offline gold table into Redis — and never re-implement the feature logic in the serving path. materialize_online.py must contain zero feature logic, and a consistency check must compare every key and every online column, not a spot sample. Rationale: Any online path that re-derives a feature is skew by construction; a consistency check that has never failed is a check you have not tested.

    Q57 · T/F+J · analyse · hard¶

    "After the leakage fix the model's R² fell from 0.943 to 0.712, so the fix made the model worse."

    Answer: False. Rationale: 0.943 was never a real number — it was produced by distance_km (the metered distance, written at dropoff_ts, r = 0.947 with the label) and a speed averaged over the trip's own pings; 0.712 is what the platform can actually deliver at request time, and the honest model that predicts ±4.6 min is cheaper than a leaking model that promises ±1.8 and delivers ±5, precisely because you believed the second.

    Q58 · DEBUG · analyse · hard¶

    # materialize_online.py
payload["rolling_zone_demand_15m"] = (
    spark.sql("SELECT COUNT(*) FROM silver.trips "
              "WHERE pickup_zone_id = '%s' AND pickup_ts > now() - INTERVAL 15 MINUTES"
              % zone_id).first()[0])
    State what is wrong, the consequence, and the fix.

    Answer: The online path recomputes a feature instead of copying it. Consequence: two implementations of one definition drift the moment either changes — a different window bound, a different status filter, a different clock — so the model is trained on one quantity and served another, and the divergence is invisible because both paths "work". Fix: read the value from gold.eta_features and write it verbatim; keep materialize_online.py free of any feature logic and let consistency_check.py prove offline == online across all 412 zone keys. Rationale: Serve, do not fork — external stores are derived copies, not new pipelines.

    Q59 · SHORT · analyse · hard¶

    dropoff_zone_id is VALID but distance_km is LEAKAGE, though both describe the destination. Explain.

    Answer: The difference is when the value is written, not what it describes. Masar's booking flow requires a stated destination before the request, so dropoff_zone_id is an input the platform holds at feature_ts. distance_km in silver.trips is the metered distance actually travelled, written at dropoff_ts — an outcome of the journey. The fix keeps the contract column name and changes the source to the routing engine's planned distance at booking. Rationale: The dependency is invisible in the schema — both columns are typed and populated identically, which is why point-in-time correctness is a property of the pipeline, not the table.

    Q60 · MCQ · apply · medium¶

    weather_condition is joined to the weather row for the trip's own hour. The correct classification and fix are:

    A. VALID — the observation exists in weather_hourly.csv B. LEAKAGE — remove the feature entirely C. UNAVAILABLE ONLINE — shift the join to the last observed hour (hour_ts <= date_trunc('hour', feature_ts) - INTERVAL 1 HOUR) on both the training and the serving side, and serve it from the Redis zone key D. STALE — refresh the weather feed hourly and leave the join unchanged

    Answer: C. Rationale: The hourly file lands after the hour it describes, so the value is point-in-time correct offline and simply unobtainable online; a leaking feature must be changed, an unavailable one must be re-sourced — and the shift must be applied on both sides or you have manufactured textbook skew.
