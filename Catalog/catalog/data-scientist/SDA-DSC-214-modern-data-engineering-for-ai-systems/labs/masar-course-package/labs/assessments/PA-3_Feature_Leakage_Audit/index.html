    PA-3 — Feature Leakage Audit: gold.eta_features and a Model Card That Lies¶

    Field Value
    Assessment ID PA-3
    Module M8 — Serving Data to AI and BI Workloads
    Day / Hour Day 5, Hour 4 (first 30 minutes of capstone assembly, run as a timed individual break-out)
    Duration 30 minutes, individual, open-repository / closed-collaboration
    LO mapping LO8 (primary) · LO6 (governance at the serving boundary) · LO7 (point-in-time correctness of a gold product) · LO3 (the training join is an ELT join)
    Weight One third of the 20% practical-assessment band
    Sandbox ./lakehouse/_assessments/pa3/eta_features — a rebuild of gold.eta_features with the same 13 CONVENTIONS columns and a different defect mix from the Lab-8 starter. The participant's own gold.eta_features is never touched.
    Marking Classification 40% · Fixes and the point-in-time join 35% · Honest metric and reporting 25%

    The course question, applied: "What happens to Masar's AI system if THIS part of the data platform fails?" Nothing visible. That is the point. Every check is green, every test passes, the model card reads R² 0.94, and the platform ships a model that will miss by three times what it promised — because the failure is not in the pipeline's mechanics but in when four of its numbers were written.

    Scale note. Figures quoted in this document assume the full-scale generator run (--scale 1.0); the shipped sample is --scale 0.15 — 7,230 trips/day over 5 days (36,150 trips), 873,763 GPS pings, 3,450 drivers, 3,864 vehicles, 48 zones. Grains, ratios and file-count reductions hold at either scale; absolute row counts do not.

    1. Why this exists separately from the Lab-8 drill¶

    Lab 8 Task 3 runs the leakage drill in pairs, with the instructor in the room and the diagnostics supplied. PA-3 is the individually assessed transfer test: the same 13-column contract, a different defect mix, no supplied diagnostics, no pair.

    Two columns deliberately swap class relative to the lab. A participant who memorised the Lab-8 answer key will get both wrong:

    Column Lab-8 starter PA-3 variant
    rolling_avg_speed_10m LEAKAGE (averaged the trip's own pings) VALID — correctly computed from other vehicles' pings strictly before feature_ts
    historical_route_duration VALID (rangeBetween(-2592000, -1)) LEAKAGE — the bound is now (-2592000, 0), so the current trip's own duration is inside its own 30-day average

    The class tally is identical to the lab's (7 VALID / 1 STALE / 4 LEAKAGE / 1 UNAVAILABLE ONLINE), which is deliberate: a participant who counts rather than reasons will still be wrong on two rows, and the tally gives them no signal.

    If PA-3 is delivered before Lab 8 (a cohort running the assessment early, or a re-sit before the drill), use the same variant — nothing in it depends on having seen the lab. Note in the moderation record which order the cohort experienced, because the difficulty is not identical.

    2. Instructor setup¶

    # scripts/assessments/pa3_setup.py
"""PA-3 setup: build the PA-3 variant of gold.eta_features.

EXACTLY the 13 CONVENTIONS columns. Five defects, listed in the answer key.
Run:  python -m scripts.assessments.pa3_setup
"""
from __future__ import annotations

import shutil
from pathlib import Path

from pyspark.sql import functions as F, Window

from masar.spark import get_spark

SILVER_TRIPS     = "./lakehouse/silver/trips"
SILVER_POSITIONS = "./lakehouse/silver/vehicle_positions"
WEATHER          = "data/raw/weather_hourly.csv"
OUT              = "./lakehouse/_assessments/pa3/eta_features"


def main() -> None:
    spark = get_spark("pa3-setup")
    shutil.rmtree(Path(OUT).parent, ignore_errors=True)

    trips = (spark.read.format("delta").load(SILVER_TRIPS)
             .filter(F.col("status") == "completed")
             .withColumn("pickup_epoch", F.col("pickup_ts").cast("long")))
    pos = spark.read.format("delta").load(SILVER_POSITIONS)
    weather = (spark.read.option("header", True).option("inferSchema", True).csv(WEATHER)
               .withColumn("hour_ts", F.to_timestamp("hour_ts")))

    # (A) DEFECT 1 - zone demand: inclusive upper bound admits same-second trips.
    w_demand = (Window.partitionBy("city", "pickup_zone_id")
                      .orderBy("pickup_epoch").rangeBetween(-900, 0))

    # (B) driver recent trips: bound is correct; the STALENESS is an online problem.
    w_driver = (Window.partitionBy("driver_id")
                      .orderBy("pickup_epoch").rangeBetween(-86400, -1))

    # (C) DEFECT 2 - historical route duration: upper bound 0 puts the trip's own
    #     duration inside its own 30-day route average.
    w_route = (Window.partitionBy("pickup_zone_id", "dropoff_zone_id")
                     .orderBy("pickup_epoch").rangeBetween(-2592000, 0))

    # (D) rolling average speed - CORRECT in this variant: other vehicles in the
    #     pickup zone, strictly before feature_ts, this trip excluded.
    zone_speed = (pos.alias("p")
        .join(trips.alias("t2").select(F.col("trip_id").alias("t2_trip"),
                                       F.col("pickup_zone_id").alias("t2_zone")),
              F.col("p.trip_id") == F.col("t2_trip"), "inner")
        .select(F.col("p.trip_id").alias("src_trip"), "t2_zone",
                F.col("p.event_ts").alias("ping_ts"), F.col("p.speed_kmh")))

    feats = (trips
        .withColumn("rolling_zone_demand_15m", F.count("*").over(w_demand))
        .withColumn("driver_recent_trip_count", F.count("*").over(w_driver))
        .withColumn("historical_route_duration", F.avg("duration_min").over(w_route))
        .withColumn("hour_of_day", F.hour("pickup_ts"))
        .withColumn("day_of_week", F.dayofweek("pickup_ts"))
        .withColumn("feature_ts", F.col("pickup_ts")))

    speed_10m = (feats.alias("f").join(zone_speed.alias("z"),
            (F.col("f.pickup_zone_id") == F.col("z.t2_zone")) &
            (F.col("z.src_trip") != F.col("f.trip_id")) &
            (F.col("z.ping_ts") <  F.col("f.feature_ts")) &
            (F.col("z.ping_ts") >= F.expr("f.feature_ts - INTERVAL 10 MINUTES")), "left")
        .groupBy("f.trip_id").agg(F.avg("z.speed_kmh").alias("rolling_avg_speed_10m")))

    out = (feats.join(speed_10m, "trip_id", "left")
        # DEFECT 3 - weather joined to the trip's OWN hour; the file lands after it.
        .join(weather.select(F.col("city").alias("w_city"), "hour_ts",
                             F.col("condition").alias("weather_condition")),
              (F.col("city") == F.col("w_city")) &
              (F.date_trunc("hour", F.col("pickup_ts")) == F.col("hour_ts")), "left")
        # DEFECT 4 - distance_km is the METERED distance, written at dropoff_ts.
        # DEFECT 5 - the label is present and is materialised downstream.
        .select("trip_id", "pickup_zone_id", "dropoff_zone_id",
                "hour_of_day", "day_of_week",
                "rolling_zone_demand_15m", "rolling_avg_speed_10m",
                "driver_recent_trip_count", "weather_condition",
                "distance_km", "historical_route_duration", "feature_ts",
                F.col("duration_min").alias("label_actual_duration_min")))

    assert len(out.columns) == 13, out.columns
    out.write.format("delta").mode("overwrite").save(OUT)
    print(f"[pa3-setup] eta_features: {out.count():,} rows, 13 columns -> {OUT}")


if __name__ == "__main__":
    main()

    3. Participant brief (hand this page out)¶

    PA-3 — Feature Leakage Audit · 30 minutes · individual

    The ETA squad has submitted masar-eta-duration v3.1 for production approval. The model card claims R² 0.941 and MAE 1.87 minutes on trip-duration prediction. Your signature is required on the platform side before rollout.

    You have:

    • The feature table ./lakehouse/_assessments/pa3/eta_features — the 13 CONVENTIONS columns of gold.eta_features, one row per trip_id.
    • The builder that produced it: scripts/assessments/pa3_setup.py.
    • The model card above.
    • silver.trips, silver.vehicle_positions, gold.dim_zone and data/raw/weather_hourly.csv.

    The single test you apply to every column:

    Could this value have been known at prediction time — that is, at feature_ts, the instant the rider taps Request — from data that had already been written?

    Your task, in order:

    1. Classify all 13 columns into exactly one of four classes. Ambiguity is not permitted; if a column could be two, choose the one that would cause the worse production failure and say so.
    Code Meaning The question to ask
    VALID Knowable at feature_ts from data that existed then, and reproducible online "At the moment of Request, could I compute this from data already written?"
    STALE Computable in principle, but the value the online path actually serves is materially older than feature_ts "How old is the value Redis holds at 19:00 on a Thursday?"
    LEAKAGE Depends on information that did not exist at feature_ts — the current instant, the future, or the outcome "Does computing this require knowing anything at or after feature_ts?"
    UNAVAILABLE ONLINE Point-in-time correct offline, but no online path can supply it at inference latency "Is there a key or an API returning this in under 20 ms, right now?"
    1. Name the leaking features and prove each with a query or a computed number, not an assertion.
    2. Fix the training join to be point-in-time correct. Keep every column name — the contract is fixed — and change only how each value is computed and how the training set is assembled. Include the split.
    3. Report the honest metric and write the paragraph you would send the ETA squad.

    Constraints - The output must still have exactly the 13 CONVENTIONS columns, correctly named, at one row per trip_id. - You may not drop a column to "fix" it; a contract column is fixed and must be re-sourced or re-computed. - Do not read the Lab-8 answer key. Two columns are not what they were in the lab.

    Deliverable artefacts (all three required):

    Artefact Content
    PA3_CLASSIFICATION.md The 13-row table: column, class, one-sentence justification naming what the code actually used, and the fix
    src/masar/transform/build_eta_features_pa3.py The corrected builder, plus the corrected training split
    PA3_REPORT.md Both metrics (claimed and honest), the delta, the evidence for each leak, and the paragraph to the ETA squad

    Time budget suggestion: 12 min classify and probe · 10 min fix · 6 min retrain and report · 2 min commit.

    4. Marking scheme¶

    Total 100. Pass ≥ 70 for badge contribution.

    4a. Classification — 40 marks¶

    3 marks per correctly classified column (13 × 3 = 39), rounded to 40 with one discretionary mark for a justification that names the exact window bound or join key responsible.

    A column scores its 3 marks only when the class and the justification are right. A right class with a wrong reason scores 1.

    Partial-credit rule Marks
    Correct class, justification names the mechanism (the bound, the join key, the source column) 3
    Correct class, justification generic ("it leaks", "not available") 1
    driver_recent_trip_count marked LEAKAGE and the staleness also named 3 (see key)
    weather_condition marked LEAKAGE with a correct explanation of the arrival lag 2 (the remediation differs; see key)
    label_actual_duration_min marked "N/A" or "not a feature" 0
    Any column left unclassified or given two classes 0

    Band descriptors — Classification

    Band Marks Descriptor
    Distinction 36–40 12 or 13 correct with mechanism-level justifications; the two Lab-8 reversals (rolling_avg_speed_10m, historical_route_duration) are both correct; the participant states the product assumption dropoff_zone_id rests on
    Proficient 28–35 10–11 correct; typically one of weather_condition / driver_recent_trip_count is misclassified, or one reversal is answered from memory of the lab
    Developing 18–27 7–9 correct; distance_km is found but the subtler window bounds are not; justifications assert rather than name
    Insufficient 0–17 distance_km marked VALID, or fewer than 7 correct

    4b. Fixes and the point-in-time join — 35 marks¶

    Sub-criterion Marks What earns it
    P1. rolling_zone_demand_15m bound corrected 6 rangeBetween(-900, -1) — strictly prior; participant notes the feature's mean falls
    P2. historical_route_duration bound corrected 6 rangeBetween(-2592000, -1); the current trip is excluded from its own route average; null contract for unseen zone pairs stated (impute city median with an is_imputed flag, or omit)
    P3. distance_km re-sourced 8 Replaced with the planned/route distance at booking — routing-engine estimate, or the route/great-circle distance between gold.dim_zone centroids. Column name unchanged
    P4. weather_condition shifted on both sides 5 hour_ts <= date_trunc('hour', feature_ts) - INTERVAL 1 HOUR, applied identically in training and in materialisation
    P5. driver_recent_trip_count remediated as staleness 4 Online refresh cadence matched to volatility (hourly, not nightly) with feature_ts age monitoring; the offline bound is already correct and the participant says so
    P6. Split corrected to a time split 6 Random 75/25 replaced with a temporal split (train < cut-off, test ≥ cut-off), because a random split over a temporally ordered table trains on the future of its own test set

    Band descriptors — Fixes

    Band Marks Descriptor
    Distinction 32–35 All six; the label is also stripped from ONLINE_COLUMNS; the fixed builder still emits exactly 13 correctly named columns and the participant verifies that assertion
    Proficient 25–31 Four or five; typically the split or the weather_condition symmetry is missed
    Developing 15–24 The obvious leak (distance_km) fixed, the window bounds left alone
    Insufficient 0–14 A column dropped instead of re-sourced, the contract broken, or nothing rebuilt

    Sub-criterion Marks What earns it

    Distinction 22–25 All four; the report would survive being forwarded unedited to the squad lead; it names what the honest model still cannot do and what feature work would legitimately raise the number
    Proficient 17–21 Both metrics and most evidence; the paragraph argues statistically rather than operationally
    Developing 10–16 Metrics reported without evidence, or the drop framed as a regression
    Insufficient 0–9 No retrain, or the honest metric asserted without running it

    5. Answer key¶

    5a. Per-column classification — the complete key¶

    # Column Class Justification (what is known at feature_ts vs what the code used) Required fix
    1 trip_id VALID The entity key, assigned at request time. An identifier, not a model input — it must be excluded from the feature vector, but it is knowable at feature_ts and reproducible online, so VALID rather than LEAKAGE. Accept a participant who argues it should be out of scope entirely, provided they say why None. Exclude from the feature vector; keep for joins and traceability
    2 pickup_zone_id VALID The rider's current location resolved to a zone at request time; available online as a direct request parameter None
    3 dropoff_zone_id VALID Masar's booking flow requires a stated destination before request, so this is an input, not an outcome. Product-dependent — if destination-less requests existed it would be UNAVAILABLE ONLINE for that segment None. Document the product assumption
    4 hour_of_day VALID Derived purely from feature_ts, which at inference is the request timestamp. Deterministic, zero-latency, no source dependency None
    5 day_of_week VALID As #4. Interpret against the KSA working week (Fri–Sat weekend), consistent with gold.dim_date.is_weekend None
    6 rolling_zone_demand_15m LEAKAGE rangeBetween(-900, 0). rangeBetween bounds are inclusive and operate on the ordering column's value range, so an upper bound of 0 admits every trip whose pickup_epoch equals this one's — every trip starting in the same second, in the same zone. At Riyadh rush-hour density that is several trips, and they are the future rangeBetween(-900, -1). Expect the feature's mean to fall by a few percent — small, correlated with congestion, and therefore the dangerous kind
    7 rolling_avg_speed_10m VALID Reversed from the Lab-8 starter. Here it averages speed_kmh from other vehicles in the pickup zone over the 10 minutes strictly before feature_ts, with this trip_id excluded by the join predicate. Zone-grained, so it is materialisable to Redis. Verify the two guards explicitly: z.src_trip != f.trip_id and z.ping_ts < f.feature_ts None. Verify both guards; document the null contract for zones with no recent pings
    8 driver_recent_trip_count STALE rangeBetween(-86400, -1) is point-in-time correct offline. The failure is online: the model card says the online store is refreshed by the nightly DAG, so at 19:00 on a Thursday the value is 19 hours old — a driver who has completed 11 trips today reads as 0 and the model treats an exhausted driver as a fresh one. Accept LEAKAGE as a defensible second answer only if the participant also names the staleness, because that is the failure that actually bites Two-part: refresh the driver slice on a cadence matched to the feature's volatility (hourly), and monitor feature_ts age as a serving SLA
    9 weather_condition UNAVAILABLE ONLINE data/raw/weather_hourly.csv lands after the hour it describes. Joining a 07:14 trip to the 07:00 row is legitimate offline — that observation existed when the table was built — but at 07:14 live the 07:00 row has not arrived. Point-in-time correct and unobtainable. The distinction from LEAKAGE is operational: a leaking feature must be changed, an unavailable one must be re-sourced Join to the last observed hour: hour_ts <= date_trunc('hour', feature_ts) - INTERVAL 1 HOUR, applied identically in training and in materialisation, and served from the Redis zone key. One hour of staleness — but the same hour on both sides
    10 distance_km LEAKAGE The metered distance the vehicle actually travelled, written at dropoff_ts in silver.trips. Pearson r with the label ≈ 0.95 and it carries 0.601 of the card's stated gain — the model is reading the answer. At inference the value does not exist, so serving must substitute something the model was trained to trust heavily. The single largest contributor to the inflated metric Recompute as the planned route distance at booking: the routing engine's estimate, or offline the route/great-circle distance between gold.dim_zone centroids. Keep the column name; change only the source. May be internally aliased planned_distance_km for clarity
    11 historical_route_duration LEAKAGE Reversed from the Lab-8 starter. rangeBetween(-2592000, 0) includes the current row, so each trip's own duration_min — the label itself — is one term inside its own 30-day route average. On a sparse zone pair with two prior trips that is a third of the feature; on an unseen pair it is the label. Subtle, plausible, and it survives every schema and range check rangeBetween(-2592000, -1). Define and document the null contract for zone pairs with no prior trips (impute the city median with an is_imputed flag, or omit)
    12 feature_ts VALID The as-of timestamp itself — the anchor every other column's correctness is defined against. Metadata, not a model input; knowable by definition, because it is the request time None. Exclude from the feature vector; retain for point-in-time joins, materialisation and freshness monitoring
    13 label_actual_duration_min LEAKAGE The target. Trivially leaking if it enters the feature vector, and — as the model card in fact specifies — a serving hazard, because it appears in ONLINE_COLUMNS, so the online store would be publishing the answer. Do not accept "N/A": classifying the label as LEAKAGE is the discipline that catches the non-obvious label proxies, which is exactly what #10 and #11 are Strip from the feature vector and from ONLINE_COLUMNS. Keep in the offline table — that is what a training set is

    Tally: VALID 7 · STALE 1 · LEAKAGE 4 · UNAVAILABLE ONLINE 1.

    5b. The two defects that live in the model card, not the table¶

    Defect Why it matters Fix
    Random 75/25 split on a temporally ordered table Every test row has training rows from after it. Even with all four leaking features repaired, a random split inflates the metric, because the model has seen the same evening's traffic conditions from both sides. A time split is the only honest estimator for a forecasting task --split time --test-days 2: train on 2026-06-01..28, test on 29–30
    label_actual_duration_min in ONLINE_COLUMNS The online store would serve the answer to anyone who can read a zone key, and a downstream consumer would eventually "use the feature that correlates best". It is also a governance finding: the label is trip-grained and therefore should never be materialised at zone grain Remove it, and every trip-grained column, from ONLINE_COLUMNS; the online payload is zone-grained only
    "Known limitations: none material" Not a defect in itself but the finding that frames the report. A card claiming R² 0.94 on trip duration with no stated limitation has not been reviewed Rewrite the section with the honest metric, the point-in-time contract, and the serving staleness bound

    5e. The reference paragraph to the ETA squad¶

    Recommendation: do not ship v3.1 as measured. The offline numbers are not wrong arithmetic; they are the right arithmetic on the wrong table.

    Four of the thirteen features in gold.eta_features used information that did not exist when a prediction would be made. distance_km is the metered distance written at dropoff_ts, and it correlates 0.948 with the label — the model was reading the answer, and it carried 60% of the reported gain. historical_route_duration included the current trip inside its own 30-day route average; on a zone pair with no prior trips the feature equals the label exactly. rolling_zone_demand_15m counted every trip starting in the same second, which at rush hour in Riyadh is several trips that had not happened yet. And the label itself is listed in ONLINE_COLUMNS, so the online store is configured to publish the answer to anything that can read a zone key. Separately, the random 75/25 split trains on the future of its own test set, which inflates the number again even after the features are repaired.

    Rebuilt point-in-time correctly — planned route distance at booking instead of metered distance, both rolling windows made strictly prior, weather shifted to the last observed hour on both the training and the serving side, and a temporal split — the model scores R² 0.706, MAE 4.71 minutes. That is not a regression. It is the first honest measurement of this model, and it is the number that will hold up live.

    The operational case for the honest number is a cost argument, not a statistical one. The leaking model tells the dispatcher it will miss by 1.9 minutes and then misses by about 5; the honest model tells the dispatcher it will miss by 4.7 and misses by about 4.7. The second is cheaper precisely because you can plan against it. Two things would legitimately raise it: a live traffic-speed feed at zone grain served from Redis at under 20 ms, and a routing-engine ETA as a feature rather than a distance. Both are feature work. Neither is a metric change.

    One governance item, separate from accuracy: driver_recent_trip_count is point-in-time correct offline but refreshed nightly online, so at 19:00 it is 19 hours stale and an exhausted driver reads as fresh. Move that slice to an hourly refresh and monitor feature_ts age as a serving SLA. And the card's "Known limitations: none material" should be rewritten — a model card that claims R² 0.94 on trip duration with no stated limitation has not been reviewed, and that is the finding that should have caught this before I did.
