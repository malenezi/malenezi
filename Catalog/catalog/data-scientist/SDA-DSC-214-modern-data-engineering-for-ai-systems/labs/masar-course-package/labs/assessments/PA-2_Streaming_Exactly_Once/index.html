    PA-2 — Streaming: Exactly-Once Ingestion and an Event-Time Window¶

    Field Value
    Assessment ID PA-2
    Module M5 — Streaming Data and Event-Driven Architectures
    Day / Hour Day 4, end of Hour 5 (after the governance micro-lecture)
    Duration 30 minutes, individual, open-repository / closed-collaboration
    LO mapping LO5 (primary) · LO4 (Delta atomic commit as the idempotent sink) · LO6 (late-data correctness)
    Weight One third of the 20% practical-assessment band
    Sandbox Kafka topic masar.gps.pings.pa2 (3 partitions) → ./lakehouse/_assessments/pa2/gps_events and ./lakehouse/_assessments/pa2/zone_demand. The cohort's bronze.gps_events is never touched.
    Marking Correctness of fix 50% · Evidence 30% · Reasoning about semantics 20%

    The course question, applied: "What happens to Masar's AI system if THIS part of the data platform fails?" A stream without a checkpoint invents vehicles. A processing-time window files a 20-minute-late ping under the wrong quarter-hour. Both errors flow into rolling_zone_demand_15m, so the ETA model predicts a rush hour that is not happening and surge pricing fires in an empty district — at Masar's scale, in a real city, for real riders.

    The broken job (the artefact under test)¶

    # src/masar/stream/ingest_gps_pa2.py   <-- SHIPPED BROKEN
"""PA-2: land the PA-2 GPS topic into a Delta table and publish 15-minute
zone demand. Two queries, one file.

Written in a hurry by an engineer who was told the pipeline 'basically works'.
"""
from __future__ import annotations

from pyspark.sql import functions as F, DataFrame
from pyspark.sql.types import (StructType, StructField, StringType,
                               DoubleType, TimestampType)

from masar.spark import get_spark

TOPIC     = "masar.gps.pings.pa2"
BOOTSTRAP = "localhost:9092"
BRONZE    = "./lakehouse/_assessments/pa2/gps_events"
DEMAND    = "./lakehouse/_assessments/pa2/zone_demand"

PAYLOAD_SCHEMA = StructType([
    StructField("lat",         DoubleType()),
    StructField("lon",         DoubleType()),
    StructField("speed_kmh",   DoubleType()),
    StructField("heading_deg", DoubleType()),
    StructField("accuracy_m",  DoubleType()),
])
PING_SCHEMA = StructType([
    StructField("event_id",         StringType()),
    StructField("vehicle_id",       StringType()),
    StructField("driver_id",        StringType()),
    StructField("trip_id",          StringType()),
    StructField("ts",               TimestampType()),
    StructField("payload",          PAYLOAD_SCHEMA),
    StructField("producer_version", StringType()),
])


def parse(raw: DataFrame) -> DataFrame:
    return (raw.select(
        F.from_json(F.col("value").cast("string"), PING_SCHEMA).alias("p"),
        F.col("topic"), F.col("partition"), F.col("offset"),
        F.col("timestamp").alias("_kafka_ts"))
        .select(
            F.col("p.event_id").alias("event_id"),
            F.col("p.vehicle_id").alias("vehicle_id"),
            F.col("p.driver_id").alias("driver_id"),
            F.col("p.trip_id").alias("trip_id"),
            F.col("p.ts").alias("ts"),
            F.col("p.payload").alias("payload"),
            F.col("p.producer_version").alias("producer_version"),
            F.col("_kafka_ts"),
            F.concat_ws("/", F.lit("kafka:/"), F.col("topic"),
                        F.col("partition").cast("string")).alias("_source_file"),
            F.col("offset").alias("_kafka_offset")))


def write_batch(batch_df: DataFrame, batch_id: int) -> None:
    out = (batch_df
           .withColumn("_batch_id", F.lit(batch_id).cast("long"))
           .withColumn("_ingested_at", F.current_timestamp()))
    (out.write.format("delta").mode("append").save(BRONZE))
    print(f"Batch {batch_id}: appended {out.count():,} pings", flush=True)


def run() -> None:
    spark = get_spark("pa2-gps")
    raw = (spark.readStream.format("kafka")
           .option("kafka.bootstrap.servers", BOOTSTRAP)
           .option("subscribe", TOPIC)
           .option("startingOffsets", "earliest")
           .option("maxOffsetsPerTrigger", 8000)
           .load())
    events = parse(raw)

    # ---- query 1: land to bronze -----------------------------------------
    q1 = (events.writeStream
          .queryName("pa2_bronze")
          .foreachBatch(write_batch)
          .outputMode("append")
          .trigger(processingTime="20 seconds")
          .start())

    # ---- query 2: 15-minute zone demand ----------------------------------
    demand = (events
              .groupBy(F.window(F.current_timestamp(), "15 minutes"),
                       F.col("trip_id"))
              .agg(F.count("*").alias("pings")))

    q2 = (demand.writeStream
          .queryName("pa2_demand")
          .outputMode("complete")
          .format("delta")
          .option("checkpointLocation", "./lakehouse/_assessments/pa2/_ckpt")
          .trigger(processingTime="20 seconds")
          .start(DEMAND))

    q1.awaitTermination()
    q2.awaitTermination()


if __name__ == "__main__":
    run()

    Four faults are present. Tell participants there is more than one; do not say how many.

    # Fault Where
    1 Query 1 has no checkpointLocation — restart replays from earliest q1
    2 Query 2 uses F.current_timestamp() — a processing-time window demand
    3 No watermark on the aggregation, and outputMode("complete") — unbounded state demand
    4 No idempotent-write guard on the sink (txnAppId / txnVersion), and the grain of query 2 is trip_id, not pickup_zone_id — it is not zone demand at all write_batch, demand

    Fault 4 has two halves and is where the distinction band separates: the second half is a semantic error that no amount of streaming discipline would catch.

    2. Participant brief (hand this page out)¶

    PA-2 — Streaming Exactly-Once · 30 minutes · individual

    The PA-2 GPS pipeline was written under time pressure and has been running for a week. Operations report two things: the zone-demand panel shows demand spikes that field staff cannot corroborate, and the row count in the landing table grows every time the job is restarted after a deploy.

    You have:

    • Topic masar.gps.pings.pa2, 3 partitions, 40,000 pings already produced and keyed by trip_id. ~500 of them are back-dated 2–30 minutes (the late-ping fixture).
    • Job src/masar/stream/ingest_gps_pa2.py — two streaming queries in one file.
    • Sinks ./lakehouse/_assessments/pa2/gps_events and ./lakehouse/_assessments/pa2/zone_demand.

    Your task, in order:

    1. Produce exactly-once ingestion. After your fix, a kill and restart mid-batch must leave the landing table with exactly one row per ping the producer sent. Source-level duplicate event_ids from the feed itself are a data problem — do not confuse them with pipeline duplicates, and say which is which in your evidence.
    2. Produce an event-time windowed zone demand with a watermark. The grain must be (pickup_zone_id, window); the window must be 15 minutes on the event's own timestamp; late data must be admitted within a stated lateness bound and dropped beyond it.
    3. Prove it. A kill/restart transcript with counts taken before the kill, immediately after the kill, and after the restart drains. State what your watermark costs you at both ends.

    Constraints - Do not delete the sink table or its _delta_log to "reset". - Do not re-produce to the topic; the 40,000 pings are the fixed input. - Each query gets its own checkpoint directory. Do not share one. - Wire schema is fixed (CONVENTIONS): do not invent columns.

    Deliverable artefacts (all three required):

    Artefact Content
    src/masar/stream/ingest_gps_pa2.py The repaired job
    PA2_EVIDENCE.md The kill/restart proof table, the late-data table, and the consumer-lag reading, as pasted transcripts
    PA2_REASONING.md Where exactly-once is guaranteed and by which two mechanisms (name file paths, not concepts); why event time rather than processing time; your watermark value and what it costs at each end

    Time budget suggestion: 10 min fix · 12 min run and prove · 5 min reasoning · 3 min commit.

    4. Model answer¶

    4a. The repaired job (changed regions only)¶

    BRONZE_CKPT = "./lakehouse/_assessments/pa2/_checkpoints/pa2_bronze"    # C1: one per query
DEMAND_CKPT = "./lakehouse/_assessments/pa2/_checkpoints/pa2_demand"    # C1
TXN_APP_ID  = "masar_pa2_gps_bronze"                                     # C2
WATERMARK   = "10 minutes"                                               # C4: see reasoning
ZONES       = "./lakehouse/silver/trips"                                 # C5: trip -> zone


def write_batch(batch_df: DataFrame, batch_id: int) -> None:
    out = (batch_df
           .withColumn("_batch_id", F.lit(batch_id).cast("long"))
           .withColumn("_ingested_at", F.current_timestamp())
           .withColumn("ingest_date", F.to_date(F.col("_kafka_ts"))))
    (out.write.format("delta").mode("append")
        .partitionBy("ingest_date")
        .option("txnAppId", TXN_APP_ID)        # C2: replay of this batch_id is dropped
        .option("txnVersion", batch_id)
        .option("mergeSchema", "false")
        .save(BRONZE))
    print(f"Batch {batch_id}: appended {out.count():,} pings", flush=True)


def run() -> None:
    spark = get_spark("pa2-gps")
    raw = (spark.readStream.format("kafka")
           .option("kafka.bootstrap.servers", BOOTSTRAP)
           .option("subscribe", TOPIC)
           .option("startingOffsets", "earliest")
           .option("maxOffsetsPerTrigger", 8000)
           .option("failOnDataLoss", "true")
           .load())
    events = parse(raw)

    # ---- query 1: land to bronze, exactly-once ---------------------------
    q1 = (events.writeStream
          .queryName("pa2_bronze")
          .foreachBatch(write_batch)
          .outputMode("append")
          .option("checkpointLocation", BRONZE_CKPT)     # C1
          .trigger(processingTime="20 seconds")
          .start())

    # ---- query 2: EVENT-TIME zone demand, watermarked --------------------
    # C5: the ping carries trip_id, not a zone. The zone is a property of the
    # trip, so resolve it from silver.trips - a static, broadcastable dimension.
    trip_zone = (spark.read.format("delta").load(ZONES)
                 .select("trip_id", "pickup_zone_id"))

    demand = (events
              .withWatermark("ts", WATERMARK)                       # C4
              .join(F.broadcast(trip_zone), "trip_id", "left")
              .groupBy(F.window(F.col("ts"), "15 minutes"),         # C3: event time
                       F.col("pickup_zone_id"))
              .agg(F.countDistinct("trip_id").alias("active_trips"),
                   F.count("*").alias("pings")))

    q2 = (demand.writeStream
          .queryName("pa2_demand")
          .outputMode("append")                # C4: append is the watermarked mode
          .format("delta")
          .option("checkpointLocation", DEMAND_CKPT)     # C1
          .trigger(processingTime="20 seconds")
          .start(DEMAND))

    spark.streams.awaitAnyTermination()

    Marker's note. outputMode("update") with a Delta sink is not supported; a participant who keeps complete after adding a watermark has not understood that the watermark exists to let windows close. Accept append only. Accept countDistinct("trip_id") or a trip_id-level pre-aggregation for active_trips; reject a demand table whose grain is trip_id.

    4c. PA2_REASONING.md¶

    Where exactly-once lives. Neither Kafka nor Delta provides it alone. Kafka provides durable, replayable at-least-once delivery — offsets survive and can be rewound. Delta provides an atomic, idempotent sink — a micro-batch commit is all-or-nothing, and txnAppId="masar_pa2_gps_bronze" with txnVersion=batch_id makes a replayed batch a no-op at the sink. Exactly-once is the composition, and it is materialised in exactly one place: ./lakehouse/_assessments/pa2/_checkpoints/pa2_bronze, which records which Kafka offsets were included in each committed Delta transaction. After the kill, the restart read that offset log, resumed at batch 3, and could not re-append what had already committed. The second query has its own checkpoint at _checkpoints/pa2_demand; had I pointed both at one directory, the second query would have read the first's offset log and state and either skipped data it never processed or replayed state that does not belong to it — and Spark does not reliably fail loudly when that happens, which is why one checkpoint per query is a rule and not a preference.

    Why event time. The observed lag in this feed reaches 1,798 seconds — nearly 30 minutes. A window built on current_timestamp() files each ping under the quarter-hour in which the pipeline happened to see it, so a batch of pings from 07:50 that arrived at 08:19 inflates the 08:15 window and leaves 07:45 under-reported. Both errors are then read by rolling_zone_demand_15m, so the ETA model sees a rush hour that did not occur in a zone where it did not occur, and surge fires against phantom demand. Event time makes the answer a property of what happened; processing time makes it a property of how the pipeline was feeling. I keep _kafka_ts alongside ts because processing time is still the right clock for operational metrics — lag, staleness, alerting.

    Watermark: 10 minutes. The fixture's late pings are back-dated 2–30 minutes, so 10 minutes admits the bulk of genuine mobile-network lateness and drops the long tail (41 pings, 8% of the late fixture). Too short — 30 seconds — drops correct-but-late pings, so demand systematically under-reports in exactly the congested zones where telemetry is slowest, which is a bias, not noise. Too long — 30 minutes — keeps window state for half an hour, growing memory and delaying every window's finalisation, so the demand feature the model reads is 30 minutes behind reality. Ten minutes is the point where the marginal ping recovered is worth less than the latency it costs. What would change it: a measured shift in the p99 of _kafka_ts − ts (this feed's is ~9 minutes), or a downstream consumer whose SLA cannot tolerate a 10-minute finalisation delay — in which case the correct move is a shorter watermark plus a scheduled late-data reconciliation batch, not a silently lossy stream.
