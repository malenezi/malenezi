    1. Why this lab matters¶

    The course question: "What happens to Masar's AI system if THIS part of the data platform fails?"

    The ETA model that riders see in the Masar app does not consume trips. It consumes vehicle positions — a continuous stream of GPS pings from ~14,000 vehicles across Riyadh, Jeddah, Dammam, Mecca and Medina. Everything downstream of this lab is fed by the pipeline you are about to build:

    Vehicles ──► Kafka ──► Spark Structured Streaming ──► bronze.gps_events ──► silver.vehicle_positions ──┬──► gold.eta_features   (AI)
 (GPS SDK)   masar.      exactly-once, checkpointed    (raw, append-only,      (deduped, unit-normalised,│
             gps.pings                                  _ingested_at,           watermarked)             └──► operations alerts (Ops)
                                                        _source_file,
                                                        _batch_id)

    Four concrete failure modes, and what each does to the AI system:

    If this fails… The AI system experiences…
    No checkpoint on the streaming query Restart replays committed offsets. bronze.gps_events gains ~7,000 duplicate pings. rolling_zone_demand_15m inflates, the ETA model predicts a phantom rush hour, surge fires in an empty district.
    Duplicate event_id not deduplicated at silver Same physical vehicle counted twice in rolling_avg_speed_10m. Speed averages are unaffected but demand counts are not — the model's most important feature drifts by +0.4% permanently.
    Out-of-order / late ts aggregated on processing time A ping that happened at 07:58 but arrived at 08:04 (tunnel, dead zone, phone buffering) is counted in the 08:00–08:05 window. Demand is misattributed to the wrong five minutes; dispatch rebalances drivers into a spike that already ended.
    Watermark too aggressive Pings past tolerance are silently dropped. The zone with the worst cellular coverage — reliably the one with the highest surge — systematically under-reports demand. The model learns that coverage holes are quiet places.

    Streaming failures are rarely loud. They do not raise exceptions; they produce plausible wrong numbers. Task 3 of this lab is the drill that turns "exactly-once" from a slogan into a number you counted yourself.

    3. Tasks¶

    Task 1 — Produce Masar GPS pings into Kafka (8 min)¶

    Open src/masar/stream/gps_producer.py. The starter file emits pings without a key, which is deliberate mistake #4 from the module. Fix it and add the fixture replay modes.

    # src/masar/stream/gps_producer.py
"""Replay Masar GPS pings into Kafka.

Key = trip_id  =>  all pings for one trip land in ONE partition  =>  strictly
ordered per trip. Without a key Kafka round-robins and per-trip order is lost.
"""
from __future__ import annotations
import argparse, json, sys, time
from pathlib import Path
from kafka import KafkaProducer

TOPIC = "masar.gps.pings"
BOOTSTRAP = "localhost:9092"


def make_producer() -> KafkaProducer:
    return KafkaProducer(
        bootstrap_servers=BOOTSTRAP,
        key_serializer=lambda k: k.encode("utf-8"),
        value_serializer=lambda v: json.dumps(v).encode("utf-8"),
        acks="all",            # durability: leader + replicas acknowledge
        linger_ms=20,          # small batching window; do NOT set this to 0
        retries=5,
    )


def emit(producer: KafkaProducer, ping: dict) -> None:
    # ping shape (data/raw/gps/gps_YYYY-MM-DD.ndjson):
    # {"event_id","vehicle_id","driver_id","trip_id","ts",
    #  "payload":{"lat","lon","speed_kmh","heading_deg","accuracy_m"},
    #  "producer_version"}
    producer.send(TOPIC, key=ping["trip_id"], value=ping)


def replay(path: Path, rate_hz: float, limit: int | None) -> int:
    producer = make_producer()
    sent = 0
    delay = 0.0 if rate_hz <= 0 else 1.0 / rate_hz
    with path.open() as fh:
        for line in fh:
            line = line.strip()
            if not line:
                continue
            emit(producer, json.loads(line))
            sent += 1
            if sent % 1000 == 0:
                print(f"  … {sent:>7,} pings sent", flush=True)
            if limit and sent >= limit:
                break
            if delay:
                time.sleep(delay)
    producer.flush()
    print(f"[producer] {sent:,} pings -> {TOPIC} from {path.name}")
    return sent


if __name__ == "__main__":
    ap = argparse.ArgumentParser()
    ap.add_argument("--source", default="data/raw/gps/gps_2026-06-01.ndjson*")
    ap.add_argument("--rate", type=float, default=2000.0, help="pings/sec; 0 = as fast as possible")
    ap.add_argument("--limit", type=int, default=50000)
    a = ap.parse_args()
    sys.exit(0 if replay(Path(a.source), a.rate, a.limit) else 1)

    Task 2 — Stream Kafka → bronze.gps_events exactly-once (14 min)¶

    bronze.gps_events must satisfy the bronze contract from CONVENTIONS: append-only, never mutated, carries _ingested_at, _source_file, _batch_id. Implement src/masar/stream/ingest_gps_stream.py.

    # src/masar/stream/ingest_gps_stream.py
"""Kafka masar.gps.pings -> bronze.gps_events, exactly-once.

Exactly-once is NOT a single feature. It is the composition of two things:
  (1) Kafka offsets recorded durably in the query CHECKPOINT, and
  (2) Delta's ATOMIC per-micro-batch commit, made idempotent with
      txnAppId/txnVersion so a replayed batch_id is a no-op.
Kill the job mid-batch and the batch either committed fully or not at all;
the restart resumes from the last committed offset. No loss, no duplication.
"""
from __future__ import annotations
from pyspark.sql import functions as F, DataFrame
from pyspark.sql.types import (StructType, StructField, StringType,
                               DoubleType, TimestampType)
from masar.spark import get_spark

TOPIC        = "masar.gps.pings"
BOOTSTRAP    = "localhost:9092"
BRONZE_PATH  = "./lakehouse/bronze/gps_events"
CHECKPOINT   = "./lakehouse/_checkpoints/gps_events_bronze"   # ONE per query. Sacred.
TXN_APP_ID   = "masar_gps_events_bronze"

# The wire schema is EXACTLY data/raw/gps/gps_YYYY-MM-DD.ndjson. Do not invent columns.
PAYLOAD_SCHEMA = StructType([
    StructField("lat",         DoubleType()),
    StructField("lon",         DoubleType()),
    StructField("speed_kmh",   DoubleType()),
    StructField("heading_deg", DoubleType()),
    StructField("accuracy_m",  DoubleType()),
])

PING_SCHEMA = StructType([
    StructField("event_id",         StringType()),
    StructField("vehicle_id",       StringType()),
    StructField("driver_id",        StringType()),
    StructField("trip_id",          StringType()),
    StructField("ts",               TimestampType()),   # EVENT time, from the device
    StructField("payload",          PAYLOAD_SCHEMA),
    StructField("producer_version", StringType()),
])


def parse(raw: DataFrame) -> DataFrame:
    return (raw
        .select(
            F.from_json(F.col("value").cast("string"), PING_SCHEMA).alias("p"),
            F.col("topic"),
            F.col("partition"),
            F.col("offset"),
            F.col("timestamp").alias("_kafka_ts"))     # PROCESSING time — keep both clocks
        .select(
            F.col("p.event_id").alias("event_id"),
            F.col("p.vehicle_id").alias("vehicle_id"),
            F.col("p.driver_id").alias("driver_id"),
            F.col("p.trip_id").alias("trip_id"),
            F.col("p.ts").alias("ts"),                 # keep the raw event time verbatim
            F.col("p.payload").alias("payload"),       # bronze keeps the struct AS RECEIVED
            F.col("p.producer_version").alias("producer_version"),
            F.col("_kafka_ts"),
            F.concat_ws("/", F.lit("kafka:/"), F.col("topic"),
                        F.col("partition").cast("string")).alias("_source_file"),
            F.col("offset").alias("_kafka_offset")))


def write_batch(batch_df: DataFrame, batch_id: int) -> None:
    """foreachBatch gives us the batch_id, which we use twice:
       - as the bronze lineage column `_batch_id`
       - as Delta's txnVersion, making a replayed batch an idempotent no-op."""
    out = (batch_df
           .withColumn("_batch_id", F.lit(batch_id).cast("long"))
           .withColumn("_ingested_at", F.current_timestamp())
           .withColumn("ingest_date", F.to_date(F.col("_kafka_ts"))))
    (out.write
        .format("delta")
        .mode("append")
        .partitionBy("ingest_date")
        .option("txnAppId", TXN_APP_ID)      # idempotent-write guard
        .option("txnVersion", batch_id)      # replay of this batch_id is dropped
        .option("mergeSchema", "false")      # bronze schema is fixed; drift must be visible
        .save(BRONZE_PATH))
    print(f"Batch {batch_id}: appended {out.count():,} pings", flush=True)


def run(starting_offsets: str = "earliest", trigger_seconds: int = 30) -> None:
    spark = get_spark("masar-gps-events-bronze")
    raw = (spark.readStream
           .format("kafka")
           .option("kafka.bootstrap.servers", BOOTSTRAP)
           .option("subscribe", TOPIC)
           .option("startingOffsets", starting_offsets)
           .option("maxOffsetsPerTrigger", 20000)     # bounded batch => predictable latency
           .option("failOnDataLoss", "true")          # surface retention gaps loudly
           .load())

    (parse(raw).writeStream
        .queryName("gps_events_bronze")
        .foreachBatch(write_batch)
        .outputMode("append")
        .option("checkpointLocation", CHECKPOINT)
        .trigger(processingTime=f"{trigger_seconds} seconds")
        .start()
        .awaitTermination())


if __name__ == "__main__":
    run()

    Task 3 — The kill / restart exactly-once proof (10 min — do not skip)¶

    This is the module's thesis. Every pair kills the job and counts.

    # 3a. Record the pre-kill state
python -m masar.tools.count --table bronze.gps_events --distinct event_id
#   rows=50,000  distinct_event_id=49,801  (the 0.4% seeded dup rate — expected, from source)

# 3b. Re-arm the producer so there is in-flight work to interrupt
python -m masar.stream.gps_producer --limit 60000 --rate 3000 &
PRODUCER_PID=$!

# 3c. Start the stream, then KILL IT MID-BATCH.
#     Wait until you see "Batch N: appended …" scroll past, then Ctrl-C
#     WITHIN the next few seconds — you want to interrupt a batch in flight,
#     not between batches.
python -m masar.stream.ingest_gps_stream
# ^C

# 3d. Count immediately after the kill
python -m masar.tools.count --table bronze.gps_events --distinct event_id

# 3e. Restart. Change NOTHING. The checkpoint does the work.
python -m masar.stream.ingest_gps_stream

# 3f. Final count once batches drain to 0
wait $PRODUCER_PID
python -m masar.tools.count --table bronze.gps_events --distinct event_id

    Task 4 — Late, duplicate and out-of-order events (12 min)¶

    Now inject the defect classes from data/fixtures/late_pings/. One fixture carries all three — late arrival, duplicate event_id and shuffled ts — because that is how they actually arrive: one reconnecting device flushes a backlog and every class is in it. Keep the bronze stream running throughout; bronze accepts everything, correctness is silver's job.

    # 4a. Produce the whole fixture: 520 pings, back-dated 2–47 minutes, 20 duplicate
#     event_ids, deliberately unsorted.
python -m masar.stream.gps_producer \
  --source data/fixtures/late_pings/gps_late_2026-06-04.ndjson --rate 0

# 4b. Isolate the duplicate-event_id class from what you just produced.
python -m masar.tools.sql --query "
  SELECT event_id, COUNT(*) AS copies
  FROM delta.\`./lakehouse/bronze/gps_events\`
  GROUP BY event_id HAVING COUNT(*) > 1 ORDER BY copies DESC LIMIT 10"

# 4c. Isolate the out-of-order class: pings whose ts goes backwards within a trip.
python -m masar.tools.sql --query "
  SELECT trip_id, COUNT(*) AS backwards_steps FROM (
    SELECT trip_id, ts,
           LAG(ts) OVER (PARTITION BY trip_id ORDER BY _ingested_at, ts) AS prev_ts
    FROM delta.\`./lakehouse/bronze/gps_events\`)
  WHERE prev_ts IS NOT NULL AND ts < prev_ts
  GROUP BY trip_id ORDER BY backwards_steps DESC LIMIT 10"

# 4d. Inspect what bronze actually received
python -m masar.tools.sql --query "
  SELECT
    COUNT(*)                                            AS rows,
    COUNT(DISTINCT event_id)                            AS distinct_events,
    COUNT(*) - COUNT(DISTINCT event_id)                 AS duplicate_rows,
    MIN(ts)                                             AS min_event_ts,
    MAX(ts)                                             AS max_event_ts,
    MAX(_kafka_ts)                                      AS max_processing_ts,
    ROUND(AVG(UNIX_TIMESTAMP(_kafka_ts) - UNIX_TIMESTAMP(ts)), 1) AS avg_lag_seconds,
    ROUND(MAX(UNIX_TIMESTAMP(_kafka_ts) - UNIX_TIMESTAMP(ts)), 1) AS max_lag_seconds
  FROM delta.\`./lakehouse/bronze/gps_events\`
"

    Task 5 — silver.vehicle_positions: dedupe, watermark, normalise (10 min)¶

    Silver's contract: one row per event_id, event-time ordered, units normalised, only positions accurate enough to trust.

    # src/masar/stream/build_vehicle_positions.py
"""bronze.gps_events -> silver.vehicle_positions (streaming).

Silver contract:
  * exactly one row per event_id                (dropDuplicatesWithinWatermark)
  * event-time semantics with 5-minute lateness (withWatermark on event_ts)
  * speed_kmh ALWAYS in km/h                    (producer_version 2.5.0 emits m/s)
  * accuracy_m <= 50                            (worse fixes are not positions, they are noise)
"""
from __future__ import annotations
from pyspark.sql import functions as F
from masar.spark import get_spark

BRONZE_PATH = "./lakehouse/bronze/gps_events"
SILVER_PATH = "./lakehouse/silver/vehicle_positions"
CHECKPOINT  = "./lakehouse/_checkpoints/vehicle_positions_silver"   # its OWN checkpoint
WATERMARK   = "5 minutes"
MAX_ACCURACY_M = 50.0

def run() -> None:
    spark = get_spark("masar-vehicle-positions")

    bronze = spark.readStream.format("delta").load(BRONZE_PATH)

"""Two consumers of silver.vehicle_positions. Neither knows the other exists.

  A) ETA feature input  -> gold.eta_features' rolling inputs (event-time windowed)
  B) Operations alerts  -> ops console (processing-time is CORRECT here: an alert
                            is about NOW, not about when the event happened)

from pyspark.sql import functions as F
from masar.spark import get_spark

SILVER_PATH = "./lakehouse/silver/vehicle_positions"

def eta_feature_input() -> None:
    """Event-time 15-min zone demand + 10-min avg speed: the two rolling inputs
    consumed by gold.eta_features (rolling_zone_demand_15m, rolling_avg_speed_10m)."""
    spark = get_spark("masar-eta-feature-input")
    positions = spark.readStream.format("delta").load(SILVER_PATH)

    rolling = (positions
        .withWatermark("event_ts", "5 minutes")
        .groupBy(F.window("event_ts", "15 minutes", "5 minutes").alias("w"),
                 F.col("trip_id"))
        .agg(F.countDistinct("vehicle_id").alias("rolling_zone_demand_15m"),
             F.avg("speed_kmh").alias("rolling_avg_speed_10m"))
        .select(F.col("w.start").alias("window_start"),
                F.col("w.end").alias("window_end"),
                "trip_id", "rolling_zone_demand_15m", "rolling_avg_speed_10m"))

    (rolling.writeStream.format("delta").outputMode("append")
        .option("checkpointLocation", "./lakehouse/_checkpoints/eta_feature_input")
        .trigger(processingTime="60 seconds")
        .start("./lakehouse/gold/_streaming/eta_feature_input")
        .awaitTermination())

    positions = spark.readStream.format("delta").load(SILVER_PATH)

        .withColumn("alert_type",

        .option("checkpointLocation", "./lakehouse/_checkpoints/ops_alerts")
        .trigger(processingTime="30 seconds")
        .start()
        .awaitTermination())

    5. Self-check questions¶

    Q1. Exactly-once is often described as a Kafka feature. Precisely which component in your pipeline provides it, and what would break if you moved the checkpoint into the same directory as another query's?

    Answer Neither Kafka nor Delta provides exactly-once alone. Kafka gives **at-least-once with replay** (durable offsets you can rewind to). Delta gives an **atomic, idempotent sink** (a micro-batch commit is all-or-nothing, and `txnAppId`/`txnVersion` makes a replayed `batch_id` a no-op). Exactly-once is the *composition*: `./lakehouse/_checkpoints/gps_events_bronze` records which Kafka offsets were included in each committed Delta transaction, so after a crash the restart resumes at the last committed offset and cannot re-append what already committed. Sharing a checkpoint directory between two queries corrupts both: the second query reads the first's offset log and state, believes it has already processed data it never saw (silent data loss) or replays state that does not belong to it (corruption). Spark does not always fail loudly on this — which is why "one checkpoint per query" is a rule, not a preference.

    Q2. data/fixtures/late_pings/gps_late_2026-06-04.ndjson delivers a trip's pings shuffled. Your silver job does not sort. Why is the result still correct?

    Answer Because every downstream computation is keyed on **event time** (`event_ts`), not on arrival order. `withWatermark("event_ts", "5 minutes")` plus `F.window("event_ts", …)` assigns each ping to the window it belongs to regardless of when it arrived, and Spark holds the window open until the watermark passes. Sorting an unbounded stream is not merely expensive — it is undefined, because there is no "last" record. Ordering is what Kafka's `trip_id` partition key gives you *within* a partition; correctness across arrival delay is what the watermark gives you. They solve different problems.

    Q3. Your dedup uses dropDuplicatesWithinWatermark(["event_id"]) rather than dropDuplicates(["event_id"]). What does the plain version cost, and what does the watermarked version give up in exchange?

    Answer Plain `dropDuplicates` on a stream keeps **every `event_id` ever seen** in state, forever. At Masar's 1.2M pings/day the state store grows unbounded and the job OOMs within days — this is module mistake #3 wearing a different hat. `dropDuplicatesWithinWatermark` bounds state to the watermark window: only `event_id`s seen within the last 5 minutes of event time are remembered. The trade-off is real — a duplicate that arrives **more than 5 minutes after its twin** will pass through. You accept that because Masar's observed duplicate mechanism is producer-side retry within seconds, so the 5-minute window covers essentially all of it. Document that assumption; if the duplicate mechanism changes, so must the window.

    Q4. Bronze accepted the producer_version = "2.5.0" pings with no error at all. Why did schema enforcement not catch the m/s incident, and where is the correct place to catch it?

    Answer Schema enforcement checks **names and types**. Version 2.5.0 emits the same key `speed_kmh` with the same type `double` — it is structurally identical and semantically wrong. This is *semantic drift*, and no schema check will ever see it. The correct place to catch it is twofold: (1) a **transform** at the bronze→silver boundary that normalises on `producer_version`, which is exactly what you wrote in Task 5 — this is why bronze must preserve `producer_version` verbatim; and (2) a **distribution check** (M6) on the silver `speed_kmh` mean per `producer_version`. A hard rule like `speed_kmh BETWEEN 0 AND 200` passes happily on m/s values; only a distribution comparison against a known-good baseline flags "2.5.0 vehicles average 8.7 km/h and 2.4.0 vehicles average 31.4 km/h." Fixing it in bronze would be wrong: bronze is append-only and as-received, and destroying the raw evidence removes your ability to prove what the device sent.

    Q5. Ops alerts aggregate on processing time; ETA features aggregate on event time. Both read the same silver table. Is one of them wrong?

    Answer No — the clock you choose follows the **question you are answering**. *"Is anything wrong right now?"* is a processing-time question. An alert about a vehicle whose last fix was 30 minutes ago is urgent **now**, at 08:22, regardless of the event's timestamp. Filing it under the 07:52 window would file it into the past and nobody would see it. *"How busy was zone Z between 07:45 and 08:00?"* is an event-time question. A ping that happened at 07:58 belongs in that window whether it arrives at 07:58 or 08:04, or the ETA model learns a demand curve shifted by network latency. The mistake is not using one clock or the other; it is using processing time for an event-time question, which is module mistake #2 and the reason `_kafka_ts` and `ts` are both preserved all the way through bronze and silver.

    Q6. The 30-second trigger produced 248 files for ~15 minutes of data. A participant proposes a 1-second trigger for lower latency. Cost this out.

    Answer A 1-second trigger produces roughly 30× the files: ~7,400 files for the same 15 minutes, ~1.7M files/year for the GPS feed alone. Consequences: (a) every downstream read pays per-file open cost — the small-files problem from M4, and a `silver.vehicle_positions` rebuild goes from seconds to minutes; (b) the `_delta_log` accumulates a commit per second, so listing and checkpointing the log itself becomes the bottleneck; (c) object-storage request charges scale with file count, so this is a direct M2 cost regression. The latency you bought is also mostly illusory: end-to-end latency is trigger interval + processing + commit, and at 1 second the fixed commit overhead dominates. The production answer is a trigger sized to the downstream SLA (30–60 s for Masar's ETA refresh) plus a **scheduled OPTIMIZE** on the sink. If a genuine sub-second requirement exists, it is served by reading Kafka directly in the inference service, not by shredding the Lakehouse.
