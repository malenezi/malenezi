    LAB 07 — Assemble And Orchestrate The Mini-Lakehouse¶

    Field Value
    Lab ID LAB-07
    Module M7 — Hands-on: Building a Mini-Lakehouse
    Day / Hour Day 5 · Hours 1–2
    Duration 90 minutes (7 timed tasks)
    Difficulty Advanced (integration lab — breadth, not new theory)
    LO mapping LO7 (primary) · LO1 (medallion contracts) · LO3 (idempotent incremental) · LO4 (Delta MERGE, OPTIMIZE, VACUUM) · LO6 (gate as a DAG task)
    Prerequisites LAB-01 through LAB-06 complete. bronze.trips, bronze.gps_events, silver.trips, silver.vehicle_positions, silver.drivers, the GX gate, and the observability module must all exist and run standalone

    Scale note. Figures quoted in this document assume the full-scale generator run (--scale 1.0); the shipped sample is --scale 0.15 — 7,230 trips/day over 5 days (36,150 trips), 873,763 GPS pings, 3,450 drivers, 3,864 vehicles, 48 zones. Grains, ratios and file-count reductions hold at either scale; absolute row counts do not.

    1. Why this lab matters¶

    The course question: "What happens to Masar's AI system if THIS part of the data platform fails?"

    Every component you need already exists. You have exactly-once streaming ingest (LAB-05), a quality gate that acts (LAB-06), an incremental silver model (LAB-03b) and a constrained Delta table with MERGE and time travel (LAB-04). Nothing in this lab is new logic.

    What does not exist yet is the guarantee that they run in the right order, exactly, and recoverably. That is what orchestration is. It is not a scheduler.

    If this fails… The AI system experiences…
    No declared dependency silver >> gold build_trip_features runs at 02:07 while build_silver_trips is still merging at 02:09. Gold builds from a half-written silver snapshot — Delta gives you a consistent snapshot, so no error is raised. The feature table is simply missing the last two hours of trips. Every night.
    Non-idempotent gold (INSERT instead of replaceWhere/MERGE) The DAG retries a transient S3 timeout. gold.zone_hourly_demand now contains two rows for the same (city, date, hour). The BI dashboard double-counts demand, the ETA model's rolling_zone_demand_15m doubles, and surge pricing fires at 2× on a normal Tuesday.
    Gold built directly from bronze The quality gate is bypassed. The 120 negative fares and the null keys that LAB-06 blocked flow straight into the feature table. Every control you built is decorative.
    No recovery path build_silver fails at 02:30. Someone re-runs "the parts that failed" by hand at 09:00, in a remembered order, having skipped the gate because "it passed yesterday." This is the twelve-notebooks failure, and it produces wrong numbers with no error and no alert.
    Over-partitioned gold gold.driver_daily partitioned by (city, date, driver_id) produces 14,000 directories per day. The dashboard query that used to take 800 ms now takes 40 s, and the M2 object-storage request bill triples.

    The thesis of this lab is Task 5: break the pipeline on purpose, then recover it with a full re-run and prove the end state is identical. If a full re-run is safe, every operational problem becomes tractable. If it is not, every operational problem becomes an archaeology project.

    3. Tasks¶

    Task 1 — Wire the DAG (15 min)¶

    # orchestration/dags/masar_medallion.py
"""The Masar Mini-Lakehouse as one dependency-ordered, idempotent DAG.

    land_bronze ─► quality_gate ─► build_silver ─┬─► gold_zone_hourly_demand ─┐
                                                 ├─► gold_driver_daily        ├─► optimize_vacuum
                                                 └─► gold_trip_features ──────┘

Three properties make this production-grade, and all three were built in
earlier modules:
  * dependency ordering  — gold cannot start until silver's task SUCCEEDS
  * idempotency          — every task is safe to re-run; retries cannot corrupt
  * atomicity per task   — a failed task leaves no half-written Delta table
Together they mean a full re-run recovers from ANY failure with no duplicates.
"""
from __future__ import annotations
from datetime import datetime, timedelta
import pendulum

from airflow import DAG
from airflow.operators.python import PythonOperator

from masar.ingest.land_bronze import land_trips, land_drivers, land_vehicles, land_zones
from masar.quality.gate import gate_and_promote_task
from masar.quality.observe import observability_task
from masar.transform.build_silver import build_silver_trips
from masar.transform.build_gold import (build_zone_hourly_demand,
                                        build_driver_daily,
                                        build_trip_features)
from masar.delta.maintain import optimize_and_vacuum

RIYADH = pendulum.timezone("Asia/Riyadh")

default_args = {
    "owner": "masar-data-platform",
    "retries": 2,
    "retry_delay": timedelta(minutes=2),
    "retry_exponential_backoff": True,
    "execution_timeout": timedelta(minutes=45),
    "depends_on_past": False,     # each run is independent BECAUSE tasks are idempotent
}

with DAG(
    dag_id="masar_medallion",
    description="Masar Mini-Lakehouse: bronze -> gate -> silver -> gold -> maintain",
    schedule="0 2 * * *",                    # nightly 02:00 Asia/Riyadh
    start_date=datetime(2026, 6, 1, tzinfo=RIYADH),
    catchup=False,                           # backfills are explicit and parameterised
    max_active_runs=1,                       # no two runs mutating silver concurrently
    default_args=default_args,
    tags=["masar", "lakehouse", "medallion"],
    params={"run_date": "{{ ds }}", "lookback_days": 3},
) as dag:

    t_land = PythonOperator(
        task_id="land_bronze",
        python_callable=lambda **ctx: (land_trips(**ctx), land_drivers(**ctx),
                                       land_vehicles(**ctx), land_zones(**ctx)),
    )

    # LAB-06's gate. On FAIL_FAST it raises GateBlocked -> this task fails ->
    # every downstream task is skipped. That is the dependency doing its job.
    t_gate = PythonOperator(task_id="quality_gate",
                            python_callable=gate_and_promote_task)

    t_silver = PythonOperator(task_id="build_silver",
                              python_callable=build_silver_trips)

    t_obs = PythonOperator(task_id="observability",
                           python_callable=observability_task)

    t_demand = PythonOperator(task_id="gold_zone_hourly_demand",
                              python_callable=build_zone_hourly_demand)
    t_driver = PythonOperator(task_id="gold_driver_daily",
                              python_callable=build_driver_daily)
    t_feats = PythonOperator(task_id="gold_trip_features",
                             python_callable=build_trip_features)

    t_maint = PythonOperator(task_id="optimize_vacuum",
                             python_callable=optimize_and_vacuum)

    # The single most important line in this file.
    t_land >> t_gate >> t_silver >> t_obs >> [t_demand, t_driver, t_feats] >> t_maint

    Task 2 — Idempotent BI marts with documented grain (20 min)¶

    Grain is a contract. Write it in the docstring, enforce it in the write, and assert it in a test. All three, every time.

    # src/masar/transform/build_gold.py
"""Gold marts and the feature table. Pure, idempotent transforms from silver.

Grain is DOCUMENTED in each docstring and ENFORCED by the write strategy:
  * partition overwrite (replaceWhere) for date-partitioned rebuilds
  * MERGE on the grain key where a partition boundary does not align
Either way, running a task twice must produce byte-identical row counts.
"""
from __future__ import annotations
from pyspark.sql import functions as F, Window
from delta.tables import DeltaTable
from masar.spark import get_spark

SILVER_TRIPS     = "./lakehouse/silver/trips"
SILVER_POSITIONS = "./lakehouse/silver/vehicle_positions"
SILVER_DRIVERS   = "./lakehouse/silver/drivers"
GOLD             = "./lakehouse/gold"
LOOKBACK_DAYS    = 3          # covers late-arriving trips (LAB-03b's lookback)


def build_zone_hourly_demand(**_) -> None:
    """gold.zone_hourly_demand
    GRAIN : exactly one row per (city, pickup_zone_id, date, hour)
    SOURCE: silver.trips  (never bronze — the gate is upstream of silver)
    WRITE : replaceWhere on the last LOOKBACK_DAYS days => idempotent rebuild
    """
    spark = get_spark()
    trips = spark.read.format("delta").load(SILVER_TRIPS)

    demand = (trips
        .filter(F.col("status") == "completed")
        .withColumn("date", F.to_date("pickup_ts"))
        .withColumn("hour", F.hour("pickup_ts"))
        .filter(F.col("date") >= F.date_sub(F.current_date(), LOOKBACK_DAYS))
        .groupBy("city", "pickup_zone_id", "date", "hour")
        .agg(F.count("*").alias("trips"),
             F.countDistinct("driver_id").alias("active_drivers"),
             F.avg("fare_sar").alias("avg_fare_sar"),
             F.avg("duration_min").alias("avg_duration_min"),
             F.avg("distance_km").alias("avg_distance_km"),
             F.avg("surge_multiplier").alias("avg_surge"))
        .withColumn("_built_at", F.current_timestamp()))

    (demand.write.format("delta")
        .mode("overwrite")
        .partitionBy("date")                     # date ONLY. Not city. Not zone.
        .option("replaceWhere",
                f"date >= current_date() - INTERVAL {LOOKBACK_DAYS} DAYS")
        .option("overwriteSchema", "false")
        .save(f"{GOLD}/zone_hourly_demand"))
    _assert_grain(f"{GOLD}/zone_hourly_demand",
                  ["city", "pickup_zone_id", "date", "hour"])


def build_driver_daily(**_) -> None:
    """gold.driver_daily
    GRAIN : exactly one row per (driver_id, date)
    SOURCE: silver.trips joined to silver.drivers
    WRITE : MERGE on the grain key — the grain does not align to a single
            partition column pair cleanly across the lookback, and MERGE is
            idempotent by construction (LAB-04b).
    """
    spark = get_spark()
    trips = spark.read.format("delta").load(SILVER_TRIPS)
    drivers = spark.read.format("delta").load(SILVER_DRIVERS)

    daily = (trips
        .withColumn("date", F.to_date("pickup_ts"))
        .filter(F.col("date") >= F.date_sub(F.current_date(), LOOKBACK_DAYS))
        .groupBy("driver_id", "date")
        .agg(F.count("*").alias("trips"),
             F.sum(F.when(F.col("status") == "completed", 1).otherwise(0))
              .alias("trips_completed"),
             F.sum(F.when(F.col("status").startswith("cancelled"), 1).otherwise(0))
              .alias("trips_cancelled"),
             F.sum("fare_sar").alias("gross_earnings_sar"),
             F.sum("distance_km").alias("distance_km"),
             F.sum("duration_min").alias("on_trip_minutes"),
             F.avg("surge_multiplier").alias("avg_surge"))
        .join(drivers.select("driver_id", "city", "rating", "status"), "driver_id", "left")
        .withColumn("completion_rate",
                    F.round(F.col("trips_completed") / F.col("trips"), 4))
        .withColumn("_built_at", F.current_timestamp()))

    path = f"{GOLD}/driver_daily"
    if not DeltaTable.isDeltaTable(spark, path):
        daily.write.format("delta").partitionBy("date").save(path)
    else:
        (DeltaTable.forPath(spark, path).alias("t")
            .merge(daily.alias("s"), "t.driver_id = s.driver_id AND t.date = s.date")
            .whenMatchedUpdateAll()
            .whenNotMatchedInsertAll()
            .execute())
    _assert_grain(path, ["driver_id", "date"])


def _assert_grain(path: str, keys: list[str]) -> None:
    """A grain assertion is a data-contract test. Failing it fails the DAG task."""
    spark = get_spark()
    df = spark.read.format("delta").load(path)
    total = df.count()
    distinct = df.select(*keys).distinct().count()
    if total != distinct:
        raise RuntimeError(
            f"GRAIN VIOLATION in {path}: {total:,} rows but only {distinct:,} "
            f"distinct {keys}. The write strategy is not idempotent.")
    print(f"[gold] {path.split('/')[-1]}: {total:,} rows, grain {keys} verified")

    Task 3 — Point-in-time-correct gold.trip_features (15 min)¶

    gold.trip_features is the platform-scale rehearsal for gold.eta_features, which you build in LAB-08. The single non-negotiable property is that no feature value may depend on information that did not exist at pickup_ts.

    # src/masar/transform/build_gold.py  (continued)

def build_trip_features(**_) -> None:
    """gold.trip_features
    GRAIN : exactly one row per trip_id
    SOURCE: silver.trips + silver.vehicle_positions
    RULE  : POINT-IN-TIME CORRECT. Every window is strictly BEFORE pickup_ts.
            rangeBetween(-3600, -1) — the -1 is not cosmetic. rangeBetween(-3600, 0)
            includes the current row's own timestamp, which on ties admits trips
            that started in the same second, i.e. information from the future.
    """
    spark = get_spark()
    trips = spark.read.format("delta").load(SILVER_TRIPS)
    positions = spark.read.format("delta").load(SILVER_POSITIONS)

    t = (trips.filter(F.col("status") == "completed")
              .withColumn("pickup_epoch", F.col("pickup_ts").cast("long")))

    # ---- prior-hour demand in the pickup zone, strictly before this trip -----
    w_zone = (Window.partitionBy("city", "pickup_zone_id")
                    .orderBy(F.col("pickup_epoch"))
                    .rangeBetween(-3600, -1))

    # ---- the driver's completed trips in the prior 24h, strictly before ------
    w_driver = (Window.partitionBy("driver_id")
                      .orderBy(F.col("pickup_epoch"))
                      .rangeBetween(-86400, -1))

    feats = (t
        .withColumn("zone_demand_prev_hr", F.count("*").over(w_zone))
        .withColumn("zone_avg_fare_prev_hr", F.avg("fare_sar").over(w_zone))
        .withColumn("driver_trips_prev_24h", F.count("*").over(w_driver))
        .withColumn("start_hour", F.hour("pickup_ts"))
        .withColumn("day_of_week", F.dayofweek("pickup_ts"))
        .withColumn("is_night", (F.hour("pickup_ts") < 6) |
                                (F.hour("pickup_ts") >= 22))
        .select("trip_id", "city", "pickup_zone_id", "dropoff_zone_id",
                "driver_id", "vehicle_id",
                F.col("pickup_ts").alias("feature_ts"),
                "start_hour", "day_of_week", "is_night",
                "surge_multiplier",
                "zone_demand_prev_hr", "zone_avg_fare_prev_hr",
                "driver_trips_prev_24h")
        .withColumn("_feature_version", F.lit("v1"))
        .withColumn("_built_at", F.current_timestamp()))

    (feats.write.format("delta").mode("overwrite")
        .option("overwriteSchema", "false")
        .save(f"{GOLD}/trip_features"))
    _assert_grain(f"{GOLD}/trip_features", ["trip_id"])
    _assert_point_in_time()


def _assert_point_in_time() -> None:
    """Structural leakage lint: recompute one feature with an inclusive window and
    require it to DIFFER. If prior-hour and through-now agree, the window is not
    actually excluding the present."""
    spark = get_spark()
    trips = (spark.read.format("delta").load(SILVER_TRIPS)
             .filter(F.col("status") == "completed")
             .withColumn("pickup_epoch", F.col("pickup_ts").cast("long")))
    strict = Window.partitionBy("city", "pickup_zone_id").orderBy("pickup_epoch").rangeBetween(-3600, -1)
    leaky = Window.partitionBy("city", "pickup_zone_id").orderBy("pickup_epoch").rangeBetween(-3600, 3600)
    cmp = (trips.withColumn("strict", F.count("*").over(strict))
                .withColumn("leaky", F.count("*").over(leaky))
                .filter(F.col("leaky") <= F.col("strict")))
    n = cmp.count()
    print(f"[lint] point-in-time: {n:,} trips where an inclusive window would not "
          f"add rows (expected: only sparse-zone edge cases)")

    Spot-check one trip by hand. Do not accept the assertion as proof — verify it yourself:

    python -m masar.tools.sql --query "
WITH probe AS (
  SELECT trip_id, city, pickup_zone_id, feature_ts, zone_demand_prev_hr
  FROM delta.\`./lakehouse/gold/trip_features\`
  WHERE zone_demand_prev_hr BETWEEN 8 AND 40
  ORDER BY feature_ts LIMIT 1
)
SELECT
  p.trip_id, p.feature_ts, p.zone_demand_prev_hr AS feature_value,
  (SELECT COUNT(*) FROM delta.\`./lakehouse/silver/trips\` s
     WHERE s.city = p.city AND s.pickup_zone_id = p.pickup_zone_id
       AND s.status = 'completed'
       AND s.pickup_ts >= p.feature_ts - INTERVAL 60 MINUTES
       AND s.pickup_ts <  p.feature_ts)                       AS recount_strictly_prior,
  (SELECT COUNT(*) FROM delta.\`./lakehouse/silver/trips\` s
     WHERE s.city = p.city AND s.pickup_zone_id = p.pickup_zone_id
       AND s.status = 'completed'
       AND s.pickup_ts >= p.feature_ts - INTERVAL 60 MINUTES
       AND s.pickup_ts <= p.feature_ts + INTERVAL 60 MINUTES) AS recount_if_leaking
FROM probe p"

    Expected output

def optimize_and_vacuum(**_) -> None:

    for path, zorder in TABLES.items():

    5. Self-check questions¶

    Q1. Your gold tasks are siblings running in parallel. build_driver_daily takes 24 s and build_trip_features takes 34 s. Could optimize_vacuum start at 25 s?

    Answer No. `[t_demand, t_driver, t_feats] >> t_maint` creates an edge from *each* gold task to `t_maint`, and Airflow's default trigger rule is `all_success` — every upstream task must have succeeded. `t_maint` starts when the slowest sibling finishes, at 34 s. This matters beyond scheduling. If `build_trip_features` fails, `optimize_vacuum` is skipped, so the maintenance job never runs against a table that is mid-rebuild. Had you used `trigger_rule="all_done"` to "make sure maintenance always runs," you would be compacting and vacuuming a table whose build just failed — potentially removing files a retry needs. The default trigger rule is a safety property, not a convenience.

    Q2. Why is catchup=False combined with an explicit pipeline-backfill target better than catchup=True?

    Answer `catchup=True` means that if the DAG is paused for a week and then unpaused, Airflow immediately schedules seven runs. They may execute concurrently (bounded only by `max_active_runs`), all mutating the same `silver.trips` and gold tables, in an order determined by the scheduler rather than by you. On a laptop this is an OOM; in production it is a stampede against shared storage. `catchup=False` plus a parameterised backfill makes reprocessing an **explicit decision with a stated range**, run serially, observable, and reviewable. It also forces you to prove idempotency across the window — which is what the stretch goal asks for. The general principle: a pipeline should never do something expensive and destructive because of a scheduling side effect. Backfills are operations, and operations should be commands.

    Q3. build_zone_hourly_demand uses replaceWhere on a 3-day window. What happens to a trip that arrives 5 days late?

    Answer It lands in `silver.trips` correctly — the MERGE is keyed on `trip_id` and has no date restriction — but it is **silently absent from `gold.zone_hourly_demand`**, because the aggregate only rebuilds the last 3 days and that trip's date falls outside the rebuild window. The gold mart is now permanently wrong for that date, and nothing raises. Three responses, in order of increasing cost: (1) size the lookback to your observed late-arrival p99 rather than to a round number — measure `pickup_ts` vs `_ingested_at` in `bronze.trips` and pick from data; (2) emit a **volume reconciliation** check (LAB-06) comparing `SUM(trips)` in the mart against `COUNT(*)` in silver per date, which turns a silent gap into an alert; (3) trigger a targeted backfill for any date whose silver row count changed since the last mart build. Note that the same lookback trade-off applies to the streaming watermark from LAB-05 — this is the same decision at a different time scale.

    Q4. A colleague says "re-running land_bronze appends the same file again, so a full re-run must duplicate bronze." Are they right?

    Answer They are right about the mechanism and wrong about the consequence — and the distinction is the whole point of Task 5. `land_bronze` does append. Bronze may well grow on a re-run, and that is acceptable by design: bronze is append-only, immutable, and carries `_batch_id` and `_source_file` precisely so that a duplicate landing is *identifiable*. Bronze's contract is "everything we ever received," not "one row per real-world event." The guarantee lives one layer down. The gate promotes into `silver.trips` with a **MERGE on `trip_id`**, and re-applying a matched row updates it to the same values — a no-op. So no matter how many times bronze receives the same trip, silver holds exactly one row for it, and every gold table derives from silver. The duplication stops at the first keyed write. Two caveats worth stating: the streaming bronze table additionally uses `txnAppId`/`txnVersion`, which makes even bronze idempotent per batch id; and if bronze growth is operationally undesirable, the fix is a landing-manifest check, not making the task non-re-runnable. A task you are afraid to re-run is a task you cannot recover.

    Q5. Which single line in the DAG file would you defend hardest in code review, and why?

    Answer `t_land >> t_gate >> t_silver >> t_obs >> [t_demand, t_driver, t_feats] >> t_maint`. Every other line configures something; this line *is* the platform's correctness guarantee. It encodes three things simultaneously: gold cannot build from unrefreshed silver (the twelve-notebooks failure), the quality gate cannot be bypassed (LAB-06's controls become structural rather than advisory), and observability runs before promotion to consumers rather than after. The specific edge to defend hardest is `t_gate >> t_silver`. Any proposal to run them in parallel "for speed," or to move the gate downstream of silver "so we can inspect what failed," destroys the guarantee that nothing unvalidated is ever readable by a consumer. The gate is upstream of the promotion or it is decoration. A close second is `max_active_runs=1`: without it, two DAG runs can MERGE into `silver.trips` concurrently, and while Delta's optimistic concurrency will keep the table *consistent*, it may fail one run with a concurrent-modification exception at 02:00 with nobody watching.

    Q6. gold.trip_features uses rangeBetween(-3600, -1). Why not -3600, 0?

    Answer `rangeBetween` on an ordered window is inclusive of both bounds, and the bound is a *value range over the ordering column*, not a row offset. With `orderBy(pickup_epoch)` and an upper bound of `0`, the frame includes every row whose `pickup_epoch` equals the current row's — that is, every trip that started **in the same second** in the same zone. At Masar's volumes that is not hypothetical: a busy Riyadh zone at 07:45 starts several trips per second. Those trips are, from the perspective of the trip being predicted, the future. Including them inflates `zone_demand_prev_hr` by a small amount that correlates strongly with exactly the congestion the model is trying to predict — which is the worst possible kind of leakage, because it is small enough to look like a real signal and large enough to move the metric. `-1` makes the frame end one second before the current row's timestamp, so the current second is excluded entirely. The general rule: for any point-in-time feature, the upper bound must be strictly less than the event time, and you should be able to point at the character in the code that makes it so.
