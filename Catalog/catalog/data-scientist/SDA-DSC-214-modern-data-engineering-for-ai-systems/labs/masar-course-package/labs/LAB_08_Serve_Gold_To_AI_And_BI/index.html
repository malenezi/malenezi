    1. Why this lab matters¶

    The course question: "What happens to Masar's AI system if THIS part of the data platform fails?"

    Five days of work arrive here. Every table you built exists to be consumed by exactly two things: the ETA model that quotes a rider's arrival time, and the operations dashboard the leadership reviews at 08:00. This is the layer where a data platform either pays for itself or quietly poisons the thing it was built to serve.

    The failure mode of this layer is unique in the course: it does not look like a failure. Streaming failures produce duplicate counts you can see. Quality failures produce quarantine rows you can count. Serving failures produce a model that scores 0.94 R² in the notebook and misses the ETA by four minutes in the app.

    If this fails… The AI system experiences…
    Feature leakage The model trains on distance_km — the metered distance, known only when the trip ends. Offline R² 0.94. At inference the value does not exist, so the serving code substitutes the planned route distance, or a zero, or the mean. Live MAE is 4× the offline number and nobody can explain why.
    Offline ≠ online The training pipeline computes rolling_zone_demand_15m from silver.vehicle_positions; the inference service recomputes it from a Kafka consumer with a different window. The model was trained on one distribution and scored on another. This is training/serving skew, and it degrades silently and permanently.
    Stale online features driver_recent_trip_count is refreshed nightly into Redis. At 19:00 on a Thursday the value is 19 hours old. A driver who has completed 11 trips today reads as having completed 0. The model treats an exhausted driver as a fresh one.
    Non-conformed dimensions Two dim_date tables exist because someone needed a fiscal calendar. The revenue dashboard and the demand dashboard disagree by 3%, and the M1 two-tier divergence you spent Day 1 diagnosing has been rebuilt inside your own gold layer.
    PII at the boundary rider_id reaches a shared dashboard and the Redis keyspace. Every dashboard viewer becomes a processor of personal data. This is a PDPL finding, and unlike the others it has a legal consequence rather than a metric one.

    The lab has two halves that must both be delivered: the BI star and the AI product, derived from the same governed silver so that the analyst's "trips per zone" and the model's demand feature cannot silently disagree. Between them sits Task 3, the leakage drill, which is mandatory.

    3. Tasks¶

    Task 1 — Build the BI star schema (12 min)¶

    Five tables, exactly as named in CONVENTIONS. Conformed means one dim_date and one dim_driver serve every fact in the platform — that is what makes numbers reconcile across dashboards.

    -- dbt/masar/models/marts/gold/dim_date.sql
{{ config(materialized='table', file_format='delta') }}
-- GRAIN: one row per calendar date. THE conformed date dimension. There is
-- exactly one of these in the platform, forever.
with spine as (
  select explode(sequence(date('2026-01-01'), date('2026-12-31'), interval 1 day)) as date
)
select
    cast(date_format(date, 'yyyyMMdd') as int)          as date_key,
    date                                                as full_date,
    year(date)                                          as year,
    quarter(date)                                       as quarter,
    month(date)                                         as month,
    date_format(date, 'MMMM')                           as month_name_en,
    day(date)                                           as day_of_month,
    dayofweek(date)                                     as day_of_week,
    date_format(date, 'EEEE')                           as day_name_en,
    -- KSA working week: Sunday..Thursday. Getting this wrong silently
    -- shifts every "weekend demand" analysis by two days.
    case when dayofweek(date) in (6, 7) then true else false end as is_weekend,
    weekofyear(date)                                    as week_of_year
from spine

    -- dbt/masar/models/marts/gold/dim_driver.sql
{{ config(materialized='table', file_format='delta') }}
-- GRAIN: one row per driver_id (type-1; current attributes only).
-- PDPL: national_id_hash and phone_hash are NOT exposed. Classification from
-- GOVERNANCE.md drives this select list, not convenience.
select
    d.driver_id                                         as driver_key,
    d.driver_id,
    d.full_name_en,
    d.city,
    d.hire_date,
    d.rating,
    d.status,
    datediff(current_date(), d.hire_date)               as tenure_days,
    case when datediff(current_date(), d.hire_date) < 90 then 'new'
         when datediff(current_date(), d.hire_date) < 365 then 'established'
         else 'veteran' end                             as tenure_band
from {{ ref('silver_drivers') }} d

{{ config(materialized='table', file_format='delta') }}
-- GRAIN: one row per vehicle_id.

    v.vehicle_id                                        as vehicle_key,

{{ config(materialized='table', file_format='delta') }}
-- GRAIN: one row per zone_id. Bilingual labels; centroid at zone resolution
-- (never per-trip coordinates — that is the PDPL minimisation line).

{{ config(materialized='incremental', file_format='delta',
          unique_key='trip_id',
          incremental_strategy='merge',
          partition_by=['pickup_date']) }}
-- GRAIN: exactly one row per trip_id.
-- PDPL: rider_id is NOT selected. It never crosses the serving boundary.
--       A pseudonym is provided for cohort analysis instead.
select
    t.trip_id,
    cast(date_format(t.pickup_ts, 'yyyyMMdd') as int)   as date_key,

    t.vehicle_id                                        as vehicle_key,
    t.pickup_zone_id                                    as pickup_zone_key,
    t.dropoff_zone_id                                   as dropoff_zone_key,

    to_date(t.pickup_ts)                                as pickup_date,
    t.pickup_ts, t.dropoff_ts, t.city, t.payment_type, t.status,
    -- measures
    t.fare_sar, t.distance_km, t.duration_min, t.surge_multiplier,
    round(t.fare_sar / nullif(t.distance_km, 0), 3)     as fare_per_km_sar
from {{ ref('silver_trips') }} t
where t.status = 'completed'
{% if is_incremental() %}
  and to_date(t.pickup_ts) >= current_date() - interval 3 days

    Task 2 — Build gold.eta_features (10 min)¶

    The AI product. Thirteen columns, exactly as specified in CONVENTIONS — no additions, no omissions.

    # src/masar/transform/build_eta_features.py
"""gold.eta_features — the AI product.

GRAIN : exactly one row per trip_id
COLUMNS (CONVENTIONS.md, exact): trip_id, pickup_zone_id, dropoff_zone_id,
  hour_of_day, day_of_week, rolling_zone_demand_15m, rolling_avg_speed_10m,
  driver_recent_trip_count, weather_condition, distance_km,
  historical_route_duration, feature_ts, label_actual_duration_min

WARNING — THIS FILE SHIPS WITH DELIBERATE DEFECTS.
Four of these columns are computed in a way that leaks, is stale, or does not
exist at inference time. Task 3 is where you find them. Do not read the
solution guide first; the drill only works if you classify before you are told.
"""
from __future__ import annotations
from pyspark.sql import functions as F, Window
from masar.spark import get_spark

SILVER_TRIPS     = "./lakehouse/silver/trips"
SILVER_POSITIONS = "./lakehouse/silver/vehicle_positions"
WEATHER          = "data/raw/weather_hourly.csv"
OUT              = "./lakehouse/gold/eta_features"


def build(**_) -> None:
    spark = get_spark("masar-eta-features")
    trips = (spark.read.format("delta").load(SILVER_TRIPS)
             .filter(F.col("status") == "completed")
             .withColumn("pickup_epoch", F.col("pickup_ts").cast("long")))
    pos = spark.read.format("delta").load(SILVER_POSITIONS)
    weather = (spark.read.option("header", True).option("inferSchema", True).csv(WEATHER)
               .withColumn("hour_ts", F.to_timestamp("hour_ts")))

    # --- (A) rolling zone demand, 15 minutes -------------------------------
    w_demand = (Window.partitionBy("city", "pickup_zone_id")
                      .orderBy("pickup_epoch")
                      .rangeBetween(-450, 450))          # <-- inspect this
    # --- (B) driver recent trip count ---------------------------------------
    w_driver = (Window.partitionBy("driver_id")
                      .orderBy("pickup_epoch")
                      .rangeBetween(-86400, 0))          # <-- and this
    # --- (C) historical route duration --------------------------------------
    w_route = (Window.partitionBy("pickup_zone_id", "dropoff_zone_id")
                     .orderBy("pickup_epoch")
                     .rangeBetween(-2592000, -1))        # prior 30 days, strictly before

    # --- (D) rolling average speed, 10 minutes ------------------------------
    speed = (pos.groupBy("trip_id")
                .agg(F.avg("speed_kmh").alias("rolling_avg_speed_10m")))  # <-- and this

    feats = (trips
        .withColumn("rolling_zone_demand_15m", F.count("*").over(w_demand))
        .withColumn("driver_recent_trip_count", F.count("*").over(w_driver))
        .withColumn("historical_route_duration", F.avg("duration_min").over(w_route))
        .withColumn("hour_of_day", F.hour("pickup_ts"))
        .withColumn("day_of_week", F.dayofweek("pickup_ts"))
        .withColumn("feature_ts", F.col("pickup_ts"))
        .join(speed, "trip_id", "left")
        .join(weather.select(F.col("city").alias("w_city"), "hour_ts",
                             F.col("condition").alias("weather_condition")),
              (F.col("city") == F.col("w_city")) &
              (F.date_trunc("hour", F.col("pickup_ts")) == F.col("hour_ts")),
              "left")                                     # <-- and this join key
        .select(
            "trip_id", "pickup_zone_id", "dropoff_zone_id",
            "hour_of_day", "day_of_week",
            "rolling_zone_demand_15m", "rolling_avg_speed_10m",
            "driver_recent_trip_count", "weather_condition",
            "distance_km",                                 # <-- and this column
            "historical_route_duration", "feature_ts",
            F.col("duration_min").alias("label_actual_duration_min")))

    feats.write.format("delta").mode("overwrite").save(OUT)
    print(f"[gold] eta_features: {feats.count():,} rows, 13 columns")


if __name__ == "__main__":
    build()

    Task 3 — THE FEATURE LEAKAGE DRILL (mandatory, 15 min)¶

    Do not skip this task. Do not shorten it. If you are behind schedule, cut Task 6.

    You will classify every one of the 13 columns of gold.eta_features into exactly one of four categories. Ambiguity is not permitted; if a column could be two, pick the one that would cause the worse production failure and say so in your justification.

    Code Meaning The test to apply
    VALID The value is knowable at feature_ts, from data that existed at feature_ts, and the same value can be produced at inference time. "At the exact moment a rider taps Request, could I compute this from data already written?"
    STALE Computable in principle, but the value the online path will actually serve is materially older than feature_ts. The feature is right offline and out of date online. "How old is the value Redis holds at 19:00 on a Thursday?"
    LEAKAGE The value depends on information that did not exist at feature_ts — the current instant, the future, or the outcome itself. "Does computing this require knowing anything that happened at or after feature_ts?"
    UNAVAILABLE ONLINE Legitimately point-in-time correct offline, but no online path can supply it at inference latency, or the source has not landed yet. "Is there a Redis key or an API that returns this in under 20 ms, right now?"

    Fill this in before reading anything else. Use LAB8_LEAKAGE.md.

    # D1 — does the demand window admit trips that had not started yet?
python -m masar.tools.sql --query "
WITH probe AS (SELECT trip_id, pickup_zone_id, feature_ts, rolling_zone_demand_15m
               FROM delta.\`./lakehouse/gold/eta_features\`
               WHERE rolling_zone_demand_15m BETWEEN 10 AND 60
               ORDER BY feature_ts LIMIT 1)
SELECT p.trip_id, p.feature_ts, p.rolling_zone_demand_15m AS as_built,
  (SELECT COUNT(*) FROM delta.\`./lakehouse/silver/trips\` s
    WHERE s.pickup_zone_id = p.pickup_zone_id AND s.status='completed'
      AND s.pickup_ts >= p.feature_ts - INTERVAL 15 MINUTES
      AND s.pickup_ts <  p.feature_ts)                       AS strictly_prior,
  (SELECT COUNT(*) FROM delta.\`./lakehouse/silver/trips\` s
    WHERE s.pickup_zone_id = p.pickup_zone_id AND s.status='completed'
      AND s.pickup_ts >  p.feature_ts
      AND s.pickup_ts <= p.feature_ts + INTERVAL 7.5 MINUTES) AS from_the_future
FROM probe p"

# D2 — when were the GPS pings behind rolling_avg_speed_10m actually recorded?
python -m masar.tools.sql --query "
SELECT t.trip_id, t.pickup_ts, t.dropoff_ts,
       MIN(p.event_ts) AS first_ping, MAX(p.event_ts) AS last_ping,
       ROUND((UNIX_TIMESTAMP(MAX(p.event_ts)) - UNIX_TIMESTAMP(t.pickup_ts))/60.0, 1)
         AS minutes_after_pickup
FROM delta.\`./lakehouse/silver/trips\` t
JOIN delta.\`./lakehouse/silver/vehicle_positions\` p ON p.trip_id = t.trip_id
GROUP BY 1,2,3 ORDER BY t.pickup_ts LIMIT 3"

    Task 4 — Materialise online and prove offline == online (10 min)¶

    The rule: copy the value, never recompute it. Any online path that re-derives a feature is skew by construction.

    # src/masar/serve/materialize_online.py
"""Materialise the latest zone-level feature slice into Redis.

Keyspace (CONVENTIONS.md):  masar:features:zone:{zone_id}

Values are COPIED from gold.eta_features. There is no feature logic in this
file and there must never be any — the moment this file computes something,
offline and online can disagree.
"""
from __future__ import annotations
import json, redis
from pyspark.sql import functions as F, Window
from masar.spark import get_spark

GOLD = "./lakehouse/gold/eta_features"
KEY  = "masar:features:zone:{zone_id}"

# Only columns that are (a) zone-grained and (b) safe to serve. The label and
# every trip-grained column are excluded — see GOVERNANCE.md and LAB8_LEAKAGE.md.
ONLINE_COLUMNS = ["rolling_zone_demand_15m", "rolling_avg_speed_10m",
                  "historical_route_duration", "weather_condition"]


def materialize(feature_version: str = "v2") -> int:
    spark = get_spark("masar-materialize-online")
    feats = spark.read.format("delta").load(GOLD)

    w = Window.partitionBy("pickup_zone_id").orderBy(F.col("feature_ts").desc())
    latest = (feats.withColumn("_rn", F.row_number().over(w))
                   .filter("_rn = 1")
                   .select("pickup_zone_id", "feature_ts", *ONLINE_COLUMNS))

    r = redis.Redis(host="localhost", port=6379, decode_responses=True)
    pipe, n = r.pipeline(), 0
    for row in latest.collect():
        payload = {c: row[c] for c in ONLINE_COLUMNS}
        payload["feature_ts"] = row["feature_ts"].isoformat()
        payload["_feature_version"] = feature_version
        pipe.set(KEY.format(zone_id=row["pickup_zone_id"]), json.dumps(payload))
        n += 1
    pipe.execute()
    print(f"[serve] materialised {n} zone keys to redis under masar:features:zone:*")
    return n

    # src/masar/serve/consistency_check.py
"""Offline == online. Compare EVERY key, not a spot check.

This is the test the capstone extension asks you to wire into CI. A serving
layer that is not continuously proven consistent is not consistent; it is
merely untested.
"""
from __future__ import annotations
import json, redis
from pyspark.sql import functions as F, Window
from masar.spark import get_spark
from masar.serve.materialize_online import GOLD, KEY, ONLINE_COLUMNS

TOL = 1e-6

def check() -> int:
    spark = get_spark("masar-consistency-check")
    w = Window.partitionBy("pickup_zone_id").orderBy(F.col("feature_ts").desc())
    offline = {r["pickup_zone_id"]: r for r in
               (spark.read.format("delta").load(GOLD)
                .withColumn("_rn", F.row_number().over(w)).filter("_rn = 1")
                .select("pickup_zone_id", "feature_ts", *ONLINE_COLUMNS).collect())}

    r = redis.Redis(host="localhost", port=6379, decode_responses=True)
    mismatches = []
    for zone_id, off in offline.items():
        raw = r.get(KEY.format(zone_id=zone_id))
        if raw is None:
            mismatches.append((zone_id, "MISSING_ONLINE", None, None)); continue
        on = json.loads(raw)
        for c in ONLINE_COLUMNS:
            ov, nv = off[c], on.get(c)
            same = (ov == nv) if isinstance(ov, str) else (
                ov is not None and nv is not None and abs(float(ov) - float(nv)) <= TOL)
            if not same:
                mismatches.append((zone_id, c, ov, nv))

    print(f"[consistency] zones checked : {len(offline)}")
    print(f"[consistency] columns/zone  : {len(ONLINE_COLUMNS)}")
    print(f"[consistency] mismatches    : {len(mismatches)}")
    for m in mismatches[:10]:
        print(f"[consistency]   MISMATCH zone={m[0]} col={m[1]} offline={m[2]} online={m[3]}")
    if mismatches:
        raise SystemExit(1)
    print("[consistency] PASS — offline == online for every zone and every column")
    return 0

    5. Self-check questions¶

    Q1. Your fixed model scores R² 0.712. A stakeholder says the old 0.943 model was better and asks you to revert. What do you say?

    Answer The 0.943 model was not better; it was measured wrong. It scored highly because `distance_km` — the *metered* distance recorded when the trip ended — correlates 0.947 with trip duration, and `rolling_avg_speed_10m` was averaged over GPS pings emitted during and after the trip. Both are outcomes of the journey, not inputs to a prediction made before it starts. Offline, the model had access to them; at 07:14:33 when a rider taps Request, neither exists. Reverting does not restore 0.943 in production — it produces 0.943 on a report and roughly the same live error as the fixed model, or worse, because the serving code must invent substitute values for the missing columns and the model was trained to trust them heavily. The concrete framing for the stakeholder: *the honest model tells you it will miss by about 4.6 minutes; the leaking model tells you it will miss by 1.8 and then misses by 5.* The second is more expensive precisely because you believed it. The right response to a disappointing honest number is better features, not a restored fiction.

    Q2. Why is dropoff_zone_id VALID while distance_km is LEAKAGE? Both describe the destination.

    Answer Because of *when the value is fixed*, not what it describes. In Masar's booking flow the rider states a destination before requesting, so `dropoff_zone_id` is an **input** the platform holds at `feature_ts`. `distance_km` in `silver.trips` is the **metered** distance the vehicle actually travelled, written at `dropoff_ts` — a different quantity that happens to share a name with something knowable. The fix keeps the contract column name and changes the source: compute `distance_km` from the routing engine's planned route at booking (or, offline, as a great-circle/route estimate between zone centroids from `gold.dim_zone`). That value exists at `feature_ts`, is reproducible online, and is genuinely predictive — it just is not clairvoyant. The general lesson: this dependency is invisible in the schema. Both columns are typed and populated identically. Only knowing *when each value is written* separates them, which is why point-in-time correctness is a property of the pipeline, not of the table. Worth noting the counterfactual: if Masar allowed destination-less requests, `dropoff_zone_id` would move to UNAVAILABLE ONLINE for that segment. The classification depends on the product, not only the data.

    Q3. weather_condition is point-in-time correct offline. Why is it still a problem?

    Answer `data/raw/weather_hourly.csv` lands after the hour it describes. Offline, joining a 07:14 trip to the 07:00 weather row is legitimate — that hour's observation existed by the time the feature table was built. Online, at 07:14, the 07:00 row has not arrived yet. The feature is correct and unobtainable, which is the definition of UNAVAILABLE ONLINE. The distinction from LEAKAGE matters operationally. A leaking feature must be *changed*; an unavailable one must be *re-sourced*. Here the fix is to shift the join to the **last observed hour** (`hour_ts <= date_trunc('hour', feature_ts) - INTERVAL 1 HOUR`), apply the same shift in training and in materialisation, and serve it from the Redis zone key so inference reads a value rather than waiting on a file. The cost is one hour of weather staleness, which for a condition category changing on the scale of hours is acceptable — and it is now the *same* one hour offline and online, which is the property that actually matters. The failure to avoid is fixing it only in the serving path. That produces a model trained on current-hour weather and served last-hour weather: textbook training/serving skew, and invisible to every check except the consistency test.

    Q4. materialize_online.py deliberately contains no feature logic. Why is that a rule rather than a style preference?

    Answer Because the alternative cannot be kept correct. The moment the online path computes anything, there are two implementations of one definition, and they will diverge — not through negligence, but through ordinary maintenance. Someone widens the offline demand window from 15 to 20 minutes and does not know the online service has its own copy; someone fixes a null-handling bug in one and not the other; the two are written in different languages by different teams on different release cycles. Divergence is the default state of duplicated logic. When it diverges, the model is trained on one distribution and scored on another. This degrades accuracy continuously and silently: no error, no alert, no row-level check fires, because both values are individually valid. It is the exact failure the M8 case study describes. Copying makes divergence structurally impossible — the online value *is* the offline value, byte for byte, and `consistency_check` proves it for every key on every run. The cost is that online features are only as fresh as the last materialisation, which is a real constraint you manage with refresh cadence (a DAG task, with freshness monitoring) and by accepting STALE classification where the cadence is not enough. That is a bounded, measurable, monitorable cost. Skew is none of those things.

    Q5. Both gold.fact_trip and gold.eta_features count trips. What structurally prevents them from disagreeing?

    Answer They both derive from `silver.trips`, which is downstream of a single quality gate and holds exactly one row per `trip_id`. Neither reads bronze; neither applies its own cleaning. The BI aggregate and the model's demand feature are two projections of one conformed table, so a trip that the gate quarantined is absent from both, and a correction MERGEd into silver reaches both on the next DAG run. This is the answer to the Day-1 two-tier problem, and it is why the medallion contract matters more than any individual transform. In the two-tier world the warehouse had one trip count and the lake had another, and reconciling them was a permanent quarterly ritual. Here it is not a process — it is a property of the topology. Two things can still break it, and both are worth naming. First, **filter divergence**: `fact_trip` selects `status = 'completed'` and so does `build_eta_features`, but if one of them changes and the other does not, the counts drift with no error. Task 1's reconciliation query is the guard, and it belongs in CI. Second, **timing**: if the star is rebuilt at 02:30 and the feature table at 04:00, they reflect different silver snapshots. The DAG's sibling-task structure from LAB-07 is what keeps them on the same run — which is a real argument for building both gold products in one DAG rather than two.

    Q6. A colleague adds driver_rating_at_trip_time from silver.drivers. Classify it before it ships.

    Answer **STALE at best, LEAKAGE at worst, depending on how `silver.drivers` is modelled — and as described it is LEAKAGE.** `silver.drivers` is a type-1 dimension: it holds the driver's *current* rating, overwritten on each load. Joining it to a trip from three weeks ago attaches today's rating to that trip. If the driver's rating fell because of incidents that happened after the trip, the feature encodes future information about that driver's behaviour — and since rating changes correlate with the very service quality that affects trip duration, this leaks in a way that will look like genuine signal. The name is itself the tell: `_at_trip_time` claims a point-in-time semantic the source cannot supply. Three responses. (1) Make the dimension type-2 (`valid_from`/`valid_to`) and join as-of `feature_ts` — correct, and the reason SCD2 exists. (2) Derive the rating from `gold.driver_daily` restricted to dates strictly before `feature_ts` — cheaper, and already point-in-time by construction. (3) Drop it; `driver_recent_trip_count` already carries much of the driver-quality signal without the modelling burden. Whichever you choose, this is the drill generalising: **every join to a mutable dimension is a point-in-time question**, and the schema will never ask it for you.
