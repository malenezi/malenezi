    LAB 03 — Build the ELT Pipeline to silver.trips¶

    Field Value
    Lab ID LAB-03 (delivered as 3a + 3b)
    Module M3 — ETL versus ELT in Modern Stacks
    Day / Hour Day 2, Hour 3 (Lab 3a) and Day 2, Hour 5 (Lab 3b)
    Duration 90 minutes total — 3a: 35 min, 3b: 55 min (10–15% theory / 85–90% lab), pairs
    Difficulty Intermediate
    LO mapping LO3 (primary — ELT pipeline design for cloud data environments), LO6 (secondary — tests, freshness, governance-as-code), LO7 (contributes — the silver node of the Mini-Lakehouse)
    Prerequisites LAB-01 complete (bronze.trips, bronze.drivers landed, append-only, with lineage); M3 lecture (ETL vs ELT, dbt layering, idempotency, incremental models, late-arriving data)
    Checkpoint git tags lab3-start (3a), lab3b-start (3b) · solutions: lab3a-solution, lab3-solution
    Deliverable A dbt project building stg_trips, stg_drivers and an incremental, merge-on-trip_id silver.trips with a 3-day lookback; ≥ 6 passing tests plus a source-freshness SLA; a demonstrated late-arrival backfill; LAB3_NOTES.md with the filled benchmark table

    Scale note. Figures quoted in this document assume the full-scale generator run (--scale 1.0); the shipped sample is --scale 0.15 — 7,230 trips/day over 5 days (36,150 trips), 873,763 GPS pings, 3,450 drivers, 3,864 vehicles, 48 zones. Grains, ratios and file-count reductions hold at either scale; absolute row counts do not.

    Why this lab matters¶

    silver.trips is the single conformed definition of "a Masar trip" — the ETA model trains on it, the demand forecast aggregates it, and the operations dashboard counts it. If this transformation fails, nothing crashes: the numbers merely become wrong, consistently and confidently. The specific failure this lab inoculates against is the most common bug in production data engineering: a WHERE trip_date = current_date() filter that silently drops trips settling after midnight, undercounting by ~2% forever. Downstream, that undercount underpays drivers, skews the demand model's training labels, and makes the dashboard disagree with the data-science notebook — the exact two-tier divergence Module 1 diagnosed, now reproduced inside one platform by a three-word filter. You will build the fix (lookback window + idempotent MERGE + a unique test) and then prove it works by landing a late trip and watching it merge exactly once.

    Part 3a — Sources, freshness and staging models (35 min)¶

    Task 1 — Declare bronze as dbt sources with a freshness SLA (15 min)¶

    Create models/staging/masar/_masar__sources.yml. Note that _ingested_at (the lineage column Lab 1 wrote) is what makes freshness measurable — this is the payoff for that discipline.

    # dbt/masar/models/staging/masar/_masar__sources.yml
# Declares bronze Delta tables as dbt sources + a freshness SLA.
version: 2

sources:
  - name: bronze
    schema: bronze
    description: "Append-only landing zone. Never mutated. Lab 1 output."
    tables:
      - name: trips
        identifier: trips
        loaded_at_field: _ingested_at
        freshness:                       # fail the build if bronze is stale
          warn_after:  {count: 6,  period: hour}
          error_after: {count: 24, period: hour}
        columns:
          - name: trip_id
            description: "Business key as received. May be duplicated at bronze."
          - name: _batch_id
            description: "Landing batch. Distinguishes re-runs of the same day."

      - name: drivers
        identifier: drivers
        loaded_at_field: _ingested_at
        freshness:
          warn_after:  {count: 24, period: hour}
          error_after: {count: 72, period: hour}

      - name: gps_events
        identifier: gps_events
        loaded_at_field: _ingested_at
        freshness:
          warn_after:  {count: 1, period: hour}
          error_after: {count: 6, period: hour}

    dbt source freshness

    What to look for: the trips source is fresh if you landed it today. Deliberately prove the check works — it is a guard, not decoration:

    # temporarily tighten the SLA to 1 minute and re-run
sed -i.bak 's/{count: 6,  period: hour}/{count: 1, period: minute}/' \
    models/staging/masar/_masar__sources.yml
dbt source freshness            # expect WARN on bronze.trips
mv models/staging/masar/_masar__sources.yml.bak \
   models/staging/masar/_masar__sources.yml

    Record in LAB3_NOTES.md: what upstream failure does a 6h warn / 24h error SLA on bronze.trips actually catch, and what does it miss? (It catches a stopped landing job. It misses a landing job that runs on time and lands empty or wrong data — that is a volume/quality check, Module 6.)

    Task 2 — Write stg_trips and stg_drivers (20 min)¶

    Staging is 1:1 with the source: rename, cast, normalise. No joins, no business rules, no aggregation. Every source quirk is isolated here so that a source rename touches exactly one model.

    Three quirks from CONVENTIONS.md must be handled at this boundary:

    Quirk Where it comes from Staging treatment
    Mixed timestamp formats (~2% DD/MM/YYYY HH:MM) pickup_ts, dropoff_ts parse both formats with coalesce, flag unparseable
    Timestamps are Asia/Riyadh wall clock; the Lakehouse stores UTC all timestamps to_utc_timestamp(..., 'Asia/Riyadh') — once, here
    Everything landed as STRING (Lab 1's inferSchema=False) all columns explicit cast per column 
    -- dbt/masar/models/staging/masar/stg_trips.sql
-- Staging: 1:1 with source. Rename, cast, normalise. NO joins, NO business logic.
{{ config(materialized='view') }}

with source as (

    select * from {{ source('bronze', 'trips') }}

),

parsed as (

    select
        cast(trip_id          as string)  as trip_id,
        cast(rider_id         as string)  as rider_id,
        cast(driver_id        as string)  as driver_id,
        cast(vehicle_id       as string)  as vehicle_id,
        initcap(trim(city))               as city,
        cast(pickup_zone_id   as string)  as pickup_zone_id,
        cast(dropoff_zone_id  as string)  as dropoff_zone_id,

        -- The source ships TWO timestamp formats (~2% of rows use dd/MM/yyyy HH:mm).
        -- Parse both, coalesce, then normalise Asia/Riyadh wall clock -> UTC ONCE.
        to_utc_timestamp(
            coalesce(
                to_timestamp(pickup_ts,  'yyyy-MM-dd HH:mm:ss'),
                to_timestamp(pickup_ts,  'dd/MM/yyyy HH:mm')
            ), 'Asia/Riyadh')             as pickup_ts,
        to_utc_timestamp(
            coalesce(
                to_timestamp(dropoff_ts, 'yyyy-MM-dd HH:mm:ss'),
                to_timestamp(dropoff_ts, 'dd/MM/yyyy HH:mm')
            ), 'Asia/Riyadh')             as dropoff_ts,

        cast(distance_km      as double)  as distance_km,
        cast(duration_min     as double)  as reported_duration_min,  -- source value; may be negative
        cast(fare_sar         as double)  as fare_sar,
        cast(surge_multiplier as double)  as surge_multiplier,
        lower(trim(payment_type))         as payment_type,
        lower(trim(status))               as status,
        nullif(trim(dropoff_geohash), '') as dropoff_geohash,        -- '' is missing, not a value

        -- lineage carried forward from bronze (Lab 1)
        _batch_id,
        _ingested_at

    from source
    where trip_id is not null            -- drop unkeyed garbage at the boundary

)

select * from parsed

    -- dbt/masar/models/staging/masar/stg_drivers.sql
-- Staging: 1:1 with bronze.drivers. hire_date arrives in MIXED formats on purpose.
{{ config(materialized='view') }}

with source as (

    select * from {{ source('bronze', 'drivers') }}

),

parsed as (

    select
        cast(driver_id  as string)   as driver_id,
        cast(full_name_en as string) as full_name_en,
        initcap(trim(city))          as driver_city,

        -- three observed formats; add a branch only for a format you have SEEN
        coalesce(
            to_date(hire_date, 'yyyy-MM-dd'),
            to_date(hire_date, 'dd/MM/yyyy'),
            to_date(hire_date, 'MMM d, yyyy')
        )                            as hire_date,

        cast(rating as double)       as driver_rating,
        lower(trim(status))          as driver_status,
        cast(national_id_hash as string) as national_id_hash,   -- PDPL: pseudonymised, never re-identify
        cast(phone_hash as string)       as phone_hash,         -- PDPL: pseudonymised
        _batch_id,
        _ingested_at

    from source
    where driver_id is not null

)

select * from parsed

    Build and inspect:

    dbt run --select staging
dbt show --select stg_trips --limit 5

# how many timestamps failed BOTH formats? (must be 0 — otherwise add a branch)
dbt show --inline "select count(*) as unparseable from {{ ref('stg_trips') }} where pickup_ts is null"
# how many hire_date values failed all three formats?
dbt show --inline "select count(*) as unparseable from {{ ref('stg_drivers') }} where hire_date is null"

    What to look for: unparseable = 0 for both. A non-zero count means the source ships a format you have not seen — go back to Lab 1's profiling output, find it, and add exactly that branch. Never "fix" it with a blanket try_cast that turns every parse failure into a silent null: that is how a 2% defect becomes a 2% invisible data loss.

    Part 3b — Incremental silver.trips, tests, and the backfill drill (55 min)¶

    Task 3 — Write silver.trips as an incremental merge with a lookback window (20 min)¶

    This is the model the whole course depends on. Four properties must hold simultaneously:

    1. Deduplicated — bronze legitimately holds two batches of the same day (Lab 1); silver keeps the latest landed version of each trip_id, not DISTINCT and not the first.
    2. Incremental with a lookback — reprocess a 3-day window, not just today, so late-arriving trips are picked up.
    3. Idempotent — MERGE on trip_id, so re-running changes nothing.
    4. Conformed — one row per real-world completed trip, typed, with derived features computed once, here.
    -- dbt/masar/models/marts/silver/silver_trips.sql
-- silver.trips: the conformed contract. One row per completed, valid trip.
{{ config(
    materialized='incremental',
    incremental_strategy='merge',
    unique_key='trip_id',
    file_format='delta',
    schema='silver',
    alias='trips',
    partition_by=['city'],
    on_schema_change='append_new_columns'
) }}

with trips as (

    select * from {{ ref('stg_trips') }}

    {% if is_incremental() %}
      -- LOOKBACK: reprocess a 3-day window so late-arriving trips are
      -- corrected (merged), not missed. Merge-on-trip_id => idempotent.
      -- NOTE: the window is on pickup_ts (event time), NOT on _ingested_at:
      -- a trip that ENDED yesterday but ARRIVED today must be inside it.
      where pickup_ts >= (
          select date_sub(max(pickup_ts), {{ var('lookback_days', 3) }})
          from {{ this }}
      )
    {% endif %}

),

-- Bronze is append-only, so the same trip_id can appear in several batches.
-- Keep the LATEST landed version per key: DISTINCT would keep a stale row.
deduped as (

    select * from (
        select
            *,
            row_number() over (
                partition by trip_id
                order by _ingested_at desc, _batch_id desc
            ) as _rn
        from trips
    )
    where _rn = 1

),

drivers as (

    select
        driver_id,
        driver_rating,
        driver_status
    from {{ ref('stg_drivers') }}

),

joined as (

    select
        d.trip_id,
        d.rider_id,                                   -- PDPL: personal data, never leaves silver un-masked
        d.driver_id,
        d.vehicle_id,
        d.city,
        d.pickup_zone_id,
        d.dropoff_zone_id,
        d.pickup_ts,                                  -- UTC (normalised in staging)
        d.dropoff_ts,                                 -- UTC
        to_date(from_utc_timestamp(d.pickup_ts, 'Asia/Riyadh')) as trip_date,  -- business date, +03
        d.distance_km,
        d.reported_duration_min,                      -- as delivered; may disagree with the truth
        round((unix_timestamp(d.dropoff_ts)
               - unix_timestamp(d.pickup_ts)) / 60.0, 2) as duration_min,      -- derived truth
        d.fare_sar,
        d.surge_multiplier,
        d.payment_type,
        d.status,
        d.dropoff_geohash,
        dr.driver_rating,
        dr.driver_status,
        round(d.fare_sar / nullif(d.distance_km, 0), 3)          as fare_per_km,
        hour(from_utc_timestamp(d.pickup_ts, 'Asia/Riyadh'))     as pickup_hour,
        dayofweek(from_utc_timestamp(d.pickup_ts, 'Asia/Riyadh')) as day_of_week,
        case when hour(from_utc_timestamp(d.pickup_ts, 'Asia/Riyadh')) < 6
             then 1 else 0 end                                    as is_night,
        d._batch_id,
        d._ingested_at,
        current_timestamp()                                       as _loaded_at

    from deduped d
    left join drivers dr on d.driver_id = dr.driver_id

    where d.status = 'completed'          -- silver = conformed, valid, completed trips
      and d.dropoff_ts > d.pickup_ts      -- reject impossible durations (source has negatives)
      and d.fare_sar > 0                  -- reject non-positive fares
      and d.distance_km > 0

)

select * from joined

    Build it:

    dbt run --select silver_trips

    Then immediately run it again and compare. On the second run the lookback selects the same window, the MERGE matches every row, and nothing changes — that is idempotency, visible.

    dbt run --select silver_trips
python - <<'PY'
from masar.spark import get_spark
spark = get_spark("lab3-verify")
df = spark.table("silver.trips")
print("silver.trips rows:", df.count(), "cols:", len(df.columns))

spark.sql("DESCRIBE HISTORY delta.`./lakehouse/silver/trips`") \

PY

    What to look for: rows == distinct trip_id (the dedup worked), 27 columns, and a MERGE operation in the Delta history whose numTargetRowsUpdated on the second run reflects an unchanged table.

    Task 4 — Declare the tests (15 min)¶

    Tests are the contract of silver.trips, checked on every build. Add them next to the model.

    # dbt/masar/models/marts/silver/_silver__models.yml
version: 2

models:
  - name: silver_trips
    description: >
      Conformed, completed Masar trips. GRAIN: one row per trip_id.
      Timestamps are UTC; trip_date is the Asia/Riyadh business date.
      Contract for all downstream AI and BI consumers.
    columns:
      - name: trip_id
        description: "Business key. Unique, non-null."
        tests: [unique, not_null]

      - name: city
        tests:
          - not_null
          - accepted_values:
              values: ['Riyadh', 'Jeddah', 'Dammam', 'Mecca', 'Medina']

      - name: status
        tests:
          - accepted_values:
              values: ['completed']         # silver holds completed trips only

      - name: fare_sar
        tests:
          - not_null
          - dbt_utils.accepted_range:
              min_value: 0
              inclusive: false

      - name: duration_min
        tests:
          - not_null
          - dbt_utils.accepted_range:
              min_value: 0
              max_value: 480                # 8h: longer is a data problem, not a trip
              inclusive: false

      - name: driver_id
        tests:
          - not_null
          - relationships:
              to: ref('stg_drivers')
              field: driver_id

      - name: pickup_ts
        tests: [not_null]

      - name: rider_id
        description: "PDPL: personal data. Never propagated raw to gold/BI/online store."
        tests: [not_null]

    Add one custom data test — SQL that must return zero rows:

    -- dbt/masar/tests/assert_no_future_trips.sql
-- A trip cannot end in the future. Catches timezone drift and bad source clocks.
select
    trip_id,
    dropoff_ts
from {{ ref('silver_trips') }}
where dropoff_ts > current_timestamp() + interval 1 hour

    Install dbt_utils (needed for accepted_range) and run the suite:

    cat > packages.yml <<'YML'
packages:
  - package: dbt-labs/dbt_utils
    version: [">=1.1.0", "<2.0.0"]
YML
dbt deps
dbt test --select silver_trips

    What to look for: every failure is a logic bug to fix, never a test to delete. The two you are most likely to hit:

    Failing test What it is telling you Correct fix
    unique_silver_trips_trip_id Dedup window is wrong — DISTINCT used, or row_number() partitioned by the wrong key Restore the row_number() over (partition by trip_id order by _ingested_at desc) filter
    relationships_silver_trips_driver_id Trips reference a driver_id absent from stg_drivers (orphan) Do not switch to an inner join (that silently deletes trips). Quantify the orphans, decide with the business whether they are quarantined (silver.trips_quarantine, Lab 6) or admitted with a null-rated driver, and record the decision

    Task 5 — The backfill drill: prove late-arriving data is handled (15 min)¶

    This is the point of the entire module. Do not skip it.

    # 1. Baseline: how many trips does silver hold, and how many for the target date?
python - <<'PY'
from masar.spark import get_spark
spark = get_spark("drill-before")
spark.table("silver.trips").groupBy("trip_date").count().orderBy("trip_date").show()
PY

# 2. Land the late-arrival fixture into BRONZE (a trip that ENDED yesterday,
#    ARRIVING today, in its own batch — exactly the production failure mode)
python -m masar.ingest.land_bronze --feed trips --date 2026-06-01 \
       --source data/fixtures/late_trips/trips_late_2026-06-02.csv

# 3. Run the incremental model
cd dbt/masar && dbt run --select silver_trips

    Verify the three properties that matter:

    python - <<'PY'
from masar.spark import get_spark
from pyspark.sql import functions as F
spark = get_spark("drill-after")

t = spark.table("silver.trips")
late_ids = [r.trip_id for r in spark.read.option("header", True)
            .csv("data/fixtures/late_trips/trips_late_2026-06-02.csv")
            .select("trip_id").collect()]

print("late trip ids:", late_ids)
print("present in silver:", t.filter(F.col("trip_id").isin(late_ids)).count())
print("counted ONCE    :", t.filter(F.col("trip_id").isin(late_ids))
                            .groupBy("trip_id").count()
                            .filter("count > 1").count() == 0)
t.groupBy("trip_date").count().orderBy("trip_date").show()
spark.sql("DESCRIBE HISTORY delta.`./lakehouse/silver/trips`") \
     .select("version", "operation", "operationMetrics").show(3, truncate=False)
PY

    What to look for: the late trip is present, appears exactly once, and the Delta history's last MERGE shows numTargetRowsInserted = 1 with numTargetRowsUpdated = 0. Now run dbt run --select silver_trips again and confirm the next MERGE inserts 0 and updates 0 rows — re-running a backfill is a no-op. That is what makes a six-month backfill safe to run twice.

    The counter-experiment (2 min, do it — it is what makes the lesson stick). Temporarily replace the lookback block with the naive filter and re-run:

    {% if is_incremental() %}
  where to_date(pickup_ts) = current_date()     -- THE BUG
{% endif %}

    Rebuild from scratch (dbt run --select silver_trips --full-refresh, then land the late fixture, then dbt run). The late trip is now missing. Record both counts side by side in LAB3_NOTES.md, then restore the correct model.

    Task 6 — Generate docs and commit (5 min)¶

    Self-check questions¶

    Q1. Why does the lookback window filter on pickup_ts rather than on _ingested_at?

    Answer Because the bug being fixed is a mismatch between *event time* and *arrival time*. A trip that happened yesterday and arrived today has an old `pickup_ts` and a new `_ingested_at`. Filtering on `_ingested_at` would select the newly arrived rows but leave the window anchored to arrival, so any correction to a row that arrived *earlier* would never be reprocessed. Filtering on `pickup_ts >= max(pickup_ts) - 3 days` reprocesses a window of *business* time, which is what the incentive calculation and the model labels are keyed on. (A production refinement is to bound both: event-time window for correctness, ingest-time for efficiency.)

    Q2. Why is DISTINCT the wrong way to remove the duplicate trip_id rows Lab 1 created?

    Answer `DISTINCT` deduplicates identical *rows*, not keys. If the second batch corrected a fare, the two rows differ, so `DISTINCT` keeps **both** — the `unique` test then fails. Worse, if you then applied `DISTINCT trip_id` semantics via a `GROUP BY`, you would get an arbitrary (often the stale) version. The correct pattern is "latest row per key": `row_number() over (partition by trip_id order by _ingested_at desc, _batch_id desc) = 1`. Deterministic, and it makes corrections win over originals.

    Q3. MERGE is idempotent and INSERT is not. Explain precisely why, in terms of what happens on a retry.

    Answer A MERGE keyed on `trip_id` matches the incoming row against the existing one and updates it in place; re-applying the identical row sets the same values, so the table state after two runs equals the state after one. An INSERT has no key semantics: the second run appends a second copy, so the table state diverges with every retry, breaking every downstream count. Retries are not an edge case — orchestrators retry on transient failure by design — so a non-idempotent transform is a duplicate generator waiting for a network blip.

    Q4. The relationships test on driver_id fails: 14 trips reference drivers absent from stg_drivers. Give two defensible responses and one indefensible one.

    Answer Defensible: (a) quarantine the orphans to `silver.trips_quarantine` with a reason code, keep silver clean, and raise the count as a source-data incident with the driver-master owner; (b) admit them with null driver attributes, document that `driver_rating` is nullable in the silver contract, and add a volume alert so a jump from 14 to 14,000 is caught. Indefensible: switching the `left join` to an `inner join`, which makes the test pass by silently deleting 14 real trips — the fare revenue disappears from BI and the trips disappear from the model's training set, with no record that anything happened.

    Q5. silver.trips keeps reported_duration_min alongside a derived duration_min. Why keep both?

    Answer `duration_min` derived from `dropoff_ts - pickup_ts` is the value downstream consumers should trust (the source column contains negatives). Keeping the source value lets you *measure the disagreement*: a rising delta between reported and derived duration is an early signal that a source system's clock, timezone, or app version has changed — exactly the class of silent semantic drift the GPS `producer_version` incident represents. Discarding the source value would make that drift undetectable. It costs one column and buys an observability signal.

    Q6. ELT is the default in this course. Name a Masar case where ETL — transforming before the data lands — is still correct.

    Answer Masking or tokenising direct identifiers before they ever reach the platform. If raw rider phone numbers or national IDs must not be stored even in bronze under PDPL data-minimisation, hashing them at the edge (as `drivers.csv` already does with `national_id_hash` and `phone_hash`) is a transform-before-load. The second case is a low-latency operational sink — a pre-aggregated dispatch feed where the transformation must happen in flight because there is no time to land and re-read. Neither undermines ELT for the analytics estate; both are narrow, justified exceptions.
