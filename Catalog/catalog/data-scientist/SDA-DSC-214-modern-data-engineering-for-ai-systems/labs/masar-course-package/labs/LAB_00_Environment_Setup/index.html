    LAB 00 — Environment Setup for the Masar Lakehouse¶

    Send this document to participants T-minus 2 days. Complete it before Day 1 Hour 1. If anything on the acceptance checklist is red at 09:00 on Day 1, you will lose Lab 1 time.

    Field Value
    Lab ID LAB-00
    Module Pre-course (supports M1–M8)
    Day / Hour T-minus 2 days, self-paced
    Duration 45–60 min (30 min if you already have Python + Docker)
    Difficulty Foundational
    LO mapping Enables LO1–LO8; no LO assessed here
    Prerequisites Laptop with admin rights, 16 GB RAM recommended (8 GB workable), 20 GB free disk, GitHub account
    Checkpoint git tag lab0-setup (branch main also works)
    Deliverable A green make doctor report pasted into the course chat, plus SETUP_NOTES.md recording your fallback plan

    Scale note. The figures in this document describe the shipped sample (--scale 0.15): 7,230 trips/day over 5 days (36,150 trips), 873,763 GPS pings, 3,450 drivers, 3,864 vehicles, 48 zones. Every other lab quotes the full-scale generator run (--scale 1.0) — 48,200 trips/day — so the row counts there are larger by design. Regenerate at --scale 1.0 (see data/README.md) if you want them to match.

    Why this lab matters¶

    The course question is "What happens to Masar's AI system if this part of the data platform fails?" — and the first thing that fails is the platform nobody could start. Every lab from Day 1 Hour 3 onward writes into the same masar-lakehouse/ working tree: Lab 1 lands bronze, Lab 3 transforms it to silver, Lab 4 makes silver ACID, Labs 5–8 stream, test, orchestrate and serve it. A broken JAVA_HOME on Day 1 therefore costs you the capstone on Day 5, not just one hour. Setting the environment up now, with the pinned versions, is the cheapest risk reduction available to you: Spark 3.5 with delta-spark 3.2 on Java 17 is a narrow compatibility window, and every version drift you introduce becomes a debugging session that eats lab time. Treat this as the first engineering decision of the course: reproducible environments are part of a reproducible data platform.

    0. What you are installing and why¶

    Component Pinned version Used from Why this pin
    Python 3.11.x Day 1 PySpark 3.5 wheels and dbt-core 1.7 are validated on 3.11; 3.12 breaks several transitive deps
    Java (JDK) 17 (LTS) Day 1 Spark 3.5 runs on 11 or 17; the course pins 17. Java 21+ raises UnsupportedClassVersionError/module errors
    PySpark 3.5.x Lab 1 Delta 3.2 is compiled against Spark 3.5 only
    delta-spark 3.2.x Lab 1 Transaction log, MERGE, time travel (M4)
    dbt-core / dbt-spark 1.7.x Lab 3 incremental_strategy='merge' on file_format='delta' via the session method
    Great Expectations 0.18.x Lab 6 1.x renamed the API used by the shipped suites
    Kafka (bitnami, single broker) 3.7 image Lab 5 Event backbone for GPS pings
    Redis 7 Lab 8 Online feature store, keyspace masar:features:zone:{zone_id}
    Docker Desktop or Colima current Lab 5, Lab 8 Runs the Kafka + Redis stack

    Rule of the course: do not "upgrade to latest". If a tool suggests an upgrade, decline. Pins are in requirements.txt.

    2. Java 17¶

    Spark is a JVM application; PySpark is a client to it. You need a JDK (not a JRE) and a correctly exported JAVA_HOME.

    macOS 

    brew install --cask temurin@17
/usr/libexec/java_home -v 17          # prints the JDK 17 path
echo 'export JAVA_HOME=$(/usr/libexec/java_home -v 17)' >> ~/.zshrc
echo 'export PATH="$JAVA_HOME/bin:$PATH"'                >> ~/.zshrc
source ~/.zshrc

    Windows (PowerShell, admin) 

    winget install EclipseAdoptium.Temurin.17.JDK
[Environment]::SetEnvironmentVariable("JAVA_HOME","C:\Program Files\Eclipse Adoptium\jdk-17.0.11.9-hotspot","User")
# Close and reopen the terminal, then:
$env:JAVA_HOME

    Linux 

    sudo apt install -y openjdk-17-jdk
echo 'export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64' >> ~/.bashrc
source ~/.bashrc

    Verify: 

    java -version        # openjdk version "17.0.x"

    10. Self-check questions¶

    Q1. Why does this course pin Java 17 rather than "whatever JDK is installed"?

    Answer Spark 3.5 supports Java 8/11/17 only. A newer JDK (21+) produces `UnsupportedClassVersionError` or module-access errors (`InaccessibleObjectException`) because Spark's reflective access to `java.nio` is blocked by the module system. Pinning the JDK is the same discipline as pinning the table format version: the platform must be reproducible before it can be trusted.

    Q2. You run the Delta smoke test and get Delta ... is not a valid Spark SQL Data Source. What is wrong, and what is not wrong?

    Answer The `delta-spark` package is installed but the session was built without the Delta extensions (`spark.sql.extensions` and the `DeltaCatalog`). The data, the JDK and the pip install are all fine. Always build the session with `get_spark()`; never construct `SparkSession.builder` ad hoc in a notebook.

    Q3. Why does the course ask you to bring up Kafka on T-2 when the streaming lab is on Day 4?

    Answer Image pulls and port conflicts are the highest-frequency Day-4 failure, and they are slow to fix on a shared classroom network. Pulling images and proving one produce/consume round trip now converts a 40-minute classroom outage into a 3-minute setup step at home.

    Q4. Your organisation's laptop cannot install Docker. Which labs are affected and what is the mitigation?

    Answer Lab 5 (Kafka streaming) and Lab 8's online store (Redis). Mitigation: use the instructor's shared broker for Lab 5 (bootstrap address issued Day 4) and the instructor's shared Redis for Lab 8 (`MASAR_REDIS_HOST` in your `.env` — `src/masar/serve/materialize_online.py` reads it, no code change). If neither is reachable, run Lab 8's offline half (`gold.eta_features`, the leakage drill, the BI star) and pair with someone who has Docker for the materialisation and consistency check. Labs 1–4, 6 and 7 are unaffected because they are pure Spark + Delta on local storage.

    Q5. Why is lakehouse/ a local directory in this course, and what does it stand in for?

    Answer It is a stand-in for an object-storage bucket (`s3://masar-lakehouse/`). The point of Module 2 is compute–storage separation: the Spark JVM is the compute, `lakehouse/` is the storage. Keeping the layout `zone/table/partition/` identical to a bucket means the same code runs unchanged against S3/ADLS.

    11. Troubleshooting¶

    Symptom Cause Fix
    JAVA_HOME is not set / Unable to locate a Java Runtime JDK installed but not exported to the shell Spark runs in macOS/Linux: export JAVA_HOME=$(/usr/libexec/java_home -v 17) (macOS) or /usr/lib/jvm/java-17-openjdk-amd64 (Linux) in ~/.zshrc/~/.bashrc; Windows: set it as a User environment variable and reopen the terminal
    UnsupportedClassVersionError: ... class file version 65.0 Java 21 on the PATH ahead of Java 17 Reorder PATH so $JAVA_HOME/bin comes first; verify with which java / where java
    Apple Silicon: SIGILL / Unable to load native-hadoop library / snappy errors x86 JDK under Rosetta, or an x86 wheel Install the arm64 Temurin 17 build (brew install --cask temurin@17 on an arm64 Homebrew at /opt/homebrew), recreate .venv, pip install --force-reinstall --no-cache-dir pyspark==3.5.*. The Unable to load native-hadoop line alone is a harmless WARN
    Apple Silicon: docker compose up hangs pulling Kafka Image manifest resolving to amd64 under emulation Use colima start --arch aarch64 and the bitnami/kafka:3.7 arm64 manifest already pinned in docker-compose.yml; as a last resort add platform: linux/amd64 to the kafka service and accept slower startup
    Windows: py4j connection refused / Python worker failed to connect back Spark launched from PowerShell without WSL2, or antivirus blocking the loopback worker Run all labs inside WSL2 Ubuntu (wsl -d Ubuntu-22.04), clone the repo inside the Linux filesystem (~/masar-lakehouse, not /mnt/c/...), and install Python/Java inside WSL
    Windows: HADOOP_HOME and hadoop.home.dir are unset / winutils.exe missing Native Windows Spark run Same fix: use WSL2. Do not chase winutils.exe — it is unsupported on this course
    WSL2 project is extremely slow Repo stored on /mnt/c (9p filesystem) Move the repo into the WSL Linux filesystem: cp -r /mnt/c/Users/<you>/masar-lakehouse ~/
    docker compose up fails: bind: address already in use (9092 / 6379) Another Kafka/Redis (or Colima remnant) holds the port lsof -i :9092 (macOS/Linux) or netstat -ano \| findstr 9092 (Windows), stop the owner, or override with KAFKA_PORT=19092 docker compose up -d and set MASAR_KAFKA_BOOTSTRAP=localhost:19092
    pip install fails behind a corporate proxy: SSLError / CERTIFICATE_VERIFY_FAILED TLS interception by the proxy Export HTTPS_PROXY=http://user:pass@proxy.corp:8080 and point pip at the corporate CA: pip config set global.cert /path/to/corp-ca.pem. Never use --trusted-host on a corporate machine without security's approval
    Spark hangs at resolve dependencies ... delta-spark behind a proxy Ivy cannot reach Maven Central Pre-download jars once on an open network (pip install delta-spark==3.2.* already ships them) and add -Dhttp.proxyHost/-Dhttp.proxyPort via PYSPARK_SUBMIT_ARGS, or use the hosted-notebook fallback (§8)
    dbt debug fails Database Error ... could not connect profiles.yml pointing at a Thrift server you are not running The course profile uses method: session; confirm dbt/masar/profiles.yml has method: session and that you run dbt from inside the activated .venv
    make doctor reports data/raw 0 feeds present Repo cloned without LFS or generator not run git lfs install && git lfs pull, then make data
    Spark run dies with java.lang.OutOfMemoryError: Java heap space on an 8 GB laptop Default driver memory too small for the GPS feed export PYSPARK_SUBMIT_ARGS="--driver-memory 4g pyspark-shell" and close browsers/Docker Desktop while running Lab 1
    Everything works, but import masar fails Package not installed in editable mode pip install -e . from the repo root, or export PYTHONPATH=$PWD/src

    12. Stretch goals (optional, before Day 1)¶

    1. Read CONVENTIONS.md end to end and write down the 16 columns of data/raw/trips_YYYY-MM-DD.csv from memory. Every lab depends on this schema.
    2. Run docker compose up -d and leave it running for an hour; check docker stats to learn how much RAM the stack costs you — you will need this on Day 4 alongside Spark.
    3. Skim one _delta_log/*.json file produced by the §3 smoke test (ls /tmp/masar_delta_check/_delta_log/). You will read these aloud in Lab 4.
    4. Configure your IDE to run python -m masar.<module> with the repo root as working directory — every lab command assumes that.

    13. Capstone linkage¶

    The capstone requires a git repository with full history and a one-command make pipeline, plus BENCHMARKS.md filled from your own runs. Both are only possible if your local environment is the pinned one: benchmark numbers from a mismatched Spark or a hosted runtime are not comparable across the cohort, and the academic-integrity check compares benchmark artefacts across repositories. This lab establishes the reproducible substrate that every capstone deliverable is measured on.
