    Masar Lakehouse (مسار)¶

    Starter repository for SDA-DSC-214 — Modern Data Engineering for AI Systems (هندسة البيانات الحديثة لأنظمة الذكاء الاصطناعي), SDAIA Academy.

    You clone this on Day 1 and grow it into your capstone. Every lab writes into the same lakehouse: Lab 1 lands bronze, Lab 3 transforms it to silver, Lab 4 makes silver ACID, Labs 5–8 stream, test, orchestrate and serve it. There are no throwaway datasets and no restarts.

    The question the whole course keeps asking: "What happens to Masar's AI system if THIS part of the data platform fails?"

    Masar is a national smart-mobility platform — ride-hailing plus public transit, operating in Riyadh, Jeddah and Dammam. Two consumers depend on the same data: an ETA model retrained weekly, and an operations dashboard read hourly. The architecture exists so they read the same numbers.

    Quickstart¶

    Do the full setup in labs/LAB_00_Environment_Setup.md two days before Day 1. The short version:

    git clone <your-fork-url> masar-lakehouse
cd masar-lakehouse
git checkout lab1-start

python3.11 -m venv .venv
source .venv/bin/activate          # Windows/WSL2: source .venv/bin/activate
make install                       # pinned stack + `pip install -e .`

make doctor                        # must report 0 fail
make data                          # generate the Masar dataset (pinned seed)
docker compose up -d               # Kafka + Redis (needed from Day 4)

make pipeline                      # build the entire medallion, end to end

    make doctor is the single source of truth for setup. Any [fail] must be fixed before Day 1. Kafka/Redis [warn] is fine until Day 4.

    The one command¶

    make pipeline

    Land bronze → quality gate → build silver → observability → three gold marts → OPTIMIZE + VACUUM. Dependency-ordered, idempotent, and safe to run twice.

    It routes through orchestration/run_local.py, which needs no Airflow. Once you have Airflow installed, USE_AIRFLOW=1 make pipeline runs the same graph through it — the task definitions are shared, so the two cannot drift.

    How the starter marks your work¶

    Everything in src/masar/** is real, working code. The parts you implement are delimited:

    # ── TODO(lab-3): keep the LATEST landed version per trip_id ───────────
#   What : ...
#   Why  : ...
#   Ref  : solutions/lab3_elt.py :: dedupe_latest_per_key
deduped = typed.dropDuplicates(["trip_id"])      # naive starter version
# ── end TODO(lab-3) ───────────────────────────────────────────────────

    The code inside the block runs — make pipeline works on Day 1. It is deliberately the naive version, the one a competent engineer writes before they have met the failure mode. The lab's own acceptance test is what exposes the gap. You are not filling in blanks; you are finding and fixing a plausible bug, which is the part that transfers.

    solutions/README.md lists every block and what its starter version gets wrong. Opening it before you attempt the task costs you the lesson.

    Two things that are unusual, and why¶

    Heavy imports are function-local. import masar never imports PySpark. So scripts/doctor.py can report a MISSING dependency instead of dying on an ImportError while trying to tell you about it, and the unit tests run in about a second on a machine with no Spark at all.

    lakehouse/ and data/raw/ are git-ignored. Data is regenerated from a pinned seed (make data), never committed. Committing Delta tables makes the repo unclonable and the _delta_log meaningless — its commits would be somebody else's.

    Everyday commands¶

    Command Does
    make List every target
    make doctor Check Java 17, Python 3.11, Spark, Delta, dbt, GX, Kafka, Redis
    make data Generate the Masar dataset from the pinned seed
    make land Land every raw feed into bronze
    make gate Run the quality gate: fail-fast, quarantine, promote
    make silver / make gold Build the conformed and served layers
    make stream Replay GPS → Kafka → bronze → silver
    make serve Materialise online features, prove offline == online, check PDPL
    make pipeline The one command. The whole medallion
    make dbt-run / make dbt-test The ELT models and their tests
    make gx Build the GX suites and render the data docs
    make optimize / make vacuum Compact files; reclaim storage (dry run)
    make test The unit tests
    make clean Remove caches and logs — keeps the lakehouse

    Useful overrides: DATE=2026-06-02, USE_AIRFLOW=1, FROM=… TO=…, LAB=7.

    The recovery drill (Lab 7's thesis)¶

    python -m masar.tools.snapshot --out /tmp/before.json
python orchestration/run_local.py --run --inject-failure build_silver
python -m masar.tools.snapshot --out /tmp/during.json
diff <(jq -S . /tmp/before.json) <(jq -S . /tmp/during.json)   # empty: the dependency held

python orchestration/run_local.py --run                        # full re-run
python -m masar.tools.snapshot --out /tmp/after.json
diff <(jq -S . /tmp/before.json) <(jq -S . /tmp/after.json)    # empty: idempotent recovery

    Both diffs empty is the capstone's central claim, demonstrated rather than asserted. If a full re-run is safe, every operational problem is tractable.

    Checkpoint tags¶

    Each lab starts from a tag. If you fall behind, check out the next -start tag and you are caught up — no lab depends on you having finished the previous one perfectly.

    Tag What you get
    lab0-setup Empty scaffold. make doctor should be green.
    lab1-start Stubs for landing and profiling.
    lab2-start Bronze landed; silver.trips sample for the scan benchmark.
    lab3-start dbt project scaffolded; sources declared.
    lab4-start silver.trips from Lab 3, unconstrained.
    lab5-start Kafka compose file; producer and stream stubs.
    lab6-start GX scaffold; the dirty-batch fixtures.
    lab7-start All prior modules importable; DAG stub.
    lab8-start gold/* from Lab 7; Redis running; dbt configured.
    lab1-solution … lab8-solution Each lab's completed state.

    Simulation and incident tags¶

    Tag Simulates Used in
    bad-batch The dirty batch mid-pipeline: 40 null keys, 120 bad fares, 25 bad city codes, 15 reversed timestamps. Fail-fast fires, then quarantine. M6 / Lab 6
    sim-swamp Bronze landed with no profiling, no lineage and overwrite-on-rerun. The data lake as swamp — the thing Lab 1 exists to prevent. M1
    sim-two-tier A separate warehouse copy that has drifted from the lake: two "revenue" numbers, neither reconcilable. The two-tier problem this course solves. M1 / M3

    Instructors also keep incident-speed-unit, which lands the producer 2.5.0 GPS batch (speed_kmh in m/s) so the Module 6 detection drill has a real incident to find.

    For instructors: publishing the tags¶

    Tags are cut from a single linear history so that a participant who checks out lab5-start gets everything Labs 1–4 produced, in the state Lab 5 assumes.

    # from a clean main, at the commit that ends each lab's setup
git tag -a lab3-start -m "LAB-03 start: dbt scaffolded, bronze landed"

# solution branches carry the completed TODO blocks
git checkout -b lab3-solution lab3-start
#   apply solutions/lab3_elt.py's blocks into src/ and dbt/
git commit -am "solution(lab3): incremental idempotent silver.trips"
git tag -a lab3-solution -m "LAB-03 solution"

# simulation tags branch off and are never merged back
git checkout -b sim-swamp lab1-start
#   remove lineage columns, switch bronze writes to overwrite, delete profiling
git commit -am "sim(swamp): unprofiled, unlineaged, overwriting bronze"
git tag -a sim-swamp -m "M1 simulation: the data swamp"

git push origin --tags

    Checklist before a cohort starts. Every -start tag must:

    1. pass make doctor with 0 fail on a clean machine;
    2. pass make test;
    3. run make pipeline to completion (the naive TODO blocks are working code — that is the point);
    4. contain the LAB_N_NOTES.md template the lab asks participants to fill in;
    5. be reachable by git fetch --tags from the fork participants cloned.

    Run steps 1–3 from a fresh clone, not from your working tree. The most common failure is a tag that works only because of an untracked file.

    The pinned stack — do not upgrade¶

    Component Pin Why this pin
    Python 3.11.x PySpark 3.5 wheels and dbt-core 1.7 are validated on 3.11; 3.12 breaks transitive deps
    Java 17 (LTS) Spark 3.5 runs on 8/11/17. Java 21+ raises UnsupportedClassVersionError
    PySpark 3.5.x Delta 3.2 is compiled against Spark 3.5 only
    delta-spark 3.2.x Transaction log, MERGE, time travel
    dbt-core / dbt-spark 1.7.x incremental_strategy='merge' on file_format='delta' via method: session
    Great Expectations 0.18.x 1.x renamed the API the shipped suites use
    Kafka bitnami 3.7 (KRaft) Single broker, no ZooKeeper, arm64-native
    Redis 7 Online feature store, masar:features:zone:{zone_id}
    Airflow 2.9 (optional) Or the shipped runner — no lab blocks on it

    Currency SAR. Timezone Asia/Riyadh (UTC+3) — stored UTC, presented +03.

    Troubleshooting¶

    Symptom Fix
    import masar fails pip install -e ., or export PYTHONPATH=$PWD/src
    Delta ... is not a valid Spark SQL Data Source Build the session with masar.spark.get_spark(), never SparkSession.builder directly
    UnsupportedClassVersionError Java 21 ahead of 17 on PATH. Reorder so $JAVA_HOME/bin comes first
    make doctor says data/raw 0 feeds present make data (and git lfs pull first if your fork uses LFS)
    Spark OOM on the GPS feed export PYSPARK_SUBMIT_ARGS="--driver-memory 4g pyspark-shell"
    bind: address already in use (9092) KAFKA_PORT=19092 docker compose up -d and set MASAR_KAFKA_BOOTSTRAP to match
    Airflow will not install Use orchestration/run_local.py. It is a supported path, not a downgrade
    dbt could not connect The course profile uses method: session; run dbt inside the activated .venv

    labs/LAB_00_Environment_Setup.md §11 has the full table, including the Windows/WSL2 and Apple Silicon cases.

    Capstone deliverables¶

    Fill these from your own runs. The templates tell you what "filled in" means.

    • docs/ARCHITECTURE.md — the design and its failure modes
    • docs/DATA_CONTRACTS.md — grain, keys, SLAs, owners, per layer
    • GOVERNANCE.md — from docs/GOVERNANCE_TEMPLATE.md
    • DECISIONS.md — from docs/DECISIONS_TEMPLATE.md
    • BENCHMARKS.md — from docs/BENCHMARKS_TEMPLATE.md, your own numbers
    • A git repository with full history and a working one-command make pipeline

    Benchmark figures are compared across the cohort. Numbers copied from the slides, from a classmate, or from the template are an academic integrity issue.
