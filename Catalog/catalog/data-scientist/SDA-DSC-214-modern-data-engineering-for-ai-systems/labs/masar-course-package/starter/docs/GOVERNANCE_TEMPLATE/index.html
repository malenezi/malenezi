    Masar — Governance and PDPL Register¶

    Capstone deliverable. Rename to GOVERNANCE.md, fill every TBD, and commit it alongside the code it describes. A governance document that is not in the repository is a governance document that is not maintained.

    Saudi Arabia's Personal Data Protection Law (PDPL) is treated here as an engineering constraint, not a policy appendix. Every section below should be answerable by pointing at code or config, not at intent.

    1. Data classification¶

    Classification is the ROOT of every other control: access, retention, what may cross the serving boundary, and what an erasure request must touch.

    The machine-readable source of truth is src/masar/governance/classification.py. This table must agree with it — if they diverge, the code wins and this document is out of date.

    Class Meaning Retention Readable by Example columns
    public No restriction no PDPL limit analyst, DS, engineer, DPO city, zone_name_en, distance_km
    operational Internal identifiers, no data subject no PDPL limit analyst, DS, engineer, DPO trip_id, vehicle_id, event_id
    commercial Financial values 7 years (tax law, not PDPL) analyst, DS, engineer, DPO fare_sar, amount_sar
    personal-coarse Indirectly identifying at low resolution 730 days DS, engineer, DPO dropoff_geohash
    personal-pseudonymised Hashed at source — still personal data 730 days engineer, DPO national_id_hash, phone_hash
    personal Directly identifies a data subject 730 days engineer, DPO rider_id, driver_id, full_name_en
    sensitive-location Precise coordinates 180 days DPO only lat, lon

    Two rules that are routinely got wrong¶

    A hash is not anonymisation. national_id_hash is pseudonymised personal data. It still belongs to a person, it is still in scope for an erasure request, and it still must not reach a dashboard. Treating a hash as anonymous is the most common PDPL mistake in a data platform, and it is usually made in good faith by someone who thinks "we hashed it" is the end of the sentence.

    Precise location is its own class. Metre-resolution lat/lon reveals homes, workplaces and routines. A zone centroid does not — the RESOLUTION is the control, which is why centroid_lat is public and lat is not.

    Unclassified means restricted. classify() returns personal for any column it does not know. An unclassified column is an unreviewed column, and the safe default for unreviewed data is the strict one. Adding a feature should require a one-line classification decision; that friction is intentional.

    3. Retention and minimisation¶

    Dataset Window Mechanism Justification
    bronze.gps_events 180 days enforce_gps_retention() → DELETE + VACUUM Precise location, purpose-bound. Masar does not need metre-resolution traces from eight months ago to run a network.
    silver.vehicle_positions 180 days as above as above
    bronze.trips TBD TBD Reprocessing substrate; balance against personal-data minimisation.
    silver.trips TBD TBD TBD
    Delta time travel 168 hours (7 days) VACUUM ... RETAIN 168 HOURS See below.

    Why RETAIN 168 HOURS, and never RETAIN 0¶

    The retention window is a genuine trade-off with two real sides:

    • Shorter — less storage, less audit history, and an erasure request is satisfied sooner (VACUUM is what makes a delete physical).
    • Longer — more storage, more ability to answer "what did the model see last Tuesday?", and personal data lingers in history longer.

    Seven days is chosen because it spans a full weekly retraining cycle: any model can be reproduced against the exact data it was trained on.

    RETAIN 0 HOURS is not the aggressive end of that trade-off. It ends the audit trail entirely and can break a reader mid-query against a version you just removed. Delta refuses it unless the retention check is disabled — treat having to disable a safety check as the answer to whether you should.

    The tension worth naming: the time travel that makes the platform auditable is the same feature that makes erasure slow. You cannot have one without accepting the other; you can only decide the window and document why.

    4. Right to erasure (PDPL Article 18)¶

    SLA: TBD (30 days is the usual statutory window) Runbook: python -m masar.governance.retention --erase-request <path> --execute

    Procedure¶

    1. Receive — the DPO logs the request with a ticket reference. An erasure with no ticket is an unexplained deletion, which is its own compliance problem.
    2. Scope — enumerate EVERY table holding a joinable identifier, not just the ones with a rider_id column.
    3. Dry run — --dry-run first. Confirm the row counts against the requester's expectation before anything is destroyed.
    4. Execute — MERGE DELETE across every table in scope.
    5. VACUUM — past the retention window. This is the step that makes the erasure real. Until it runs, the request has been recorded, not honoured.
    6. Audit — an immutable record in lakehouse/governance/erasure_audit: ticket reference, hashed subject id, timestamp, per-table row counts. The audit log must prove which request was executed without itself becoming a register of the people who asked to be forgotten — hence the hash.

    The trap this procedure exists to close¶

    GPS pings are keyed by trip_id and vehicle_id. They have no rider_id.

    A rider-keyed erasure across silver.trips therefore does not touch silver.vehicle_positions, and the data subject's metre-resolution location trace survives an erasure that reported success. The fix is to resolve the subject's trip_ids first and delete positions by trip_id (erase_rider_positions).

    Any erasure procedure that does not enumerate every table holding a JOINABLE identifier is incomplete, and "we deleted the rider table" is the most common form of that mistake.

    Table Holds rider_id? Reached how
    bronze.trips yes direct
    silver.trips yes direct
    silver.trips_quarantine yes direct
    gold.fact_trip pseudonym only recompute after silver delete
    silver.vehicle_positions no via trip_id join
    Redis online store no (zone grain) n/a — no per-subject key exists

    5. The serving boundary¶

    Rule: raw rider_id and precise GPS never cross into a BI product or the online store.

    Enforced by python -m masar.serve.pdpl_boundary_check, which exits non-zero. It belongs in CI: governance that lives in a PDF is checked when someone remembers; governance that lives in a build step is checked every time.

    Three controls, applied in order, each doing a different job¶

    1. Pseudonymise — sha2(rider_id, 256). Keeps cohort analysis possible without exposing the identifier.
    2. Minimise — DROP the raw column. Keeping it beside its own hash protects nothing; a column you did not publish cannot leak and does not have to be found again during an erasure.
    3. Reduce resolution — zone ids, not coordinates. The analyst question is about districts.

    Documented exceptions¶

    Every allow-list entry in masar.serve.pdpl_boundary_check.BOUNDARY_TARGETS must be justified here. An exception with no justification recorded is a leak with a comment in front of it.

    Dataset Column allowed Justification
    gold.fact_trip rider_pseudonym Cohort analysis without the identifier; still in scope for erasure.
    gold.fact_trip driver_key Driver-level BI is a stated business purpose; exposure is to a named analyst role, never to the online store.
    gold.dim_driver driver_id, full_name_en Driver-level reporting requires a label. national_id_hash and phone_hash are excluded.

    What this costs — be honest¶

    An analyst can no longer join a rider to a support ticket, or map a dropoff to a building. Both are real capabilities and both are gone.

    State at least one thing your organisation genuinely cannot do as a result. Governance that costs nothing usually protects nothing — if you cannot name a cost, you have probably not applied a control.

    8. Review checklist¶

    • Every column in silver.* and gold.* has a classification
    • Every classification has a retention window and an access rule
    • Every retention window has a stated justification, not just a number
    • pdpl_boundary_check runs in CI and blocks the build on failure
    • Every allow-list exception is justified in §5
    • The erasure runbook has been rehearsed end to end, including VACUUM
    • The erasure scope includes silver.vehicle_positions via the trip join
    • VACUUM retention is documented and is never 0
    • The audit log records ticket refs and hashed subject ids, not raw ids
    • At least one capability genuinely lost to governance is named in §5
