    Masar — Architecture Decision Record¶

    Capstone deliverable. Rename to DECISIONS.md. One entry per decision that was genuinely contested. Ten thorough ADRs beat forty thin ones.

    An ADR records a decision and the alternative you rejected. If you cannot name a real alternative and a real cost, you did not make a decision — you followed a default, and that needs no record.

    Two entries are worked through below as examples of the depth expected. The rest are stubs.

    Scale note. Figures quoted in this document assume the full-scale generator run (--scale 1.0); the shipped sample is --scale 0.15 — 7,230 trips/day over 5 days (36,150 trips), 873,763 GPS pings, 3,450 drivers, 3,864 vehicles, 48 zones. Grains, ratios and file-count reductions hold at either scale; absolute row counts do not.

    Template¶

    ## ADR-00N — <decision, stated as an outcome>

**Status:** proposed | accepted | superseded by ADR-00M
**Date:** YYYY-MM-DD
**Deciders:** <names>
**Module:** M1–M8

### Context
What forced a choice? What constraint, incident or requirement?

### Options considered
| Option | Pros | Cons |
|---|---|---|
| A (chosen) | | |
| B | | |

### Decision
What we do, in one sentence, in the present tense.

### Consequences
What this costs, what it forecloses, what now needs monitoring.

### How we would know we were wrong
The observation that would make us revisit this. An ADR with no falsifier is
a statement of preference.

    ADR-001 — Partition silver.trips by city, not by trip_id¶

    Status: accepted · Date: 2026-06-02 · Module: M2, M4

    Context¶

    silver.trips grows by ~42,000 rows/day. Queries filter overwhelmingly by city and date range. Partitioning determines both scan cost and file count, and file count determines object-storage request cost — which at Masar's read volume is not a rounding error.

    Options considered¶

    Option Pros Cons
    city (chosen) 5 partitions; matches the dominant filter; large files Riyadh is ~55% of volume — skew
    trip_id Perfectly even 42,038 directories/day. Metadata storm, 3× request bill, 800 ms → 40 s dashboards
    (city, date) Finer pruning ~15 partitions/day; small files within a day at this volume
    none Simplest Every query scans everything

    Decision¶

    Partition by city. ZORDER by (city, pickup_ts) in the nightly OPTIMIZE to recover the intra-partition pruning that a date partition would have given.

    Consequences¶

    Riyadh partitions are ~3× the others; acceptable at this scale, and it is the first thing to revisit if a single-city query becomes the hot path. ZORDER must actually run — without it the pruning argument does not hold.

    How we would know we were wrong¶

    DESCRIBE DETAIL shows average file size dropping below ~64 MB, or the p95 dashboard query exceeds 3 s with numFiles climbing between OPTIMIZE runs.

    ADR-002 — Materialise online features by copying from gold, never recomputing¶

    Status: accepted · Date: 2026-06-04 · Module: M8

    Context¶

    The ETA model needs zone features in under 50 ms at inference. The Lakehouse cannot serve that latency directly, so a derived copy in Redis is required. The question is what writes it.

    Options considered¶

    Option Pros Cons
    Copy from gold.eta_features (chosen) Consistent by construction; one feature implementation Freshness bounded by the batch cadence (~15 min)
    Recompute in the serving path Always fresh Two implementations of one feature = skew, guaranteed eventually
    Serve from the Lakehouse directly One store Cannot meet 50 ms

    Decision¶

    masar.serve.materialize_online copies values from gold.eta_features verbatim. There is no arithmetic in that module and there must never be any. masar.serve.consistency_check compares every key and every column against the offline table and exits non-zero on any mismatch; it runs in CI.

    Consequences¶

    Online features are up to one batch stale, which is acceptable for zone-demand features and would not be for a per-second signal. The consistency check is now load-bearing: if it is disabled, the guarantee is gone and nothing else would notice.

    How we would know we were wrong¶

    The consistency check fails, or a product requirement appears that needs sub-batch freshness — at which point the answer is a streaming write into Redis from the same feature job, still without a second implementation.

    What makes an ADR worth reading¶

    • A real alternative. "We considered doing it badly" is not an option.
    • A stated cost. Every decision forecloses something. Name it.
    • A falsifier. What would change your mind, expressed as an observation.
    • A date and a person. Decisions age; anonymous ones age worst.

    The test: hand the ADR to an engineer who joins in six months. Can they tell whether the decision still applies, without asking you?
