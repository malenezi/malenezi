    Masar Lakehouse — Architecture¶

    The question this architecture exists to answer: "What happens to Masar's AI system if THIS part of the data platform fails?" Every component below is documented with its failure mode, because a design that only describes the happy path is a design nobody can operate.

    Masar (مسار) is a national smart-mobility platform: ride-hailing plus public transit, operating in Riyadh, Jeddah and Dammam. Two consumers depend on the same data — an ETA model retrained weekly, and an operations dashboard read hourly — and the whole point of the architecture is that they read the same numbers.

    Scale note. Figures quoted in this document assume the full-scale generator run (--scale 1.0); the shipped sample is --scale 0.15 — 7,230 trips/day over 5 days (36,150 trips), 873,763 GPS pings, 3,450 drivers, 3,864 vehicles, 48 zones. Grains, ratios and file-count reductions hold at either scale; absolute row counts do not.

    Storage is ./lakehouse/ locally and an object-storage bucket (s3://masar-lakehouse/) in production. The directory layout is identical — zone/table/partition=.../part-*.parquet — so the move is a configuration change, not a rewrite. That is compute-storage separation made physical: kill the JVM and the data is still there.

    2. The layers, and what each one promises¶

    Bronze — an append-only ledger of what ARRIVED¶

    Property Decision Failure mode if you get it wrong
    Write mode append, never overwrite A bug found in week six is unfixable for weeks one to five: the evidence is gone.
    Typing Everything lands as STRING (inferSchema=False) Inference guesses at the two timestamp formats and silently nulls the 2% that do not match — destroying evidence before anyone looked.
    Schema mergeSchema=false An upstream schema change is absorbed silently, and the drift Module 6 exists to catch never surfaces.
    Lineage _ingested_at, _source_file, _batch_id on every row "Which file produced this row?" is the first question a regulator asks, and landing time is the only cheap moment to answer it.

    Landing the same day twice doubles the rows, and that is correct. The two batches are distinguishable by _batch_id, so silver can deterministically keep the latest version per key without ever having lost the earlier one. Overwriting would have made the duplication invisible and the history unrecoverable.

    The gate — the only door into silver¶

    Three outcomes, decided by each expectation's meta.response_class (quality/gate_config.yml is the policy; masar.quality.gate is the engine):

    • FAIL_FAST — integrity. Null or duplicate business key, missing event time, schema change, type change. Promoting anything from such a batch is worse than promoting nothing. The task raises; every downstream task is skipped.
    • QUARANTINE — partial. Bad fares, impossible durations, unknown cities. Bad rows go to silver.trips_quarantine with their reason; good rows are promoted. Alert either way.
    • All pass — promote, alert nothing.

    Getting this split wrong fails in two directions, and the second is worse: too much fail-fast and someone adds a bypass flag until the gate is decoration; too much quarantine and a batch with duplicate keys reaches silver, where MERGE becomes ambiguous and the result is undefined.

    Silver — the conformed contract¶

    One row per business key. Completed, valid trips only. Timestamps stored UTC, presented Asia/Riyadh (+03). City codes mapped to names exactly once. speed_kmh always in km/h, whatever the producer version claimed.

    Enforced in three independent places, on purpose:

    1. Delta CHECK constraints on the table — every future write, every writer.
    2. dbt tests on the model — every build, in CI.
    3. The gate at promotion — every batch, before it lands.

    Anything filtered out still exists in bronze. Nothing is destroyed; it is excluded from the contract downstream consumers may rely on.

    Gold — two products, one truth¶

    • BI: a conformed star (fact_trip + dim_date, dim_driver, dim_vehicle, dim_zone) plus two marts (zone_hourly_demand, driver_daily). Conformed dimensions are what make numbers reconcile across dashboards; two dim_dates is how "last week" comes to mean two different things.
    • AI: eta_features and trip_features, point-in-time correct, plus a Redis slice at masar:features:zone:{zone_id} copied from gold — never recomputed.

    3. The five decisions that carry the design¶

    3.1 Partition on cardinality, not on the key¶

    silver.trips is partitioned by city: five values. Partitioning by trip_id would create 42,038 directories — a metadata storm, a tripled object-storage request bill, and a dashboard query that goes from 800 ms to 40 s. gold.driver_daily is partitioned by date only, not by (city, date, driver_id), for the same reason.

    3.2 Idempotency is what makes recovery possible¶

    Every task is safe to re-run. That is not tidiness; it is the property that turns "re-run the whole thing" into a safe instruction. Without it, a 02:30 failure becomes a 09:00 archaeology project in which somebody re-runs "the parts that failed", in a remembered order, having skipped the gate because "it passed yesterday".

    Table Strategy Why this one
    bronze.* append + txnAppId/txnVersion The ledger grows; replayed batches are dropped by Delta.
    silver.trips MERGE on trip_id Keyed upsert: re-running updates the same rows to the same values.
    gold.zone_hourly_demand replaceWhere on the date window Replaces exactly the partitions recomputed; O(lookback), not O(history).
    gold.driver_daily MERGE on (driver_id, date) The grain does not align to one partition column cleanly.
    gold.*_features full overwrite Small, derived, cheap to rebuild; simplest correct thing.

    3.3 Event time everywhere it matters¶

    Late data is the norm, not the exception. Three mechanisms, one principle:

    • Silver lookback — a 3-day window on pickup_ts (event time), not on _ingested_at. A trip that ended Monday but arrived Wednesday must stay inside the window for the full lookback, so every re-run re-merges it.
    • Streaming watermark — 5 minutes on event_ts. Bounds both the lateness tolerated and the state kept.
    • Feature windows — strictly prior, rangeBetween(..., -1).

    The one place processing time is correct is the operations alerter: an alert is about NOW, not about when the event happened.

    3.4 Point-in-time correctness is structural, not a review item¶

    Every rolling feature is declared as a FeatureWindow in masar.transform.feature_spec and asserted at build time. A window whose upper bound is not strictly negative fails the build.

    rangeBetween(-3600, 0) reads as "the last hour" and is not: rangeBetween is inclusive of both bounds, so it admits every other trip that started in the same second. In a busy zone at 07:14 that is several trips which had not happened yet. One character; a metric that lies. A lint that runs beats a rule everyone agrees with.

    3.5 PDPL is a constraint on the design, not a review at the end¶

    Classification (masar.governance.classification) is the root of everything else: access control, retention windows, what may cross the serving boundary, and what an erasure request has to touch.

    Two rules that are routinely got wrong:

    1. A hash is not anonymisation. national_id_hash is pseudonymised personal data. It still belongs to a person, is still in scope for erasure, and still must not reach a dashboard.
    2. Precise location is its own class. Metre-resolution lat/lon reveals homes and routines. A zone centroid does not — the resolution is the control.

    masar.serve.pdpl_boundary_check asserts all of this and exits non-zero, so it belongs in CI. Governance that lives in a PDF is checked when someone remembers; governance that lives in a build step is checked every time.

    4. Failure modes, and what holds¶

    If this fails The AI system… What contains it
    Landing overwrites instead of appending degrades invisibly — no reprocessing is possible after any later bug append-only bronze; _batch_id makes re-lands visible
    The gate is bypassed trains on negative fares and unkeyed rows gold builds from silver only; the DAG edge enforces it
    Silver dedup keeps an arbitrary row silently loses ~half of all corrections row_number() over _ingested_at desc
    A gold task appends instead of merging double-counts demand → surge fires at 2× on a normal Tuesday replaceWhere / MERGE + a grain assertion on every write
    A feature window includes the present offline R² rises, live performance does not FeatureWindow.assert_point_in_time() fails the build
    A producer changes a field's meaning learns a fleet that never speeds up per-producer_version distribution check vs a frozen baseline
    The streaming job is killed mid-batch (nothing) checkpointed offsets + Delta's atomic commit with txnVersion
    Online features are recomputed rather than copied training/serving skew appears weeks later consistency_check compares every key, exits non-zero
    VACUUM RETAIN 0 HOURS is run loses the audit trail and the erasure evidence retention is config (MASAR_VACUUM_RETAIN_HOURS), never 0; the Delta retention check stays enabled

    5. Orchestration¶

    land_bronze ─► quality_gate ─► build_silver ──┐
                               build_drivers ─┴─► observability ─┬─► gold_zone_hourly_demand ─┐
                                                                 ├─► gold_driver_daily        ├─► optimize_vacuum
                                                                 └─► gold_trip_features ──────┘

    The graph is declared once, in masar.orchestration.runner, and imported by both orchestration/dags/masar_medallion.py (Airflow 2.9 TaskFlow) and orchestration/run_local.py (no Airflow at all). They cannot disagree about what the pipeline is, and no lab ever blocks on an orchestrator install.

    quality_gate has retries=0 on purpose: retrying a deterministic integrity rejection is a slower way of ignoring it.
