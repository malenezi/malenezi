    Masar Lakehouse — Data Contracts¶

    A data contract is a promise one team makes to another about the shape, quality and timeliness of a dataset — plus the place that promise is enforced. A contract with no enforcement point is a wish.

    Every table below states: grain, keys, freshness SLA, owner, what breaks a consumer, and where the contract is enforced.

    Fill in the Owner column with a real person or rota before the capstone review. "The data team" is not an owner; it is an absence of one.

    How to read the enforcement column¶

    Enforcement Means
    Delta CHECK The table rejects the write. Every writer, forever.
    dbt test The build fails in CI before anything is published.
    GX + gate The batch is blocked or split at promotion time.
    Grain assert The build task raises if row count ≠ distinct key count.
    Lint A build-time assertion on the code, not the data.

    Layered on purpose. Any single one of these can be bypassed by someone in a hurry; three cannot be bypassed by accident.

    Bronze — the landing zone¶

    Promise: everything that arrived, exactly as it arrived, with lineage. Non-promise: uniqueness, typing, validity, or completeness of any kind.

    Table Grain Keys Freshness SLA Owner Enforcement
    bronze.trips one row per delivered record (duplicates expected) none warn 6h / error 24h TBD source freshness (dbt), _batch_id lineage
    bronze.gps_events one row per delivered ping none warn 1h / error 6h TBD source freshness, txnAppId/txnVersion idempotency
    bronze.drivers one row per delivered roster record none warn 24h / error 72h TBD source freshness
    bronze.vehicles one row per delivered record none warn 24h / error 72h TBD source freshness
    bronze.zones one row per delivered record none warn 72h / error 168h TBD source freshness
    bronze.payments one row per delivered record none warn 6h / error 24h TBD source freshness

    Universal bronze columns. Every table carries _ingested_at (when the platform saw it), _source_file (which file or Kafka partition it came from) and _batch_id (which landing run produced it).

    What breaks a consumer: treating bronze as if it had a grain. It does not. Counting bronze.trips and reporting it as "trips yesterday" will be wrong the first time a day is re-landed — which is a normal, correct operation.

    Retention: indefinite for trips (the reprocessing substrate); 180 days for bronze.gps_events (precise location, purpose-bound — see GOVERNANCE_TEMPLATE.md).

    Silver — the conformed contract¶

    Promise: one row per business key; conformed, typed, valid. This is THE contract. Changing a column here is a breaking change and goes through review as one.

    silver.trips¶

    Field Value
    Grain Exactly one row per trip_id
    Primary key trip_id (unique, not null)
    Foreign keys driver_id → silver.drivers, pickup_zone_id/dropoff_zone_id → dim_zone
    Partitioned by city (5 values — never by trip_id)
    Freshness SLA ≤ 6 hours behind bronze
    Volume ~42,000 rows/day, ±30% tolerance
    Owner TBD

    Guarantees:

    • status = 'completed' only. Cancellations and no-shows stay in bronze.
    • pickup_ts, dropoff_ts in UTC; trip_date is the Asia/Riyadh business date. Both source timestamp formats are parsed.
    • city is a conformed NAME (Riyadh), never a raw code (RUH).
    • fare_sar > 0, distance_km > 0, dropoff_ts > pickup_ts.
    • duration_min is DERIVED from the timestamps, not the reported value. reported_duration_min is kept alongside it and may disagree — that disagreement is itself a data-quality signal.
    • dropoff_geohash is ~3.1% null. Known, tolerated, monitored at a 95% threshold so a degradation is an event.

    Enforcement: Delta CHECK (positive_fare, valid_duration, known_city) · dbt tests (unique, not_null, accepted_values, accepted_range, relationships) · GX + gate at promotion.

    What breaks a consumer: a duplicated trip_id. Every downstream MERGE becomes ambiguous, which is undefined behaviour rather than a wrong number.

    silver.vehicle_positions¶

    Field Value
    Grain Exactly one row per event_id
    Primary key event_id
    Partitioned by event_date
    Freshness SLA ≤ 15 minutes behind the stream
    Volume ~1.2M rows/day
    Owner TBD

    Guarantees:

    • Deduplicated within a 5-minute watermark.
    • speed_kmh is ALWAYS km/h, whatever producer_version claimed. Producer 2.5.0 emits m/s under the same key and type; the conversion happens here, once, so no consumer has to know it ever happened.
    • accuracy_m ≤ 50. A worse fix is noise, not a position.
    • lat/lon inside the Saudi bounding box.
    • event_lag_s and is_late are retained so lateness stays measurable.

    Enforcement: GX gps_events.contract (including the per-version mean check) · streaming filters in build_vehicle_positions.

    What breaks a consumer: the speed unit. Every value stays individually plausible, so nothing errors; the ETA model simply learns that a third of the fleet crawls, and ETAs for those vehicles inflate for weeks.

    silver.drivers · silver.payments · silver.trips_quarantine¶

    Table Grain Keys SLA Owner
    silver.drivers one row per driver_id, type-1 driver_id ≤ 24h TBD
    silver.payments one row per payment_id payment_id ≤ 6h TBD
    silver.trips_quarantine one row per rejected row per batch none n/a TBD

    silver.trips_quarantine carries _quarantine_reasons (an array — a row can be wrong in more than one way), _quarantined_at and _batch_id. A quarantine table without reasons is a landfill: "120 rows rejected" starts an investigation, "120 rows: fare_non_positive" ends one.

    Gold — the served products¶

    Promise: stable, documented, consumer-facing. Two consumers, one truth.

    BI: the conformed star¶

    Table Grain Key SLA Owner Notes
    gold.fact_trip one row per trip_id trip_id ≤ 6h TBD FKs to all four dimensions; no rider_id — a pseudonym only
    gold.dim_date one row per calendar date date_key static TBD THE conformed date dimension. Exactly one exists. is_weekend = Fri+Sat (KSA)
    gold.dim_driver one row per driver_id (type-1) driver_key ≤ 24h TBD national_id_hash/phone_hash excluded by classification
    gold.dim_vehicle one row per vehicle_id vehicle_key ≤ 24h TBD
    gold.dim_zone one row per zone_id zone_key ≤ 168h TBD Centroid at ZONE resolution, never per-trip
    gold.zone_hourly_demand one row per (city, zone, date, hour) composite ≤ 6h TBD Also an input to surge pricing
    gold.driver_daily one row per (driver_id, date) composite ≤ 6h TBD
    gold.bi_trips_safe one row per trip_id trip_id ≤ 6h TBD PDPL-safe analyst view

    Conformed dimensions are the contract. One dim_date, one dim_zone, shared by every fact and mart. Two of either is how the revenue dashboard and the demand dashboard start disagreeing about what "last week" means, and the disagreement is discovered in a steering committee.

    gold.zone_hourly_demand is special. Surge pricing reads it. A double-counted row here is not a reporting error — it is a price. That is why its write is MERGE on the full grain key and why _assert_grain runs on every build.

    AI: the feature products¶

    Table Grain Key SLA Owner
    gold.eta_features one row per trip_id trip_id ≤ 6h TBD
    gold.trip_features one row per trip_id trip_id ≤ 6h TBD
    Redis masar:features:zone:{zone_id} one key per zone zone_id ≤ 15 min TBD

    gold.eta_features columns are fixed by CONVENTIONS.md and are not negotiable — the training join, the online store and the model all agree on them:

    trip_id, pickup_zone_id, dropoff_zone_id, hour_of_day, day_of_week,
rolling_zone_demand_15m, rolling_avg_speed_10m, driver_recent_trip_count,
weather_condition, distance_km, historical_route_duration, feature_ts,
label_actual_duration_min

    Guarantees:

    • Point-in-time correct. Every rolling window is strictly prior: rangeBetween(..., -1). Declared in masar.transform.feature_spec and asserted at build time.
    • Available at inference. No column may depend on data that does not exist at prediction time. distance_km is the ROUTED distance, not the actual — the column name is the contract, the provenance is the implementation.
    • _feature_version on every row and every Redis payload. Without it, "which features produced this prediction?" is unanswerable at exactly the moment somebody needs the answer.
    • Online == offline. The Redis slice is COPIED from gold, never recomputed. masar.serve.consistency_check compares every key and every column and exits non-zero on any mismatch.

    What breaks a consumer: a feature computed differently online and offline. It will not disagree at first. It will disagree after someone fixes a rounding bug in one of the two implementations, and the model will get quietly worse with nothing in any log.

    Contract change process¶

    1. Propose — open a PR against the model, its _*__models.yml, and this file. A schema change with no contract update is not reviewable.
    2. Classify — new columns get a PDPL classification in masar.governance.classification. classify() fails closed, so an unclassified column is treated as personal until somebody has looked.
    3. Test — add the dbt test that makes the new guarantee enforceable. A guarantee with no test is a comment.
    4. Announce — additive changes need notice; removals and renames need agreement from every named owner.
    5. Version — bump _feature_version for any change to a feature's MEANING, even if its name and type are unchanged. Especially then: that is exactly the change nothing else detects.
