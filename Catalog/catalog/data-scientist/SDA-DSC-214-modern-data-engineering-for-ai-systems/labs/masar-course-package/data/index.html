    Masar (مسار) data package — SDA-DSC-214¶

    Course: Modern Data Engineering for AI Systems · SDAIA Academy Golden thread: Masar, the national smart-mobility platform of a Saudi ride-hailing and public-transit operator. Every lab in this course grows the same lakehouse from the same data. There are no throwaway datasets here.

    Everything in this directory is fully synthetic. See Licence and provenance.

    What is shipped¶

    data/
  raw/                       5 days of the Masar raw zone, generated at --scale 0.15
    trips_2026-06-0[1-5].csv         7,230 rows/day
    gps/gps_2026-06-0[1-5].ndjson.gz ~175,000 pings/day  (GZIPPED — see below)
    payments_2026-06-0[1-5].csv      ~6,970 rows/day
    drivers.csv                      3,450 rows
    vehicles.csv                     3,864 rows
    zones.csv                        48 rows (Riyadh / Jeddah / Dammam districts, EN + AR)
    weather_hourly.csv               360 rows (3 cities x 120 hours)
    _MANIFEST.json                   per-file row count, byte size, sha256, and the seed
  fixtures/                  the staged incidents each lab is built around
    corrections/  late_trips/  late_pings/  dirty_batch/
    currency_shift/  erasure_request/  incident_speed_unit/
    README.md  _FIXTURES.json
  generators/
    generate_masar.py        the raw zone
    inject_defects.py        the fixtures
    emit_gps_stream.py       GPS -> Kafka topic masar.gps.raw (Module 5)
    nyc_tlc_prep.py          OPTIONAL real-world benchmark (NYC TLC yellow taxi)
    verify_sample.py         manifest + profile verification
  DATA_DICTIONARY.md         one table per file: type, nullability, PDPL class, retention

    Total on disk: ~39 MB.

    GPS is gzipped¶

    The shipped GPS files are gps_YYYY-MM-DD.ndjson.gz, not .ndjson. Five days of raw NDJSON would be 220 MB; gzipped it is 26 MB, which keeps the whole package inside the 40 MB repo budget. Nothing else is compressed.

    Every tool in this package reads either form transparently. In your own code:

    import gzip, json
opener = gzip.open if path.endswith(".gz") else open
with opener(path, "rt", encoding="utf-8") as fh:
    events = [json.loads(line) for line in fh]

    # Spark reads gzipped NDJSON natively — the codec is inferred from the extension.
spark.read.json("data/raw/gps/*.ndjson.gz")      # works
spark.read.json("data/raw/gps/")                 # also works: mixed .ndjson / .ndjson.gz

    # pandas, likewise
pd.read_json(path, lines=True, compression="infer")

    Gzip is not splittable, so one file is one Spark task. At the shipped scale that is irrelevant (5 MB per file); at full scale, regenerate without --gzip-gps — which is the default — and you get plain, splittable NDJSON.

    Regenerating¶

    Everything is seeded. Same seed + same arguments ⇒ byte-identical output, on any machine with Python 3.11 and no third-party packages.

    cd data/generators

# the shipped sample, exactly as committed
python3 generate_masar.py --start 2026-06-01 --days 5 --out ../raw --scale 0.15 --gzip-gps
python3 inject_defects.py --raw ../raw --out ../fixtures --start 2026-06-01 --days 5

# FULL SCALE — the 30-day dataset the lab specs describe (~9 GB, ~7 minutes)
python3 generate_masar.py --start 2026-06-01 --days 30 --out ../raw --scale 1.0

# full scale but compressed (~1.3 GB) if disk is tight
python3 generate_masar.py --start 2026-06-01 --days 30 --out ../raw --scale 1.0 --gzip-gps

# a clean copy with EVERY deliberate defect switched off (useful as a control)
python3 generate_masar.py --days 5 --out ../raw_clean --scale 0.15 --clean

    Dependencies: Python 3.11 standard library only. No Faker, no numpy required (verify_sample.py uses pandas for the profile pass; the manifest pass is stdlib-only).

    Size and scale table¶

    Per day, and for the 30-day window the course assumes:

    --scale trips/day GPS pings/day trips CSV/day GPS NDJSON/day GPS .gz/day 30 days, plain 30 days, --gzip-gps
    0.02 964 ~23,300 149 KB 5.9 MB 0.7 MB ~200 MB ~30 MB
    0.15 (shipped) 7,230 ~175,000 1.1 MB 44 MB 5.1 MB ~1.4 GB ~200 MB
    0.50 24,100 ~581,000 3.7 MB 147 MB 17 MB ~4.6 GB ~680 MB
    1.00 (lab spec) 48,200 ~1,161,000 7.3 MB 295 MB 34 MB ~9.0 GB ~1.3 GB

    Fixed-size files regardless of scale: drivers.csv 3,450 rows / 406 KB, vehicles.csv 3,864 rows / 286 KB, zones.csv 48 rows / 3 KB. weather_hourly.csv is 72 rows/day. payments_*.csv follows trips (~96% of trips generate a payment row).

    Generation runs at roughly 14 seconds per full-scale day on a lab laptop, single-threaded.

    Verifying a regeneration¶

    raw/_MANIFEST.json records, for every file: relative path, row count, byte size, sha256, plus the seed and every argument used. That is what makes a regeneration checkable rather than merely plausible.

    cd data/generators

# stdlib only: recompute every sha256 and compare
python3 verify_sample.py --manifest-only

# plus a full profile: row counts, null rates, duplicate counts, observed defect rates
python3 verify_sample.py

    Exit code 0 means every file matched and every observed defect rate is within 25% of the documented rate. Anything else prints exactly which file or which rate drifted.

    To prove a fresh regeneration reproduces the shipped data byte-for-byte:

    python3 generate_masar.py --start 2026-06-01 --days 5 --out /tmp/check --scale 0.15 --gzip-gps
diff <(jq -S '.files' ../raw/_MANIFEST.json) <(jq -S '.files' /tmp/check/_MANIFEST.json) && echo IDENTICAL

    (generated_at_utc is the only field that legitimately differs between runs.)

    The deliberate defects¶

    raw/ is not clean, on purpose. These are the background defects — the everyday mess a real feed carries. They are all documented, all controlled by a CLI flag, and all ON by default. --clean turns every one of them off.

    defect flag documented rate observed in the shipped sample
    trips.dropoff_geohash NULL (injected, of completed rows) --null-geohash-rate 3.100% 3.081%
    trips mixed timestamp format (DD/MM/YYYY HH:MM) --mixed-ts-rate 2.000% 2.017%
    trips.duration_min negative --negative-duration-per-day ~12/day @ scale 1.0 15 rows (3/day at scale 0.15)
    gps duplicate event_id --gps-dup-rate 0.400% 0.398%
    gps out-of-order ts --gps-ooo-rate 1.000% 1.001%
    drivers.hire_date in three formats --no-hire-date-formats 3 formats 3 (YYYY-MM-DD 2,137 · DD/MM/YYYY 835 · Mon DD, YYYY 478)

    One number that needs explaining: dropoff_geohash¶

    The observed overall null rate of dropoff_geohash in raw/ is 9.840%, not 3.1%. That is correct and it is two different things added together:

    • 3.081% of completed trips have an injected NULL geohash. This is the deliberate defect the lab specs name.
    • 6.974% of all trips are cancelled_rider / cancelled_driver / no_show. Those rows have no dropoff at all, so dropoff_ts, distance_km, duration_min and dropoff_geohash are structurally NULL. This is not a defect; it is what the data means.

    Profiling bronze naively and reporting "9.8% nulls" is itself a teaching moment: a null rate without a WHERE status = 'completed' predicate is a number about the schema, not about quality. Both figures are printed by the generator and by verify_sample.py, and both are recorded in _MANIFEST.json.

    The fixtures under fixtures/ are a different category: staged, isolated incidents rather than background noise. Each has its own README with the exact detection signal.

    The signature incident¶

    fixtures/incident_speed_unit/gps_2026-06-05_v250.ndjson.gz is the one to read first.

    A device-firmware rollout moves 34% of the fleet to producer_version 2.5.0. The payload keeps the field name speed_kmh and its double type — and starts writing metres per second. Schema validation passes. Range checks pass. Freshness, volume and row counts are all normal. No error is raised anywhere.

    gold.eta_features.rolling_avg_speed_10m silently falls by 3.6× for a third of the fleet, the ETA model starts over-predicting journey times, and nobody connects it to a line in a device changelog.

    Verified in the shipped sample: for the same 47,583 events, mean speed_kmh is 35.45 before the unit change and 9.85 as shipped — exactly 3.60×, the m/s → km/h factor. Compared against the whole raw day (mean 33.63 km/h across all vehicles and hours) the observed ratio is 3.41×; the gap is not an error, it is the incident being scoped to afternoon and evening hours, when speeds are genuinely lower. Segmenting drift by producer_version removes that confound — which is precisely why you must segment.

    That is the course's unifying question made concrete:

    "What happens to Masar's AI system if THIS part of the data platform fails?"

    Here, nothing failed. Every component did exactly what it was told. Type-compatibility is not semantic compatibility.

    Streaming the GPS feed (Module 5)¶

    cd data/generators

# 500 events/s, one hour of event time per minute, to Kafka topic masar.gps.raw
python3 emit_gps_stream.py --date 2026-06-01 --rate 500 --speedup 60

# with live faults
python3 emit_gps_stream.py --date 2026-06-05 --inject late,dupes,unit-shift

# no broker? it degrades to NDJSON and says so — the lab is not blocked
python3 emit_gps_stream.py --date 2026-06-01 --sink file --out ./replay.ndjson

    Needs kafka-python for the Kafka path (pip install kafka-python). Messages are keyed by vehicle_id so a vehicle's pings stay in one partition and per-vehicle ordering survives — Lab 5 asks participants to justify that choice against keying by trip_id.

    Optional: the NYC TLC benchmark¶

    python3 generators/nyc_tlc_prep.py --month 2024-01 --out ../raw_nyc

    Downloads a month of NYC TLC yellow-taxi Parquet from the official CloudFront endpoint (https://d37ci6vzurychx.cloudfront.net/trip-data/yellow_tripdata_{YYYY}-{MM}.parquet) and maps it onto the Masar trips schema.

    This is the dataset the DataTalksClub Data Engineering Zoomcamp is built on, and it earns that place: it is large (~3M rows/month, ~40 GB across the history), genuinely messy (negative total_amount, zero-distance trips, timestamps outside their own file's month), and it has had real schema changes — precise coordinates removed in 2016-07 and replaced by PULocationID/DOLocationID, congestion_surcharge and airport_fee added mid-stream, and CSV → Parquet with type changes in 2022-05.

    No lab depends on it. With no internet the script prints the exact URL, where to save the file, and the one-line curl to fetch it elsewhere — then exits cleanly.

    Licence and provenance¶

    Fully synthetic. No real personal data. No real trips, riders, drivers, vehicles or plates.

    • Every rider_id, driver_id, vehicle_id and trip_id is generated from a seeded PRNG.
    • Driver names are assembled from a small internal pool of common Saudi given and family names. Any resemblance to a real individual is coincidental and statistically inevitable given the pool size — these are not records about anyone.
    • national_id_hash, phone_hash and plate_hash are SHA-256 digests of synthetic strings. There is no underlying real identifier, and nothing to reverse.
    • GPS coordinates are jittered around published district centroids. They describe no person's movements.
    • Zone names, districts and approximate centroids are real public geography (Riyadh, Jeddah, Dammam) — public reference data, not personal data.
    • Currency is SAR; the fare model is invented and does not represent any operator's tariff.

    The dataset is nonetheless treated as if it were personal data throughout the course. That is the point: rider_id and precise GPS are classified, minimised, retained and erased under Saudi PDPL rules in every lab. See DATA_DICTIONARY.md for the per-column classification and retention policy.

    The optional NYC TLC data is not synthetic: it is public trip-record data published by the New York City Taxi & Limousine Commission, containing no rider identifiers and (since 2016-07) no precise coordinates. If you publish anything derived from it, cite https://www.nyc.gov/site/tlc/about/tlc-trip-record-data.page.
