    SDA-DSC-214 — Modern Data Engineering for AI Systems¶

    هندسة البيانات الحديثة لأنظمة الذكاء الاصطناعي¶

    Complete instructor-ready training package — SDAIA Academy, Capacity Building Sector.

    Specialist level · 5 days × 5 learning hours = 25 hours · PySpark 3.5 · Delta Lake 3.2 · dbt 1.7 · Kafka · Great Expectations 0.18 · Redis.

    Everything here is built around one evolving artefact: Masar (مسار), the national smart-mobility data platform of a Saudi ride-hailing and public-transit operator. There are no throwaway example datasets. Every lab produces a component of the Mini-Lakehouse capstone, so by Day 5 each participant owns a working, tested, governed Lakehouse feeding both an AI feature service and a BI dashboard.

    The unifying question, repeated at every module boundary:

    “What happens to Masar’s AI system if this part of the data platform fails?”

    The design goal for this revision was to make the course less about learning five tools and more about engineering one trustworthy data product for AI.

    What is in this package¶

    Folder Contents
    slides/ The comprehensive 105-slide instructor deck (.pptx), plus the generator sources that build it
    labs/ 9 participant lab guides + 8 instructor solution guides
    labs/case_studies/ 11 facilitator-ready case studies (CS-01 … CS-11)
    labs/activities/ 10 interactive activity kits with printable materials (ACT-01 … ACT-10)
    labs/assessments/ Quiz bank (60 items), 3 practical assessments, capstone brief, rubric, scoring sheets
    data/ Seeded Masar synthetic data generators, 5 days of generated sample data, and 7 defect fixtures
    starter/ The starter repository participants clone: src/masar, dbt project, GX suites, DAG, docker-compose, Makefile
    CONVENTIONS.md The canonical schema, table-name and repo-layout contract every artefact follows
    CONSISTENCY_REPORT.md Cross-package reconciliation record and known open items

    1 · The slide deck¶

    slides/SDA-DSC-214_Modern_Data_Engineering_for_AI_Systems.pptx — 105 slides, English, 16:9, speaker notes throughout.

    Structure: course framing → Day 1 (M1 architecture evolution, M2 compute–storage economics) → Day 2 (M3 ETL vs ELT) → Day 3 (M4 Delta Lake and ACID) → Day 4 (M5 streaming, M6 quality, observability and governance) → the signature incident case study → Day 5 (M7 Mini-Lakehouse, M8 serving AI and BI) → capstone, rubric and instructor appendix.

    The deck is rebuildable: cd slides && node build.js. Design system in lib.js, slide constructors in kit.js, content in c0_intro.js … c7_close.js. Edit content, rebuild, and the layout engine re-fits every text block automatically.

    2 · Labs and activities¶

    Lab Title Day
    LAB_00 Environment setup (send T-minus 2 days) before
    LAB_01 Land the Masar raw feeds into bronze 1
    LAB_02 Cost and elasticity model 1
    LAB_03 ELT pipeline to silver.trips 2
    LAB_04 Delta: ACID, MERGE, time travel, maintenance 3
    LAB_05 Stream GPS into the Lakehouse (exactly-once) 4
    LAB_06 Quality gate and governance 4
    LAB_07 Assemble and orchestrate the Mini-Lakehouse 5
    LAB_08 Serve gold to AI and BI + the leakage drill 5

    Each participant guide is standalone: header table, why-it-matters, exact setup commands, timed steps with full runnable code, expected console transcripts, acceptance checkboxes, self-check questions with hidden answers, an extended troubleshooting table, stretch goals, and the capstone requirement it satisfies. Each solution guide adds reference code, timed teaching moments, common wrong answers and how to redirect, minute-by-minute checkpoints, the filled benchmark table, and grading notes.

    Three case studies were added specifically for this revision:

    • CS-09 — Databricks medallion architecture. Medallion as progressive refinement, anchored on the instructor question “Masar receives 15 million GPS events daily — which transformations belong in Bronze, Silver and Gold, and which must never occur before Bronze persistence?” Deliverable: a one-page Architecture Decision Record. Includes a 20-transformation classification table, a filled exemplar ADR and a blank template.
    • CS-10 — LinkedIn and Kafka. Kafka's origin as a central messaging backbone, turned into a scored design exercise rather than a tool tutorial: Vehicles → Kafka → Structured Streaming → bronze.gps_events → silver.vehicle_positions → fan-out to ETA features and operations alerts, with three escalating rounds (late events, duplicates, out-of-order timestamps).
    • CS-11 — The Masar National Mobility Data Incident. The signature case study of the course. At 08:00 demand-forecasting accuracy drops 18% while the BI dashboard looks entirely normal. Teams investigate a six-stage evidence pack and reconstruct the chain: GPS producer 2.4.0 → 2.5.0 silently changes speed_kmh to metres per second → schema validation passes because the type is unchanged → Silver continues → rolling_avg_speed_10m is corrupted → the ETA feature distribution shifts → the model degrades, invisibly to BI. Includes the remediation exercise, a blameless post-incident review template, and the facilitator answer key with the exact detection queries.

    ACT-09 — feature validity classification is the client-requested activity that connects data engineering directly to production AI reliability: every column of gold.eta_features is classified as VALID / STALE / LEAKAGE / UNAVAILABLE ONLINE against the single question “could this feature have been known at prediction time?” It also appears as the mandatory drill in LAB_08 and as practical assessment PA-3.

    3 · Data and supporting files¶

    Fully synthetic, no real personal data. Seeded and reproducible — a regeneration is byte-identical.

    data/generators/generate_masar.py     seeded generator, CLI, writes _MANIFEST.json (rows, sha256, seed)
data/generators/inject_defects.py     the 7 teaching fixtures
data/generators/emit_gps_stream.py    Kafka replay to masar.gps.raw, --inject late,dupes,unit-shift
data/generators/nyc_tlc_prep.py       optional real-world track: NYC TLC trip records mapped to Masar
data/generators/verify_sample.py      manifest + profile verification
data/raw/                             5 days (2026-06-01..05) at --scale 0.15, GPS gzipped
data/fixtures/                        corrections · late_trips · late_pings · dirty_batch ·
                                      currency_shift · erasure_request · incident_speed_unit
data/DATA_DICTIONARY.md               per column: type, nullable, example, meaning, PDPL class, retention

    Shipped sample: 36,150 trips · 873,763 GPS pings · 34,803 payments · 3,450 drivers · 3,864 vehicles · 48 zones · 360 weather hours (~39 MB). Regenerate at full scale with python generate_masar.py --start 2026-06-01 --days 30 --out ../raw --scale 1.0 (≈ 48,200 trips and 1.16M pings per day; ≈ 9 GB for 30 days, or ≈ 1.3 GB with --gzip-gps).

    Verified defect rates in the shipped sample:

    Defect Documented Observed
    trips.dropoff_geohash null (injected, of completed trips) 3.100% 3.081%
    trips mixed timestamp format 2.000% 2.017%
    gps duplicate event_id 0.400% 0.398%
    gps out-of-order ts 1.000% 1.001%
    drivers.hire_date distinct formats 3 3

    The incident fixture is the one to know about: incident_speed_unit/gps_2026-06-05_v250.ndjson, 47,583 events at producer_version 2.5.0 whose mean speed_kmh is 3.60× lower than the 2.4.0 population in the same hour — schema-identical, semantically wrong.

    NYC TLC is wired in as the optional real-world benchmark (nyc_tlc_prep.py). It is the dataset behind the DataTalksClub Data Engineering Zoomcamp precisely because it is large, messy, has anomalies, requires cleaning, and has had genuine schema changes over time. Masar remains primary because every defect in it is injected deliberately, documented, and reproducible from a pinned seed.

    4 · Starter repository¶

    starter/ is what participants clone. make doctor validates Java 17, Python 3.11, Spark, Delta, Kafka, Redis, dbt and Great Expectations and prints a ✓/✗ table. make pipeline runs the whole medallion. 51 masar.* modules, all importable without PySpark installed; 142 unit tests that run without Spark; 19 # TODO(lab-N): blocks with matching reference solutions in solutions/.

    Publish these checkpoint tags before delivery: lab1-start … lab8-start, lab1-solution … lab8-solution, bad-batch, sim-swamp, sim-two-tier.

    Delivery checklist (T-minus 1 week)¶

    • Push all checkpoint tags to the course repository
    • Regenerate the Masar dataset at the delivery scale and verify against _MANIFEST.json
    • Dry-run all 8 labs on a clean machine and on the hosted-notebook fallback
    • Bring up the Kafka + Redis stack and pre-pull the images (this is the boot-time risk)
    • Send labs/LAB_00_Environment_Setup.md to participants two days out
    • Print the A4 posters: medallion architecture, Delta transaction log, exactly-once, quality-gate flow, the full Mini-Lakehouse pipeline
    • Print the activity materials: ACT-01 cards, ACT-02 folder listings, ACT-05/06 card decks, ACT-09 feature deck
    • Load the fixtures onto the shared drive
    • Confirm the classroom network allows the package index and the container registry
